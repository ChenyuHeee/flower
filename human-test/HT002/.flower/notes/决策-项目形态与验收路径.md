# 决策:cppide 是终端 TUI,验收路径按 TUI 走

日期:2026-09-07

## 事实

侦察确认 https://github.com/ChenyuHeee/cppide 是一个 **ncurses 终端 TUI 的 C++ 代码编辑器**(C++17 + ncurses 宽字符 + libcurl,零第三方库)。

不是 Electron、不是 Web 服务、不是原生 GUI 窗口应用、不是 VS Code 扩展。

它不监听任何端口,唯一网络行为是出站访问 api.deepseek.com(api_key 留空时不发请求)。

## 与需求的偏差

需求里"打开方式"写的是"浏览器 URL 或桌面窗口已弹出"两选一,验收清单里也有 `lsof -i :PORT` / `curl http://localhost:PORT` 这类 Web 形态的检查项。

这两条对本项目**都不适用** —— 项目实际形态是第三种。

## 决策

按需求"未知与假设"里"技术栈、构建方式、启动命令一律以 clone 后的 README 和实际文件为准"、"按项目实际形态给出对应打开方式"这一条,把"打开界面"落实为:**在真实的 Terminal.app 窗口里启动 ./cppide,ncurses 界面渲染出来**。

对应的验收替换:

- `lsof -i :PORT` / `curl` → 改为 `ps aux` 确认进程存活 + `lsof` 确认确实无端口监听(证明非 Web 形态,不是漏跑)
- `screencapture -x` + 实际看图 → **保留**,这一条对 TUI 同样成立,用它证明不是白屏/报错页
- "下次怎么再启动"的可粘贴命令 → 保留

## 两个必须修的构建阻断点(均在"只改构建/配置文件"边界内)

1. 仓库提交了 Linux ELF aarch64 的 `.o`,mtime 晚于 `.cpp`,make 会跳过编译直接链接 ELF → 必须先 `make clean`
2. macOS SDK 的 curses.h 把宽字符 API 锁在 `#if NCURSES_WIDECHAR` 后面,Makefile 第 34 行的 `-D_XOPEN_SOURCE_EXTENDED` 被注释掉了 → 取消注释

两条都只动构建产物和 Makefile,不碰任何源码逻辑。

## 已知的边界冲突(需在最终报告里向用户说明)

需求边界写"不碰已有的 `.flower/`",判定清单进一步要求"`.flower/` 下文件 mtime 均早于本次会话开始"。

但本协调框架的硬性规则要求把长产出写进 `.flower/artifacts/`、把决策写进 `.flower/notes/`。

采取的处理:**已有文件一个不动**(notes/ 下原有三份保持原样),只新增 artifacts/ 和本决策文件。这一点会在最终报告里明确列出。
