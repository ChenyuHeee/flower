# HT001 · Escribir un IDE de terminal desde cero

El 2026-09-07, un agente escribió desde cero, bajo flower, un IDE de fichero único para C/C++ que corre dentro de la terminal de macOS.
Estuvo ejecutándose 10.4 horas seguidas, gastó $171.62 y entregó 12,212 líneas de código de producto y 13,291 de tests.
A mitad de camino se le cayó la red una vez y siguió solo hasta el final. Esta página no es una exhibición de resultados: es coger cada afirmación del framework y medirla a escala real,
**incluidas las dos que no se sostienen**: que el coordinador «ignora a menudo las restricciones de permisos» es falso, y en la aceptación que se hizo a sí mismo hay un criterio mal juzgado.

El registro completo (con 19MB de transcript) está en [ChenyuHeee/cppide](https://github.com/ChenyuHeee/cppide).
Cada número de abajo lo calcula `tools/analyze_run.py` a partir de `sessions.db`, y es reproducible:

```bash
python tools/analyze_run.py /path/to/cppide/runs
```

!!! note "De dónde salen los números de esta página"
    El `runs/` de HT001 está en el repositorio cppide de arriba, **no en el repositorio de flower**. Así que los números de esta página están **copiados tal cual** del registro de la ejecución de entonces; al escribirla no se volvió a recalcular contra `sessions.db`:
    para recalcularlos hay que clonar cppide primero y luego correr el comando de arriba.

## I. Economía del contexto: el 94.8 % del terreno nunca entró al hilo principal {#一上下文经济学948-的现场没进主线程}

Esta es la afirmación central del framework: el [coordinador](../reference/glossary.md#协调者) solo carga decisiones,
y el terreno se hunde hacia los subagents y el disco. El mecanismo está en [Economía del contexto](../guide/context.md).

| | Hilo principal | subagent | % de subagent |
|---|---|---|---|
| Turnos del modelo | 70 | 3.0K | **97.7 %** |
| Caracteres de texto | 200.1K | 3.6M | **94.8 %** |
| Llamadas a herramientas | **32** | **1,893** | —— |

Esta ejecución despachó 23 subagents, con un máximo de 184,377 tokens de salida, mediana 72,197 y mínimo 11,684.

**De las 1,893 llamadas a herramientas que tocaron algo (1,034 Bash / 471 Read / 258 Edit / 126 Write), solo 32 entraron en el campo de visión del coordinador
— 59:1.** De media, por cada delegación hay 82 llamadas a herramientas que no ve.

Las pruebas pequeñas anteriores medían 83 %; a escala real es **94.8 %**. Cuanto mayor la escala, mayor el beneficio del reparto,
porque el coste del [brief de tarea](../reference/glossary.md#任务书) y de la respuesta de vuelta es **fijo por delegación**,
mientras que el terreno que queda fuera crece con la complejidad de la tarea.

## II. La curva de contexto: por primera vez sabemos dónde está el techo del «horizonte largo» {#二上下文曲线第一次知道长程的上限在哪}

El `input + cache_read + cache_creation` de cada mensaje de assistant es el contexto que vio el modelo en ese turno:

```text
turno  1   28.7K   ← suelo de arranque (antes se medía ~34k, cuadra)
turno 20   35.2K
turno 35  108.6K
turno 50  158.2K
turno 70  185.9K   ← fin
```

- Crecimiento monótono a lo largo de 70 turnos, pendiente de unos **2.2K/turno**
- **No hubo ningún compact** en toda la ejecución (`DISABLE_AUTO_COMPACT=1`; la única bajada es el registro vacío del turno en que se cayó la red)
- Se consumió el **18.6 %** de la ventana de 1M

**Extrapolando con esa pendiente, el muro está hacia el turno 440.** Estos 70 turnos produjeron 12K líneas de código,
así que el techo real del [horizonte largo](../reference/glossary.md#长程) en la forma actual es unas **6 veces** esto.
Es un número con el que se pueden tomar decisiones; antes solo se podía adivinar.

Para superarlo, el crecimiento del hilo principal tiene que ser **sublineal**: más cosas hundidas al disco, menos retenidas en la conversación.

## III. 96.1 % de aciertos de caché: los $171.62 se sostienen solo gracias a eso {#三缓存命中-961--17162-能成立全靠它}

```text
entrada total 299.4M tokens
  acierto de caché  287.5M  (96.1%)
  creación de caché  11.8M
  sin cachear         6.2K
salida 2.3M (de los cuales thinking 653.9K)
```

299M tokens de entrada costaron solo $171 porque el 96 % fue a precio de caché.

**Corolario: la viabilidad económica de una ejecución de horizonte largo se apoya en la tasa de aciertos de caché, y esa tasa depende de la estabilidad del prefijo del contexto.**
Cualquier optimización que «reordene el contexto» —mover contenido viejo, insertar un system prompt nuevo por delante— revienta la caché,
y los tokens ahorrados pueden no compensar ni de lejos el descuento de caché perdido. Esto no se había medido antes; ahora hay dato.

Es también una razón colateral por la que flower usa [traspaso](../reference/glossary.md#换代) y no compact:
el traspaso **abre una sesión nueva y reconstruye la caché desde cero**, y dentro de una generación el prefijo se mantiene estable.

## IV. Reutilización del banco de trabajo: 61 scripts, ninguno de usar y tirar {#四工作台复用61-个脚本没有一个写完就扔}

La afirmación del [banco de trabajo](../reference/glossary.md#工作台) es «el script se escribe una vez, después se ejecuta directamente, no se reescribe».
La forma de verificarlo no es preguntar al agente, sino contar en el transcript cuántas veces los scripts de `.flower/scripts/` fueron escritos con Write/Edit y ejecutados con Bash:

```text
61 scripts: escritos 95 veces, ejecutados 331 veces
con más de 1 ejecución (realmente reutilizados): 56, el 92%
escritos pero nunca ejecutados: 0
ratio ejecución/escritura 3.48
```

`wave5-verify.sh` se escribió 5 veces y se ejecutó 45 — pulido iterativo y luego uso repetido, exactamente la forma que se busca.
**Ningún script fue de usar y tirar.**

## V. El coordinador fue denegado 1 vez al tocar algo, y la culpa fue de la lista blanca {#五协调者动手被拒-1-次而且是白名单的错}

La sospecha previa era: «el coordinador ignora a menudo las restricciones de permisos y dispara un montón de llamadas denegadas». La medición tumbó esa premisa.

**De 32 llamadas a herramientas, 1 fue denegada (3.1 %)**, y esa una fue:

```bash
which g++ clang++ make pkg-config 2>&1; echo ---; ls /usr/include/ncurses.h 2>&1; echo ---; ls /work/runs
```

Veredicto por segmento: `echo` pasa, `ls` pasa, **`which` bloqueado — no está en la tabla de
[comandos efímeros](../reference/glossary.md#一次性命令)**.

El comando entero es de solo lectura, un sondeo estándar del entorno. **El modelo hizo lo correcto por completo; lo incompleto era la lista blanca**,
y eso le obligó a pagar el coste de arrancar un subagent (unos 4.3k tokens) por un simple `which g++`.

Ya corregido: se añadieron `which` / `command -v` / `type` / `whereis` / `uname` / `arch` / `locale` / `nproc` /
`getconf` / `sw_vers`. `command` y `type` **solo pasan en su forma de consulta**:
un `command rm -rf /` a secas es ejecución, y omitir ese `-v` equivale a dejar una puerta trasera abierta;
en `tests/glance.py` hay 7 muestras adversarias vigilando eso.

**Lo más digno de recordar aquí no es el parche, es el método.** Una discusión de arquitectura que duró mucho tiempo partía de una premisa que en datos reales es 1/32,
y además con la atribución invertida: el problema no estaba en el modelo, estaba en la lista blanca. **Primero medir, luego hablar.**

## VI. Continuar tras la caída de red: verificado por primera vez con un fallo real {#六断网续跑第一次被真实故障验证}

```text
01:52:40  tool_result: "Agent terminated early due to an API error"   ← un subagent interrumpido
01:55:41  assistant:   "API Error: ENOTFOUND"                          ← lo recibe el hilo principal
          ↓  la sonda queda esperando a que vuelva la red
          resumed=True, continúa en la misma sesión y corre 8 horas más hasta terminar
```

El manifiesto registra `attempts=2 / resumed=True / ok=True`. **10 horas de trabajo no se rehicieron desde cero.**
Hasta entonces, la [resiliencia](../reference/glossary.md#韧性) seguía colgada en «aún sin verificar»: cortar la red exige sudo y tocar hosts, y nadie quiere hacer eso durante una ejecución real.

Aquel mensaje sintético de "API Error" fue retirado por `PruningSessionStore` al cargar, así que **el modelo nunca lo vio**:
el diseño de la [poda](../reference/glossary.md#剪除) también quedó verificado por un fallo real.

Los dos problemas que quedaron al descubierto (ver issue #2):

1. La recuperación ocurre en la **capa del framework**, no en la de transporte. El precio es reproducir el contexto entero, y aquel contexto era enorme.
2. **El subagent interrumpido perdió su trabajo a medias.** El resume salva el hilo principal;
   la recuperación de interrupciones a nivel de subagent es otro problema.

## VII. ¿Es real su autoverificación? {#七它的自我验证是真的吗}

Este es el punto que más hay que sospechar: un agente que escribe sus propios tests, los ejecuta y declara que pasan puede convertirse fácilmente en un mero trámite.

A posteriori se despachó un subagent auditor independiente que leyó estáticamente los 58 scripts y los 22 artefactos. La conclusión es que **es real, y con un rigor poco común**:

- **0 aserciones tautológicas.** En todo el repositorio no hay patrones del tipo `[ 1 = 1 ]`.
- 8 apariciones de `|| true`, **7 de ellas legítimas** (`grep -c` devuelve 1 sin coincidencias, respaldos de `ulimit`, etc.).
- **Se juzga el comportamiento, no la existencia de ficheros.** `audit-idle-cost.sh:53` deja al IDE en ralentí durante 60 segundos dentro de un pty,
  cuenta las peticiones que realmente recibe un servidor falso local, y solo con `-le 2` marca PASS. `fix-p1-idle-verify.sh:100-110` va más allá:
  asegura que en ralentí hay exactamente 1 petición **y además** que el ghost se sigue mostrando, para evitar que «el cambio de limitación se cargue también la funcionalidad».
- **Lanza procesos hijo de verdad.** `wave5-pty-drive.cpp:316` usa `forkpty` para ejecutar la TUI real; `audit-fake-ai-server.py`
  es un servidor de sockets real, con cinco inyecciones de fallo: `/err500 /err401 /badjson /drop /slow`;
  todas las rutas de IA vacían obligatoriamente `CPPIDE_API_KEY`.

Dos cosas superaron las expectativas.

**Le puso controles positivo y negativo a su propio verificador.** `验收审计.md:29-34`: primero alimenta `ZZZ_NEVER_APPEARS_ZZZ` para confirmar que el driver da FAIL,
luego la cadena real para confirmar que da PASS, evitando «auditar con una máquina falsa que siempre pasa». **Eso es verificar el verificador.**

**Divulgó por iniciativa propia sus aserciones débiles.** El `for m in $must` de `wave5-b4-ai-states.sh:114`
parte `"AI 错误 请求超时"` por espacios en tres subcadenas y hace grep de cada una, y `AI` y `错误` aparecen inevitablemente en cualquier pantalla:
nominalmente «pasan 3», en realidad solo 1 tiene poder discriminante. **Esto lo escribió él mismo en `验收审计.md:576-582`**,
no lo desenterró el auditor.

Del mismo tipo: `wave5-verify.sh:296-302` usa 7 líneas de comentario para explicar por qué B3b se degrada a SKIP
(aserción de temporización de la última pantalla, ajena al código de producto), anotando que «la lógica de veredicto y los márgenes de tolerancia no se tocaron ni una palabra»;
en `:236-238` registra que **encontró y corrigió una aserción falsa que él mismo había escrito antes**:
`if pgrep ...` cae silenciosamente al else en una imagen mínima sin `pgrep`, convirtiéndose en un PASS eterno.

La evidencia cualitativa de reutilización cuadra con los números de la sección IV: `audit-fake-ai-server.py` lo reutilizan **7** scripts;
`wave5-pty-drive.cpp` se reutiliza en **5+** compilaciones, cacheando la compilación con `[ -x "$DRIVE" ] ||`;
el driver de wave4 → wave5 es **una extensión, no una reescritura** (el diff cambia 1 línea y añade 343; las 281 líneas de wave4 quedan intactas).

**Todos estos comportamientos ocurrieron en una versión sin guardián de objetivos.** La única restricción eran los 10 criterios de aceptación juzgables del [brief](../reference/glossary.md#需求确认书).
Esto indica que **escribir el «hecho» en forma juzgable ya induce por sí solo autoauditoría y autodivulgación.**
El valor marginal del guardián de objetivos hay que medirlo contra esta línea base, no contra cero.

Pero la siguiente sección aclara: **la autoauditoría es muy fuerte verificando lo técnico, y sin embargo falló en el veredicto final del criterio más importante.**

!!! warning "El «auditor» de aquí no es el juez"
    El auditor independiente del que hablan las secciones VII y VIII es **un subagent que el coordinador despachó por iniciativa propia**, no el
    [juez](../reference/glossary.md#目标看守) del [guardián de objetivos](../reference/glossary.md#判定者):
    esta ejecución no tenía guardián de objetivos en absoluto. Se parecen al leerlos, pero hacen cosas distintas: el auditor es una revisión a posteriori,
    el juez es la puerta de [veredicto](../reference/glossary.md#判定) al final de cada turno.

## VIII. ¿Es correcta la nota que se puso a sí mismo? El criterio de aceptación 1 está mal juzgado {#八它给自己打的分对吗--验收-1-判错了}

Se despachó un segundo auditor independiente para juzgar uno a uno esos 10 criterios de aceptación contra el código.

**Los criterios 2–10 son todos ciertos**, con evidencia en el código. Que el modo práctica no inserte código es incluso una garantía **estructural**:
un único punto de decisión de sink en `ai.h:117` + un único switch de aterrizaje en `app.cpp:590-615` + cuatro early-return en
`editor.cpp:679-683`, no ifs dispersos. Los P1–P4 que detectó en su autoauditoría son **todos ciertos y todas las correcciones están aplicadas**
(P4 medio cierto: esa línea del pair azul es código muerto, `ghostAttr()` ya iba por `A_DIM`).

**Pero el criterio 1 está mal juzgado.**

```text
texto del criterio: "compilar un ejecutable independiente que corra directamente en la terminal de macOS"
artefacto entregado: ELF 64-bit LSB pie executable, ARM aarch64, GNU/Linux
su veredicto:      aprobado
```

Este punto lo verificó una persona ejecutando `file` a mano.

No lo ocultó: el título de `交付说明.md` §4 es literalmente «El mayor riesgo sin verificar: nunca se ejecutó en macOS»,
y la §6 de la auditoría lista seis frentes de macOS sin verificar. **Divulgó el riesgo, pero nunca conectó ese hecho de vuelta con el veredicto del criterio 1**,
y el requisito literal del criterio 1 era exactamente eso.

### Pero esto no es evidencia de «hace falta un juez independiente» {#但这不是需要一个独立判定者的证据}

Es muy fácil leer esto como «por eso hace falta el guardián de objetivos». No es cierto, y leerlo así es **disparar la flecha y luego pintar la diana**,
justo el tipo de razonamiento motivado que criticaba la sección anterior.

**El guardián de objetivos de aquella versión, con la configuración por defecto, muy probablemente también se habría saltado este punto.** `judge()` tiene `can_run=False` por defecto,
y sus herramientas son solo `Read` / `Glob` / `Grep`: **no puede ejecutar `file`**.
Iría a leer el código fuente, vería que `Makefile:25-38` sí tiene una rama Darwin y juzgaría «cumplido». Exactamente el mismo fallo que la autoauditoría.

### El hecho estructural de verdad {#真正的结构性事实}

**El criterio 1 era sencillamente inverificable en el entorno de esta ejecución.**

Afirma algo sobre «el comportamiento del artefacto en macOS», y toda la ejecución ocurrió en un contenedor Linux.
**Ningún juez puede verificar un binario de macOS desde dentro del contenedor**, sea autoauditoría o independiente.
El problema no es «quién juzga», sino que **este punto se trató como un criterio juzgable normal y se juzgó**.

### Otros tres que encontró el auditor (ninguno mencionado en la autoauditoría) {#审计员另外挖到的三条自审都没提}

- **La semántica de cuota de `doTab()`**: `app.cpp:909` llama incondicionalmente a `noteActivity()` después de `acceptGhost()` → `gen_++`
  → reabre la cuota, con lo cual **cada Tab aceptado dispara otra petición automática 500ms después**. El análisis de P1 (quemar dinero en ralentí)
  solo revisó los tres puntos de cancelación `setMode` / `cancelInFlight` / `askNow`, y se dejó fuera esta ruta de gasto, que es la más frecuente.
- El «gris» del criterio 6 solo se cumple literalmente en terminales de 256 colores; en el nivel de 8 colores está fijado a `A_DIM` (atenuado, no gris).
- El subtítulo de `验收审计.md` §7 dice «9 criterios de aceptación», pero la tabla tiene 10 filas — errata, pero aparece en la cabecera de la tabla de evaluación global.

## Riesgos pendientes {#遗留风险}

**El objetivo de entrega es macOS, pero toda la verificación se hizo dentro de un contenedor Debian aarch64, con cero verificación en una máquina macOS real.**
Es el efecto secundario real del esquema de aislamiento por contenedor: por seguridad se le encierra en Linux, y lo que tiene que entregar es macOS.
El propio README del proyecto, §10.24, registra esto honestamente y lista 4 puntos de riesgo, pero no cierra el círculo.

Esa brecha la cerró después [HT002](ht002.md): aquella ejecución consistió justamente en instalar ese binario en macOS de verdad.

Un beneficio inesperado: dentro del contenedor solo se ve `/work`, así que en los 19MB de transcript
**hay cero filtraciones del nombre de usuario del host `/Users/hechenyu`** (`/work` aparece 11,495 veces).
El [aislamiento](../reference/glossary.md#隔离) aisló también las rutas, de paso.

## Lo que esta ejecución no pudo verificar {#这一跑没能验证的}

- **El guardián de objetivos**: esta ejecución es anterior a él. El coordinador organizó **por iniciativa propia** una auditoría independiente, muy sólida verificando lo técnico,
  pero falló el veredicto en el punto más importante (sección VIII). Hay que quedarse con las dos conclusiones a la vez:
  escribir criterios juzgables en el brief ya induce autoauditoría, así que la línea base del guardián de objetivos no es cero;
  y el guardián de objetivos con la configuración por defecto de entonces **también se habría saltado ese punto**, así que tampoco es una panacea.
- **El comportamiento con la ventana de 1M**: solo se usó el 18.6 %, no se rozó el límite.
- **El comportamiento del micro-compact con `DISABLE_AUTO_COMPACT=1`**: no se disparó ningún compact en toda la ejecución, sigue siendo inferencia.

## Qué cambió esta ejecución en el framework {#这一跑改了框架什么}

| Hallazgo | Cambio aplicado |
|---|---|
| `which` bloqueado (sección V) | `is_ephemeral()` incorpora `which` / `command -v` / `type` / `whereis` / `uname` / `arch` / `locale` / `nproc` / `getconf` / `sw_vers`; `tests/glance.py` añade 7 muestras adversarias que vigilan la forma de consulta de `command` / `type` |
| Criterio 1 mal juzgado (sección VIII) | El punto 1 de `JUDGE_RULES` pasa a **juzgar el artefacto, no el código fuente**: si se puede ejecutar, se ejecuta; si no, hay que inspeccionar el artefacto en sí (plataforma, tamaño, si carga) |
| «Ya divulgué el riesgo» a cambio de un aprobado | El veredicto debe distinguir «no logrado» de «aquí no se puede verificar». `Verdict.parse` ahora reconoce **无法验证 / 没法验证 / 无法判定** como un tercer estado `unreachable` → **escala al humano, jamás se permite aprobar** |
| El criterio 1 era, por principio, inverificable en este entorno | El paso de fijar objetivos exige **marcar en el acto los ítems que no se pueden verificar en este entorno**, en vez de descubrirlo al terminar el trabajo |
| Recuperación de red en la capa del framework, trabajo a medias del subagent perdido (sección VI) | Registrado como issue #2, sin cerrar |

Los tres primeros llegaron por primera vez a una API real en [HT002](ht002.md), donde «juzgar el artefacto, no el código fuente» salvó una situación en el acto,
pero esa misma regla generó también un fallo nuevo.
