# 이어가기

같은 디렉터리에서 `flower`를 한 번 더 실행하면 지난번 그 대화를 이어서 말한다 —— 프로세스가 kill되든, 터미널이 죽든,
머신이 재부팅되든 마찬가지다. session이라는 단어를 알 필요도 없고, 어떤 id도 기억할 필요 없다. 이 페이지는 그것이 무엇으로 성립하는지,
언제 조용히 실패하는지, 그리고 일부러 이어가지 않으려면 어떻게 하는지를 다룬다.

!!! note "이어가기는 핸드오프가 아니다"
    [이어가기](../reference/glossary.md#接续)는 **프로세스를 넘나드는** 것이다: 다음 프로세스가 지난번 [런](../reference/glossary.md#运行)을 이어받는다.
    [핸드오프](../reference/glossary.md#换代)는 **한 번의 런 내부**에서 일어난다: 컨텍스트가 거의 차면 현재 [세션](../reference/glossary.md#会话)이
    [인계서](../reference/glossary.md#交接书)를 한 부 써 두고, 새 세션이 이어받는다 —— [핸드오프](handoff.md)를 보라.

    둘은 자동으로 맞물리며, 추가 배선이 필요 없다: [계보](../reference/glossary.md#血缘)가 기록하는 것은 언제나 그 스텝을 **마지막으로**
    이어받은 세션이므로, 다음 웨이크가 이어붙는 대상은 그 후임 세션이다.

## 무슨 문제를 푸는가

디스크에는 사실 전부 남아 있다. `runs/sessions.db`에는 모든 과거 세션의 **완전한** transcript가 있고, `需求.md` / `目标.md`는
동결된 산출물이며, 코드는 작업 공간에 그대로 있다.

**사라지는 것은 단 한 줄의 매핑** —— "어느 스텝이 어느 session을 썼는가"뿐이다. 예전에는 이것이 메모리의 `ctx["_sessions"]` 안에서만 살아 있어서
프로세스가 끝나면 사라졌다. 그래서 새 프로세스가 뜨면 [코디네이터](../reference/glossary.md#协调者)는 기억을 잃은 신입이 된다: 누구를 파견했는지,
어떤 막다른 길을 시도해 봤는지, 왜 어떤 방안을 기각했는지를 전부 처음부터 다시 한다.

[HT002](../cases/ht002.md)에서는 컴파일 flag를 시험하느라 한 시간을 돌았다. 프로세스를 바꾸면 그 한 시간이 통째로 날아간다.

## 어떻게 쓰는가(최소 코드)

명령행에서는 아무것도 설정할 필요가 없다. `flower` 경로는 이어가기가 기본으로 켜져 있다:

```bash
cd ~/proj && flower "写个 md 转 html 的脚本"     # 첫 실행
# …다 돌았거나, Ctrl-C로 나가 버렸거나, 머신이 재부팅됐거나

cd ~/proj && flower "顺便支持代码块高亮"          # 지난번 그 대화를 이어서
cd ~/proj && flower                              # 아무 말도 안 함 = 하던 것 계속
cd ~/proj && flower --new "另一件事"              # 이번엔 이어붙이지 않음
```

직접 [워크플로](../reference/glossary.md#流程)를 작성할 때도 이어가기는 기본으로 켜져 있다 —— `Workflow.continuous`의 기본값이
`True`다:

```python
import asyncio

from flower import AgentSpec, Runtime, Step, Workflow

terse = AgentSpec(
    name="terse",
    instructions="回答极简,一行以内,不解释不寒暄。",
    allowed_tools=["Read", "Glob"],
    max_turns=4,
)


async def main() -> None:
    wf = Workflow([Step("取词", terse, "读 seed.txt,只回文件里那个词。")])   # continuous 기본값 True
    rt = Runtime(workspace=".", run_dir="runs")
    try:
        ctx = await wf.run(rt)
    finally:
        rt.close()
    print(ctx["_woke"])                  # 몇 번째 웨이크인지, 첫 실행이면 1
    print(ctx["_sessions"])              # {"取词": "<session_id>"}


asyncio.run(main())
```

같은 디렉터리에서 이 코드를 두 번째로 실행하면 `ctx["_woke"]`는 `2`이고, `ctx["_sessions"]["取词"]`는 첫 번째와
**같은 id**다 —— "取词" 스텝이 새 세션을 연 것이 아니라 지난번 그 세션을 이어서 돌린 것이다.

!!! tip "이 디렉터리가 이어붙는지만 알고 싶다면"
    `wake_state()`는 읽기 전용 탐침으로, **단 한 바이트도 쓰지 않는다**:

    ```python
    from flower import wake_state

    st = wake_state(".", run_dir="runs")
    print(st["waking"], st["checks"], st["woke"], st["steps"])
    ```

    `{"waking", "brief", "goal", "checks", "woke", "steps"}`를 반환한다. `waking` = 요구 확인서가 존재하고 네 섹션이 모두 갖춰짐;
    `checks` = 판정 체크리스트 항목 수; `woke` = 지금까지 웨이크한 횟수; `steps` = 스텝 이름에서 session_id로의 매핑.
    명령행은 이것으로 프롬프트가 "무엇을 할지" 물을지 "하던 것을 이어갈지" 물을지 결정한다.

## 실제로 하는 일

### 디스크에 남는 세 개의 파일

`run_dir`의 기본값은 `./runs`이며, **현재 작업 디렉터리 기준이지 workspace 기준이 아니다**.

| 경로 | 무엇이 들어가는가 |
|---|---|
| `runs/lineage.json` | 계보: `{"workspace": "…", "woke": N, "steps": {"스텝명": "session_id"}}`. 이어가기는 전적으로 이것에 의존한다 |
| `runs/sessions.db` | SQLite, 전체 transcript. 테이블은 `entries` / `meta` / `summaries`, key는 `project_key/session_id[/subpath]` —— subagent의 transcript는 subpath로 분리 저장된다 |
| `runs/manifest.json` | JSON 배열, **프로세스를 넘어 누적되는** 런 매니페스트. 스텝마다 한 줄이며, 나중에 session_id를 찾을 유일한 곳이다 |

계보 파일은 이렇게 생겼다:

```json
{
  "workspace": "/Users/you/proj",
  "woke": 3,
  "steps": {"干活": "47395075-bec7-466e-80cd-f4d60b360235"}
}
```

`manifest.json`의 각 줄은 `StepResult`의 모든 필드다 —— `step`, `session_id`, `ok`, `cost_usd`,
`num_turns`, `text`, `error`, `started_at`, `ended_at`, `attempts`, `errors[]`, `resumed`,
`retired[]`, `context` —— 여기에 수동으로 채운 `duration_s`(`@property`라서 `asdict()`가 잡지 못한다)와
`run`(프로세스 표식, `YYYYmmdd-HHMMSS-<6자리 hex>`)이 더해진다.

스텝 이름은 그 안에서 네 가지 형태를 가지며, 그 스텝이 어떻게 끝났는지가 한눈에 보인다: `<步骤名>`(첫 시도),
`<步骤名>#retry<N>`(일반 재시도), `<步骤名>#round<N>`(판정을 통과 못 해 되돌려져 이어서 함),
`<步骤名>·判定#<N>`([판정자](../reference/glossary.md#判定者) 라운드).

디스크 쓰기는 **덮어쓰기가 아니라 덧붙이기**다: 기록할 때마다 파일을 다시 읽고 `run` 필드로 중복을 제거한다 —— 이 프로세스의 줄은 최신 것으로 교체하고,
남의 줄은 그대로 둔다. 그래서 같은 디렉터리에서 여러 flower를 병렬로 돌려도 안전하다.

### `continuous=True`는 `resume_from`의 의미를 바꾼다

가장 빠뜨리기 쉬운 항목이다: `Workflow.continuous`의 기본값이 `True`이므로 `resume_from=None`은
**"완전히 새 세션"을 뜻하지 않는다**.

| 작성 방식 | 한 번의 런 안에서 | 프로세스를 넘어(`continuous=True`) |
|---|---|---|
| `resume_from=None`(기본) | 새 세션, prompt로 전달한 컨텍스트만 사용 | **계보에서 같은 이름 스텝의 session을 가져와 이어서 실행** |
| `resume_from="上一步名"` | 같은 세션을 이어서 실행, 완전한 컨텍스트 | 왼쪽과 같음 |
| `resume_from=…, fork=True` | 분기, 원래 세션을 오염시키지 않음 | 왼쪽과 같음 |

매 프로세스가 깨끗한 새 세션이길 원하면 `Workflow(..., continuous=False)`를 명시해야 한다.

계보를 적재할 때 검증이 하나 더 있다: 읽어 온 각 `(스텝명, session_id)`에 대해 먼저 `runtime.has_session(sid)`로
그것이 아직 `sessions.db`에 있는지 확인하고, 살아 있을 때만 쓴다. 계보 파일이 `sessions.db`보다 오래 살아남을 수 있고,
존재하지 않는 session을 resume하면 서브프로세스가 뜬 뒤에야 터지기 때문이다.

!!! warning "스텝 이름은 프로세스를 넘어 안정적인 키다"
    계보는 `Step.name`으로 인덱싱된다. **스텝 이름을 바꾸면 계보가 끊긴다** —— 오류는 나지 않고, 다음 실행이 그냥 새 세션이 될 뿐이다.
    접미사가 붙은 이름(`#retry`, `#round`, `·判定#`)은 계보에 들어가지 않으며, `Lineage.remember`는 언제나 원래 이름을 쓴다.

### 두 가지 불변식

**하나, session_id를 얻는 즉시 디스크에 쓴다. 스텝이 끝날 때까지 기다리지 않는다.**

프로세스가 강제로 죽는 것이야말로 막으려는 상황이다. 실제로 당해 봤다: 2026-09-07 Terminal.app이 두 번 죽었고, 커널이 SIGHUP을 보냈다.
SIGHUP의 기본 동작은 즉시 종료이므로 `finally`는 한 줄도 돌지 않는다. 당시 계보는 **스텝 경계**에서 기록되고 있었기 때문에,
첫 스텝 안에서 죽은 그 런은 `steps`가 비어 있었고, 사람은 이미 답한 질문에 다시 답해야 했다(issue #6 참조).

지금은 `Runtime.on_session`이 id를 얻는 그 순간 디스크에 쓴다 —— 실제로 가장 이른 시점은 첫 assistant 메시지이며,
init 시스템 메시지는 Python SDK에서 `session_id`를 갖고 있지 않다. 쓸 때는 먼저 `.tmp`에 쓰고 원자적으로 교체하므로
도중에 죽어도 반쪽짜리 파일이 남지 않는다. 기록 실패(`OSError`)는 조용히 삼키고, 이번 런을 함께 죽이지 않는다.

이 훅은 **`runtime.run` 이 한 문장만 감싼다**. gate 이전에 `try/finally`로 떼어 낸다. 판정자는 같은
`Runtime`을 쓰므로, 훅이 여전히 걸려 있으면 판정자의 session이 작업 스텝의 계보에 기록되어 버린다.

**둘, 맞지 않으면 없는 것으로 치고, 오류는 내지 않는다.**

맞지 않는 경우는 세 가지다: 작업 공간 경로가 바뀜(디렉터리가 복사되어 옮겨짐 —— [HT001](../cases/ht001.md)이 바로 컨테이너에서 복사해 나온 경우),
session이 이미 DB에 없음(`sessions.db`를 지운 적 있음), 계보 파일이 깨짐. 어느 쪽이든 조용히 "처음부터 시작"으로 되돌아간다.

`workspace` 필드는 가드다: SDK의 `project_key`는 작업 공간 경로에서 유도되며(`/`, `_`, `.`를 전부 `-`로 치환),
디렉터리가 복사되어 옮겨진 뒤에는 옛 session_id를 새 위치에서 아예 조회할 수 없으므로, 경로가 맞지 않으면 없는 것으로 친다.

**이어가기는 있으면 좋은 것이고, 그것이 실패한다고 해서 사람이 일하는 것을 막아서는 안 된다.**

### 프로세스가 죽는 것과 머신이 재부팅되는 것

두 경우 결과는 같다 —— 둘 다 이어붙는다 —— 하지만 과정은 다르다:

| 상황 | 무슨 일이 일어나는가 | 다음 실행 |
|---|---|---|
| `Ctrl-C` 한 번 | 협조적 중단, **메시지 경계**에서 깔끔하게 끊긴다. 김에 한마디 덧붙일 수도 있고, 같은 프로세스 안에서 같은 세션을 resume해 이어서 돌린다. 중단은 실패 시도로 치지 않으며 재시도 횟수를 먹지 않는다 | 이어가기와 무관 |
| `Ctrl-C` 두 번 | 곧바로 `KeyboardInterrupt`를 던지며 종료. 뒷정리는 스토어를 닫는 데까지만 하고, **진행 중이던 스텝은 `manifest.json`에 들어가지 않는다** | 계보는 이미 기록되어 있으므로 이어붙는다 |
| `SIGTERM` / `SIGHUP` | 핸들러가 먼저 `rescue()`를 호출해 진행 중이던 스텝도 `manifest.json`에 기록하고(`error="killed-by-signal"` 표시), 그다음 기본 동작을 복구해 실제로 종료한다 | 위와 같음, 이어붙는다 |
| `SIGKILL`, 정전, 머신 재부팅 | 뒷정리가 전혀 없음 | 마찬가지로 이어붙는다 —— 세 파일이 모두 디스크에 있고, 계보는 id를 얻는 그 순간 기록되었다 |

전제는 하나뿐이다: **같은 `workspace`와 같은 `run_dir`**. `run_dir`는 현재 작업 디렉터리 기준이므로,
다른 디렉터리에서 `flower`를 치면 다른 `runs/`를 찾게 되어 이어붙지 않는다.

### 판정자는 언제나 새 세션이다

이것은 **구조적으로 보장되는** 것이지, 기억에 의존하는 것이 아니다.

판정자는 `Step`이 아니다 —— `with_goal`의 gate에서 직접 `rt.run()`으로 파견되며
([목표 가드](goal.md) 참조), 계보 경로를 전혀 거치지 않는다. 그래서 매 라운드, 매 웨이크마다 완전히 새로운 한 쌍의 눈이다.

바로 그것이 판정자의 존재 가치 전부다: **워커가 몇 번 시도했는지, 얼마나 고생했는지 모르기 때문에 그를 위해 변명해 주지 않는다.**
판정자까지 이어가게 하면 목표 가드는 자기 감사로 퇴화한다.

`tests/lineage_offline.py` 4절이 이것을 못 박아 두었다.

### 웨이크할 때 한 그 말은 세 곳에 떨어져야 한다

이미 쓴 적 있는 디렉터리에서의 `flower "顺便支持代码块高亮"`는 **새 작업이 아니라 한마디를 더 한 것**이다.
이것은 동시에 세 가지를 한다 —— 하나라도 빠지면 조용히 실패한다:

| 어디에 떨어지는가 | 빠지면 어떻게 되는가 |
|---|---|
| `需求.md`에 덧붙임(`## 唤醒时追加`) | 스텝 경계를 넘기지 못한다. 다음 스텝은 새 session이고 동결된 산출물만 읽는다 |
| 작업 스텝의 prompt로 사용 | 코디네이터가 아예 받지 못한다 |
| **`目标.md` 재유도를 트리거** | 판정자가 읽는 것은 여전히 옛 체크리스트라, **새로 추가한 일이 됐는지 안 됐는지가 판정에 아예 들어가지 않는다** |

세 번째가 가장 빠뜨리기 쉽다. 판정자는 동결된 `目标.md`만 읽으므로 중간에 추가한 것은 보이지 않는다 —— 재유도하지 않으면 옛 체크리스트대로
"달성"으로 판정해 버리고, 정작 원했던 그 일은 검증조차 되지 않는다. 대가는 덧붙일 때마다 목표 설정을 한 번 더 도는 것이다([HT002](../cases/ht002.md) 실측
$0.41 / 3분).

**아무 말도 하지 않고 웨이크하면**(그냥 엔터) 덧붙이지도, 재유도하지도 않으므로 한 푼도 더 들지 않는다.

### 첫 스텝(요구 확인) 안에서 죽어도 이어붙는다

`clarify_step`에는 `resume_prompt`(상수 `CLARIFY_RESUME`)가 달려 있다: 확인 도중에 죽고 다시 시작하면
[확인자](../reference/glossary.md#确认者)에게 "아까 끝내지 못한 요구 확인을 이어서 계속 —— 처음부터 다시 하는 것이 아님"이라고 말하지,
원래 요청을 새 작업처럼 다시 보내지 않는다. 위의 "session_id를 얻는 즉시 기록"과 맞물려, 첫 스텝에서 죽어
`需求.md`가 아직 동결되지 않은 런도 이제 이어붙으며, 다시 답할 필요가 없다.

반대로, 이미 동결된 선행 스텝은 **스텝 통째로 건너뛴다**: `需求.md`의 네 섹션이 갖춰져 있으면 요구 확인을 건너뛰고(내용은 여전히 ctx에 주입된다),
`目标.md`가 갖춰져 있으면 목표 설정을 건너뛴다.

### 이어갈 때 보내는 말은 같은 말이 아니다

이것은 `Step.resume_prompt`가 관리한다. 상대의 컨텍스트에는 확인서, 목표, 지난번 어디까지 했는지가 **이미 있는데**,
"이 요구대로 하라: <확인서 전문>"을 그대로 다시 보내는 것은 순수한 노이즈이며, 더 나쁘게는 "요구가 바뀌었으니 다시 보라"로 읽힌다.

`resume_prompt`를 주지 않으면 `prompt`를 그대로 쓴다 —— 어떤 스텝은 원래 전문을 다시 보내야 한다(목표 설정이 체크리스트를 재유도할 때
필요한 것이 바로 그 완전한 확인서다).

### 웨이크할 때 먼저 한 줄을 보고한다

```text
<- 在 ~/explore/test-ide 接上上次  需求已确认 · 目标 15 条 · 干活上下文 80.2K · 第 3 次唤醒

== 干活 ==============================  3/3  <- 接上次 · 第 3 次唤醒
```

보고하지 않으면 "이게 대체 기억하고 있는 건가"를 전혀 체감할 수 없는데, 그것이 이 레이어의 가치 전부다. 배너에서
`需求已确认`은 항상 나오고, `目标 N 条`는 판정 체크리스트가 비어 있지 않을 때만, `干活上下文 X`는 `sessions.db`에서
그 세션 마지막 라운드의 컨텍스트 규모를 조회할 수 있어야 나온다.

**컨텍스트 숫자는 의도적으로 드러낸 것이다** —— 이유는 아래 "대가" 절에 있다.

### 복원력: 네트워크가 끊기면 매달려 기다리고, 오류는 이어받은 컨텍스트에 들어가지 않는다

[복원력](../reference/glossary.md#韧性)과 이어가기는 한 세트다: 한 번에 몇 시간을 돌면 네트워크는 반드시 한 번 끊기는데, 기본 동작이 아주 나쁘다 ——
끊기는 그 순간 harness가 transcript에 **합성 assistant 메시지**(`isApiErrorMessage=true`,
`model="<synthetic>"`)를 밀어 넣고, 본문은 "API Error: Can't reach the API server …"다. 이 메시지가 세션의 리프가 되고,
이후 resume하면 "모델이 직전에 한 말"로 다시 먹여지기 때문에 모델은 자기가 네트워크 장애를 논하는 중이라고 착각한다.

`Resilience`는 세 가지를 한다:

**하나, 탐침은 DNS + TCP만 한다.** `reachable(host, port, timeout=5.0)`은 `getaddrinfo`와 TCP 핸드셰이크 한 번만 돌리며,
**HTTP를 보내지 않고, 자격 증명을 싣지 않고, 돈을 쓰지 않는다**. 어떤 예외든 도달 불가로 친다. 어느 주소를 탐침할지는 `endpoint()`가 결정하고,
`ANTHROPIC_BASE_URL`을 따라가며, 기본값은 `https://api.anthropic.com`, 포트 기본값은 `443`(http면 `80`)이다.
**자체 게이트웨이를 쓰면 반드시 게이트웨이를 탐침해야 한다** —— `api.anthropic.com`이 뚫린다고 게이트웨이가 뚫린다는 뜻은 아니다.

**둘, 기다려야 할 것과 멈춰야 할 것을 구분한다.** `classify(text)`는 `"transient"` / `"fatal"` / `"unknown"`을 반환하며,
**fatal을 먼저 판정한 뒤 transient를 판정한다** —— 401 같은 텍스트에도 "connection"이라는 단어가 자주 들어가서, 순서를 뒤집으면 하염없이 기다리게 된다.
기본값: `max_attempts=6`(첫 시도 포함), `base_delay=4.0`, `max_delay=120.0`, `probe_timeout=5.0`,
`probe_interval=15.0`, `max_offline_wait=3600.0`(1시간), `retry_unknown=True`.
백오프는 `min(base_delay * 2**(attempt-1), max_delay)`에 ±25% 지터를 곱한다.

session_id를 이미 받았다면 **처음부터 다시가 아니라 resume해서 이어 돌리므로**, 앞서 쓴 비용이 헛되지 않는다. 이어 돌릴 때 보내는 것은
`Resilience.resume_prompt`다: "직전 라운드가 도중에 중단되어 끝나지 않았다. 워크벤치에 이미 기록된 것을 확인하고,
중단된 지점부터 이어서 하라. 처음부터 다시 하지 마라." 이것은 **의도적으로 어떤 오류 세부도 담지 않는다** ——
모델은 "중단됐으니 이어서 하라"만 알면 되고, ENOTFOUND인지 503인지는 알 필요가 없다.

**셋, 재시도 폭풍이 만들어 낸 오류는 resume 이후의 컨텍스트에 들어가지 않는다.** 이것은 [프루닝](../reference/glossary.md#剪除)이 하는 일이다.
`Runtime`의 세션 스토어는 `PruningSessionStore`로 고정되어 있고, `load()` 시점에 세 가지를 한다:

- 합성 API 오류 메시지를 떼어 낸다. **SQLite에는 원본 그대로 남고**, 다시 먹이지 않을 뿐이다
- 오래된 거부된 호출을 떼어 내고, 최근 `keep_denials=1`개만 남긴다
- 중단으로 남겨진 `tool_result`를 중립적 설명 "[직전 라운드가 여기서 중단되어 이 도구 결과는 생성되지 않았다]"로 교체한다. 본문만 바꾸고 항목은 떼지 않는다

0개가 아니라 1개를 남기는 데는 이유가 있다: 거부된 호출은 실행된 적이 없어 결과에 정보가 없는데도 자리는 적잖이 차지하고
(실측 한 건이 273자 = 93자 거부 문구 + 180자 **차단된 명령 원문**), 게다가 **오해를 유발한다** ——
실측에서 코디네이터가 "Bash를 직접 쓰지 말라"를 몇 건 읽고 나자, 허용된 `git status`조차 더는 시도하지 않는 학습된 무력감을 익혔다.
하지만 가장 최근 한 건은 남겨 두면 쓸모가 있다: 모델이 같은 라운드에서 차단된 같은 명령을 반복 재시도하는 것을 막는다.

떼어 내기에는 구조적인 금지선이 하나 있다: transcript는 `parentUuid` 단일 체인이므로, 한 건을 떼면 그 자식을 가장 가까운 살아 있는 조상에 이어 붙여야 한다.
그러지 않으면 체인이 거기서 끊기고 앞선 이력이 전부 사라진다.

[HT001](../cases/ht001.md)에서 실제로 한 번 겪었다: 네트워크 단절 타임라인 01:52:40 → 01:55:41, `manifest.json`의 그 스텝은
`attempts=2` / `resumed=True` / `ok=True`였고, 이어 돌린 뒤 8시간 넘게 더 돌아 완료했다.

마지막으로 오해하기 쉬운 것: **`Runtime(trim=False)`는 "아무것도 정리하지 않는다"는 뜻이 아니다**. `trim`은 기본값이 `False`지만,
그것은 **큰 도구 결과 [트리밍](../reference/glossary.md#裁剪)** 레이어만 끈다. 단절 잔여물 제거, 거부된 호출 제거,
중단 잔여물 중립화, [일회성 명령](../reference/glossary.md#一次性命令) 결과의 만료 표시 —— 이 네 가지는 그대로 수행된다
(`ephemeral` 기본값 `True`, `keep_denials` 기본값 `1`).

### 대가: 컨텍스트는 계속 늘고, 끝이 없다

이것은 이어가기의 고유한 대가이지 버그가 아니다.

[HT001](../cases/ht001.md)의 "작업" 스텝은 10.44시간을 연속으로 돌았고, [메인 스레드](../reference/glossary.md#主线程) 컨텍스트는
1라운드 **28.7K**, 20라운드 **35.2K**, 35라운드 **108.6K**, 50라운드 **158.2K**, 70라운드 **185.9K**로
단조 증가했으며 기울기는 약 **2.2K/라운드**였다. 전 구간 compact 없이 1M 윈도의 **18.6%**를 썼다. 이 기울기로 외삽하면
벽에 부딪히는 지점은 약 **440라운드** —— 현재 형태의 "롱호라이즌" 상한은 그때의 약 **6배**다. 영구적인 이어가기는 언젠가 윈도에 부딪힌다는 뜻이다.

두 레이어가 이것을 관리한다:

1. **트리밍**(`flower --no-trim`으로 끌 수 있고, `flower` 경로에서는 기본으로 켜짐) —— resume할 때 오래된 큰 도구 결과를
   파일 포인터로 바꾼다. 내용은 사라지지 않고, 상주하지 않을 뿐이다
2. **[핸드오프](handoff.md)** —— 임계치에 도달하면 인계서를 써 놓고 새 세션으로 교체한다. **[compact](../reference/glossary.md#压缩)가 아니다**:
   문서는 읽을 수 있고 고칠 수 있으며, 무엇이 사라졌는지 보인다. 그래서 컨텍스트는 벽까지 계속 오르는 대신 주기적으로 내려간다

**그래서 웨이크 줄에는 반드시 컨텍스트 숫자를 보고해야 한다**: 사람이 볼 수 있어야 벽에 부딪히기 전에 스스로 다시 시작할지 결정할 기회가 생긴다.

덧붙이자면, `--rounds`(작업 총 라운드 수)는 **웨이크할 때마다 초기화된다**. 의도적이다 —— 새 웨이크는 새 의도이므로,
지난번에 쓴 라운드 수를 물려받아서는 안 된다.

### 새로 한 건 시작하기

```bash
flower --new "另一件事"
```

또는 웨이크 프롬프트에서 바로 `/new`를 친다:

```text
接着上次? 直接回车 = 接着做;也可以说点新的;/new = 重开一件事(Ctrl-C 退出)
> /new
要做什么? 一句话就够,回车开始(Ctrl-C 退出)
> …
```

**삭제가 아니라 아카이브다.** `lineage.json`, `需求.md`, `目标.md`를 함께 `notes/archive/<YYYYmmdd-HHMMSS>/`로 **옮기고**,
계보의 `steps`와 `woke`도 동시에 0으로 만든다. 세 가지는 같은 이력의 세 면이라, 일부만 거두면 "목표는 남았는데 대화는 사라진"
반쪽 상태가 남는다.

`sessions.db`는 건드리지 않는다 —— 그것은 아카이브이고, 안의 transcript는 모두 여전히 조회할 수 있다.

코드로는 `Lineage.archive(into, extra=[...])`에 해당한다.

## 언제 쓰지 말아야 하는가

- **매번 깨끗한 출발점이 필요한 경우.** 같은 워크플로를 배치로 돌리기, 대조 평가하기, 남에게 버그를 재현시키기 ——
  이런 것들은 지난번 컨텍스트를 짊어져서는 안 된다. `Workflow(..., continuous=False)`를 쓰거나, 매번 다른 `run_dir`를 쓰라.
- **디렉터리가 옮겨지거나 복사될 수 있고, `run_dir`가 지속적이지 않은 경우.** 컨테이너 안에서 돌면서 `runs/`가 컨테이너 내부 파일 시스템에 놓이거나,
  작업 공간을 다른 머신으로 rsync하는 경우 —— 이어가기는 **조용히 실패한다**(경로 가드가 맞지 않는 계보를 거절한다).
  이것을 보장으로 여기지 마라.
- **이번이 새 의도이고 컨텍스트가 이미 큰 경우.** 이어가기는 무관한 이력을 함께 짊어지며, 매 라운드 그 대가를 token으로 치른다.
  참느니 `--new`로 아카이브하고 다시 시작하는 편이 낫다.
- **일회성 단일 agent.** `flower once`는 `Workflow`를 거치지 않아 계보가 없다. 이어 돌리려면 직접 `--resume <session_id>`를 줘야 한다.
- **이어가기를 백업으로 쓰기.** 그것은 "어느 스텝이 어느 session을 썼는가"만 기록한다. 코드, 산출물, 결정은 작업 공간과
  [워크벤치](../reference/glossary.md#工作台)에 남아야 하며, transcript에서 파내길 기대해서는 안 된다.
