# Goal guard

"끝났는지 아닌지"는 worker가 말하지 않는다. [판정자](../reference/glossary.md#判定者)는 목표만 세우고,
판정만 하고, 직접 손대지 않는 역할이다. 시작 전에 [brief](../reference/glossary.md#需求确认书)를 판정 가능한
체크리스트로 바꾸고, 그 뒤로는 매 라운드 작업이 끝날 때마다 **독립적으로 한 번 판정해서** [verdict](../reference/glossary.md#判定)를 낸다 —
달성했으면 다음으로 넘어가고, 달성하지 못했으면 "무엇이 모자란지"를 들려 돌려보내 계속 시키고,
불가능하다고 판정되면 멈추고 사람에게 묻는다.

## 어떤 문제를 해결하는가

[clarify](clarify.md)가 막는 것은 **"원하는 것과 다른 것을 만드는 일"**이다. 이 층이 막는 것은 다른 종류다.
**"사실은 안 끝났는데, 스스로 끝났다고 말하는 일"**. 두 가지는 반드시 분리해야 한다. 실패 방식이 다르기 때문이다.

| | 실패가 어떻게 생겼는가 | 언제 드러나는가 |
|---|---|---|
| 요구가 틀림 | 모든 산출물이 틀린 요구를 기준으로 지어짐 | 몇 시간 뒤, 산출물 전부 폐기 |
| 완성도 판단이 틀림 | 절반만 돌린 테스트, 한 군데 고치고 세 군데 빠뜨림, "아마 문제없을 것" | 당신이 직접 써볼 때 |

두 번째를 worker 스스로에게 맡길 수 없는 이유는 **체계적인 낙관 편향**이 있기 때문이다.
정직하지 않아서가 아니라 — 자기 사각지대를 볼 수 없어서다. 자기가 무엇을 했는지는 알지만, 무엇을 빠뜨렸는지는 모른다.

그래서 판정은 **작업에 참여하지 않고, 자기 [session](../reference/glossary.md#会话)에서 도는** 역할에게 맡긴다.
그가 보는 것은 목표와 현장뿐이고, worker가 몇 번 시도했는지, 얼마나 고생했는지는 모른다. 그러니 대신 변명해 주지도 않는다.
clarifier가 독립 session에서 도는 것과 같은 이치다.

## 어떻게 쓰는가(최소 코드)

### 코드 없이: 커맨드라인

```bash
flower                      # 기본으로 goal guard가 켜져 있다
flower --no-goal            # 끄기: 작업이 끝나면 끝난 것으로 친다
flower --rounds 5           # 최대 다섯 라운드(기본 3)
flower --judge-can-run      # 판정자가 명령을 실행할 수 있게 한다(판정이 더 단단해진다)
```

### 직접 배선하기

두 함수가 각각 절반씩 맡는다. 섞지 말 것: `goal_step()`은 **목표를 세우고**(독립된 한 step),
`with_goal()`이 **판정 루프**다(작업 step 하나를 감싼다).

```python
from pathlib import Path
from flower import HumanChannel, Step, Workbench, Workflow, clarify_step, goal_step, with_goal

wb = Workbench(Path.cwd()).ensure()
ch = HumanChannel(log_path=wb.notes / "问答记录.md")   # 기본값은 질문 횟수 무제한
goal_path = wb.notes / "目标.md"

work = Step("干活", spec=협조자, prompt=lambda ctx: f"照这个做:\n{ctx['确认需求']}")

wf = Workflow(channel=ch, workbench=wb, steps=[
    clarify_step(ch, brief_path=wb.notes / "需求.md", prompt="帮我做一个 X"),
    goal_step(ch, goal_path=goal_path),
    with_goal(work, ch, goal_path=goal_path, rounds=3),
])
```

`goal_step(channel, *, goal_path, ...)`:

| 파라미터 | 기본값 | 설명 |
|---|---|---|
| `goal_path` | — | 목표를 어디에 떨어뜨릴지. [workbench](../reference/glossary.md#工作台)의 `notes/` 아래에 둔다. 이유는 brief와 같다 |
| `brief_key` | `"确认需求"` | `ctx`의 어느 키에서 brief를 읽을지. **읽지 못하면 `"(没有确认书)"`만 받는다** |
| `name` | `"设定目标"` | step 이름이자 `ctx` 안의 키 이름 |
| `spec` / `instructions` | `None` / `""` | 직접 만든 `AgentSpec`, 또는 판정자에게 도메인 지시를 덧붙임 |
| `always_set` | `False` | `True` = 매번 다시 설정 |
| `on_fail` / `retries` | `"stop"` / `0` | `Step`과 동일 |
| `**spec_kw` | — | `judge()`로 그대로 전달: `can_run` / `model` / `effort` / `max_turns` / `max_budget_usd` |

`with_goal()`은 작업 step 하나를 판정이 붙은 루프로 감싼다:

```python
with_goal(step, channel, *, goal_path, spec=None, rounds=3,
          instructions="", can_run=False, name=None, **spec_kw)
```

**`rounds`는 총 라운드 수이지 추가 라운드 수가 아니다** — 내부적으로 `retries = max(0, rounds - 1)`로 떨어진다.
그래서 `rounds=3`은 최대 세 라운드까지 작업하고, `rounds=1`은 "한 라운드 돌고, 한 번 판정하고, 통과 못 하면 실패"다.
전체 시그니처와 필드 의미는 [Python API](../reference/api.md)를 보라.

`ctx`에는 키가 세 개 추가된다:

```python
ctx[GOAL_KEY]     # "_goal" —— Goal 객체; ctx["设定目标"]은 그 markdown
ctx[VERDICT_KEY]  # "_verdict" —— 가장 최근 Verdict, UI용
ctx[ROUND_KEY]    # "_goal_rounds" —— 몇 라운드 돌았는지
```

판정자는 `ctx["_runtime"]`을 통해 파견된다 — `Workflow.run`이 런타임과 event 출구를 모두 `ctx`에 넣어 두기 때문에
`gate`가 스스로 agent를 띄울 수 있고, 판정 과정도 그대로 당신의 UI에 찍힌다
(그러지 않으면 그 십몇 초 동안 화면이 새까매서 멈춘 것처럼 보인다).

잘 안 돌 때는 먼저 이 손잡이들을 돌려 보라:

| 증상 | 무엇을 돌릴까 |
|---|---|
| 판정이 너무 헐거워서, 달성이라는데 실제로는 아님 | `--judge-can-run`으로 진짜 한 번 돌리게 한다; 또는 `instructions`에 도메인 판정 기준을 추가 |
| 판정이 너무 엄해서 계속 되돌려보냄 | `目标.md`의 판정 체크리스트가 요구보다 더 높게 쓰여 있지 않은지 본다. **그 파일을 고쳐라** |
| 라운드만 계속 헛돎 | 판정자가 "달성 불가"를 줘야 하는데 "미달성"을 줬다. 무엇이 불가능인지 설명하는 지시를 추가하라 |
| 너무 비쌈 | `--rounds 1`, 또는 `--no-goal`로 완전히 끈다 |
| 방해받고 싶지 않음 | `--timeout 0`: 달성 불가일 때 사람에게 묻지 않고 바로 멈춘다(이유는 디스크에 남는다) |

## 실제로 무엇을 하는가

### 목표는 어떻게 생겼는가

`goal_step`은 brief를 읽고 두 단락을 출력해 `.flower/notes/目标.md`에 얼려 둔다:

```markdown
# 目标
让 conv.py 能把 md 转成 html。

# 判定清单
- 跑 `python conv.py a.md` 产出 a.html
- 输出里含 `<h1>`
- 列表被转成 `<ul><li>`
```

**판정 체크리스트가 이 층의 가치 전부다.** "구현이 완전함"은 판정할 수 없고, "무엇을 실행해서 무엇이 보이는가"라야 판정할 수 있다.
체크리스트는 brief의 「검수 기준」에서 나오지만, 각 항목이 그 자리에서 검증 가능한 형태로 다시 쓰여야 한다 — 모호한 항목은 판정자가 채운다.
두 단락이 모두 비어 있지 않아야(`statement`에 내용이 있고 `checks`가 비어 있지 않아야) 온전한 것으로 치고, 아니면 이 step은 통과시키지 않는다.

### 체크리스트의 길이는 "실패 방식이 몇 가지인가"가 정한다

판정자가 얼마나 엄밀한가가 정하는 게 아니다. `git clone && make && ./app` 같은 작업은 **세 개에서 다섯 개면 충분**하다:
빌드 성공, 실행됨, 쓸 수 있음.

**실측으로 넘어진 적이 있다**([HT002](../cases/ht002.md)): "저장소를 설치해서 돌린다"는 작업 하나가 체크리스트 **15개**로 쓰였고,
그중 **5개**만 "물건이 쓸 수 있는가"를 검증했고, **6개**는 "과정에서 규칙을 지켰는가"를 검증했으며
(`~/.zshrc`의 mtime 확인, `.flower/` 디렉터리가 변경됐는지 확인 포함 — 그건 프레임워크 자신의 디렉터리다),
**4개**는 원리상 검증 불가능했다.

#### 경계는 판정 항목이 아니다

그때의 주된 원인이 이것이다:

| | 무엇을 제약하는가 | 어떻게 지키는가 |
|---|---|---|
| **경계** | **어떻게 작업하는가**("프로젝트 디렉터리 안에서만 설치할 것", "업무 코드는 건드리지 말 것") | **넘지 않음**으로 지키지, 사후 자기 증명으로 지키지 않는다 |
| **판정 항목** | **내놓은 결과물**("돌아가는가", "결과가 맞는가") | 그 자리에서 검증해서 지킨다 |

"`brew install`을 실행하지 않았음"을 판정 항목으로 쓰면, 경계를 하나 추가할 때마다 검사가 하나씩 늘어난다는 뜻이다 —
그리고 경계야말로 clarify 단계에서 잔뜩 쓰도록 권장되는 것이다. 정말 해명이 필요하면 한 줄로 넘기고, 여섯 개로 쪼개지 마라.

### 검증할 수 없는 항목은 목표를 세울 때 바로 알린다

체크리스트에서 `[此环境无法验证:原因]`으로 표시된 항목이 있으면, `goal_step`은 **목표를 얼리는 그 순간에** 알림을 하나 보낸다:

```text
  # 目标里有 4/15 条在这个环境里验不了 —— 判定时它们必然过不去,会停下来问你。
    现在改 .flower/notes/目标.md 还来得及:
      · 界面截图并实际看图 [此环境无法验证:屏幕录制未授权]
      · ...
```

**왜 미리 알리는가**: 이런 항목들의 운명은 목표를 세우는 그 순간에 이미 정해져 있고, 판정 때 반드시 통과하지 못한다.
HT002는 먼저 **$35.90의 작업 + $1.40의 판정**을 쓴 뒤에야 그걸 발견했다 —
발견 시점을 목표 설정 단계로 앞당기면, 같은 정보의 비용이 **$37**에서 **$0**으로 떨어진다.

알리기만 하고 막지는 않는다: 사람이 그대로 돌리기를 선택할 수 있다(HT002는 결국 "이 결과를 받아들인다"를 골랐다).
`Goal.unverifiable`이 이 명단이고, event payload에 UI용 구조화 데이터가 들어 있다.

### 결론은 두 개가 아니라 세 개다

```text
干活 ──> 判定 ──达成────> 往下走
              ├─未达成──> 打回,带上“差在哪”,续跑同一个会话接着做
              └─无法达成─> 停下来问人:接受 / 改目标 / 你判断错了
```

세 번째 결론이 핵심이다. "달성/미달성"만 있으면, **실제로는 불가능한** 목표 하나가 coordinator를
라운드마다 헛돌게 만들어 예산이 바닥날 때까지 태운다 — 그게 진짜로 돈을 태우는 것이다. 그래서 판정자에게는 명시적으로 요구한다:
"한 라운드 더 돌아도 소용없다"라야 달성 불가다(필요한 외부 조건이 없음, 요구가 자기모순, 판정 항목을 애초에 검증할 수 없음).
단지 "아직 다 못 했다"면 미달성이다.

달성 불가일 때 프레임워크는 멈추고 사람에게 묻는다:

```text
  ? 目标被判为**无法达成**:缺少 X 依赖,判定项 2 无法验证
    怎么办?
     1) 接受这个结果,就这样往下走
     2) 修改目标
     3) 你判断错了,继续做
```

- **받아들임** → 이 step은 통과한 것으로 치고, 이유는 기록에 남는다
- **목표 수정** → 이어서 새 목표가 무엇인지 묻고, 원래 목표 뒤에 **append**한 뒤(무엇을 고쳤는지 보인다) 한 라운드 더
- **판단이 틀렸다**(그리고 당신이 직접 친 자유 응답 전부) → 당신의 말을 들려 돌려보내고, 한 라운드 더

**아무도 응답하지 않으면 멈춘다.** 계속 헛돌지 않는다 — 의도적이다. 불가능하다고 판정됐고 물어볼 사람도 없는데
계속 돌리면 라운드마다 돈을 태우는 것이고, 그게 가장 피해야 할 일이다. 멈출 때는 `StepAbort`를 던지고, 이유는
`ctx["_aborted"]`에 쓰이며, 목표 파일과 `runs/manifest.json`은 그대로 남아 사람이 돌아와서 이어 결정한다.

!!! warning ""못 했다"와 "여기서는 검증할 수 없다"는 다른 결론이다"
    `Verdict`의 세 값은 `ACHIEVED` / `NOT_YET` / `UNREACHABLE`이다.
    **`UNREACHABLE`은 절대로 통과로 판정해서는 안 된다** — 그건 "멈추고 사람에게 묻는" 경로이지 "한 라운드 더"가 아니다.
    판정자가 쓴 "无法验证 / 没法验证 / 验证不了 / 无法判定 / unverifiable"은 **전부** `UNREACHABLE`로 귀속된다.
    "여기서는 검증할 수 없다"를 "달성"으로 치는 것은 "그럴듯하니 되겠지" 한마디로 작업을 접는 것이고,
    "미달성"으로 치는 것은 애초에 검증 불가능한 일을 라운드마다 다시 하게 만드는 것이다.

### 판정이 모호하면 = 미달성

`Verdict.parse`의 인식 순서: 먼저 제목 단락에서 "结论 / 判定" 단락을 취한다. 제목 단락이 없으면
전체가 `1` / `true`면 달성, `0` / `false`면 미달성으로 친다(판정자에게 "0/1만 넘겨라"라고 요구하면
정말로 숫자 하나만 돌려줄 가능성이 크다). 그래도 안 맞으면 결론 텍스트에서 키워드를 찾고(긴 단어부터),
마지막으로 고립된 `1` / `0`을 찾는다.

**전부 안 맞으면 `state`는 비고 `ok`는 `False`가 되어, 프레임워크는 미달성으로 처리한다.** 이 규칙은 의도적이다.
"판정이 안 나온다"와 "끝났다"는 다른 일이고, 모호하면 일률적으로 미달성으로 치며 기본 이유를 한 줄 덧붙인다
("判定者没给出明确结论,按未达成处理").

### 판정하는 것은 산출물이지 소스 코드가 아니다

!!! warning "소스 코드만 읽는 판정은 산출물을 판정할 수 없다"
    [HT001](../cases/ht001.md)에서 검수 기준의 원문은 "독립 실행 파일을 컴파일해서 macOS
    터미널에서 바로 실행"이었는데, 판정은 `Makefile:25-38`에 Darwin 분기가 실제로 있다는 것만 읽고 **통과**로 판정했다 —
    실제로 인도된 산출물은 `ELF 64-bit LSB pie executable, ARM aarch64, GNU/Linux`였다.

    **틀린 것은 goal guard가 아니다**: 그 run에는 아직 이 메커니즘이 없었고, 그 항목을 판정한 것은 coordinator가 스스로
    임시로 파견한 독립 감사자였다. 하지만 goal guard로 바꿨어도 똑같이 놓쳤을 것이다 — 판정자는 기본이 `can_run=False`이고,
    손에 든 것은 `Read` / `Glob` / `Grep`뿐이라 **`file`을 실행할 수 없다**. 그러니 똑같이 `Makefile`을 읽는 수밖에 없고,
    똑같이 Darwin 분기를 보고 달성으로 판정했을 것이다. 이 실패의 요점은 "누가 판정하는가"가 아니라 "무슨 증거로 판정하는가"에 있다.

    이 교훈은 `JUDGE_RULES`에 쓰였다: 판정하는 것은 **산출물**이며, "소스에 macOS 분기가 있으니
    돌아갈 것"과 같은 추론은 받아들이지 않는다.

[HT002](../cases/ht002.md)는 `judge_can_run`을 켜서 판정자가 실제로 `file` / `lsof`를 실행한
경우라서 이 함정을 피했다 — 첫 문장이 "나는 그 답변만 보고 결론 내지 않는다. 현장으로 간다."였고, 그다음:

```text
file cppide        → Mach-O 64-bit executable arm64
lsof -p 96040      → 起于 16:10,16:15 仍活着
```

판정 prompt 안의 그 문장도 같은 뜻이다: 직접 현장을 보고, 판정 체크리스트를 한 항목씩 대조하며, **증거를 보지 못한 판정 항목은
통과하지 않은 것**이다.

### "되돌려보냄"은 이어서 하는 것이지 처음부터 다시 하는 게 아니다

되돌려보낼 때는 `Step.on_reject`를 쓴다: 다음 라운드는 **방금 부결당한 그 session을 `resume`**하고, prompt를 판정 피드백으로 바꾼다
(`Verdict.feedback()`은 "무엇이 모자란지"만 주고 방안은 주지 않는다). 그래서 이미 끝낸 작업, 읽은 파일, 돌아간 길이
전부 컨텍스트에 남아 있고, 차이만 메우면 된다.

차이는 step 이름에 쓰여 있어서 `runs/manifest.json`에서 한눈에 보인다:

```text
干活            第一轮
干活#round2     被打回后接着做      ← on_reject 生效,resume 上一轮
干活#retry1     普通重试(重头跑)    ← 没有 on_reject 时的老行为
```

판정자 자신은 **언제나 새 session**이다: `with_goal`의 gate는 `Runtime.run`을 직접 호출하고 `resume`을 주지 않는다.
step 이름에는 라운드가 붙고(`干活·判定#1`), 접미사가 붙은 이름은 프로세스 간 [lineage](../reference/glossary.md#血缘)에 들어가지 않는다.
gate에서 `ctx["_runtime"]`을 얻지 못하면 `StepAbort`를 던지며, **통과한 척하지 않는다**.

### 건너뛰기와 재설정

목표 파일이 이미 있고 온전하면 이 step은 **건너뛴다**(brief와 같다) — [long-horizon](../reference/glossary.md#长程)
run이 무너져 재시작할 때, 앞서 낸 결론을 다시 계산할 이유가 없다. 다시 설정하려면 그 파일을 지우거나 `always_set=True`.

**예외: wake 때 당신이 한마디 더 한 경우.** 그 말은 brief에 append되고, 그래서 이 step은 **다시 도출된다**
(`always_set=True`). 다시 도출하지 않으면 판정자가 읽는 것은 여전히 얼어붙은 옛 체크리스트여서, 당신이 새로 추가한 그 일이
끝났는지 아닌지가 아예 판정에 들어가지 않는다 — 옛 체크리스트대로 "달성"이라고 판정한다. 다시 도출하는 비용은 실측 **$0.41 / 3분**이다.
[continuity](continuity.md)를 보라.

### 판정자가 명령을 실행할 수 있는가

기본은 **불가**다. `judge()`의 사전승인 목록은 질문 도구에 `Read` / `Glob` / `Grep`이고,
`can_run=True`일 때만 `Bash`가 추가된다. 트레이드오프:

- `Bash`를 준다(CLI의 `--judge-can-run`) → 검수 명령을 실제로 한 번 돌릴 수 있어 판정이 더 단단해진다
- 하지만 그러면 작업 공간을 변경할 수 있게 된다 → "겸사겸사 좀 고치고" 나서 통과로 판정할 수 있고, 그러면 이 판정은 의미가 없다

clarifier와 마찬가지로 **`Write` / `Edit` / `Agent`는 없다**. 이걸 집행하는 것은 `whitelist_guard`라는 hook이지
**`allowed_tools`가 아니다** — 후자는 **사전승인 목록이지 배타적 화이트리스트가 아니어서**, 모델은 목록에 없는 도구도 얼마든지 호출한다.
두 항목이 여전히 성립함을 보이는 실측 증거: HT002에서 "设定目标"의 그 판정자는 `Bash`를 **11번** 실행했는데,
당시 그의 사전승인 목록에는 `Bash`가 아예 없었다. 또 **$0.1짜리 프로브**에서
`allowed_tools=["Read"]`인 agent가 `Write`와 `Bash` 호출을 그대로 냈고, 그것을 막은 것은 권한 계층과 경로 안전장치였다
(`"requested permissions to write ... but you haven't granted it yet"` /
`"Output redirection was blocked..."`). 오늘은 이 두 종류의 호출이 hook에 의해 그 자리에서 `deny`된다 —
**막는 것은 hook이지 목록이 아니다**.

!!! warning "목표를 세우는 그 판정자는 기본적으로 `Bash`를 받지 못한다"
    `goal_step()`에는 **`can_run` 형식 파라미터가 없어서** `**spec_kw`로만 갈 수 있다: `goal_step(ch, goal_path=…, can_run=True)`.
    명시하지 않으면 `Bash`가 없고, `JUDGE_RULES`의 "먼저 `uname -a`로 네가 어디 있는지 똑똑히 봐라"라는 항목을 실행할 수 없다 —
    그래서 이 머신에서는 아예 검증할 수 없는 체크리스트를 써 줄 수 있다. `with_goal()`은 다른 이야기라서,
    독립된 `can_run` 형식 파라미터가 있다(기본 `False`).

### 왜 라운드 수에는 상한이 있고 질문 횟수에는 없는가

질문은 거의 돈이 들지 않지만, 한 라운드의 작업은 진짜 돈이다. 그래서:

- **질문은 횟수 무제한**(`max_asks=None`) — 명확해질 때까지 묻고, 그 판단은 clarifier 자신이 한다
- **라운드에는 상한**(`rounds=3`) — 다만 진짜 안전장치는 이 숫자가 아니라 세 번째 결론 「달성 불가」다:
  그것이 나오는 즉시 멈추고 사람에게 묻지, 라운드가 소진되기를 기다리지 않는다

## 언제 쓰지 말아야 하는가

**작업이 너무 작아서 판정이 작업보다 더 장황할 때.** 이 층은 단순한 문제를 복잡하게 만든다. 그리고 실측된 사실이다:
HT002의 "저장소 하나를 clone해서 macOS에 설치하고 돌린다"는 일에서 판정 체크리스트가 15개로 쓰였고,
그중 6개는 과정의 규칙 준수를 검증했고 4개는 원리상 검증 불가능했다. 그 라운드의 판정 자체가 **$1.4037 / 37 라운드 / 0.09h**를 썼고,
run 전체는 **$38.2409 / 0.97h**였다. 작업의 실패 방식이 애초에 두세 가지뿐이라면 `--no-goal`이 더 이득이다.

**목표를 판정 가능한 체크리스트로 쓸 수 없을 때.** 탐색적인 작업("이 저장소가 대충 어떤 건지 좀 봐라")에는 "끝났다"의 기준이 없고,
억지로 목표를 세우면 예쁘지만 판정이 안 되는 체크리스트만 나온다. 이런 일은 `flower once`, 또는 `--no-goal`.

**핵심 판정 항목을 이 환경에서 검증할 수 없을 때.** 판정자는 기본이 `can_run=False`이고 도구는
`Read` / `Glob` / `Grep`뿐이라 — **`file`을 실행할 수 없고**, 소스를 읽는 수밖에 없다. [HT001](../cases/ht001.md)의
"macOS 터미널에서 바로 실행"이라는 검수 기준은, run 전체가 Linux 컨테이너 안에서 돌았다:
**어떤 판정자도 컨테이너 안에서 macOS 바이너리를 검증할 수 없다**, 자체 검사든 독립이든 상관없이.
`--judge-can-run`이 일부는 구할 수 있지만(적어도 `file`은 실행할 수 있다), 구할 수 없는 부분은 목표를 세울 때
`[此环境无法验证:…]`로 표시해서 "멈추고 사람에게 묻는" 경로를 타게 해야지, 판정자가 똑똑해지기를 기대할 일이 아니다.

**무인 운영이고 중단이 허용되지 않을 때.** 달성 불가로 판정됐는데 응답할 사람이 없으면 이 step은 **멈추고**, [workflow](../reference/glossary.md#流程) 전체가 거기서 끝난다.
"일단 끝까지 돌리고 보자"가 목적이면 `--no-goal`, "멈추되 기다리지는 마라"가 목적이면 `--timeout 0` —
질문은 즉시 무응답으로 떨어지고, 이유는 디스크에 쓰인다.

**이것은 요구가 맞는지는 상관하지 않는다.** 판정 체크리스트는 brief에서 도출되므로, brief가 틀렸으면 판정은 틀린 일을 정확하게 검증할 뿐이다.
그건 [clarify](clarify.md) 층의 일이다.
