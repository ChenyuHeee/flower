# 사전 확인

손대기 전에 요구를 먼저 분명히 묻는다. [확인자](../reference/glossary.md#确认者)는 질문만 하고 손은 대지 않는 역할이며,
분명해질 때까지 묻고 마지막에 정확히 네 단락짜리 [브리프](../reference/glossary.md#需求确认书)를 출력해
디스크에 동결한다. 이후 모든 [스텝](../reference/glossary.md#步骤)은 이 문서를 읽고 시작하며, 요구를 다시 추측하지 않는다 ——
그리고 그 문답은 하류 컨텍스트에 **한 번도 들어가지 않는다**.

## 무엇을 해결하는가 {#解决什么问题}

flower가 컨텍스트를 정리하는 수단은 전부 **현장**을 치운다: 시효 만료, 거부된 호출 제거, 오류 메시지 제거,
큰 결과 [스필](../reference/glossary.md#落盘). 현장은 잃어도 괜찮다. 다시 돌리면 나온다.

그렇지 않은 오류가 한 종류 있다: **목표를 잘못 이해한 것**. 이것은 **컨텍스트 정리가 오히려 악화시키는** 유일한 종류의 오류다.
현장이 버려지고 나면, 남는 것은 정확히 그 잘못된 전제 위에 세워진 결정이고, 그것은 올바른 결정과 완전히 똑같아 보인다 ——
그 전제가 의심스럽다는 흔적은 어디에도 없다.

[롱호라이즌](../reference/glossary.md#长程)은 이것을 최악까지 증폭한다: 잘못된 전제로 몇 시간을 달리고,
[subagent](../reference/glossary.md#subagent)를 열몇 개 파견하고, 디스크에 산출물을 잔뜩 남긴 뒤에야 드러난다.
그때 비싼 것은 token이 아니라, **모든 산출물이 잘못된 요구에 맞춰 지어졌다**는 사실이다.
[HT001](../cases/ht001.md)의 계산서가 이 비율을 보여준다: 요구를 확인하는 스텝이 **$0.3704 / 5 라운드 / 0.06h**,
그 뒤 실제로 일하는 스텝이 **$171.2476 / 31 라운드 / 10.44h**.

그래서 "멈추고 물어볼" 수 있는 통로가 필요하고, 그것은 반드시 착수 **이전**이어야 한다.

## 쓰는 법(최소 코드) {#怎么用最小代码}

### 코드 없이: 커맨드라인 {#零代码命令行}

프로젝트 디렉터리로 들어가 그냥 실행한다:

```bash
cd /path/to/your/project
flower
```

```text
要做什么? 一句话就够,回车开始(Ctrl-C 退出)
> 帮我做一个 X
```

터미널에는 이런 질문이 뜬다:

```text
  ? 这个工具是给命令行用,还是要有 Web 界面?
     1) 纯命令行
     2) Web 界面
     3) 两个都要
你的回答 (回车=跳过,让它自己判断) > 1
```

- **번호**를 입력해 선택하거나, 그냥 타이핑해서 답한다
- **엔터 = 이 질문을 건너뛰기**. 스스로 판단하게 두고 그 가정은 「미지와 가정」에 기록된다
- 네 단락이 모두 갖춰져야 통과하며, 브리프는 `.flower/notes/需求.md`에 동결된다
- **다시 돌려도 또 캐묻지 않는다** —— 다시 확인받고 싶으면 그 파일을 지우거나 `--new`를 붙인다

무엇을 묻는지만 보고 그 아래로는 일을 시키지 않으려면: `flower --clarify-only`. 질문에 하드 쿼터를 주려면: `--asks 12`
(줬을 때만 선택지 아래에 `(还能问 N 次)` 한 줄이 더 나온다. 기본값은 횟수 무제한이고 그 줄은 나오지 않는다). 지키는 사람이 없으면: `--timeout 0`.
이 경로의 구현은
[`flower/workflow/starter.py`](https://github.com/ChenyuHeee/flower/blob/main/flower/workflow/starter.py)에 있다.

!!! warning "답은 표준 입력으로 들어온다. 진짜 터미널에서 돌려야 한다"
    파이프, `nohup`, CI에서는 답할 사람이 없다. stdin이 EOF를 읽는 순간 그때 걸려 있던 질문은 "입력이 닫혔다"로 처리되어 건너뛰고,
    그 뒤의 모든 질문은 `--timeout`을 꽉 채워 기다리게 된다. 이런 상황에서는 그냥 `--timeout 0`을 줘라 ——
    모든 질문이 즉시 빈손이 되고, 스스로 판단해 가정을 「미지와 가정」에 적는다.

### 직접 배선하기 {#自己接线}

```python
from pathlib import Path
from flower import HumanChannel, Step, Workbench, Workflow, clarify_step

wb = Workbench(Path.cwd()).ensure()
ch = HumanChannel(log_path=wb.notes / "问答记录.md")   # 기본은 질문 횟수 무제한, 사람을 30분 기다림
wf = Workflow(channel=ch, workbench=wb, steps=[
    clarify_step(ch, brief_path=wb.notes / "需求.md", prompt="帮我做一个 X"),
    Step("干活", spec=协调者, prompt=lambda ctx: f"照这份需求做:\n\n{ctx['确认需求']}"),
])
```

`prompt`에는 **당신의** 원래 요구만 적는다. 한 문장이면 충분하다. 무엇을 물을지는 확인자가 스스로 정한다 ——
당신의 도메인에서 무엇을 물어야 하는지 프레임워크는 모르고, 알아서도 안 된다. 위의 `协调者`는 당신이 `coordinator()`로
직접 만든 `AgentSpec`이다. [워크플로 설계](workflow.md)를 보라.

`clarify_step()`의 인자:

| 인자 | 기본값 | 설명 |
|---|---|---|
| `channel` | — | `HumanChannel`. **같은 인스턴스**를 `Workflow(channel=...)`에도 달아야 한다 |
| `brief_path` | — | 브리프를 어디에 둘지. 반드시 달아 둔 그 [워크벤치](../reference/glossary.md#工作台) 안이어야 한다. 아래 참조 |
| `prompt` | — | 당신의 원래 요구. `str` 또는 `Callable[[Ctx], str]` |
| `name` | `"确认需求"` | 스텝 이름이자 `ctx`의 키 이름 |
| `spec` | `None` | 직접 만든 `AgentSpec`. 주면 `clarify()`로 만들지 않는다 |
| `instructions` | `""` | `CLARIFIER_RULES` 뒤에 덧붙이는 도메인 지시 |
| `always_ask` | `False` | `True` = 매번 다시 확인(요구를 바꿀 때 쓴다) |
| `on_fail` | `"stop"` | 네 단락이 안 갖춰졌을 때의 행선지. `Step.on_fail`과 같다 |
| `retries` | `0` | 네 단락이 안 갖춰졌을 때 몇 번 재시도할지 |
| `**spec_kw` | — | `clarify()`로 그대로 전달: `can_read` / `model` / `effort` / `max_turns` / `max_budget_usd` |

다 돌고 나면 `ctx`에 세 가지가 들어 있다:

```python
ctx["确认需求"]     # str, 네 단락의 압축판(prompt_block). 하류 prompt에 바로 삽입한다. 키 이름 = 스텝 이름
ctx[BRIEF_KEY]     # "_brief" —— Brief 객체. 단락별로 꺼내려면 이걸 쓴다
ctx[MISSING_KEY]   # "_brief_missing" —— 네 단락이 안 갖춰졌을 때만 존재: 어떤 단락이 빠졌는지, UI 표시용
```

잘 안 돌 때는 이 손잡이들부터 돌려라:

| 증상 | 무엇을 돌리나 |
|---|---|
| 너무 많이, 너무 잘게 묻는다 | `max_asks`에 하드 쿼터를 준다. `instructions`에 당신 도메인에서 무엇이 자명한지 적는다 |
| 너무 조금 묻고 착수한다 | `instructions`에 반드시 확실히 해야 할 항목을 지목한다(횟수는 기본이 이미 무제한이라 쿼터를 만져봐야 소용없다) |
| 네 단락을 성의 없이 채운다 | `instructions`에 당신 도메인의 예시를 하나 준다 |
| 지키는 사람이 없는데 멈춰 있다 | `timeout_s=0` |
| 매번 다시 확인받고 싶다 | `always_ask=True`, 또는 브리프 파일을 지운다 |

## 실제로 하는 일 {#它实际做了什么}

### 트리거 시점: 세 군데 배선, 새 필드는 하나도 없다 {#触发时机三处接线一个新字段都没加}

`clarify_step()`이 만들어내는 것은 평범한 `Step`이고, 콜백 세 개를 채워 넣었을 뿐이다:

| 어디에 붙나 | 언제 도나 | 무엇을 하나 |
|---|---|---|
| `Step.when` | 이 스텝에 들어가기 전 | 브리프가 이미 있고 네 단락이 갖춰졌으면 **건너뛰고**, 그것을 `ctx`에 채워 넣는다 |
| `Step.gate` | 이 스텝이 끝나고 결과를 하류에 넘기기 전 | 네 단락이 다 안 적혔으면 **더 못 가게 막는다**. 갖춰졌으면 `write()`로 **동결** |
| `Step.reduce` | 통과한 뒤 | 하류로 **파싱된 네 단락**을 넘긴다. 모델 원문이 아니다 |

**건너뛸 때도 `ctx`를 채운다.** 이건 놓치기 쉽다. `when`이 `False`를 반환하면 `Workflow`는 이 스텝을 실행하지 않고,
당연히 `ctx[step.name]`도 쓰지 않는다 —— 그래서 `clarify_step`은 `when` 안에서 이미 있는 브리프를 채워 넣는다.
그러지 않으면 재실행 시 하류가 `KeyError`를 받는다.

`reduce`가 넘기는 것은 모델 원문이 아니라 `Brief.prompt_block()`이다. 원문에는 모델이 더 써넣은 것이 섞여 있을 수 있기 때문이다
(실측에서 코드 전체를 답변에 붙여 넣었다).

[이어가기](../reference/glossary.md#接续) 때 이 스텝은 다른 한 문장으로 말을 연다 —— `CLARIFY_RESUME`:
"아까 다 못 끝낸 요구 확인을 이어서 계속한다 —— **새로 시작하는 게 아니다**……". 이 문장을 주지 않으면
이어가기가 원래 요구를 새 태스크로 다시 보내게 되고, 확인자가 이미 물어본 것을 또 물을 수 있다.

### 경계: 문답은 하류 컨텍스트에 들어가지 않는다 {#边界问答不进下游的上下文}

```text
확인자          독립 세션  ────→  디스크에 동결된 네 단락짜리 브리프
                                          │
작업(다음 스텝)  새 세션(resume_from=None)◄─┘   네 단락만 받는다
```

`clarify_step`의 `resume_from`은 기본값 `None`이므로 다음 스텝은 **새 세션**이고, 브리프만 받는다.
그 문답은 [코디네이터](../reference/glossary.md#协调者)의 컨텍스트에 **한 번도 들어가지 않는다** ——
"들어갔다가 잘려나간" 것이 아니다. 이 차이는 실질적이다. 잘려나간 것은 `sessions.db`에 여전히 남아 있고
resume으로 다시 딸려 올 수도 있다. 애초에 들어간 적 없는 것에는 이 문제가 없다.

문답 자체는 **`log_path`에 append된다**. 이 사본은 컨텍스트를 차지하지 않고, compact의 영향도 받지 않으며, 기계를 바꿔도 남는다 ——
워크벤치와 같은 발상이다.

### 네 단락은 각각 한 종류의 실패를 막는다 {#四段各挡一类失败}

| 단락 | 무엇을 쓰나 | 안 쓰면 어떻게 되나 |
|---|---|---|
| **목표(目标)** | 한 문장: 무엇을 만들고, 누가 쓰나 | 만들어진 것이 다른 물건이다 |
| **검수 기준(验收标准)** | 판정 가능한 조건, 한 줄에 하나씩. "잘 만든다"는 안 되고 "`x`를 돌리면 `y`가 나온다"여야 한다 | 아무도 "다 됐다"를 판정할 수 없다 |
| **경계(边界)** | **무엇을 하지 않는지 명시** | 범위가 번진다. 이 단락이 뒤따르는 **모든** subagent를 붙든다 |
| **미지와 가정(未知与假设)** | 못 물어본 것, 타임아웃으로 빈손이 된 것, 스스로 추측한 것, 한 줄에 하나씩 | **잘못된 전제가 조용히 묻힌다** |

네 번째 단락이 롱호라이즌 런의 퓨즈다. 앞의 세 단락 중 어느 하나가 틀렸어도, 가정이 네 번째 단락에 명시되어 있으면
뒤에서 읽는 사람이 막을 기회가 생긴다. 묻어버리면 몇 시간 뒤 산출물이 전부 폐기될 때에야 알게 된다.
잘못된 전제를 완전히 피할 수는 없지만, **명시적으로** 만들 수는 있다.

네 단락이 다 갖춰져야 통과하고, 어느 단락이 빠졌는지는 `Brief.missing()`이 알려준다 —— 반환값은 중국어 단락 이름이라 그대로 표시하면 된다.

파싱은 표기에 매우 관대하다. `## 目标` / `**目标**` / `目标:` / `3. 边界` 전부 인식하고, 제목 뒤에 바로 본문이 오는 것
(`目标: 做一个 X`)도 인식하며, 흔한 별칭도 인식한다(`验收条件`→验收标准, `不做什么`→边界,
`未知项与假设`→未知与假设). 같은 단락이 여러 번 나오면 내용이 있는 첫 번째를 취한다. 예외 두 가지는 알아둬야 한다:

- `Brief.parse()`는 **먼저 펜스 코드 블록을 벗겨낸다**. **닫히지 않은** 펜스를 만나면 거기서부터 뒤를 통째로 버린다.
  모델 출력이 잘렸을 때 뒤쪽 단락이 전부 파싱되지 않는다 → 네 단락 미충족 → `gate`가 되돌려 보낸다.
- `Brief.load()`는 `"(未填)"`를 빈 것으로 본다. 브리프를 손으로 편집하면서 `to_markdown()`의 자리표시 문구를 그대로 베껴두면
  그 단락은 여전히 빠진 것으로 친다.

### 경계: 확인자가 건드릴 수 있는 것 {#边界确认者能碰什么}

**제약 없는** 확인자를 한 번 돌려봤다(`/tmp/probe_ask.py`, **$0.8908 / 230초**):
질문 두 개를 하고 나서 **바로 코드를 쓰기 시작했다**. 권한에 막히자 **코드 전체를 답변 본문에 붙여 넣었다**.
프롬프트에 "코드를 쓰지 마라"라고 써도 이것은 못 막는다 —— 그때의 시스템 프롬프트에도 비슷한 말이 이미 있었다. 그래서 장치가 두 개다:

**첫째, hook 하나가 쓰기 도구를 막는다.** `clarify()`의 무승인 목록은
`mcp__human__ask`와 (`can_read=True`일 때) `Read` / `Glob` / `Grep` / `WebFetch` / `WebSearch`이고,
`Write` / `Edit` / `Bash` / `Agent`는 없다. 실제로 이것을 집행하는 것은 `Runtime`이 자동으로 다는 `whitelist_guard`다.
무승인 목록에서 역산해 `Bash` / `Write` / `Edit` / `NotebookEdit` 중 막아야 할 것들을 정하고,
걸리면 `deny`한다. "일하지 말라는 요구를 받은" 것이 아니라 **일할 수가 없는** 것이다.

읽기를 주는 것은 남는 장사다. 저장소를 한 번 훑으면 질문 몇 개를 아낄 수 있고, 이 세션은 쓰고 버리므로 좀 더러워져도 상관없다
(`can_read=False`로 읽기조차 안 줄 수도 있다).

**이건 반드시 hook이어야 하고, `allowed_tools`만으로는 안 된다.** 후자는 **무승인 목록이지 배타적 화이트리스트가 아니다** ——
모델은 목록에 없는 도구도 얼마든지 호출한다. 아직 유효한 실측 증거 두 가지:

- [HT002](../cases/ht002.md)에서 "목표 설정" 스텝의 [판정자](../reference/glossary.md#判定者)가
  실제로 **`Bash`를 11번** 돌렸다. `judge()`는 기본이 `can_run=False`이고 목록에 `Bash`가 아예 없는데도 그랬다
  (그 런에는 아직 이 hook이 없었다 —— 오늘 같은 호출이면 `whitelist_guard`가 그 자리에서 `deny`한다.
  이것이야말로 막는 주체가 목록이 아니라 hook임을 보여준다).
- **$0.1짜리 프로브**: `allowed_tools=["Read"]`인 agent에게 파일을 쓰라고 시켰다 ——
  `Write`는 권한 계층이 거부했고(`"requested permissions to write ... but you haven't granted it yet"`),
  `Bash`는 경로 안전 검사가 거부했다(`"Output redirection was blocked. For security, Claude Code may
  only write to files in the allowed working directories"`). **호출은 나갔고**,
  다른 계층이 막은 것이다.

`clarify()`는 `permission_mode`를 명시하지 않고, `AgentSpec`의 기본값 `"default"`를 물려받는다.
`coordinator()`의 기본은 `"acceptEdits"`다 —— 누군가 이 값을 확인자에게 그대로 넘기면 그 보호는 사라진다.

**둘째, 프레임워크는 그 네 단락만 파싱하고 나머지는 전부 버린다.** `Brief.parse()`는 펜스 코드 블록을 먼저 떼어낸 뒤 제목을 찾는다 ——
붙여 넣어도 하류로 못 간다. "하류를 오염시키는" 경로의 마지막 차단문이다.

### 경계: 질문 채널 {#边界提问通道}

모델 쪽 질문 도구의 이름은 `mcp__human__ask`(인자 `question`, 선택 `options`)다.
`HumanChannel`은 인프로세스 MCP 서버이며, **등록하는 도구는 두 개다** ——
`mcp__human__ask`와 `mcp__human__inbox`. 확인자의 무승인 목록에는 앞의 하나만 있다
(수신함은 코디네이터용이다).

```python
HumanChannel(
    on_event=None,        # 푸시형 UI의 콜백. Workflow에 달면 Workflow.run이 자동으로 연결한다
    max_asks=None,        # 기본은 횟수 무제한
    timeout_s=1800.0,     # 30분. None = 영원히 대기. <= 0 = 완전 자동
    log_path=None,        # 문답을 이 파일에 append. 컨텍스트를 차지하지 않는다
    amend_path=None,      # 런 도중 사람이 한 말을 이 파일에 append(보통 브리프 그 자체)
    over_budget_text=..., timeout_text=..., declined_text=...,   # 세 가지 빈손 상황의 문구
)
```

롱호라이즌 agent의 평상시는 **아무도 안 보고 있는 상태**다. 그래서 "멈춰서 사람을 기다린다"는 우아하게 실패할 수 있어야 한다:

| 설정 | 동작 |
|---|---|
| `timeout_s=1800.0`(기본) | 30분 대기. 시간이 되면 설명 한 줄을 반환한다. **에러가 아니다** |
| `timeout_s=None` | 영원히 대기. 사람이 지킨다고 확신할 때만 쓴다(CLI로는 이 값을 줄 수 없다. `--timeout`은 float다) |
| `timeout_s=0`(음수도 동일) | **완전 자동**: 모든 질문이 즉시 빈손이 된다. 기다리는 척하지 않는다 |
| `max_asks=None`(기본) | **횟수 무제한** —— 몇 번 물을지는 확인자가 스스로 판단한다 |
| `max_asks=N` | 하드 쿼터. 초과한 질문 도구는 **곧바로 거절**된다. 블로킹도 에러도 없다 |
| `max_asks=0` | 질문 금지(CI / 무인 운영) |

`remaining`은 `max_asks=None`일 때 `-1`을 반환한다(0도 아니고 무한도 아니다). 터미널은 이를 보고 "앞으로 N번 더" 표시를 하지 않는다.

타임아웃이 반환하는 원문은 이렇다:

> 응답하는 사람이 없다. 네 판단대로 계속하고, 이 질문과 네가 채택한 가정을 「미지와 가정」 단락에 적어라.
> 같은 질문을 반복하지 말고, 여기서 멈추지도 마라.

세 가지 빈손(타임아웃 / 쿼터 소진 / 사람이 직접 건너뜀)의 문구는 모두 같은 동작을 가리킨다: **가정을 네 번째 단락에 적어라.**
이것이 무인 운영에서도 네 번째 단락에 내용이 남는 이유이고, 롱호라이즌 런이 계속 굴러갈 수 있는 이유다.
쿼터를 프롬프트에 적는 것은 권고일 뿐이고, **채널에서 세는 것이 보장이다**.

실측으로 확인한 메커니즘 사실 하나: 인프로세스 MCP 도구 핸들러 안에서 외부 future를 `await`해도 **데드락이 나지 않는다** ——
핸들러가 걸려 있는 동안에도 이벤트 루프는 계속 돌고, 다른 태스크든 **다른 스레드**든 답을 채워 넣을 수 있다.
그래서 `answer()` / `decline()`은 웹 백엔드나 TUI 입력 스레드에서 바로 호출해도 된다(내부적으로
`loop.call_soon_threadsafe`를 쓴다). 이건 예외가 아니라 평상시다. UI 콜백이 던진 예외는 `ui_errors`에 모이고
**런을 중단시키지 않는다** —— 프런트엔드가 죽었다고 세 시간짜리 작업을 같이 데려가면 안 된다. 전체 멤버 목록은 [Python API](../reference/api.md)를 보라.

!!! warning "`max_turns`를 작게 잡으면 '분명해질 때까지 묻는다'는 빈말이 된다"
    `clarify()`의 `max_turns` 기본값은 `None`(무제한)이다. **질문 하나가 곧 한 라운드다** ——
    16으로 잡으면 "많아야 열몇 개만 묻는다"와 같고, 게다가 **조용히** 적용된다. 채널 쪽 `max_asks=None`은
    여전히 "무제한"이라고 적혀 있어서, 누가 목을 조른 건지 사람 눈에 안 보인다. 질문을 풀어주려면 `HumanChannel.max_asks`와
    `clarify(max_turns=...)` **두 기본값 모두 `None`으로 남겨야 한다**.

### 브리프를 어디에 두나: 반드시 달아 둔 그 워크벤치 {#确认书落在哪必须是挂上去的那个工作台}

워크벤치 인덱스는 system prompt에 주입되므로, 코디네이터는 시작하자마자 요구 파일이 어디 있는지 알고,
일을 파견할 때 경로만 넘기면 된다. 내용을 [태스크 브리프](../reference/glossary.md#任务书)에 베껴 넣을 필요가 없다.

!!! warning "인덱스는 코디네이터까지만이다"
    subagent는 자기 system prompt를 가지며, 세션 수준의 그 부분을 **물려받지 못한다**(실측 **$0.2461**,
    `tests/prelude_live.py`). 그래서 "코디네이터가 경로를 전달"이지 "모든 subagent가 자동으로 안다"가 아니다.

관건은 **어느** 워크벤치냐다. 맞는 방식은 하나뿐이다: 직접 만들고 `Workflow`에 달아서,
드라이버가 같은 객체를 `Runtime`에 넘기게 하는 것.

```python
wb = Workbench(Path.cwd()).ensure()
wf = Workflow(channel=ch, workbench=wb, steps=[            # ← 달아 준다
    clarify_step(ch, brief_path=wb.notes / "需求.md", prompt="…"),
    ...,
])
```

틀리는 방식이 둘 있는데, 둘 다 **에러를 내지 않으므로** 특히 조심해야 한다:

```python
# ✗ 경로를 직접 조립: 프로세스 cwd 기준이라, Runtime(workbench=True)이 만드는 <run_dir>/workbench와는
#   서로 다른 디렉터리다. 브리프는 A에 쓰이고 주입된 인덱스는 B를 훑는다 —— 위의 약속이 조용히 무효가 된다.
clarify_step(ch, brief_path=Path(".flower/notes/需求.md"), prompt="…")

# ✗ Runtime에서 거꾸로 가져오려는 시도: cli.py를 거치면 불가능하다. 먼저 main()을 호출해 Workflow를 만들고
#   그 뒤에 Runtime을 만든다 —— 그때는 brief_path가 이미 확정된 뒤다.
rt = Runtime(workspace="repo", workbench=True); wb = rt.workbench
```

드라이버를 직접 쓸 때(`cli.py`를 거치지 않을 때)는 `Workbench`를 먼저 만들고, **같은 객체**를
`Workflow(workbench=wb)`와 `Runtime(workbench=wb)`에 동시에 준다. `tests/trial_offline.py`의
5번 항목은 "브리프가 `prompt_block()`에 나타난다"를 직접 단언하고, 11번 항목은 이 단언이 회귀를 잡아낸다는 것을 확인한다.

### 검증 상태 {#验证状态}

**오프라인 전부 통과**(`tests/clarify.py`, **52항목**, 비용 없음): 질문 채널의 다섯 가지 의미(블로킹 대기 /
쿼터 소진 / 타임아웃 빈손 / 건너뛰기 / 스레드 간 응답), 네 단락 파싱("코드를 붙여 넣은" 샘플 포함),
`clarify()` 역할에 쓰기 도구가 **없음**, `clarify_step`의 세 군데 배선.

**CLI 경로 오프라인 관통**: 완성된 브리프를 미리 놓기 → 첫 스텝 건너뛰기 → 채널이 표준 입력 스레드에 자동 연결 →
브리프가 `ctx`에 주입 → 깔끔한 종료.

**실제 API로는 돌려보지 않았다.** $0.8908짜리 프로브는 **실제 요청**이었지만, 그것이 측정한 것은 "제약 없는 확인자가 무엇을 하는가"이지
지금 이 경로가 아니다.

## 언제 쓰지 말아야 하나 {#什么时候不该用它}

**요구가 이미 동결된 물건일 때.** 요구가 파일에 적혀 있거나, 상류 시스템이 지정해 주거나, 이번이 같은 일의 재실행이라면 ——
물을 것이 없다. 요구 텍스트를 작업 스텝에 바로 먹이거나, `clarify_step`을 남겨 두고 `when`이 건너뛰게 두면 된다
(브리프가 있으면 어차피 묻지 않는다).

**물을 사람이 없고, 스스로 추측하게 두고 싶지도 않을 때.** `timeout_s=0`이면 모든 질문이 즉시 빈손이 되고,
네 번째 단락은 자기 가정으로 잔뜩 채워진다 —— 설계상 그렇지만, 그 브리프의 신뢰도는 곧 그 가정들의 신뢰도와 같다.
CI에서는 `max_asks=0`(질문을 명시적으로 금지)이 더 깔끔하고, 요구는 외부에서 온전히 주는 편이 낫다.

**한 번 쓰고 마는 작은 일.** 확인 스텝 자체에 돈이 든다: [HT002](../cases/ht002.md)에서
"저장소를 clone해 macOS에 설치하고 돌린다" 정도의 일에 요구 확인이 **$0.5306 / 9 라운드 / 0.10h**를 썼다.
일이 작을수록 이 스텝의 비중은 볼썽사나워진다. `flower once` 같은 단일 agent 경로에는 이 스텝이 없다.

**요구를 바꿀 때 대화를 다시 하면 안 된다.** 브리프는 동결된 물건이고, 스필된 순간부터 요구의 기준은 파일이다 ——
올바른 방법은 **그 파일을 고치는 것**이다. 이미 확인이 끝난 디렉터리에서 `--clarify-only`는 **아무 일도 하지 않는다**
(그 워크플로에는 이 스텝 하나뿐인데, 그 스텝이 건너뛰어지기 때문이다). 다시 확인받으려면 `--new`를 함께 주거나,
직접 배선할 때 `always_ask=True`를 준다.

**"다 됐는지"는 이것이 판정하지 않는다.** 그건 다른 계층이다. [목표 가드](goal.md)를 보라. 사전 확인이 막는 것은
"만들어진 게 원하던 게 아니다"이지, "다 됐다고 말했는데 사실은 안 됐다"가 아니다.
