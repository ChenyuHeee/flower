# HT001 · 터미널 IDE를 밑바닥부터 작성하기

2026-09-07, 한 agent가 flower 위에서 macOS 터미널에서 돌아가는 C/C++ 단일 파일 IDE를 밑바닥부터 만들어냈다.
연속 10.4시간을 돌았고, $171.62를 썼으며, 12,212줄의 제품 코드와 13,291줄의 테스트를 내놓았다.
도중에 네트워크가 한 번 끊겼지만 스스로 이어서 완주했다. 이 페이지는 성과 전시가 아니다 —— 프레임워크의 주장 하나하나를 실제 규모에서 측정한 기록이며,
**거기에는 측정해 보니 성립하지 않았던 두 가지도 포함된다**: coordinator가 "권한 제한을 자주 무시한다"는 것은 거짓이었고, 스스로 매긴 검수 중 한 항목은 오판이었다.

전체 기록(19MB transcript 포함)은 [ChenyuHeee/cppide](https://github.com/ChenyuHeee/cppide)에 있다.
아래의 모든 숫자는 `tools/analyze_run.py`가 `sessions.db`에서 계산한 것이며 재현 가능하다:

```bash
python tools/analyze_run.py /path/to/cppide/runs
```

!!! note "이 페이지의 숫자는 어디서 왔는가"
    HT001의 `runs/`는 위 cppide 저장소에 있고, **flower 저장소에는 없다**. 따라서 이 페이지의 숫자는
    당시 run 기록에서 **그대로 옮겨온** 것이며, 이 페이지를 쓰면서 `sessions.db`를 놓고 다시 계산해 보지는 않았다 ——
    재계산하려면 먼저 cppide를 clone한 뒤 위 명령을 돌려야 한다.
    [HT002](ht002.md)는 반대다: 원본 기록이 이 저장소 안에 있고, 그 페이지의 숫자는 한 줄씩 재계산했으며,
    맞지 않은 두 곳은 페이지에 그대로 적어 두었다.

## 1. 컨텍스트 경제학: 94.8%의 현장은 main thread에 들어오지 않았다 {#一上下文经济学948-的现场没进主线程}

이것이 프레임워크의 핵심 주장이다 —— [coordinator](../reference/glossary.md#协调者)는 결정만 담고,
현장은 subagent와 디스크로 가라앉힌다. 메커니즘 자체는 [컨텍스트 경제학](../guide/context.md)을 보라.

| | main thread | subagent | subagent 비중 |
|---|---|---|---|
| 모델 turn | 70 | 3.0K | **97.7%** |
| 본문 문자 | 200.1K | 3.6M | **94.8%** |
| 도구 호출 | **32** | **1,893** | —— |

이 run은 23개의 subagent를 파견했고, 출력 token은 최대 184,377, 중앙값 72,197, 최소 11,684였다.

**직접 손을 댄 1,893회의 도구 호출(1,034 Bash / 471 Read / 258 Edit / 126 Write) 중 coordinator의 시야에 들어온 것은 32회뿐이다
—— 59:1.** 한 번 사람을 보낼 때마다 평균 82개의 도구 호출은 coordinator에게 보이지 않았다.

이전 소규모 테스트에서는 83%로 측정됐지만, 실제 규모에서는 **94.8%**다. 규모가 클수록 분업의 이득이 커진다 ——
[task brief](../reference/glossary.md#任务书)와 회신의 비용은 **파견 1회당 고정**인 반면,
바깥에 차단되는 현장은 과제 복잡도에 따라 늘어나기 때문이다.

## 2. 컨텍스트 곡선: "long-horizon"의 상한이 어디인지 처음 알게 됐다 {#二上下文曲线第一次知道长程的上限在哪}

각 assistant 메시지의 `input + cache_read + cache_creation`이 그 turn에서 모델이 본 컨텍스트다:

```text
제 1turn   28.7K   ← 시작 바닥값(이전 실측 약 34k, 맞아떨어짐)
제20turn   35.2K
제35turn  108.6K
제50turn  158.2K
제70turn  185.9K   ← 종료
```

- 70 turn 동안 단조 증가, 기울기 약 **2.2K/turn**
- 전 구간 **compact는 한 번도 발생하지 않음**(`DISABLE_AUTO_COMPACT=1`; 유일한 하락은 네트워크가 끊긴 turn의 빈 기록)
- 1M 윈도의 **18.6%** 사용

**이 기울기로 외삽하면 벽에 부딪히는 지점은 약 440 turn이다.** 이번 70 turn이 12K줄의 코드를 산출했으므로,
현재 형태에서 [long-horizon](../reference/glossary.md#长程)의 실제 상한은 이번의 약 **6배**다.
의사결정에 쓸 수 있는 숫자이며, 이전에는 추측만 가능했다.

이를 돌파하려면 main thread의 증가를 **선형 이하**로 만들어야 한다 —— 더 많이 디스크로 가라앉히고, 대화에는 더 적게 남긴다.

## 3. 캐시 적중률 96.1% —— $171.62가 성립하는 것은 전적으로 이것 덕분이다 {#三缓存命中-961--17162-能成立全靠它}

```text
총 입력 299.4M token
  캐시 적중  287.5M  (96.1%)
  캐시 신규   11.8M
  비캐시       6.2K
출력 2.3M(그중 thinking 653.9K)
```

299M 입력 token이 $171밖에 들지 않은 것은 96%가 캐시 가격으로 처리됐기 때문이다.

**따라서: long-horizon run의 경제성은 캐시 적중률 위에 서 있고, 캐시 적중률은 컨텍스트 접두부의 안정성에 달려 있다.**
"컨텍스트를 재배열하는" 모든 최적화 —— 오래된 내용을 옮기거나, 앞쪽에 새 시스템 prompt를 끼워 넣는 것 —— 는 캐시를 깨뜨리고,
아낀 token이 잃어버린 캐시 할인을 도저히 상쇄하지 못할 수 있다. 이전에는 측정된 적이 없었고, 이제 숫자가 있다.

이는 flower가 compact 대신 [handoff](../reference/glossary.md#换代)를 쓰는 부수적 이유이기도 하다:
handoff는 **새 session을 열어 캐시를 처음부터 쌓는** 것이므로, 한 세대 안에서는 접두부가 계속 안정적이다.

## 4. workbench 재사용: 61개 스크립트, 쓰고 버린 것은 하나도 없다 {#四工作台复用61-个脚本没有一个写完就扔}

[workbench](../reference/glossary.md#工作台)의 주장은 "스크립트는 한 번 쓰면 이후에는 그냥 실행할 뿐, 다시 쓰지 않는다"이다.
검증 방법은 agent에게 묻는 것이 아니라, `.flower/scripts/`의 스크립트가 transcript에서 Write/Edit된 횟수와 Bash로 실행된 횟수를 세는 것이다:

```text
61개 스크립트: 작성 95회, 실행 331회
실행 횟수 > 1인 것(실제 재사용): 56개, 92%
작성했지만 한 번도 실행되지 않은 것: 0개
실행/작성 비 3.48
```

`wave5-verify.sh`는 5번 작성되고 45번 실행됐다 —— 반복해서 다듬은 뒤 계속 사용하는, 바로 원하던 형태다.
**쓰고 버려진 스크립트는 하나도 없다.**

## 5. coordinator의 직접 조작은 1회 거부됐고, 그마저 화이트리스트의 잘못이었다 {#五协调者动手被拒-1-次而且是白名单的错}

착수 전의 의심은 이랬다: "coordinator가 권한 제한을 자주 무시해서 대량의 거부 호출을 유발한다." 실측은 이 전제를 무너뜨렸다.

**32회의 도구 호출 중 거부는 1회(3.1%)**, 그리고 그 한 번은 이것이었다:

```bash
which g++ clang++ make pkg-config 2>&1; echo ---; ls /usr/include/ncurses.h 2>&1; echo ---; ls /work/runs
```

구간별 판정: `echo` 통과, `ls` 통과, **`which` 차단 —— 
[ephemeral command](../reference/glossary.md#一次性命令) 목록에 없었다**.

명령 전체가 순수 읽기 전용이며, 표준적인 환경 탐지다. **모델은 완전히 옳게 했고, 화이트리스트가 불완전했다.**
`which g++` 한 줄 때문에 subagent 기동 비용(약 4.3k token)을 치르게 만든 것이다.

수정 완료: `which` / `command -v` / `type` / `whereis` / `uname` / `arch` / `locale` / `nproc` /
`getconf` / `sw_vers`를 추가했다. `command`와 `type`은 **질의 형식만 통과시킨다** ——
맨몸의 `command rm -rf /`는 실행이고, `-v`를 빼먹으면 뒷문을 여는 것과 같다.
`tests/glance.py`에 7개의 적대적 샘플이 이를 지키고 있다.

**여기서 가장 기억할 것은 그 패치가 아니라 방법이다.** 오래 이어진 아키텍처 논의의 출발 전제가 실제 데이터에서는 1/32였고,
게다가 귀인이 반대였다 —— 문제는 모델이 아니라 화이트리스트였다. **먼저 측정하고 말하라.**

## 6. 네트워크 단절 후 이어 달리기: 실제 장애로 처음 검증됨 {#六断网续跑第一次被真实故障验证}

```text
01:52:40  tool_result: "Agent terminated early due to an API error"   ← subagent 하나가 중단됨
01:55:41  assistant:   "API Error: ENOTFOUND"                          ← main thread가 수신
          ↓  프로브가 걸린 채 네트워크 복구를 대기
          resumed=True, 같은 session을 이어 달려 8시간 넘게 더 돌고 완료
```

manifest에는 `attempts=2 / resumed=True / ok=True`가 기록돼 있다. **10시간짜리 작업을 처음부터 다시 하지 않았다.**
그 전까지 [resilience](../reference/glossary.md#韧性)는 계속 "아직 미검증" 상태였다 —— 네트워크를 끊으려면 sudo로 hosts를 고쳐야 하는데, 실제 run 중에 그러고 싶은 사람은 없다.

합성된 그 "API Error" 메시지는 `PruningSessionStore`가 load 시점에 걷어냈고, **모델은 그것을 보지 못했다** ——
[prune](../reference/glossary.md#剪除)의 설계도 함께 실제 장애로 검증됐다.

드러난 두 가지 문제(issue #2 참조):

1. 복구가 전송 계층이 아니라 **프레임워크 계층**에서 일어난다. 대가는 전체 컨텍스트를 다시 재생하는 것이고, 그때의 컨텍스트는 컸다.
2. **중단된 그 subagent의 반제품 작업은 사라졌다.** resume이 구한 것은 main thread이고,
   subagent 수준의 중단 복구는 별개의 문제다.

## 7. 그것의 자기 검증은 진짜인가 {#七它的自我验证是真的吗}

여기가 가장 의심해야 할 지점이다: agent가 스스로 테스트를 쓰고, 스스로 돌리고, 스스로 통과를 선언하는 것은 형식적 절차로 전락하기 쉽다.

사후에 독립 감사 subagent를 하나 파견해 58개 스크립트와 22개 산출물을 정적으로 모두 읽게 했다. 결론은 **진짜이며, 엄격함이 드물 정도**였다:

- **항진 단언 0건.** 저장소 전체에 `[ 1 = 1 ]` 류의 패턴이 없다.
- `|| true`는 총 8곳, **7곳은 정당**하다(`grep -c`가 매칭 없을 때 1을 반환, `ulimit` 대비 등).
- **판정 대상이 파일 존재가 아니라 동작이다.** `audit-idle-cost.sh:53`은 IDE를 pty 안에서 60초간 유휴 상태로 돌리고,
  로컬 가짜 서버가 실제로 받은 요청 건수를 세어 `-le 2`일 때만 PASS다. `fix-p1-idle-verify.sh:100-110`은 한 걸음 더 나아간다:
  유휴 시 정확히 1회임을 단언하는 **동시에** ghost가 여전히 표시됨을 단언한다 —— "레이트 제한 변경이 기능까지 죽이는" 것을 막기 위해서다.
- **실제로 자식 프로세스를 띄운다.** `wave5-pty-drive.cpp:316`은 `forkpty`로 TUI를 실제 실행한다. `audit-fake-ai-server.py`는
  진짜 socket 서버로 `/err500 /err401 /badjson /drop /slow` 다섯 가지 장애 주입을 지원한다.
  모든 AI 경로는 `CPPIDE_API_KEY`를 강제로 비운다.

예상을 넘어선 것이 두 가지 있었다.

**자기 검증기에 대해 양성/음성 대조를 만들었다.** `验收审计.md:29-34`: 먼저 `ZZZ_NEVER_APPEARS_ZZZ`를 먹여 드라이버가 FAIL하는지 확인하고,
그다음 진짜 문자열을 먹여 PASS하는지 확인한다 —— "항상 PASS하는 가짜 기계로 감사하는" 상황을 피하기 위해서다. **검증기 자체를 검증하고 있다.**

**자신의 약한 단언을 자발적으로 공개했다.** `wave5-b4-ai-states.sh:114`의 `for m in $must`는
`"AI 错误 请求超时"`를 공백으로 세 개의 부분 문자열로 쪼개 각각 grep하는데, `AI`와 `错误`는 어느 화면에서든 반드시 나타난다 ——
명목상 "3건 통과"지만 실제로 변별력이 있는 것은 1건뿐이다. **이 항목은 그 자신이 `验收审计.md:576-582`에 써넣은 것**이며,
감사자가 파낸 것이 아니다.

같은 부류로: `wave5-verify.sh:296-302`는 7줄의 주석으로 B3b 항목이 왜 SKIP으로 강등됐는지 설명하고
(마지막 화면 타이밍 단언이며 제품 코드와 무관), "판정 로직과 허용 범위는 한 글자도 바꾸지 않았다"고 명시한다.
`:236-238`은 **자신이 앞서 작성한 가짜 단언을 발견하고 고친 것**을 기록한다 ——
`if pgrep ...`이 `pgrep`이 없는 경량 이미지에서는 조용히 else로 빠져 항상 PASS가 되던 문제다.

재사용의 정성적 증거는 4절의 숫자와 일치한다: `audit-fake-ai-server.py`는 **7개** 스크립트에서 재사용됐고,
`wave5-pty-drive.cpp`는 **5개 이상**의 컴파일에서 재사용되며 `[ -x "$DRIVE" ] ||`로 컴파일 결과를 캐시한다.
wave4 → wave5의 드라이버는 **재작성이 아니라 확장**이다(diff는 1줄만 수정, 343줄 추가, wave4의 281줄은 원형 그대로 유지).

**이 모든 행동은 goal guard가 없는 버전에서 일어났다.** 유일한 제약은 [brief](../reference/glossary.md#需求确认书)에 적힌
판정 가능한 검수 기준 10개였다. 이는 다음을 말해준다: **"완료"를 판정 가능한 형태로 적어두는 것만으로도 자기 감사와 자기 공개를 유도할 수 있다.**
goal guard의 한계 가치는 이것을 기준선으로 삼아 재야 하며, 0을 기준선으로 삼아서는 안 된다.

다만 다음 절이 보여주듯: **자기 감사는 검증 기술 면에서는 매우 강했지만, 가장 중요한 한 항목의 최종 판정에서 틀렸다.**

!!! warning "여기서 말하는 "감사자"는 judge가 아니다"
    7절과 8절에서 말하는 독립 감사자는 **coordinator가 자발적으로 파견한 subagent**이며,
    [goal guard](../reference/glossary.md#目标看守)의 [judge](../reference/glossary.md#判定者)가 아니다 ——
    이 run에는 애초에 goal guard가 없었다. 둘은 읽기에는 비슷하지만 하는 일이 다르다: 감사자는 사후 회고이고,
    judge는 매 turn 종료 시점의 [verdict](../reference/glossary.md#判定) 관문이다.

## 8. 스스로 매긴 점수는 맞았는가 —— 검수 1은 오판이었다 {#八它给自己打的分对吗--验收-1-判错了}

두 번째 독립 감사자를 파견해, 그 10개 검수 기준을 코드와 하나씩 대조해 판정하게 했다.

**검수 2–10은 전부 사실**이었고, 코드 증거도 모두 있었다. 연습 모드에서 코드를 끼워 넣지 않는 것은 심지어 **구조적** 보장이다:
유일한 sink 결정 지점 `ai.h:117` + 유일한 착지 switch `app.cpp:590-615` + 네 개의 early-return
`editor.cpp:679-683`으로, 흩어진 if가 아니다. 자기 감사가 발견한 P1–P4도 **전부 사실이고 수정도 전부 반영됐다**
(P4는 절반만 사실: 그 파란색 pair 줄은 죽은 코드이며, `ghostAttr()`는 원래부터 `A_DIM`을 탄다).

**하지만 검수 1은 오판이었다.**

```text
기준 원문:  "독립 실행 파일 하나를 컴파일해, macOS 터미널에서 바로 실행"
납품된 산출물: ELF 64-bit LSB pie executable, ARM aarch64, GNU/Linux
그것의 판정:  통과
```

이 항목은 사람이 직접 `file`을 돌려 확인했다.

숨긴 것은 아니다 —— `交付说明.md` §4의 제목 자체가 "가장 큰 미검증 리스크: macOS에서 한 번도 돌려보지 않음"이고,
감사 §6도 macOS의 미검증 항목 여섯 가지를 나열했다. **리스크는 공개했지만, 그 사실을 검수 1의 판정으로 되돌려 연결한 적이 한 번도 없다.**
그런데 검수 1의 문언상 요구가 정확히 그 사안이었다.

### 그러나 이것은 "독립 judge가 필요하다"는 증거가 아니다 {#但这不是需要一个独立判定者的证据}

이 항목을 "그러니 goal guard가 필요하다"로 읽기 쉽다. 틀렸고, 그렇게 읽는 것이야말로 **화살을 쏘고 나서 과녁을 그리는 것**이다 ——
바로 앞 절에서 비판한 그 동기적 추론이다.

**당시 버전의 goal guard도 기본 설정에서는 이 항목을 놓쳤을 가능성이 크다.** `judge()`의 기본값은 `can_run=False`이고,
도구는 `Read` / `Glob` / `Grep`뿐이다 —— **`file`을 돌릴 수 없다.**
소스를 읽으러 가서 `Makefile:25-38`에 실제로 Darwin 분기가 있는 것을 보고 "달성"으로 판정했을 것이다. 자기 감사와 똑같은 실패다.

### 진짜 구조적 사실 {#真正的结构性事实}

**검수 1은 이 run의 환경에서는 애초에 검증 불가능했다.**

그것이 단언하는 것은 "산출물의 macOS에서의 동작"인데, run 전체는 Linux 컨테이너 안에 있었다.
**어떤 judge도 컨테이너 안에서 macOS 바이너리를 검증할 수 없다.** 자기 감사든 독립이든 마찬가지다.
문제는 "누가 판정하느냐"가 아니라, **이 항목이 평범한 판정 가능 기준으로 취급되어 판정되었다는 것**이다.

### 감사자가 추가로 파낸 세 가지(자기 감사는 전부 언급하지 않음) {#审计员另外挖到的三条自审都没提}

- **`doTab()`의 쿼터 의미론**: `app.cpp:909`가 `acceptGhost()` 이후 무조건 `noteActivity()` → `gen_++`
  → 쿼터 재개방을 하므로, **Tab으로 수락할 때마다 500ms 뒤에 자동 요청이 한 번 더 발생한다**. P1(유휴 상태의 비용 소모) 분석은
  `setMode` / `cancelInFlight` / `askNow` 세 취소 지점만 살폈고, 가장 빈번한 이 과금 경로를 놓쳤다.
- 검수 6의 "회색"은 256색 터미널에서만 문자 그대로 성립한다. 8색 단계에서는 `A_DIM`으로 고정된다(어두워지는 것이지 회색이 아니다).
- `验收审计.md` §7의 소제목은 "검수 기준 9개"라고 적혀 있는데 표에는 10줄이 있다 —— 오기이지만, 총평 표 머리에 나타난다.

## 9. spill과 workbench의 최종 규모 {#九落盘与工作台最终规模}

103회의 [spill](../reference/glossary.md#落盘), 791.4K 문자가 경로 포인터로 치환되어 컨텍스트에 상주하지 않았다.

`.flower/` 최종: 스크립트 58개(250K), 산출물 22개(330K), 노트 5개(43K).

## 남은 리스크 {#遗留风险}

**납품 목표는 macOS인데, 모든 검증은 Debian aarch64 컨테이너 안에서 이루어졌고 macOS 실기 검증은 0이다.**
이는 컨테이너 isolation 방식의 실제 부작용이다: 안전을 위해 Linux에 가두었는데, 납품 대상은 macOS다.
프로젝트 자체 README §10.24는 이 사실을 정직하게 기록하고 리스크 4가지를 나열했지만, 닫히지는 않았다.

이 공백은 이후 [HT002](ht002.md)가 메웠다 —— 그 run이 바로 이 바이너리를 실제 macOS에 설치하는 것이었다.

의외의 이득: 컨테이너 안에서는 `/work`만 보이므로, 19MB transcript에
**호스트 사용자명 `/Users/hechenyu`가 단 한 번도 유출되지 않았다**(`/work`는 11,495회 등장).
[isolation](../reference/glossary.md#隔离)이 경로까지 함께 격리해 준 셈이다.

## 이 run이 검증하지 못한 것 {#这一跑没能验证的}

- **goal guard**: 이 run은 그것을 추가하기 이전이다. coordinator가 **자발적으로** 독립 감사를 조직했고 검증 기술은 매우 단단했지만,
  가장 중요한 항목에서 오판했다(8절). 두 결론을 함께 기록해야 한다 ——
  brief에 판정 가능한 기준을 분명히 적는 것만으로 자기 감사를 유도할 수 있으므로 goal guard의 기준선은 0이 아니다.
  그리고 당시 기본 설정의 goal guard **역시 그 항목을 놓쳤을 것**이므로, 그것도 만병통치약은 아니다.
- **1M 윈도에서의 거동**: 18.6%만 사용했고 경계에 닿지 않았다.
- **`DISABLE_AUTO_COMPACT=1` 하에서 마이크로 compact의 거동**: 전 구간 compact가 발동되지 않았으므로 여전히 추론이다.

## 이 run이 프레임워크에서 바꾼 것 {#这一跑改了框架什么}

| 발견 | 반영된 변경 |
|---|---|
| `which`가 차단됨(5절) | `is_ephemeral()`에 `which` / `command -v` / `type` / `whereis` / `uname` / `arch` / `locale` / `nproc` / `getconf` / `sw_vers` 추가; `tests/glance.py`에 적대적 샘플 7개를 넣어 `command` / `type`의 질의 형식을 지킴 |
| 검수 1 오판(8절) | `JUDGE_RULES` 1번 항목을 **판정 대상은 소스가 아니라 산출물**로 변경 —— 돌릴 수 있으면 돌려보고, 돌릴 수 없어도 산출물 자체(플랫폼, 크기, 로드 가능 여부)를 검사 |
| "리스크는 공개했다"가 통과 판정으로 바뀜 | 판정은 "달성하지 못함"과 "여기서는 검증할 수 없음"을 구분해야 한다. `Verdict.parse`는 이제 **无法验证 / 没法验证 / 无法判定**을 제3 상태 `unreachable`로 인식한다 → **사람에게 올려 묻고, 통과 판정은 절대 금지** |
| 검수 1이 이 환경에서는 원리상 검증 불가 | 목표 설정 단계에서 **이 환경에서 검증할 수 없는 항목을 그 자리에서 표시**하도록 요구, 작업을 끝낸 뒤에 발견하지 말 것 |
| 네트워크 복구가 프레임워크 계층에서 일어나고, subagent 반제품이 소실됨(6절) | issue #2로 기록, 미해결 |

앞의 세 가지는 [HT002](ht002.md)에서 처음 실제 API에 적용됐고, 그중 "소스가 아니라 산출물을 판정한다"는 그 자리에서 한 번 구제했다 ——
하지만 같은 규칙이 새로운 실패도 하나 만들어냈다.
