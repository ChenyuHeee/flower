# HT002 · macOS에 설치해서 실행시키기

2026-09-07, 과제는 한 문장이다: **[cppide](https://github.com/ChenyuHeee/cppide)를 clone 해서
이 macOS에 설치하고 실행시켜라.** 결과는 **$38.24 / 4 스텝 / 약 1시간**,
프로그램은 실제로 macOS에서 돌았고(PID 96040, arm64 Mach-O),
[판정](../reference/glossary.md#判定) 결론은 **달성 불가**여서 사람에게 올라갔고, 사람은 그 결과를 받아들였다.

이것이 **[목표 감시](../reference/glossary.md#目标看守)를 처음 얹은** 런이다 ——
[HT001](ht001.md)의 교훈에서 고쳐 나온 것들이고, 그날 전부 처음으로 실제 API 위에서 돌았다.
그 덕에 HT001이 빠졌던 함정 하나는 막았지만, 동시에 정반대 방향의 새로운 실패를 만들어냈다:
**`git clone && make && ./cppide`를 한 시간짜리로 만들어버린 것.** 이 페이지에서 가장 값진 부분은 후자다.

원본 기록은 [`human-test/HT002/`](https://github.com/ChenyuHeee/flower/tree/main/human-test/HT002/)에 있고,
장부는 [`runs/manifest.json`](https://github.com/ChenyuHeee/flower/blob/main/human-test/HT002/runs/manifest.json)과
`runs/sessions.db`에서 계산했다:

```bash
python tools/analyze_run.py human-test/HT002/runs
```

## 1. 헤드라인: `git clone && make && ./cppide`를 한 시간으로 만들었다 {#一头条它把-git-clone--make--cppide-变成了一小时}

이번에 가장 중요한 발견이며, 아래의 모든 "메커니즘이 돌았다"보다 중요하다.

목표 설정 스텝에서 [판정자](../reference/glossary.md#判定者)는 자기 자신에게
**판정 항목 15개**를 써 주었다
([`.flower/notes/`](https://github.com/ChenyuHeee/flower/tree/main/human-test/HT002/.flower/notes) 아래 `目标.md`에 원문이 있다).
성격별로 나누면:

| 분류 | 항목 수 | 예 |
|---|---|---|
| **실제로 "물건이 되는지"를 검증** | **약 5** | 빌드 exit 0; 프로세스 ≥30초 생존; 재시작 명령이 새 shell에서 재실행 가능 |
| **"과정이 규칙을 지켰는지"를 검증** | **6** | `~/.zshrc` / `.zprofile` / `.bash_profile`의 mtime이 모두 이번 세션보다 이전; `brew install` / `npm -g` / `sudo`를 실행하지 않음; **`.flower/`의 mtime이 변하지 않음, `runs/`가 인위적으로 늘거나 줄지 않음** |
| **원리상 검증 불가** | **4** | 스크린샷을 찍고 그림을 봄; devtools console; 수동 클릭; 본인 확인 |

**"이게 대체 쓸 수 있는 물건인가"를 검증하는 건 3분의 1뿐이다.** 여섯 항목은 자기 자신이 규칙을 지켰는지를 검증한다 ——
그중 하나는 **`.flower/` 디렉터리의 mtime**을 본다. 그건 **프레임워크 자기 자신의 디렉터리**다.

### `.flower/`를 검사하는 그 항목이, 스스로를 실패로 판정했다 {#那条查-flower-的清单自己把自己判失败了}

이건 이론적인 문제가 아니다. 판정 라운드에서 판정자는 "미통과" 항목에 있는 그대로 적었다:

> **`.flower/` 아래 파일 mtime이 모두 세션 시작보다 이전** —— 문자 그대로 실패: `INDEX.md` 16:14,
> `artifacts/01–05`(15:40–16:12), `notes/决策-项目形态与验收路径.md` 15:43 모두 세션 중에 기록됨.

원인은 이렇다: **프레임워크는 긴 산출물을 `.flower/artifacts/`에, 결정을 `.flower/notes/`에 쓰도록 강제한다.**
판정 항목의 그 한 줄은 이 디렉터리를 건드리지 말라고 요구한다. 두 규칙이 정면으로 충돌했고, 그것도 판정 항목이 스스로 만들어낸 충돌이다 ——
작업자가 긴 산출물을 하나도 쓰지 않았다면 오히려 더 규칙에 맞았을 것이다.

그것을 어물쩍 넘기지는 않았다. 작업 스텝은 최종 보고서에서 이 충돌을 자발적으로 명시했고,
결정 기록에도 처리 방식을 적었다 —— **기존 파일은 하나도 건드리지 않음**
(`需求.md`, `目标.md`, `问答记录.md` 세 건의 mtime과 MD5가 전후 동일), 추가만 함.
판정자는 재검토 후 "이 항목이 막으려던 변조는 발생하지 않았다"에 동의했지만, 그래도 규칙대로 미통과에 넣고 사람에게 넘겼다.

### 근본 원인 1: 경계를 판정 항목으로 취급했다 {#根因一边界被当成了判定项}

사전 확인 단계에서 뽑아낸 [경계](../guide/clarify.md)("프로젝트 디렉터리 안에서만 설치할 것", "업무 코드는 건드리지 말 것")는
원래 **어떻게 일할지**를 제약하는 것인데, **산출물**을 검증하는 체크 항목으로 쓰여버렸다.
그래서 `.zshrc` mtime 검사, `.flower/` mtime 검사 같은 항목이 생겼다.

**경계 ≠ 판정 항목. 경계는 과정을 제약하고, 판정 항목은 결과를 검증한다.** 이 둘을 섞으면 경계를 하나 더할 때마다 판정이 하나씩 늘어난다.
그런데 경계는 하필 확인 단계에서 잔뜩 쓰도록 권장되는 것이다 —— `CLARIFIER_RULES`는 명시적으로 이렇게 쓴다:
"**무엇을 하지 않을지 명확히 하라**. 이 문단이 뒤에서 일하는 모든 사람을 통제한다."

원본 기록을 대조하면 이 증폭 사슬의 각 고리가 보인다:
[요구 확인서](../reference/glossary.md#需求确认书)의 경계는 "현재 디렉터리에 이미 있는 `.flower/`와 `runs/`를 건드리지 않는다"였는데,
판정 항목에 오면 "`.flower/` 아래 파일의 mtime이 모두 이번 세션 시작보다 이전"으로 격상된다 ——
"기존 것을 건드리지 마라"에서 "디렉터리 전체에 새 파일이 있어서는 안 된다"로 바뀐 것이다.

### 근본 원인 2: `JUDGE_RULES`에는 한 방향의 압력만 있었다 —— 그리고 그건 그날 추가한 것이다 {#根因二judge_rules-只有一个方向的压力--而那是当天加的}

그날 이른 시각, [HT001](ht001.md)의 교훈에서 `JUDGE_RULES`에 이런 것들을 써 넣었다:

- "각 항목은 그 자리에서 검증 가능해야 한다", "빠진 것, 모호한 것은 네가 채워라"
- "판정 대상은 산출물이지 소스코드가 아니다"(macOS 반면 사례 포함)
- "현재 환경에서 검증할 수 없는 항목은 그 자리에서 표시하라"
- "먼저 네가 어디 있는지 똑똑히 봐라(`uname -a` 해도 된다)"

**한 줄 한 줄이 전부 더 많은 검사, 더 엄격한 쪽으로 민다. 규칙 전체에 "과제의 규모에 걸맞아야 한다"는 문장은 한 줄도 없다.**

즉, HT001의 "과도한 통과 선언"이라는 실패를 겨냥해 최적화했더니 **정반대의 실패 —— 과도한 검사**를 만들어낸 것이다.
이건 스스로 만든 것이지, 모델의 문제가 아니다.

### 근본 원인 3: [issue #3](https://github.com/ChenyuHeee/flower/issues/3)와 겹쳤다 {#根因三和-issue-3httpsgithubcomchenyuheeeflowerissues3-叠加了}

실제로 막힌 것은 macOS의 두 가지 이식성 결함이다:

- `src/proc.cpp`가 `::sigemptyset`을 쓰는데, Apple SDK는 함수 프로토타입 뒤에 그것을 다시 함수형 매크로로 정의한다
  (`#ifndef _ANSI_SOURCE`로만 가드됨). 그래서 `::sigemptyset(&s)`가 `::(*(&s)=0,0)`로 전개되어 문법 오류가 난다
- `src/ui.cpp`가 `::_exit`를 쓰면서 `<unistd.h>`를 include 하지 않는다

**세 줄이면 고칠 수 있다.** 그런데 사용자가 확인 단계에서 "업무 코드는 건드리지 말라"고 답했고 에이전트는 그것을 엄격히 집행했다.
그래서 우회해서 컴파일 flag를 시험하고, subagent를 파견하고, 결정 기록을 썼다.
**그때 사람이 "그 두 줄은 고쳐도 된다"고 한마디 끼워 넣을 수 있었다면 10분이면 끝났다.**
경계를 금지령으로 쓰면 최대한 엄격하게 해석되고, 중간에 그것을 풀 수 있는 통로가 하나도 없다.

원본 기록에서 이 우회가 얼마나 길었는지 볼 수 있다: 총 네 개의 차단 지점이 있었고,
그중 순수 컴파일 flag로 해결되는 건 `::_exit` 하나뿐이었다. `::sigemptyset` 쪽은 `-D`/`-U` 조합을 **6가지** 시도해 전부 실패했다
(`_POSIX_C_SOURCE` 계열은 덤으로 `st_mtimespec`와 `O_CLOEXEC`까지 깨뜨린다).
이 막다른 길 자체가 13.6K짜리 타당성 보고서 한 건을 낳았다.

### 다만 공정하게: 경계가 더 나은 해법을 끌어냈다 {#但要公道边界逼出了一个更好的解法}

최종안은 소스를 고치는 게 아니라, Makefile에서 **`#undef`만 하는 심 헤더를 생성**한 뒤 `-include`로 강제로 앞세우는 것이다:

```make
$(MACSHIM):
	@printf '#include <signal.h>\n#undef sigemptyset\n#undef sigfillset\n...' > $@
CPPFLAGS += -include $(MACSHIM) -include unistd.h
```

이건 소스를 고치는 것보다 낫다 —— 업스트림 저장소는 한 줄도 건드리지 않고, 누가 clone 해도 빌드된다. 심은 `build/`에 생성되어 저장소에 들어가지 않고,
`clean`에 `rm -rf build`를 추가해 회수한다. `make -n UNAME_S=Linux`로 실측하면 전개 결과에 `-include`가 없어 Linux 경로는 오염되지 않았다.
최종 `git diff`는 `Makefile` 파일 하나뿐, **+14 / −2**.

즉 경계가 만들어낸 것은 **더 높은 비용의 더 나은 해법**이다. 문제는 그것이 틀렸다는 게 아니라,
**이 트레이드오프를 사람이 하지 못했다는 것**이다 —— 그리고 못한 이유가 바로 issue #3다.

!!! note "`git status`에 64건이 있는데 왜 소스 변경이 0이라고 하는가"
    cppide 저장소는 `.o` 30개, `.d` 30개, 바이너리 2개를 **버전 관리에 커밋**해 두었고, 그것도 Linux ELF aarch64에
    mtime이 `.cpp`보다 늦다 —— 먼저 `make clean`을 하지 않으면 `make`가 컴파일을 건너뛰고 그 ELF를 그대로 링크해서 반드시 깨진다.
    그래서 `git status --porcelain`의 64건 중 63건은 git이 추적하는 컴파일 산출물이고 나머지 하나는 `?? build/`다.
    확장자로 필터링하면 `git diff -- 'src/*.cpp' 'src/*.h' README.md config.sample.json | wc -c`는 `0`이다.
    이 정확한 표현은 컴플라이언스 감사가 끌어낸 것이다 —— 코디네이터는 원래 뭉뚱그려 "`src/` 변경 0"이라고 쓰려 했고, 감사가 그 문장이 성립하지 않는다고 지적했다.

## 2. 목표 감시가 제대로 한 것 {#二目标看守做对了什么}

메커니즘 쪽은 전부 돌았고, **그날 넣은 두 개의 변경이 산출물에 직접적인 지문을 남겼다.**

**그것이 쓴 판정 항목의 첫 줄**:

> `uname -a`가 Darwin 25.2.0(macOS)을 보여준다…… 아래의 모든 "실행됨/열림" 항목은 이 기계에서
> 실제로 돌려서 얻은 결과여야 한다. **"소스에 macOS 분기가 있으니 돌 것이다" 같은 추론은 받지 않는다**

그것이 바로 그날 아침 HT001의 교훈에서 `JUDGE_RULES`에 써 넣은 문장이다.

**그날 추가한 `[此环境无法验证:…]` 표시를 세 번 썼고**, 각각 이유를 달았다 ——
devtools console(구동할 수 있는 브라우저가 없고, 이를 위해 헤드리스 브라우저를 설치하는 것은 경계를 넘는다),
수동 클릭(사람이 화면 앞에 있어야 한다), 본인 확인(그 사람만 줄 수 있다).

**판정자의 첫마디는 "나는 그 답변만 보고 결론 내지 않는다. 현장으로 간다"였다.** 그리고:

```text
file cppide        → Mach-O 64-bit executable arm64
lsof -p 96040      → txt 指向 /Users/hechenyu/explore/test-ide/cppide/cppide
                     起于 16:10,16:15 仍活着
```

그것은 스스로 이렇게 썼다: "**meta 교훈에 있던 그 'Linux ELF를 납품' 함정은, 이번엔 밟지 않았다.**
Linux ELF가 Darwin에서 PID로 살아 있을 수는 없다. 이건 Makefile에서 추론한 게 아니다."

소스가 정말 변하지 않았는지도 확인했다: `src/` 아래 모든 `.cpp` / `.h`의 mtime이 전부 15:32(clone 시각)이고,
바뀐 것은 `Makefile`(16:06)뿐이며, `.o` / `.d`(16:07)는 추적되는 컴파일 산출물의 재빌드다.

**닿지 못한 부분도 있는 그대로 밝혔다.** 판정자의 Bash는 작업 디렉터리 안으로 제한되어
`git ls-remote` 대조와 `~/.zshrc`의 mtime은 실행할 수 없었고, 독립 감사의 출력을 신뢰할 수밖에 없었다 ——
이 두 항목은 따로 떼어 "내가 직접 다시 돌리지는 못했다"고 설명했다.

## 3. "달성 불가"로 판정하고, 사람에게 묻는다 {#三判定无法达成然后问人}

3상태 판정과 사람 개입, [전 경로](../guide/goal.md)가 처음으로 실제로 돌았다.

판정 결론은 **달성 불가**였고, 스크린샷 항목에서 막혔다: `screencapture -x`도 `-l <window-id>`도
`could not create image from display`를 반환했다 —— 화면 녹화의 TCC 권한이 부여되지 않았고,
권한을 주려면 사람이 시스템 설정에서 클릭해야 하는데, 그 자체가 경계가 금지한 시스템 변경이다.

> "**subagent를 한 라운드 더 파견해도 이 그림은 나오지 않는다. 규칙상 통과로 판정해서는 안 되고, '미달성'으로 판정해서도 안 된다.
> 이건 그냥 달성 불가이며, 멈춰서 사람에게 넘겨야 한다.**"

그래서 항목 중 "원리상 검증 불가"가 3건에서 4건이 되었다 —— **15건 중 4건이 이 환경에서는 애초에 검증할 수 없다**.
그런데 이 사실은 $35.8950짜리 작업과 $1.4037짜리 판정을 **쓰고 난 뒤에야** 발견됐다.
목표 설정 스텝은 $0.4117밖에 안 들었고, 그때 발견했어야 했다.

프레임워크는 이 결론을 사람에게 물었고(문답 기록 q7에 남음), 세 가지 선택지 중 사람은 "이 결과를 수용"을 골랐고, 게이트가 열려 워크플로가 완료되었다.

**대체물 하나도 거절했다.** 작업자는 AppleScript로 터미널 창의 텍스트를 읽어 왔고,
그것은 실제로 렌더링된 TUI였다 —— 행 번호 열, `src/main.cpp` 본문, `─[编译]─[运行]─[AI*]─[输入]─` 패널 바,
`练习模式 │ main.cpp │ 1:1 │ C++` 상태 바. 흰 화면도 에러 화면도 아니었다. 판정자는 말했다:

> "작업한 쪽이 그걸 '그림을 봤다'로 둔갑시키지 않았다. 이 자기 절제는 옳다.
> **하지만 그건 항목이 요구하는 그것을 대체할 수 없고, 나도 대신 쳐 주지 않는다.**"

!!! warning "'리스크를 공개했다'는 통과가 아니다"
    HT001이 넘어진 게 바로 이거다: "macOS에서 한 번도 돌려보지 않았다"를 납품 설명에 써 놓고도 검수 1을 통과로 판정했다.
    HT002에서 판정자는 더 나은 대체 증거(진짜 TUI 텍스트)를 손에 쥐고도, 그것으로 항목을 대신하는 것을 거부했다.
    이 차이가 [판정](../reference/glossary.md#判定) 3상태 설계의 전부다 ——
    `UNREACHABLE`은 `NOT_YET`의 완곡한 표현이 아니라, "멈춰서 사람에게 물어야 한다"이다.

## 4. `allowed_tools`는 하드 화이트리스트가 아니다 {#四allowed_tools-不是硬白名单}

이번 런을 분석하다가 주장과 맞지 않는 사실을 하나 발견했다. [세션](../reference/glossary.md#会话)별로 도구 호출을 뜯어보면:

| 세션 | 실제로 쓴 것 | 화이트리스트에 있는 것 |
|---|---|---|
| 요구 확인 | **WebFetch**, Glob, ask×6 | 당시 `clarify()`는 ask + `Read`/`Glob`/`Grep`만 |
| 목표 설정 | **Bash ×11** | `judge()`의 기본값은 `can_run=False`, **Bash 없음** |
| 작업·판정 | **Bash ×31**, WebFetch | 위와 동일 |
| 작업(코디네이터) | Bash ×1, Agent ×6 | 정상 |

`goal_step`에는 **`can_run`을 넘기는 코드 경로가 전혀 없다.** 그러니 "목표 설정" 줄은 설정 문제일 수가 없다.

**$0.1짜리 프로브 검증**: `allowed_tools=["Read"]`인 에이전트에게 파일을 쓰라고 시켜 봤다 ——

```text
Write → 权限层:"requested permissions to write ... but you haven't granted it yet"
Bash  → 路径安全:"Output redirection was blocked. For security, Claude Code may
        only write to files in the allowed working directories"
```

**모델은 화이트리스트에 없는 도구도 호출할 수 있다.** 다만 permission 계층과 경로 보안이 막았을 뿐이다. 따라서:

- `allowed_tools`는 **무승인 목록**이지 배타적 화이트리스트가 아니다
- 당시 `clarify()` / `judge()`를 실제로 보호한 것은 상속된 `permission_mode="default"`였다
- 그리고 그 둘은 `delegate_only=False` → **`delegate_guard` hook이 없다.**
  코디네이터는 hook이 지켜주지만, **이 두 역할은 당시 flower 자체의 메커니즘이 전혀 없었다**

`clarify()`의 docstring에는 "쓰기 도구를 주지 않는다 —— 일을 시작할 수 없다"고 쓰여 있고,
$0.8908짜리 반면 실측 전체가 이 문장을 위해 한 것이었다. **이 문장의 메커니즘적 근거는 틀렸다.**

!!! note "이 절의 두 사실은 나중에 모두 바뀌었다"
    `whitelist_guard`는 이제 무조건 붙는다: `delegate_only=False`인 역할에는 `Runtime`이 이 hook을 자동으로 장착하므로
    `clarify()` / `judge()`가 더 이상 "아무 메커니즘도 없는" 상태가 아니다. 또한 `WebFetch`는 지금은 `clarify()`의 화이트리스트에 들어 있어서
    표 첫 줄의 예시는 이미 무효다 —— **결론은 여전히 성립하지만, 지금은 $0.1 프로브 증거 하나에만 기대고 있다.**
    자세한 것은 이 페이지 마지막 절 참조.

## 5. 컨텍스트 곡선: 스텝 경계에서 리셋된다 {#五上下文曲线步骤边界会重置}

```text
第 1轮   36.8K
第25轮   80.2K   ← 峰值
第26轮   32.9K   ← 断崖:新步骤 = 新会话(resume_from=None)
第121轮  64.8K
```

샘플 네 점 중 세 점(1 / 25 / 121 턴, 36.8K / 80.2K / 64.8K)은 원본 기록과 하나하나 일치한다.
**26턴의 32.9K는 다시 계산하면 맞지 않는다**: `store_key` 순으로 메인 스레드 assistant 메시지를 재생하면
26번째(새 세션의 첫 번째)의 `input + cache_read + cache_creation`은 31,972 token = **32.0K**이고,
32.9K는 같은 세션의 두 번째 값(31,970 + 948)이다. 이 페이지는 32.9K를 유지한다 —— 차이는 0.9K이고,
"절벽처럼 떨어진다"는 결론은 두 값 모두에서 성립한다.

HT001은 185.9K까지 단조 증가했다 —— 스텝 하나가 10시간 돌았다.
HT002는 네 스텝으로 나누었고 스텝마다 새 세션을 열었기 때문에 **컨텍스트가 구조적으로 리셋됐다.**
이것은 "요구 확인서와 목표는 동결물이고, 하류는 문서만 받지 대화는 받지 않는다"는 설계의 직접적 효과다 —— 곡선에서 보인다.

캐시 적중 **90.8%**(HT001은 96.1%). 적중률은 세션 길이에 따라 올라가므로 짧은 세션은 오히려 단위당 조금 더 비싸다 ——
이건 HT001 3절의 결론과 같은 동전의 양면이다.

## 6. HT001과의 대조 {#六和-ht001-对照}

| | [HT001](ht001.md) | HT002 |
|---|---|---|
| 과제 | 터미널 IDE를 맨바닥에서 작성 | 그것을 macOS에 설치해 실행 |
| 비용 / 소요 | $171.62 / 10.44h | $38.24 / 0.97h |
| 스텝 | 2(목표 감시 없음) | **4(목표 설정 + 판정 포함)** |
| subagent | 23개 | 6개 |
| 코디네이터 도구 호출 | 32 | **7**(그중 6회가 Agent) |
| subagent 도구 호출 | 1,893 | 212 |
| 메인 스레드 컨텍스트 | 28.7K → **185.9K** 단조 증가 | 36.8K → 80.2K, **스텝 경계에서 리셋** |
| 캐시 적중 | 96.1% | 90.8% |
| **워크벤치 스크립트** | **58개, 331회 실행, 92% 재사용** | **0개** |
| 판정 | 없음(코디네이터의 자발적 내부 검토) | 3상태 판정, "달성 불가" 판정, 사람에게 질문 |

**마지막 줄이 주목할 만하다.** HT002는 재사용 스크립트를 하나도 쓰지 않았다 —— 과제가 한 시간짜리라 축적할 만한 게 없었다.
이는 워크벤치의 가치가 **과제 길이에 따라 커진다**는 뜻이다. 짧은 과제에서 그것은 순수 오버헤드다.

## 이 런이 프레임워크를 어떻게 바꿨나 {#这一跑改了框架什么}

| 발견 | 반영된 변경 |
|---|---|
| 판정 항목 15개 중 쓸 수 있는지를 검증하는 건 약 5개뿐(1절) | `JUDGE_RULES`에 역방향 압력 추가: **항목 개수는 실패 방식의 수가 결정하지, 엄밀함의 정도가 결정하지 않는다.** 그리고 이번 건을 반면 사례로 규칙 원문에 기록("'설치해서 실행' 과제 하나가 15개 항목으로 쓰였고, 그중 5개만 쓸 수 있는지를 검증했다" —— 규칙에서는 반올림해 5로 적었고, 이 페이지 1절의 분류 기준은 약 5다) |
| 경계가 판정 항목으로 쓰였다 | `JUDGE_RULES`에 **"경계는 판정 항목이 아니다"**를 못 박아 넣음 |
| 4/15 항목이 이 환경에서 검증 불가인데, $35.8950 + $1.4037을 쓰고 나서야 발견 | 목표 설정 스텝에서 검증 불가 항목에 `[此环境无法验证:原因]` 접미를 그 자리에서 붙이도록 요구 —— 이번에 3건은 제대로 썼고, 스크린샷 항목 하나를 빠뜨렸다 |
| `clarify()` / `judge()`에 hook 보호가 없음(4절) | `whitelist_guard`가 무조건 연결됨: `delegate_only=False`인 역할은 `Runtime`이 자동 장착하며, 워크벤치 활성화 여부에 더 이상 의존하지 않는다 |
| 부작용: 목표 설정의 judge가 이제 Bash를 못 쓴다 | `whitelist_guard`가 생긴 뒤로, `can_run=True`를 명시적으로 넘기지 않으면 `JUDGE_RULES`의 "먼저 `uname -a`로 네가 어디 있는지 봐라" 항목이 **실행되지 않는다** —— 고친 뒤에 새로 생긴 트레이드오프다 |
| `clarify()` docstring의 메커니즘적 근거가 틀렸다 | 수정됨. `WebFetch`도 `clarify()`의 화이트리스트에 들어갔으므로 그 예시는 무효가 되었고, 결론은 $0.1 프로브에 걸어 두었다 |
| 중간에 한마디 끼워 넣을 통로가 없다(1절 근본 원인 3) | [issue #3](https://github.com/ChenyuHeee/flower/issues/3)로 기록, 미해결 —— 이번엔 과도한 복잡화와 직접 겹쳤고, "그 두 줄은 고쳐도 된다" 한마디면 한 시간을 아낄 수 있었다 |

이 런을 한 문장으로 요약하면: **지난번의 실패를 겨냥해 최적화하면, 방향이 반대인 새 실패를 만들어내기 쉽다.**
HT001은 프레임워크에 "쉽게 통과로 판정하지 마라"를 가르쳤고, HT002는 그 규칙에 "과도하게 검사하지 마라"가 딸려오지 않으면 무슨 일이 생기는지를 즉시 시연했다.
둘 다 `JUDGE_RULES`에 써야 하며, 하나라도 빠지면 기운다.
