# 자주 겪는 문제와 해결

문제가 터졌을 때 사람은 어느 모듈이 망가졌는지 모른다 — 자기가 무엇을 봤는지만 안다. 그래서 이 페이지는
서브시스템이 아니라 **당신이 관찰한 현상**으로 묶었다.

각 항목의 구조는 동일하다: **증상**(실제로 본 것) → **원인** → **어떻게 할 것인가**.

이 중 다섯 항목은 **알려진 결함**이며, 설계 의도가 아니다. 해당 항목들은 버그라는 사실을 그대로 적고,
issue 링크와 우회 방법을 준다 — 의도된 동작인 것처럼 포장하지 않는다.

## 설치가 안 되거나 실행이 안 될 때 {#装不上}

설치 전체 절차는 [install.md](../getting-started/install.md#一句话安装)를 보라. 이 절은 "설치는 끝났는데
명령이 실행되지 않는" 경우만 모았다.

### Python 버전이 3.10 미만 {#python-版本}

**증상**: 설치 도중 문법 오류가 튀어나오거나, pip가 조건을 만족하는 버전을 찾을 수 없다고 한다.

**원인**: flower는 Python ≥ 3.10을 요구한다. 유일한 런타임 의존성은 `claude-agent-sdk`이고 네이티브 바이너리는
그 wheel 안에 들어 있다 — 그래서 설치 실패는 대개 네트워크가 아니라 인터프리터 버전 문제다.

**어떻게 할 것인가**: 먼저 어느 인터프리터에 설치할 것인지 확인한다.

```bash
python3 --version
```

3.10 미만이면 다른 인터프리터로 바꿔서 설치한다. 시스템에 딸려 온 `python3`가 터미널의 `python`이 가리키는
그것이 아닌 경우가 흔하다. 설치 전에 버전을 한 번 맞춰보는 편이 설치 후에 원인을 뒤지는 것보다 싸다
([install.md](../getting-started/install.md#装之前确认-python) 참조).

### 설치는 끝났는데 `flower: command not found` {#command-not-found}

**증상**:

```text
zsh: command not found: flower
```

**원인**: 패키지는 설치됐지만, 생성된 실행 스크립트가 있는 디렉터리가 `PATH`에 없다. 이건 "설치가 안 된 것"과는
다른 얘기다 — `python3 -c "import flower"`가 에러를 내지 않으면 패키지는 멀쩡하다.

**어떻게 할 것인가**: `flower` 스크립트의 shebang은 절대 경로라서, 이미 `PATH`에 있는 디렉터리로 심볼릭 링크를
하나 걸어주면 그걸로 충분하다. 아무것도 source 할 필요 없다.

```bash
ln -sf "$PWD/.venv/bin/flower" ~/.local/bin/flower
```

### macOS: `install.sh`가 알려준 대로 PATH를 추가했는데도 command not found {#macos-path}

!!! warning "알려진 문제([issue #16](https://github.com/ChenyuHeee/flower/issues/16))"

    이 안내는 하필 그것이 필요한 바로 그 머신에서 작동하지 않는다.

**증상**: macOS에서 `install.sh`를 돌리고, 마지막에 출력된 안내대로 `~/.local/bin`을 `PATH`에 추가하고,
터미널을 다시 열었는데도 `flower`가 여전히 command not found다.

**원인**: pip 폴백 경로로 빠졌을 때, macOS의 pip는 실행 스크립트를 `~/Library/Python/3.X/bin`에 설치한다.
그런데 `install.sh`가 추가하라고 안내하는 건 `~/.local/bin`이다. 두 디렉터리가 어긋나므로 안내대로 해도 소용이 없다.

??? note "`install.sh`가 설치 방식을 고르는 순서, 그리고 그 안내문의 원문"

    우선순위는 두 단계가 아니라 네 단계다(`install.sh:35-56`):

    ```text
    1. uv 있음        → uv tool install --force
    2. 없으면 pipx 있음 → pipx install --force
    3. 그것도 없으면  → curl astral.sh/uv/install.sh 로 uv 부트스트랩, 성공하면 uv 로 설치
    4. 부트스트랩도 실패 → "$PY" -m pip install --user --upgrade    ← 문제가 되는 건 이 경로
    ```

    마지막 PATH 안내문의 원문(`install.sh:62-68`, `command -v flower`가 실패할 때만 출력된다):

    ```text
    ! 但 flower 不在 PATH 上。
      把这一行加进你的 ~/.zshrc 或 ~/.bashrc:
        export PATH="$HOME/.local/bin:$PATH"
    ```

    `BINDIR`은 `$HOME/.local/bin`으로 하드코딩되어 있다(`install.sh:63`). 1번과 3번 경로에서는 이게 맞다
    — uv가 거기에 설치하니까. **4번 pip 폴백만 macOS에서 어긋난다.** 그래서 이 함정은 앞의 세 경로가
    전부 실패한 머신에서만 나타난다.

**어떻게 할 것인가**: 디렉터리를 추측하지 말고 인터프리터에게 물어본다.

```bash
python3 -c "import sysconfig; print(sysconfig.get_path('scripts', scheme='posix_user'))"
```

출력된 디렉터리를 `PATH`에 추가하거나, 거기서 `~/.local/bin`으로 심볼릭 링크를 건다:

```bash
ln -sf "$(python3 -c "import sysconfig; print(sysconfig.get_path('scripts', scheme='posix_user'))")/flower" ~/.local/bin/flower
```

### uv / pipx / pip로 설치한 게 서로 다른 flower다 {#三种装法}

**증상**: `flower`는 실행되는데 소스를 고쳐도 반영되지 않는다. 혹은 업그레이드했는데 여전히 옛 버전이다.
혹은 같은 머신의 두 터미널이 다르게 동작한다.

**원인**: 세 가지 설치 방식이 패키지와 실행 스크립트를 서로 다른 곳에 둔다. `PATH`에서 먼저 걸리는 게 실행된다.

??? note "세 가지 설치 방식이 어디에 떨어지는가"

    | 설치 방식 | 실행 스크립트 | 언제 쓰나 |
    |---|---|---|
    | `python3 -m venv .venv` + `pip install -e .` | `.venv/bin/flower` | 소스를 고칠 때. 고치면 즉시 반영된다 |
    | `uv tool install` / `pipx install` | `~/.local/bin/flower` | 고치지 않고 쓰기만 하되 격리된 환경이 필요할 때 |
    | `pip install --user` | Linux `~/.local/bin`, macOS `~/Library/Python/3.X/bin` | 폴백. 디렉터리는 앞 항목 참조 |

**어떻게 할 것인가**: 지금 실행되는 게 어느 것인지 먼저 확인하고, 어느 쪽을 고칠지 정한다.

```bash
which -a flower                      # PATH 상의 동명 실행 파일을 전부 나열
head -1 "$(which flower)"            # shebang 이 가리키는 인터프리터, 패키지는 그 환경에 있다
```

소스를 고칠 거면 venv + `-e .`를 쓰고, `uv` / `pipx`로 설치한 것과 공존시키지 마라 — 공존시키면 원인 추적 비용이
한 번 재설치하는 것보다 훨씬 크다([install.md](../getting-started/install.md#从源码装) 참조).

## 자격 증명과 게이트웨이 {#凭证}

### `缺少凭证:需要 ANTHROPIC_API_KEY 或 ANTHROPIC_AUTH_TOKEN` {#缺少凭证}

**증상**:

```text
缺少凭证:需要 ANTHROPIC_API_KEY 或 ANTHROPIC_AUTH_TOKEN
```

**원인**: flower는 `setting_sources=[]`로 호스트 설정을 차단하므로 자격 증명을 직접 가져와야 한다. 전체 탐색 순서는
[config.md](config.md#凭证查找优先级)를 보라.

**어떻게 할 것인가**: 저장소 루트의 `.env`에 쓰거나, 프로세스 환경 변수에 넣는다.

```bash
cp .env.example .env        # ANTHROPIC_AUTH_TOKEN 또는 ANTHROPIC_API_KEY 를 채운다
```

`.env`는 이미 gitignore에 들어 있다. 컨테이너에서의 방식은 [deploy.md](deploy.md#凭证)를 보라.

### "flower는 `~/.claude/settings.json`을 읽지 않는다"라고 하는데 — 이 말은 틀렸다 {#settings-json}

**증상**: 자격 증명이 제대로 설정되지 않았을 때 `env.py:192`가 이 한 줄을 출력한다:

```text
flower 不读 ~/.claude/settings.json —— 那是可移植性的代价
```

**원인**: 이 문장은 코드와 맞지 않는다. `env.py:56-75`는 `~/.claude/settings.json`을 **실제로 읽는다.** 거기서
자격 증명 필드만 가져와 마지막 폴백으로 쓴다 — `install.sh`가 광고하는 것도 바로 이 동작이다. 이 문장은 폴백까지
전부 비어 있을 때만 출력되므로 무언가를 실패시키지는 않는다. 하지만 사람으로 하여금 "flower는 내 Claude Code
토큰을 못 쓰는구나"라는 결론에 이르게 하고, 그건 틀렸다. [issue #13](https://github.com/ChenyuHeee/flower/issues/13)에
기록되어 있다.

**어떻게 할 것인가**: 이 머신에 Claude Code를 설치한 적이 있다면 자격 증명을 새로 발급받을 필요가 없다. 폴백이 알아서 집어 온다
([install.md](../getting-started/install.md#本机装过-claude-code-的话可能一个问题都不问) 참조).
정말로 이 문장을 봤다면, 그 파일에도 쓸 만한 자격 증명 필드가 없다는 뜻이다 — 앞 항목대로 `.env`를 써라.

### 실제로 적용된 자격 증명과 엔드포인트가 무엇인지 확실치 않다 {#生效值}

**증상**: 분명 `.env`를 고쳤는데 요청이 여전히 옛 게이트웨이로 간다. 혹은 지금 어떤 모델을 쓰는지 설명할 수 없다.

**원인**: 자격 증명과 엔드포인트는 출처가 여럿이다(프로세스 환경, `.env`, 폴백). 누가 이겼는지는 설정 파일이 아니라
런타임이 말해준다.

**어떻게 할 것인가**: `-v`를 붙여 한 번 띄운다. 기동 시 `describe()`가 출력된다: 적용된 `BASE_URL`과 모델 매핑,
토큰은 마스킹된다.

```bash
flower -v
```

스위치 전체 표는 [cli.md](cli.md#全局开关)에, 변수 전체 표는 [config.md](config.md#环境变量)에 있다.

### `.env`에 `KEY=`를 남겨두면 하위 출처가 영원히 채우지 못한다 {#空值占位}

**증상**: 프로세스 환경에 토큰을 export 했고 `.env`에도 `ANTHROPIC_AUTH_TOKEN=` 줄이 있는데, 여전히
"자격 증명 없음"이 뜬다.

**원인**: 빈 값도 하나의 할당이다. 우선순위가 높은 출처의 `KEY=`가 그 키를 **점유해 버리고**, 우선순위가 낮은
출처는 더 이상 채워 넣지 않는다. 그런데 `check_credentials()`(`env.py:184`에 정의)는 "값이 비어 있지 않은가"를
판단하므로 결국 누락으로 처리된다. "점유"와 "누락"은 다른 두 가지인데 현상은 똑같다 — 이 부류 문제에서
스스로 알아채기 가장 어려운 지점이다.

**어떻게 할 것인가**: 줄 전체를 지워라. 빈 값을 남기지 마라.

```bash
grep -n '^[A-Za-z_][A-Za-z0-9_]*=$' .env     # 빈 값 줄 전부 나열
```

지운 뒤 `-v`로 적용값을 한 번 더 확인한다. 파싱 규칙은 [config.md](config.md#env-解析)에 있다.

### 서드파티 게이트웨이: 연결은 되는데 첫 라운드부터 실패한다 {#网关}

**증상**: 401 / 403. 혹은 모델명이 존재하지 않는다는 에러. 혹은 시작하자마자 [handoff](glossary.md#换代)가 일어나고
"시작 바닥값(startup floor)" 얘기가 나온다.

**원인**: 설정 오류가 세 부류이고, 현상이 각각 다르다.

??? note "게이트웨이 설정 오류 세 부류, 각각 어떻게 구분하나"

    | 현상 | 대개는 | 어디를 고치나 |
    |---|---|---|
    | 401 / 403 | 자격 증명 자체는 맞지만 이 게이트웨이가 발급한 게 아니거나, `BASE_URL`에 경로가 빠졌거나 끝에 슬래시가 붙었다 | [config.md](config.md#凭证变量) |
    | 모델명이 존재하지 않는다는 에러 | 게이트웨이가 자기만의 모델명만 인식하는데 매핑이 없다 | [config.md](config.md#模型变量) |
    | 시작하자마자 handoff, "시작 바닥값" 에러 | window를 너무 작게 잡았다: 임계값이 역할의 시작 바닥값보다 낮다([coordinator](glossary.md#协调者)는 실측 약 34k) | `--window`, [handoff.md](../guide/handoff.md#阈值怎么算) 참조 |

**어떻게 할 것인가**: 설정을 건드리기 전에 `-v`로 적용값을 한 번 찍어본다. window 항목은 특히 맞춰볼 가치가 있다 —
개발용 이 머신의 게이트웨이는 `claude-opus-5[1m]`으로 설정되어 있는데, 예전처럼 20만으로 계산하면 15만마다
한 세대씩 넘어간다. 실제로는 95만까지 돌 수 있으니 **5배 차이**이고, [long-horizon](glossary.md#长程) 작업이
잘게 토막 난다.

## 실행은 되는데 동작이 이상하다 {#行为不对}

이 묶음의 증상은 에러가 아니다. **명령이 끝나고 종료 코드는 0인데 한 일이 틀렸다.**
앞의 네 항목은 확인된 코드 결함이고 issue도 올라가 있다. 여기 적은 건 수정 방법이 아니라 우회 방법이다.
마지막 항목은 설계 의도다.

### `flower setup`이 agent를 하나 띄운다 {#setup-跑成了-agent}

**증상**: `flower setup`을 실행하면 엔드포인트와 토큰을 물어볼 줄 알았는데, "무엇을 하고 싶은가"를 묻기 시작하고
이어서 go의 전체 workflow를 돌면서 `setup`이라는 단어를 작업 설명으로 취급한다. 다 돌고 나면 자격 증명은 한 글자도
쓰이지 않았다.

**원인**: `cli.py:758`의 `_CMDS`에 `"go"`, `"run"`, `"once"`만 있고 `"setup"`이 빠졌다.
기본 서브커맨드를 채우는 단계에서 argv `["setup"]`이 `["go", "setup"]`으로 재작성된다 —
`setup`이 서브커맨드에서 `go`의 첫 번째 위치 인자, 즉 요구사항 자체로 강등된 것이다.
**어떤 argv로도 설정 마법사에 도달할 수 없다.** [#11](https://github.com/ChenyuHeee/flower/issues/11)에 보고되어 있다.

**어떻게 할 것인가**: Ctrl-C로 끊고 설정 파일을 직접 쓴다. `setup`이 원래 하려던 것도 이 파일에 글자를 쓰는 일뿐이다:

```bash
mkdir -p ~/.config/flower
cat > ~/.config/flower/.env <<'EOF'
ANTHROPIC_AUTH_TOKEN=sk-...
EOF
```

전체 변수명과 자격 증명 탐색 순서는 [config.md](config.md#凭证变量)를 보라.
쓰고 나서 아무 디렉터리에서나 `flower -v`를 한 번 실행하면, 기동 시 출력되는 적용 엔드포인트가 확인 결과다.

### 전각 `？`로는 oracle 질의가 발동하지 않는다 {#全角问号}

**증상**: [oracle 질의](cli.md#旁路问答)의 방식대로 입력 프롬프트에 `？这个目录能删吗`라고 쳤는데
[oracle](glossary.md#旁路顾问)이 뜨지 않고, 그 문장이 현재 질문에 대한 답변으로 취급되거나 그대로 수신함에 들어간다.

**원인**: `cli.py:733`이 `startswith("?")` 판정을 연달아 두 번 하는데, **두 번 모두 같은 ASCII 문자를 쓴다.**
코드 의도상 두 번째는 전각 `？`를 판정해야 했다. 중국어 입력기가 기본으로 찍어내는 게 바로 전각이다 — 이 기능의
주요 사용자가 하필 한 명도 쓸 수 없다. [#12](https://github.com/ChenyuHeee/flower/issues/12)에 보고되어 있다.

!!! warning "이 항목은 요구사항을 오염시킨다"
    빗나간 `？`는 에러도 내지 않고 버려지지도 않는다. 일반 입력으로 처리된다:
    clarify 단계에서는 현재 질문에 대한 답변으로, 그 외에는 수신함으로 들어간다.
    **혼자 슬쩍 물어보려던 한마디가 brief에 적힌다.** 잘못 친 걸 발견하면 그 자리에서
    `.flower/notes/需求.md`를 고쳐라. 하위 단계의 기준은 그 파일이다.

**어떻게 할 것인가**: 반각으로 바꿔서 `?`를 치거나, 반각 `?`를 먼저 친 뒤 중국어로 돌아와 본문을 쓴다.

### `once`의 누적 비용이 영원히 `$0.00`, 소요 시간이 영원히 `0:00` {#once-计数为零}

**증상**: `flower once`를 처음부터 끝까지 돌려도 하단 상태 줄의 누적 비용이 계속 `累计 $0.00`이고
타이머는 계속 `0:00`이다. 같은 모델로 같은 작업을 `go`에서 돌리면 숫자가 나온다.

**원인**: `once`의 `render()`가 **이벤트를 하나 받을 때마다 `Render`를 새로 만든다.**
누산기도 함께 다시 만들어지므로 매번 0에서 시작한다. 누적값이 집계되지 않는 게 아니라 반복해서 0으로 초기화되는 것이다.
[#14](https://github.com/ChenyuHeee/flower/issues/14)에 보고되어 있다.

**어떻게 할 것인가**: 숫자가 정확해야 하면 `go`로 가라. 그 경로는 영향을 받지 않는다. `once`의 단일 라운드 형태를
쓰면서 비용도 보고 싶다면, 다 돌고 나서 `runs/manifest.json`을 확인하라 — 각 step의 비용이 거기 기록되고,
그 기록은 정확하다. 자세한 건 [config.md](config.md#run-dir)를 보라.

### `plugin/`에 넣은 skill이 계속 로드되지 않는다 {#plugin-不加载}

**증상**: [deploy.md](deploy.md#写一个-skill完整例子)대로 skill을 작성했고 디렉터리 구조도 맞는데,
agent가 그 존재를 아예 모르는 것처럼 행동한다 — **에러도 없고 로그 한 줄도 없다.**

**원인**: `plugin/`이 wheel에 포함되지 않았다. 설치된 패키지에서 `PLUGIN_DIR`은
`<site-packages>/plugin`을 가리키는데 그 디렉터리는 존재하지 않고, 로드 전 존재 여부 검사에서 조용히 건너뛴다.
**`install.sh`의 세 경로 전부 이 문제에 걸린다.** 소스 체크아웃한 저장소에서만 로드된다.
[#15](https://github.com/ChenyuHeee/flower/issues/15)에 보고되어 있다.

**어떻게 할 것인가**: 먼저 경로가 실제로 어디로 해석되는지 자가 점검한다.

```bash
python3 -c "from flower.core.agent import PLUGIN_DIR; print(PLUGIN_DIR, PLUGIN_DIR.is_dir())"
```

`False`가 나오면 이 문제다. skill을 쓰려면 현재로선 방법이 하나뿐이다: **소스 체크아웃으로 실행하라.**

```bash
git clone https://github.com/ChenyuHeee/flower
cd flower
python3 -m venv .venv && .venv/bin/pip install -e .
ln -sf "$PWD/.venv/bin/flower" ~/.local/bin/flower
```

`-e`로 설치한 패키지는 체크아웃 디렉터리를 가리키므로 `PLUGIN_DIR`이 실제 `plugin/`에 떨어지고,
위 자가 점검을 다시 돌리면 `True`가 나온다.

### `-T`가 `go`에서는 효과가 안 보인다 {#trim-与-go}

**증상**: `flower go`에 `-T`를 붙여 보고 안 붙여 보고 비교했는데 동작이 완전히 같다. 스위치가 고장 난 것처럼 보인다.

**원인**: **이 항목은 결함이 아니라 설계 의도다.** `go` 경로는 원래 [trim](glossary.md#裁剪)이 기본으로 켜져 있어서,
`-T`가 표현하는 의도가 이미 충족되어 있다. 그래서 한 번 더 준다고 달라지지 않는다. 이 경로의 실제 스위치는 반대 방향인
`--no-trim`이다 — trim을 끄고 싶을 때만 명시적으로 준다. `-T`는 `run`과 `once`에서만 의미 있는 스위치다.

**어떻게 할 것인가**: `go`에서 trim이 켜져 있는지 확인하고 싶으면 `-v`로 기동 출력을 보라. `-T`의 유무로 판단하지 마라.
끄고 싶으면 `--no-trim`을 준다. 스위치의 전체 의미는 [cli.md](cli.md#全局开关)에 있다.

## 다 했다고 하는데 안 되어 있다 {#没做完}

[goal guard](../guide/goal.md)는 바로 이 부류를 막으려고 존재한다 — worker에게는 체계적인 낙관 편향이 있다.
자기가 무엇을 했는지는 알지만 무엇을 빠뜨렸는지는 모른다. 그런데 guard 자체도 오판하고, 오판하는 방향에는 규칙성이 있다.
아래 다섯 항목을 "통과시키면 안 될 것을 통과시킨 경우"와 "계속 통과시키지 않는 경우"로 나눠 정리했다.

### "여기선 검증할 수 없다"고 하고는 통과시킨다 {#无法达成不是未达成}

**증상**: verdict에 "현재 환경에서는 이 항목을 검증할 수 없으므로 달성된 것으로 본다"라고 적혀 있고, workflow가 그대로 진행된다.

**원인**: [judge](glossary.md#判定者)가 「달성 불가능」과 「미달성」을 하나의 결론으로 뭉갰다. 이 둘은 **다른 결론**이며,
[결론은 둘이 아니라 셋이다](../guide/goal.md#三个结论不是两个)가 말하는 게 바로 이것이다:
「미달성」은 되돌려 보내 계속 하게 하는 것이고, 「달성 불가능」은 **멈춰서 사람에게 묻는 것**이다 — 받아들일지, 목표를 바꿀지,
아니면 판정이 틀렸다고 할지. 결론이 "달성/미달성" 둘뿐이면, 사실은 불가능한 목표 하나가 coordinator를 라운드마다 헛돌게 해서
한도가 바닥날 때까지 태운다.

**어떻게 할 것인가**: **"여기선 검증 못 한다"를 절대 달성으로 취급하면 안 된다.** judge에게 주는 `instructions`에
당신의 상황에서 무엇이 불가능에 해당하는지 명시해서, 「달성 불가능」을 줘야 할 때 「달성 불가능」을 주게 하라.
정말로 멈춰서 질문받고 싶지 않다면 `--timeout 0`을 줘라: 달성 불가능일 때 바로 멈추고 이유는 디스크에 남는다.
얼렁뚱땅 넘어가는 게 아니라.

### 소스를 읽고 나서 다 됐다고 한다 {#判产出物}

**증상**: verdict의 이유가 "코드에 X가 이미 구현되어 있다", "함수 시그니처가 요구를 만족한다"인데,
빌드 산출물도 명령 출력도 실행 중인 서비스도 하나도 건드려지지 않았다.

**원인**: judge가 소스 코드 쪽으로 유도됐다. [판정 대상은 산출물이지 소스가 아니다](../guide/goal.md#判的是产出物不是源码) —
소스가 맞아 보이는지와, 내놓은 물건이 쓸 수 있는지는 별개다. 전자는 worker가 이미 확신하고 있는 것이고,
한 번 더 확신해도 새 정보가 생기지 않는다.

**어떻게 할 것인가**: 판정 항목은 **산출물**에 대한 단언으로 써야 한다. "내보내기 기능을 구현했다"는 안 되고,
"`./app export out.csv`를 실행하면 `out.csv`에 헤더가 3열 있다"여야 한다. 목표를 쓰는 그 단계에서 이렇게 써야 하고,
그렇지 않으면 judge가 모호한 항목을 보고 알아서 채워 넣는 수밖에 없다.

### judge가 명령을 실행할 수 없어서 Makefile을 읽고 통과시킨다 {#判定者不能跑命令}

**증상**: 목표가 "Linux에서 실행되는 바이너리를 빌드한다"인데 판정이 통과했다.
직접 `file`을 돌려 보면 산출물이 Mach-O이고 ELF가 전혀 아니다.

**원인**: judge는 기본이 `judge(can_run=False)`라서 **손에 든 게 `Read` / `Glob` / `Grep`뿐이다.**
이 세 도구로는 파일을 읽을 수 있지만 **`file`도 못 돌리고 `./app --version`도 못 돌린다.**
그래서 차선책으로 Makefile을 읽고, Darwin 분기에 크로스 컴파일이 적혀 있는 걸 보고는 조건이 충족됐다고 판단한다.
거짓말을 한 게 아니다. **자기 능력 범위 안에서 증거에 가장 가까운 것을 찾은 것**이다.

??? note "언제 `can_run`을 반드시 켜야 하나"
    판단 기준은 간단하다: **목표에 "빌드된 물건" 같은 말이 나오면 켜라.**

    - 산출물 계열: 바이너리, 이미지, 패키징 파일, 생성된 데이터 — 켠다
    - 동작 계열: 서비스가 뜨는지, 명령이 0을 반환하는지, 출력이 어떤 패턴에 맞는지 — 켠다
    - 순수 텍스트 계열: 문서를 썼는지, 어떤 필드가 schema에 추가됐는지 — 켤 필요 없다

    커맨드라인에서는 `--judge-can-run`이다. 직접 배선할 때는 진입점마다 쓰는 법이 다르지만, 결국 전부
    `judge()`의 그 파라미터로 떨어진다:

    | 진입점 | 어떻게 넘기나 | 출처 |
    |---|---|---|
    | `judge()` | `can_run=`이 정식 파라미터 | `roles.py:361` |
    | `with_goal()` | `can_run=`이 파라미터이고, `judge()`로 전달한다 | `goal.py:155` → `:170` |
    | `goal_step()` | **`can_run` 파라미터가 없지만** `**spec_kw`로 들어가고, 그 줄이 바로 `judge(..., **spec_kw)`다 — 도달한다 | `goal.py:97` → `:105` |
    | `starter_flow()` | `judge_can_run=`을 `with_goal(can_run=…)`으로 변환한다. `--judge-can-run`이 타는 게 이 경로다 | `starter.py:105` → `:196` |

    대가는 judge가 실제로 명령을 실행하므로 한 라운드가 더 느리고 더 비싸진다는 것이다. 대신 검증 대상이
    설명서가 아니라 **현장**이 된다. [judge가 명령을 실행할 수 있는가](../guide/goal.md#判定者能不能跑命令)를 보라.

**어떻게 할 것인가**: 목표가 산출물에 관한 것이면 `--judge-can-run`을 켜라. 켜지 않을 때는
"읽기만 해도 판정 가능해야 한다"를 판정 항목 작성의 하드 제약으로 삼아라 — 그렇게 쓸 수 없는 항목은
애초에 명령 실행이 필요한 항목이다.

### 판정 체크리스트가 십수 개인데 계속 통과하지 못한다 {#清单长度}

**증상**: 매 라운드 되돌려 보내지고, 무엇이 부족한지 길게 나열되고, 고칠수록 늘어나고, 작업이 끝나지 않는다.

**원인**: 체크리스트를 "내가 얼마나 엄밀하고 싶은가" 기준으로 썼지, "이 작업에 실패 방식이 몇 가지인가" 기준으로 쓰지 않았다.
[체크리스트 길이는 실패 방식이 몇 가지인가로 정해진다](../guide/goal.md#清单的长度由有多少种失败方式决定):
`git clone && make && ./app` 같은 작업은 **세 개에서 다섯 개면 충분하다** — 빌드 성공, 실행됨, 쓸 수 있음.
[HT002](../cases/ht002.md#那条查-flower-的清单自己把自己判失败了)의 실제 사고에서는
"저장소를 설치해서 돌린다"는 작업이 **15개** 항목으로 쓰였다: 물건이 쓸 만한지 검증하는 건 5개뿐이었고,
6개는 절차를 지켰는지 검증했고, 나머지 4개는 **원리상 검증 자체가 불가능했다.**

**어떻게 할 것인가**: `.flower/notes/目标.md`를 고쳐라. 판정의 근거는 그 파일이다. 항목마다
"이건 어떤 실패에 대응하는가"를 물어보고, 답할 수 없으면 지워라. 목표 설정 단계에서 검증 불가능한 항목에 대해
어차피 경고를 하니, 경고받은 항목을 억지로 남기지 마라.

### 경계가 판정 항목으로 쓰였다 {#边界不是判定项}

**증상**: 체크리스트에 "`brew install`을 실행하지 않았다", "프로젝트 디렉터리 밖의 파일을 수정하지 않았다" 같은 항목이 있고,
judge가 결백을 입증하려고 `~/.zshrc`의 mtime을 뒤지고 `.flower/` 디렉터리가 건드려졌는지 확인한다.

**원인**: 경계와 판정 항목은 서로 다른 것을 제약한다. 이 둘을 섞은 게 HT002 사고의 주요 원인이었다
([근본 원인 1](../cases/ht002.md#根因一边界被当成了判定项)).

| | 무엇을 제약하나 | 어떻게 지키나 |
|---|---|---|
| **경계** | **어떻게 일하는가**("프로젝트 디렉터리 안에서만 설치할 것", "비즈니스 코드는 건드리지 말 것") | **넘지 않음**으로 지킨다. 사후 자기 증명이 아니다 |
| **판정 항목** | **내놓은 물건**("실행되는가", "결과가 맞는가") | 현장 검증으로 지킨다 |

경계는 clarify 단계에서 잔뜩 쓰라고 권장되는 바로 그 부분이다. 그걸 항목마다 체크리스트로 옮기면,
경계 하나를 추가할 때마다 검사가 하나씩 늘어난다. 그런데 이런 검사는 대부분 검증할 수 없고 —
검증 불가능한 항목은 라운드 전체를 함께 실패로 끌고 간다.

**어떻게 할 것인가**: 경계는 brief의 「경계」 절에 남겨두고, 넘지 않음으로 지켜라. 판정 체크리스트에 넣지 마라.
정말 설명이 필요하면 한 문장으로 끝내라. **여섯 개로 쪼개지 마라.**

## 컨텍스트와 비용 {#上下文与花费}

long-horizon 실행에서 컨텍스트와 돈은 같은 문제다: 컨텍스트가 상한까지 차면 handoff를 하거나 이 step이 터진다.
그리고 매 라운드 반복해서 하는 말은 이후 모든 라운드에서 다시 값을 치러야 한다.

### 중간에 스스로 새 session을 열고 "handoff"라고 한다 {#换代打断}

**증상** 이벤트 스트림에 `handoff`가 나타나고, `payload["phase"]`가 먼저 `near` 다음 `done`이 되고,
중간에 [handoff document](glossary.md#交接书)를 쓰는 한 라운드가 더 들어간다. 그 뒤로는 하던 일을 그대로 계속한다.

**원인** 컨텍스트가 임계값에 접근했다. flower는 **compact를 하지 않는다** — 현재 session의 상태를 5절짜리
handoff document로 쓰고, 새 session을 띄워 그걸 읽고 이어서 하게 한다. [compact](glossary.md#压缩)는
"막힌 길" 같은 가장 비싼 정보까지 함께 지워 버리지만, handoff document는 명시적이고 디스크에 남아 있고
언제든 고칠 수 있다: 인계받은 session이 읽는 게 바로 그 파일이다.

**어떻게 할 것인가** 정상 경로이므로 신경 쓰지 않아도 된다. handoff는 재시도로 세지 않는다 — `attempts`가 늘지 않고
(그건 실패를 세는 값이다), 태워버린 session_id는 `StepResult.retired`에 기록되며, 외부로 나가는 `session_id`는
언제나 살아 있는 후임 쪽이다
([../guide/handoff.md#换代不算重试账怎么记](../guide/handoff.md#换代不算重试账怎么记) 참조).
정말로 SDK의 auto-compact로 되돌리고 싶으면 `--no-handoff`를 써라.

??? note "임계값은 어떻게 정해지고, 기본값은 왜 이렇게 공격적인가"
    `at = window - headroom`. `window`는 **기본 100만**이고 모델명으로 판단한다: 이름에 `haiku`가 들어가면 20만,
    나머지는 100만. `headroom`은 기본 50k다 — auto-compact가 −33k에서 발동하므로 handoff는 그보다 앞서야 하고,
    "handoff를 쓰는" 일 자체가 한 라운드를 더 돌아야 한다. 50k는 이 두 조건을 동시에 만족한다.

    크게 잡는 건 치명적 오류가 아니다: 실제 window가 더 작으면 임계값에 영원히 닿지 않고, 요청이 API에서
    「prompt가 너무 길다」로 반려된다. flower는 이 신호를 알아보고(`handoff.is_overflow()`) 그 자리에서
    기계적으로 조립한 축약본으로 handoff를 하므로 이 step은 실패하지 않는다
    ([../guide/handoff.md#is_overflow把硬错变成当场换代](../guide/handoff.md#is_overflow把硬错变成当场换代) 참조).

    실측값 하나는 언급할 가치가 있다: 개발용 이 머신의 게이트웨이는 `claude-opus-5[1m]`으로 설정되어 있다.
    예전처럼 20만으로 계산하면 15만마다 한 세대씩 넘어가는데, 실제로는 95만까지 돌 수 있다 — **5배 차이**이고,
    long-horizon 작업이 잘게 토막 난다.

### 시작하자마자 handoff가 일어나고 멈추지 않는다 {#一开局就换代}

**증상** 에러에 "시작 바닥값"이 언급되거나, 같은 step에서 handoff가 반복되다가 `max_generations=8`에 부딪힌다.

**원인** `window`를 작게 잡아서 임계값이 이 역할의 시작 바닥값보다 낮다 — coordinator는 실측 약 34k이고,
시스템 프롬프트와 [workbench](glossary.md#工作台) 인덱스만으로 그만큼 먹는다. 새 session이 입을 떼자마자 선을 넘고,
그래서 handoff document를 쓰고, 세대를 넘기고, 또 선을 넘고, 끝나지 않는다
(handoff는 재시도 한도를 먹지 않는데, 그건 의도된 것이다).

**어떻게 할 것인가** `--window`를 모델의 실제 window에 맞춰라. `-v`가 적용된 엔드포인트와 모델 매핑을 출력한다.
정상적인 장시간 실행에서는 8세대까지 갈 일이 없다. 정말 부딪혔다면 거의 확실히 이 원인이고, 에러 메시지도 그렇게 말한다
([../guide/handoff.md#一道防跑飞的闸](../guide/handoff.md#一道防跑飞的闸) 참조).
관련된 다른 증상으로 "handoff가 항상 축약본으로 떨어진다"가 있는데, 이유는 `runs/manifest.json`의 `errors`에 적힌다.

### 중간에 멈추고 예산이 다 됐다고 한다 {#预算到顶}

**증상** [step](glossary.md#步骤)이 끝나기 전에 멈추고, 이유는 비용 초과다.

**원인** `AgentSpec(max_budget_usd=...)`는 **하드 상한**이지 부드러운 알림이 아니다. `Runtime.total_cost()`는
이번 run의 합계다.

**어떻게 할 것인가** 상한을 올리기 전에 헛돌고 있는 게 아닌지 먼저 확인하라. 라운드마다 되돌려 보내지면서
매 라운드 진전이 없다면, 대개 judge가 「달성 불가능」을 줘야 할 자리에 「미달성」을 준 것이다 —
사실은 불가능한 목표 하나가 한도가 바닥날 때까지 계속 태운다
([../guide/goal.md#三个结论不是两个](../guide/goal.md#三个结论不是两个) 참조).
정상적으로 일하고 있음을 확인한 다음에 상한을 올려라.

### 이번 run은 왜 이렇게 비싼가 {#为什么这么贵}

**증상** 비용이 예상을 훨씬 넘는데, 출력을 봐도 돈이 어디에 쓰였는지 알 수 없다.

**원인** 장부는 모델의 컨텍스트 안에 없다. 각 step의 `session_id`, 비용, 재시도 횟수, 실패 원인은
`runs/manifest.json`에만 기록되고 **프로세스를 넘어 append**된다. 재시도 이력과 에러 원문도 여기에만 있다 —
모델은 볼 수 없고, 그건 의도된 것이다: 거부된 호출이 컨텍스트에 쌓이면 coordinator는 "어차피 Bash는 막히는구나"를
학습해서 `git status`조차 시도하지 않게 된다
(`Runtime(keep_denials=1)`이 기본으로 이미 정리하고 있다. 값을 키우지 마라).

**어떻게 할 것인가** `runs/manifest.json`을 열어 step별로 비용을 맞춰본다(디스크 레이아웃은 [config.md#磁盘布局](config.md#磁盘布局) 참조).
실측 참고값 몇 가지:

| | 비용 |
|---|---|
| subagent 하나의 시작 바닥값(분할 상각 불가) | ~4.3k tokens |
| coordinator의 시작 바닥값 | ~34k tokens |
| `tests/smoke.py` 단일 agent 전체 체인 | ~$0.21 |
| `tests/flow_demo.py` workflow 세 가지 연결 방식 | ~$0.39 |
| `tests/delegation.py` 분업 + 컨텍스트 분포 측정 | ~$0.71 |
| `tests/isolation.py` issue 세 개, worktree 세 개 | ~$0.9 |

### 컨텍스트가 일보다 빨리 늘어난다 {#上下文涨得快}

**증상** 매 라운드 [task brief](glossary.md#任务书)에 같은 규율("먼저 파일을 읽고 고쳐라", "비즈니스 코드는 건드리지 마라",
"고친 뒤 테스트를 돌려라")이 반복되는데, [worker](glossary.md#执行者)는 원래부터 그대로 하고 있다.

**원인** coordinator가 하는 모든 말은 자기 transcript에 들어가고, transcript는 늘기만 하고 줄지 않는다.
규율을 한 번 반복하면 이번 라운드에 값을 치르고, **이후 모든 라운드에서도 그 부분에 대해 다시 값을 치른다.**
상대가 이미 아는 것을 반복하는 이득은 0이고, 비용은 영구적이다.

**어떻게 할 것인가** 규율은 메커니즘에 넣고 매 라운드의 말에 넣지 마라: `allowed_tools`, brief의 「경계」 절,
workbench 인덱스로 표현할 수 있는 것은 task brief에 쓰지 마라. task brief에는 이번 라운드에 무엇이 바뀌었는지만 써라.
분업 자체가 가장 많이 아끼는 층이다
([../guide/context.md#第一层分工省得最多](../guide/context.md#第一层分工省得最多) 참조).
resume 할 때는 예전의 큰 도구 결과를 `-T`로 파일 포인터로 바꿀 수 있다.

## 중단과 continuity {#中断与接续}

### 프로세스가 kill 되고 머신이 재부팅됐다 {#进程被杀}

**증상** 중간에 사라졌고, 터미널을 다시 열었는데 어떻게 주워 담아야 할지 모르겠다.

**원인** 주워 담을 게 없다. [lineage](glossary.md#血缘)(`runs/lineage.json`)는 step 이름 → session_id를 기록하고,
step이 끝날 때마다 디스크에 떨군다. 쓸 때는 먼저 `.tmp`에 쓰고 원자적으로 교체하므로 — 중간에 죽어도 반쪽짜리 파일이 남지 않는다.

**어떻게 할 것인가** **같은 디렉터리**로 돌아가 `flower`를 다시 실행하면 각 step이 지난번 session을 이어간다:
요구사항을 다시 캐묻지 않고, 목표를 다시 세우지 않고, coordinator가 어떤 막다른 길을 시도했는지까지 기억한다.
아무 말도 하고 싶지 않으면 그냥 엔터를 쳐라
([../guide/continuity.md#进程被杀和机器重启](../guide/continuity.md#进程被杀和机器重启) 참조).
judge는 예외다 — `Step`이 아니라 gate에서 직접 파견되므로 lineage 경로를 전혀 타지 않고,
따라서 매 라운드가 완전히 새로운 한 쌍의 눈이다.

### 매번 처음부터 시작하고 전혀 이어지지 않는다 {#接不上}

**증상** 같은 디렉터리에서 다시 실행했는데 요구사항을 또 캐묻는다.

**원인** "맞지 않음"이 세 가지 있고, flower는 전부 **조용히 처음부터 시작으로 되돌아가며 에러를 내지 않는다** —
[continuity](glossary.md#接续)는 있으면 좋은 것이고, 그게 안 된다고 사람이 일하는 걸 막아서는 안 된다:

- `runs/lineage.json`이 없거나, 그 안의 `workspace`가 지금 경로와 일치하지 않는다(디렉터리를 복사해 옮겼으면 이렇게 된다)
- session이 이미 `runs/sessions.db`에 없다(DB를 지웠다)
- lineage 파일이 깨졌다

**어떻게 할 것인가** 먼저 `runs/lineage.json`이 있는지, `workspace`가 맞는지 보라
(세 파일의 역할은 [../guide/continuity.md#落在磁盘上的三个文件](../guide/continuity.md#落在磁盘上的三个文件) 참조).
디렉터리를 옮긴 뒤에 continuity가 안 되는 것은 **의도된 것이다**: `project_key`는 워크스페이스 경로에서 유도되므로
옛 session은 새 위치에서 조회되지 않는다.

### 새로 시작하고 싶지만 이력은 버리고 싶지 않다 {#想重开}

**증상** 요구사항이 이미 다른 방향으로 바뀌었는데, 지난번 얘기를 이어서 하게 하고 싶지 않다.

**원인** 기본 동작이 이어서 말하는 것이다. 이미 쓴 디렉터리에서 `flower "顺便支持代码块高亮"`는 새 작업이 아니라
한마디 더 한 것이다.

**어떻게 할 것인가** `--new`. 이건 **삭제가 아니라 아카이빙**이고, 옛 것들은 `notes/archive/`에 남는다.
[wake](glossary.md#唤醒) 시점에 현재 컨텍스트 규모를 한 줄로 먼저 알려주는데, 크다 싶으면 이 경로를 타면 된다.

### 네트워크가 끊겼는데 에러도 안 내고 움직이지도 않는다 {#断网}

**증상** 화면에 새 이벤트가 없고 프로세스는 살아 있다. 멈춘 것처럼 보인다.

**원인** 네트워크 단절은 실패가 아니라 "잠깐 기다림"으로 취급된다. flower는 매달려 기다린다: 먼저 DNS를 탐지하고,
그다음 TCP를 탐지하고, 통하면 계속한다
([../guide/continuity.md#韧性断网时挂着等而且错误不进接续后的上下文](../guide/continuity.md#韧性断网时挂着等而且错误不进接续后的上下文) 참조).
HT001에서 이 동작이 실제 장애로 검증됐다
([../cases/ht001.md#六断网续跑第一次被真实故障验证](../cases/ht001.md#六断网续跑第一次被真实故障验证) 참조).

**어떻게 할 것인가** 기다려라. `-v`로 탐지가 도는 걸 볼 수 있다. 대기 중에 쌓인 에러들은 **continuity 이후의 컨텍스트에
들어가지 않는다** — 그것들은 `runs/manifest.json`에만 남고, 인계받은 session이 보는 건 깨끗한 현장이다.
줄줄이 이어진 타임아웃에 끌려가지 않는다.

### Ctrl-C를 연속으로 두 번 누르면 마무리가 다 되지 않는다 {#双重-ctrl-c}

**증상** `kill`(SIGTERM)로 종료한 것과 Ctrl-C를 연속 두 번 누른 것이 남기는 현장이 다르다.

**원인** 알려진 구멍이다. Ctrl-C 두 번은 `KeyboardInterrupt`를 던진다: `cli.py`의 `_drive`에 있는 `finally`가
`rt.close()`는 호출하지만 `rt.rescue()`는 **호출하지 않는다** — `rescue()`를 호출하는 건 SIGHUP/SIGTERM 핸들러뿐이다.

**어떻게 할 것인가** lineage는 두 경로 모두에서 보존되므로(step이 끝날 때마다 원자적으로 디스크에 떨어진다)
다시 실행하면 그대로 이어진다. 이 구멍 때문에 진행 상황을 잃지는 않는다. 온전한 마무리를 원하면
Ctrl-C를 난타하지 말고 `kill <pid>`를 써라.

## 병렬과 isolation {#并行与隔离}

### `not in a git repository` {#不是-git-仓库}

**증상** isolation을 켜면 시작도 못 하고 `not in a git repository`가 뜬다.

**원인** `worker(..., isolate=True)`는 git worktree로 agent마다 사본을 하나씩 준다.
workspace가 git 저장소가 아니면 만들 수 없다.

**어떻게 할 것인가** 이 항목은 **조용히 성능 저하로 넘어가지 않는다** — 정말로 저장소 안에서 돌리거나,
`isolate`를 끄거나 둘 중 하나다. isolation이 보장하는 건 "여러 agent가 동시에 고쳐도 서로의 작업 트리가 보이지 않는다"이고,
병합에 충돌이 없다는 걸 대신 보장해 주지는 않는다.

### 격리된 agent가 workbench에 쓰지 못한다 {#隔离写不进工作台}

**증상** subagent가 "쓰기 권한 거부"를 보고하고 스크립트와 산출물이 디스크에 떨어지지 않는다.
혹은 산출물이 어느 한 worktree에 떨어져서 다른 agent가 보지 못한다.

**원인** worktree는 agent마다의 **사본**이고, workbench는 agent를 가로지르는 **공유 층**이다.
공유해야 할 것을 사설 울타리 안에 넣었으니 남이 못 가져가는 게 당연하다.

**어떻게 할 것인가** isolation을 켤 때는 workbench를 **저장소 밖**으로 지정한다:

```python
wb = Workbench(Path.cwd(), home=Path.cwd().parent / ".flower-proj").ensure()
```

워크스페이스 바깥에 두면 `Runtime`이 자동으로 `add_dirs`로 권한을 준다. `Runtime(workbench=True)`는 이 처리를
이미 하고 있고, 직접 만든 `Workbench`의 권한은 직접 줘야 한다.

!!! warning "workbench에는 기본 위치가 두 개 있고, 서로 다르다"
    `Workbench(workspace)` — CLI와 `starter_flow()`가 타는 경로다 — 는 workbench를 `<workspace>/.flower`에 둔다.
    반면 `Runtime(workbench=True)`(즉 `-W`)는 `<run_dir>/workbench`, 그러니까 `runs/workbench`에 둔다.
    그래서 `flower`를 한 번 실행하면 `.flower/`가 생기지만, Python에서 `Runtime(workbench=True)`를 호출하면 **생기지 않는다.**

### flower를 실행하면 `.flower/`가 생기는데, 직접 짠 스크립트에서는 안 생긴다 {#两个工作台默认值}

**증상** brief가 분명히 `.flower/notes/需求.md`에 쓰였는데 coordinator는 읽은 적이 없는 것처럼 군다. **에러는 없다.**

**원인** 손에 든 게 서로 다른 두 개의 workbench 객체다. brief는 A 디렉터리에 쓰였는데, system prompt에 주입되는
인덱스는 B 디렉터리를 스캔한다. "시작하자마자 요구사항 파일이 어디 있는지 안다"는 약속이 **조용히 무효화된다.**
두 가지 실수 모두 에러를 내지 않는다: `brief_path`를 직접 조립해 프로세스 cwd에 상대로 두면 `-W`가 만드는
`<run_dir>/workbench`와는 다른 디렉터리다. `Runtime`에서 거꾸로 가져오려는 것도 안 된다 —
`cli.py`는 먼저 `main()`을 호출해 `Workflow`를 만들고 그 뒤에 `Runtime`을 만드는데, 그때는 `brief_path`가
이미 확정되어 있다.

**어떻게 할 것인가** `Workbench`를 직접 만들어 **같은 객체**를 `Workflow`와 `Runtime`에 동시에 물리면 위치가 고정된다:

```python
wb = Workbench(Path.cwd()).ensure()
wf = Workflow(channel=ch, workbench=wb, steps=[...])
rt = Runtime(workspace=".", workbench=wb)
```

`tests/trial_offline.py`가 이걸 못 박아 두었다: 다섯 번째 단언이 brief가 `prompt_block()`에 나타나는지 확인한다.
그리고 인덱스는 **coordinator**의 system prompt에만 주입되고 subagent는 상속받지 못한다(실측 $0.2461, `tests/prelude_live.py`) —
경로는 coordinator가 아래로 전달해야 하고, 모든 subagent가 자동으로 아는 게 아니다
([../guide/workflow.md#工作台要挂在-workflow-上](../guide/workflow.md#工作台要挂在-workflow-上) 참조).
