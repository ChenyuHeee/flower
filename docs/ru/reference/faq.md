# Частые вопросы и разбор ошибок

Когда что-то ломается, человек не знает, какой модуль сломался, — он знает только то, что видит. Поэтому эта страница сгруппирована по **наблюдаемым симптомам**, а не по подсистемам.

Структура у каждого пункта одинаковая: **симптом** (то, что вы реально видите) → **причина** → **что делать**.

Пять пунктов — это **известные дефекты**, а не задуманное поведение. В таких пунктах прямо сказано, что это баг, дана ссылка на issue и способ обойти — они не выдаются за осознанное решение.

## Не ставится / не запускается {#装不上}

Полный процесс установки — в [install.md](../getting-started/install.md#一句话安装). Здесь только случаи «установилось, но команда не запускается».

### Версия Python ниже 3.10 {#python-版本}

**Симптом**: во время установки вылетает синтаксическая ошибка, либо pip прямо говорит, что не нашёл подходящей версии.

**Причина**: flower требует Python ≥ 3.10. Единственная рантайм-зависимость — `claude-agent-sdk`, нативный бинарник лежит внутри её wheel, — значит, проблема с установкой почти всегда в версии интерпретатора, а не в сети.

**Что делать**: сначала выясните, в какой интерпретатор вы ставите.

```bash
python3 --version
```

Если ниже 3.10 — возьмите другой и поставьте заново. Системный `python3` часто не тот, на который указывает `python` в вашем терминале; сверить версию до установки дешевле, чем разбираться после (см. [install.md](../getting-started/install.md#装之前确认-python)).

### Установилось, но `flower: command not found` {#command-not-found}

**Симптом**:

```text
zsh: command not found: flower
```

**Причина**: пакет установлен, но каталог со сгенерированным исполняемым скриптом не попал в `PATH`. Это не то же самое, что «не установилось»: если `python3 -c "import flower"` не падает, пакет в порядке.

**Что делать**: у скрипта `flower` shebang — абсолютный путь, поэтому достаточно сделать симлинк в каталог, который уже есть в `PATH`; ничего сорсить не нужно.

```bash
ln -sf "$PWD/.venv/bin/flower" ~/.local/bin/flower
```

### macOS: добавил PATH по подсказке `install.sh`, всё равно command not found {#macos-path}

!!! warning "Известная проблема ([issue #16](https://github.com/ChenyuHeee/flower/issues/16))"

    Этот совет не работает ровно на той машине, где он нужен.

**Симптом**: на macOS отработал `install.sh`, по его финальной подсказке добавили `~/.local/bin` в `PATH`, перезапустили терминал — `flower` по-прежнему command not found.

**Причина**: когда дело доходит до запасного варианта с pip, pip на macOS кладёт исполняемые скрипты в `~/Library/Python/3.X/bin`, а `install.sh` предлагает добавить `~/.local/bin`. Каталоги не совпадают, и следование подсказке ничего не даёт.

??? note "В каком порядке `install.sh` выбирает способ установки и как звучит та самая подсказка"

    Приоритетов четыре, а не два (`install.sh:35-56`):

    ```text
    1. есть uv         → uv tool install --force
    2. иначе есть pipx → pipx install --force
    3. иначе           → curl astral.sh/uv/install.sh, подтянуть uv; если получилось — ставим через uv
    4. и это не вышло  → "$PY" -m pip install --user --upgrade    ← ломается именно здесь
    ```

    Оригинальный текст финальной подсказки про PATH (`install.sh:62-68`, печатается только если `command -v flower` ничего не нашёл):

    ```text
    ! 但 flower 不在 PATH 上。
      把这一行加进你的 ~/.zshrc 或 ~/.bashrc:
        export PATH="$HOME/.local/bin:$PATH"
    ```

    `BINDIR` жёстко зашит как `$HOME/.local/bin` (`install.sh:63`). Для путей 1 и 3 это верно — uv ставит именно туда; **не сходится только у запасного pip на macOS**. Поэтому в эту яму попадают лишь машины, где первые три варианта не сработали.

**Что делать**: не гадайте про каталог — спросите у интерпретатора.

```bash
python3 -c "import sysconfig; print(sysconfig.get_path('scripts', scheme='posix_user'))"
```

Добавьте напечатанный каталог в `PATH` или сделайте из него симлинк в `~/.local/bin`:

```bash
ln -sf "$(python3 -c "import sysconfig; print(sysconfig.get_path('scripts', scheme='posix_user'))")/flower" ~/.local/bin/flower
```

### uv / pipx / pip поставили разные flower {#三种装法}

**Симптом**: `flower` запускается, но правки в исходниках не действуют; или после обновления всё равно старая версия; или два терминала на одной машине ведут себя по-разному.

**Причина**: три способа установки кладут пакет и исполняемый скрипт в разные места, а запускается тот, который в `PATH` встретился первым.

??? note "Куда попадает каждый из трёх способов"

    | Способ установки | Исполняемый скрипт | Когда использовать |
    |---|---|---|
    | `python3 -m venv .venv` + `pip install -e .` | `.venv/bin/flower` | Нужно править исходники. Правки действуют сразу |
    | `uv tool install` / `pipx install` | `~/.local/bin/flower` | Только использовать, нужен изолированный環境 |
    | `pip install --user` | Linux `~/.local/bin`, macOS `~/Library/Python/3.X/bin` | Запасной вариант. Каталог — см. пункт выше |

**Что делать**: сначала выясните, что именно сейчас запускается, потом решайте, какую копию править.

```bash
which -a flower                      # 列出 PATH 上所有同名的
head -1 "$(which flower)"            # shebang 指向哪个解释器,包就在那个环境里
```

Правите исходники — берите venv + `-e .` и не держите её рядом с копией от `uv` / `pipx`: разбираться в сосуществовании дороже, чем переустановить один раз (см. [install.md](../getting-started/install.md#从源码装)).

## Учётные данные и шлюз {#凭证}

### `缺少凭证:需要 ANTHROPIC_API_KEY 或 ANTHROPIC_AUTH_TOKEN` {#缺少凭证}

**Симптом**:

```text
缺少凭证:需要 ANTHROPIC_API_KEY 或 ANTHROPIC_AUTH_TOKEN
```

**Причина**: flower отсекает конфигурацию хоста через `setting_sources=[]`, поэтому учётные данные нужно приносить с собой. Полный порядок поиска — в [config.md](config.md#凭证查找优先级).

**Что делать**: пропишите их в `.env` в корне репозитория либо в окружение процесса.

```bash
cp .env.example .env        # 填 ANTHROPIC_AUTH_TOKEN 或 ANTHROPIC_API_KEY
```

`.env` уже в gitignore. Как это делается в контейнере — см. [deploy.md](deploy.md#凭证).

### Оно пишет «flower не читает `~/.claude/settings.json`» — это неправда {#settings-json}

**Симптом**: когда учётные данные не настроены, `env.py:192` печатает строку:

```text
flower 不读 ~/.claude/settings.json —— 那是可移植性的代价
```

**Причина**: эта фраза не соответствует коду. `env.py:56-75` **действительно читает** `~/.claude/settings.json`, забирая оттуда только поля с учётными данными, как последний запасной уровень — именно это и рекламирует `install.sh`. Строка печатается только после того, как запасной уровень оказался пуст, поэтому она ничего не ломает; но она подводит человека к выводу «flower не умеет использовать мой токен из Claude Code», а это неверно. Записано в [issue #13](https://github.com/ChenyuHeee/flower/issues/13).

**Что делать**: если на машине стоял Claude Code, заново получать учётные данные не нужно — запасной уровень подберёт их сам (см. [install.md](../getting-started/install.md#本机装过-claude-code-的话可能一个问题都不问)). Если вы реально видите эту строку — значит, и в том файле нет пригодных полей с учётными данными; заведите `.env` по предыдущему пункту.

### Непонятно, какие учётные данные и эндпоинт реально действуют {#生效值}

**Симптом**: `.env` вроде бы изменён, а запросы всё ещё уходят на старый шлюз; или невозможно сказать, какая модель используется сейчас.

**Причина**: у учётных данных и эндпоинта несколько источников (окружение процесса, `.env`, запасной уровень), и кто победил — видно не по конфигу, а по рантайму.

**Что делать**: запустите один раз с `-v`. На старте печатается `describe()`: действующий `BASE_URL` и маппинг моделей, токен замаскирован.

```bash
flower -v
```

Полная таблица флагов — в [cli.md](cli.md#全局开关), полная таблица переменных — в [config.md](config.md#环境变量).

### В `.env` осталась строка `KEY=`, и ниже по цепочке значение уже не подставится {#空值占位}

**Симптом**: токен экспортирован в окружение процесса, в `.env` есть строка `ANTHROPIC_AUTH_TOKEN=`, и всё равно ошибка «нет учётных данных».

**Причина**: пустое значение — это тоже присваивание. `KEY=` из более приоритетного источника **занимает** ключ, и менее приоритетные источники его уже не заполнят; а `check_credentials()` (определена в `env.py:184`) проверяет «значение непусто» — и рапортует об отсутствии. «Занято» и «отсутствует» — это разные вещи, а симптом ровно один и тот же; именно поэтому такую проблему тяжелее всего заметить самому.

**Что делать**: удалите строку целиком, не оставляйте пустых значений.

```bash
grep -n '^[A-Za-z_][A-Za-z0-9_]*=$' .env     # 列出所有空值行
```

После удаления ещё раз проверьте действующие значения через `-v`. Правила разбора — в [config.md](config.md#env-解析).

### Сторонний шлюз: подключение есть, но первый же раунд падает {#网关}

**Симптом**: 401 / 403; либо сообщение, что такой модели нет; либо [смена поколения](glossary.md#换代) прямо на старте с жалобой на «стартовый пол».

**Причина**: три типа ошибок конфигурации, у каждого свой симптом.

??? note "Три типа ошибок настройки шлюза и как их различить"

    | Симптом | Скорее всего | Куда лезть |
    |---|---|---|
    | 401 / 403 | Учётные данные валидны, но выданы не этим шлюзом; либо в `BASE_URL` не хватает пути или лишний слеш в конце | [config.md](config.md#凭证变量) |
    | Модель не найдена | Шлюз знает только свои имена моделей, маппинг не настроен | [config.md](config.md#模型变量) |
    | Смена поколения сразу на старте, жалоба на «стартовый пол» | Окно задано слишком маленьким: порог ниже стартового пола роли (у [координатора](glossary.md#协调者) замерено около 34k) | `--window`, см. [handoff.md](../guide/handoff.md#阈值怎么算) |

**Что делать**: сначала `-v`, чтобы увидеть действующие значения, и только потом менять конфиг. Особенно стоит свериться по окну: на машине разработки шлюз настроен на `claude-opus-5[1m]`, и если считать по 200 тысячам, поколение менялось бы каждые 150 тысяч, тогда как реально доступно 950 тысяч — **разница в 5 раз**, и [долгосрочная](glossary.md#长程) работа рубится в лапшу.

## Запускается, но ведёт себя неправильно {#行为不对}

В этой группе симптом — не ошибка: **команда отработала, код возврата 0, а сделано не то**. Первые четыре пункта — подтверждённые дефекты кода, issue заведены; здесь даны обходные пути, а не исправления. Последний пункт — задуманное поведение.

### `flower setup` запускает агента {#setup-跑成了-agent}

**Симптом**: выполняете `flower setup`, ожидая, что вас спросят про эндпоинт и токен, а оно начинает спрашивать «что нужно сделать» и проходит полный go-процесс, приняв слово `setup` за описание задачи. По итогу в учётных данных не появилось ни символа.

**Причина**: в `_CMDS` на `cli.py:758` перечислены только `"go"`, `"run"`, `"once"` — `"setup"` пропущен. Шаг подстановки подкоманды по умолчанию переписывает argv `["setup"]` в `["go", "setup"]`: `setup` из подкоманды превращается в первый позиционный аргумент `go`, то есть в саму задачу. **Никакой argv не доводит до мастера настройки.** Заведено [#11](https://github.com/ChenyuHeee/flower/issues/11).

**Что делать**: прервите по Ctrl-C и напишите конфиг напрямую. `setup` и сам только пишет в этот файл:

```bash
mkdir -p ~/.config/flower
cat > ~/.config/flower/.env <<'EOF'
ANTHROPIC_AUTH_TOKEN=sk-...
EOF
```

Полные имена переменных и порядок поиска учётных данных — в [config.md](config.md#凭证变量). После записи запустите `flower -v` в любом каталоге: напечатанный на старте действующий эндпоинт и есть проверка.

### Полноширинный `？` не запускает вопрос в обход {#全角问号}

**Симптом**: по описанию из [вопроса в обход](cli.md#旁路问答) вы ввели в приглашении `？этот каталог можно удалить`, но [оракул](glossary.md#旁路顾问) не поднялся — фраза была принята за ответ на текущий вопрос или как есть попала во входящие.

**Причина**: на `cli.py:733` подряд идут две проверки `startswith("?")`, и **обе используют один и тот же ASCII-символ**. По замыслу вторая должна была проверять полноширинный `？`. Китайская раскладка по умолчанию печатает именно полноширинный — то есть основная аудитория этой возможности не может ею воспользоваться вообще. Заведено [#12](https://github.com/ChenyuHeee/flower/issues/12).

!!! warning "Этот пункт загрязняет требования"
    Непопавший `？` не даёт ошибки и не отбрасывается. Он обрабатывается как обычный ввод: на этапе уточнения — как ответ на текущий вопрос, в остальное время — уходит во входящие.
    **Фраза, которую вы хотели задать в сторону, попадает в бриф.** Заметив опечатку, тут же правьте `.flower/notes/需求.md` — именно этот файл является эталоном ниже по цепочке.

**Что делать**: переключитесь на半角 и наберите `?`; либо сначала наберите `?` в半角, а потом переключитесь обратно на китайскую раскладку для текста.

### У `once` накопленная стоимость всегда `$0.00`, а время — всегда `0:00` {#once-计数为零}

**Симптом**: `flower once` отрабатывает от начала до конца, а в нижней строке состояния накопленная стоимость всё время показывает `累计 $0.00` и таймер стоит на `0:00`, тогда как та же модель на той же работе в `go` показывает нормальные цифры.

**Причина**: `render()` в `once` **создаёт новый `Render` на каждое полученное событие**, вместе с ним пересоздаются накопители, и счёт каждый раз начинается с нуля. Накопленные величины постоянно обнуляются, а не «не считаются». Заведено [#14](https://github.com/ChenyuHeee/flower/issues/14).

**Что делать**: нужны точные цифры — идите через `go`, этот путь не затронут. Если хочется однораундовой формы `once` и при этом видеть счёт, после прогона смотрите `runs/manifest.json` — стоимость каждого шага записана там, и эта запись верна. Подробнее в [config.md](config.md#run-dir).

### Skill, положенный в `plugin/`, никогда не загружается {#plugin-不加载}

**Симптом**: skill написан по [deploy.md](deploy.md#写一个-skill完整例子), структура каталогов верная, но агент ведёт себя так, будто о нём не знает — **ни ошибки, ни строчки в логах**.

**Причина**: `plugin/` не попадает в wheel. В установленном пакете `PLUGIN_DIR` указывает на `<site-packages>/plugin`, такого каталога нет, и проверка существования перед загрузкой молча пропускает шаг. **Все три пути `install.sh` попадают под это**, загрузка работает только в репозитории, выкаченном из исходников. Заведено [#15](https://github.com/ChenyuHeee/flower/issues/15).

**Что делать**: сначала проверьте, во что вообще разрешается путь.

```bash
python3 -c "from flower.core.agent import PLUGIN_DIR; print(PLUGIN_DIR, PLUGIN_DIR.is_dir())"
```

Напечаталось `False` — это как раз этот случай. Хотите skill — способ сейчас ровно один: **запускаться из исходников**.

```bash
git clone https://github.com/ChenyuHeee/flower
cd flower
python3 -m venv .venv && .venv/bin/pip install -e .
ln -sf "$PWD/.venv/bin/flower" ~/.local/bin/flower
```

Установка через `-e` указывает обратно в каталог выкачки, `PLUGIN_DIR` попадает на реальный `plugin/`, и та же проверка напечатает `True`.

### `-T` не даёт видимого эффекта на `go` {#trim-与-go}

**Симптом**: добавили `-T` к `flower go`, сравнили с запуском без него — поведение идентично, флаг как будто сломан.

**Причина**: **это задумано, а не дефект.** На пути `go` [усечение](glossary.md#裁剪) включено по умолчанию, намерение, выражаемое `-T`, уже выполнено, и повторное указание ничего не меняет. Настоящий переключатель на этом пути — обратный `--no-trim`: явно задавать нужно только выключение. `-T` осмыслен как переключатель только для `run` и `once`.

**Что делать**: чтобы убедиться, что на `go` усечение действительно включено, смотрите стартовый вывод с `-v`, а не судите по наличию `-T`; чтобы выключить — передайте `--no-trim`. Полная семантика флагов — в [cli.md](cli.md#全局开关).

## Говорит, что сделано, а сделано не всё {#没做完}

[Страж цели](../guide/goal.md) существует именно для того, чтобы ловить такое: у исполнителя есть системный оптимистический сдвиг — он знает, что сделал, и не знает, что пропустил. Но и сам страж ошибается, причём ошибается закономерно. Ниже пять пунктов, разделённых на «пропустил то, что пропускать нельзя» и «не пропускает вообще».

### Оно пишет «здесь проверить невозможно» — и пропускает {#无法达成不是未达成}

**Симптом**: в вердикте написано «в текущем окружении этот пункт проверить нельзя, считаем достигнутым», и workflow идёт дальше.

**Причина**: [судья](glossary.md#判定者) слепил «недостижимо» и «не достигнуто» в один вывод. Это **разные выводы**, об этом и говорит [выводов три, а не два](../guide/goal.md#三个结论不是两个): «не достигнуто» — вернуть на доработку, «недостижимо» — **остановиться и спросить человека**, принять ли это, изменить ли цель, либо признать, что судья ошибся. Когда выводов всего два («достигнуто/не достигнуто»), реально невыполнимая цель заставит координатора крутиться раунд за раундом, пока не кончится лимит.

**Что делать**: **«здесь не проверить» никогда нельзя считать достижением.** В `instructions` для судьи поимённо перечислите, что в вашем сценарии считается невыполнимым, чтобы он выдавал «недостижимо» там, где должен. Если вы не хотите, чтобы вас останавливали вопросом, ставьте `--timeout 0`: при «недостижимо» прогон просто остановится, причина останется на диске, а не будет замазана.

### Оно прочитало исходники и объявило работу сделанной {#判产出物}

**Симптом**: в обосновании вердикта написано «в коде X уже реализован», «сигнатура функции соответствует требованию», а артефакты сборки, вывод команд, поднятый сервис — ничего из этого не тронуто.

**Причина**: судью увели в исходники. [Судим артефакт, а не исходник](../guide/goal.md#判的是产出物不是源码) — «выглядит ли код правильно» и «работает ли то, что сдано» — разные вещи. Первое исполнитель уже считает верным; убедиться в этом ещё раз не даёт новой информации.

**Что делать**: пункты вердикта нужно формулировать как утверждения об **артефакте**. «Реализована функция экспорта» не годится; «запустить `./app export out.csv`, в `out.csv` три колонки заголовка» — годится. Так и надо писать на шаге постановки цели, иначе судье останется додумывать расплывчатые формулировки самому.

### Судья не может запускать команды — и пропускает, прочитав Makefile {#判定者不能跑命令}

**Симптом**: цель — «собрать бинарь, работающий на Linux», вердикт положительный. Вы сами делаете `file` — артефакт оказывается Mach-O, никакого ELF.

**Причина**: судья по умолчанию — `judge(can_run=False)`, у него на руках **только `Read` / `Glob` / `Grep`**. Эти три инструмента читают файлы, но **не запускают ни `file`, ни `./app --version`**. Поэтому он идёт по пути наименьшего сопротивления: читает Makefile, видит в ветке Darwin кросс-компиляцию и считает условие выполненным. Он не солгал — он **нашёл самое похожее на доказательство в пределах своих возможностей**.

??? note "Когда `can_run` обязателен"
    Критерий простой: **если в цели появляются слова про «то, что собрано» — включайте.**

    - Артефакты: бинарь, образ, пакет, сгенерированные данные — включать
    - Поведение: сервис поднимается, команда возвращает 0, вывод соответствует шаблону — включать
    - Чистый текст: написана ли документация, добавлено ли поле в schema — не нужно

    В командной строке это `--judge-can-run`. При ручной сборке пайплайна разные точки входа выглядят по-разному, но всё сводится к одному и тому же параметру `judge()`:

    | Точка входа | Как передать | Где смотреть |
    |---|---|---|
    | `judge()` | `can_run=` — обычный параметр | `roles.py:361` |
    | `with_goal()` | `can_run=` — параметр, пробрасывается в `judge()` | `goal.py:155` → `:170` |
    | `goal_step()` | **Параметра `can_run` нет**, но он попадает в `**spec_kw`, а там как раз `judge(..., **spec_kw)` — дойдёт | `goal.py:97` → `:105` |
    | `starter_flow()` | `judge_can_run=`, превращается в `with_goal(can_run=…)`; `--judge-can-run` идёт именно этим путём | `starter.py:105` → `:196` |

    Плата — судья реально выполняет команды, раунд вердикта становится медленнее и дороже; взамен он проверяет **саму площадку**, а не инструкцию к ней. См. [может ли судья запускать команды](../guide/goal.md#判定者能不能跑命令).

**Что делать**: если цель про артефакт — включайте `--judge-can-run`. Если не включаете, держите жёсткое ограничение при написании пунктов вердикта: «проверяемо чтением». Пункт, который так не формулируется, изначально требует запуска команд.

### В списке вердикта больше десятка пунктов, и он никогда не проходит {#清单长度}

**Симптом**: каждый раунд возвращают на доработку, список расхождений длинный, чем больше правишь — тем он длиннее, работа не заканчивается.

**Причина**: список написан по принципу «насколько я хочу быть строгим», а не «сколько у этой работы способов провалиться». [Длину списка определяет число способов провалиться](../guide/goal.md#清单的长度由有多少种失败方式决定): для задачи вида `git clone && make && ./app` **хватает трёх-пяти пунктов** — собралось, запускается, работает. В реальной аварии из [HT002](../cases/ht002.md#那条查-flower-的清单自己把自己判失败了) задача «поставить репозиторий и запустить» была расписана на **15 пунктов**: только 5 проверяли работоспособность, 6 — соблюдение процесса, а ещё 4 **в принципе непроверяемы**.

**Что делать**: правьте `.flower/notes/目标.md` — именно этот файл является основанием для вердикта. По каждому пункту спросите: «какому способу провалиться он соответствует», и удалите те, на которые нет ответа. На шаге постановки цели про непроверяемые пункты и так предупреждают — не оставляйте их насильно.

### Границы записаны как пункты вердикта {#边界不是判定项}

**Симптом**: в списке появляются пункты вида «не запускал `brew install`», «не менял файлы вне каталога проекта», и судья, доказывая свою невиновность, лезет смотреть mtime у `~/.zshrc` и проверять, не трогали ли каталог `.flower/`.

**Причина**: границы и пункты вердикта ограничивают разные вещи; их смешение и стало главной причиной аварии HT002 ([корневая причина один](../cases/ht002.md#根因一边界被当成了判定项)).

| | Что ограничивает | Как соблюдается |
|---|---|---|
| **Границы** | **Как вы работаете** («ставить только внутри каталога проекта», «бизнес-код не трогать») | **Не выходя за них**, а не доказывая постфактум |
| **Пункты вердикта** | **То, что сдано** («запускается или нет», «результат верный или нет») | Проверкой на месте |

Границы — это как раз тот раздел, который на этапе уточнения предлагают заполнять подробно. Перенос их по одному в список вердикта означает, что каждая новая граница добавляет ещё одну проверку, а большинство таких проверок невыполнимы — и непроверяемый пункт утаскивает весь раунд вердикта в провал.

**Что делать**: границы остаются в разделе «границы» брифа, соблюдаются тем, что за них не выходят, и в список вердикта не попадают. Если действительно нужна отчётность — одна фраза, **а не шесть пунктов**.

## Контекст и стоимость {#上下文与花费}

В долгосрочном прогоне контекст и деньги — это одна и та же проблема: контекст упирается в потолок, и либо происходит смена поколения, либо шаг падает; а всё, что повторяется в каждом раунде, приходится оплачивать заново в каждом следующем.

### На середине оно само открыло новую сессию и сказало «смена поколения» {#换代打断}

**Симптом** В потоке событий появляется `handoff`, `payload["phase"]` сначала `near`, потом `done`, между ними тратится лишний раунд на написание [документа передачи](glossary.md#交接书), после чего работа продолжается как обычно.

**Причина** Контекст подошёл к порогу. flower **не делает compact** — он записывает состояние текущей сессии в документ передачи из пяти разделов и поднимает новую сессию, которая читает его и продолжает. [Compact](glossary.md#压缩) заодно стирает самую дорогую информацию вроде «тупиковых путей», а документ передачи явный, лежит на диске и правится в любой момент: принимающая сессия читает именно этот файл.

**Что делать** Это нормальный путь, вмешиваться не нужно. Смена поколения не считается повтором — `attempts` не растёт (он считает провалы), сожжённый session_id пишется в `StepResult.retired`, а наружу отдаётся `session_id` всегда живого преемника (см. [../guide/handoff.md#换代不算重试账怎么记](../guide/handoff.md#换代不算重试账怎么记)). Если очень хочется вернуться к auto-compact из SDK — `--no-handoff`.

??? note "Откуда берётся порог и почему значение по умолчанию такое агрессивное"
    `at = window - headroom`. `window` **по умолчанию 1 миллион**, определяется по имени модели: если в имени есть `haiku`, считается 200 тысяч, иначе — 1 миллион. `headroom` по умолчанию 50k — auto-compact срабатывает на −33k, смена поколения должна успеть раньше, а само «написать передачу» требует ещё одного раунда; 50k покрывает и то и другое.

    Переоценка окна — не фатальная ошибка: если реальное окно меньше, порог просто никогда не будет достигнут, запрос отобьётся API с «prompt слишком длинный», flower распознаёт этот сигнал (`handoff.is_overflow()`) и тут же делает смену поколения на механически собранном деградированном документе — шаг не падает (см. [../guide/handoff.md#is_overflow把硬错变成当场换代](../guide/handoff.md#is_overflow把硬错变成当场换代)).

    Замер, который стоит упомянуть: на машине разработки шлюз настроен на `claude-opus-5[1m]`. Если считать по 200 тысячам, поколение менялось бы каждые 150 тысяч, тогда как реально доступно 950 тысяч — **разница в 5 раз**, долгосрочная работа рубится в лапшу.

### Смена поколения сразу на старте, и её не остановить {#一开局就换代}

**Симптом** В ошибке упоминается «стартовый пол», либо один и тот же шаг меняет поколение снова и снова, пока не упрётся в `max_generations=8`.

**Причина** `window` задан слишком маленьким, порог оказался ниже стартового пола этой роли — у координатора замерено около 34k, столько занимают системный prompt и индекс [верстака](glossary.md#工作台). Новая сессия переходит границу с первого слова, пишет передачу, меняет поколение, снова переходит границу — и так бесконечно (смена поколения не ест лимит повторов, это сделано намеренно).

**Что делать** Выставьте `--window` по реальному окну модели; `-v` печатает действующий эндпоинт и маппинг моделей. Нормальный длинный прогон не доходит до 8 поколений — если дошёл, причина почти наверняка эта, о чём прямо сказано и в тексте ошибки (см. [../guide/handoff.md#一道防跑飞的闸](../guide/handoff.md#一道防跑飞的闸)). Смежный симптом — «передача всегда деградированная»: причина пишется в `errors` в `runs/manifest.json`.

### Останавливается на полпути со словами, что бюджет исчерпан {#预算到顶}

**Симптом** [Шаг](glossary.md#步骤) не доделан и останавливается с причиной «превышена стоимость».

**Причина** `AgentSpec(max_budget_usd=...)` — **жёсткий потолок**, а не мягкое напоминание; `Runtime.total_cost()` — сумма по текущему прогону.

**Что делать** Прежде чем поднимать потолок, убедитесь, что оно не крутится вхолостую. Раунд за раундом возвращают, и в каждом нет прогресса — обычно это судья, который должен был выдать «недостижимо», а выдал «не достигнуто»: реально невыполнимая цель будет жечь бюджет до конца лимита (см. [../guide/goal.md#三个结论不是两个](../guide/goal.md#三个结论不是两个)). Убедились, что работа идёт — тогда поднимайте потолок.

### Почему этот прогон такой дорогой {#为什么这么贵}

**Симптом** Стоимость сильно выше ожидаемой, но по выводу непонятно, куда ушли деньги.

**Причина** Счёт не находится в контексте модели. `session_id` каждого шага, стоимость, число повторов и причины провалов пишутся только в `runs/manifest.json`, **дописываются между процессами**. История повторов и оригинальные тексты ошибок тоже только там — модель их не видит, и это намеренно: если отклонённые вызовы копятся в контексте, координатор выучивает «Bash всё равно заблокируют» и перестаёт даже пробовать `git status` (`Runtime(keep_denials=1)` по умолчанию уже чистит, не увеличивайте).

**Что делать** Откройте `runs/manifest.json` и сверьте стоимость по шагам (раскладка на диске — [config.md#磁盘布局](config.md#磁盘布局)). Несколько замеренных ориентиров:

| | Стоимость |
|---|---|
| Стартовый пол одного subagent (не размазывается) | ~4.3k tokens |
| Стартовый пол координатора | ~34k tokens |
| `tests/smoke.py`, полная цепочка одного агента | ~$0.21 |
| `tests/flow_demo.py`, три способа связывания workflow | ~$0.39 |
| `tests/delegation.py`, разделение труда + замер распределения контекста | ~$0.71 |
| `tests/isolation.py`, три issue в трёх worktree | ~$0.9 |

### Контекст растёт быстрее, чем делается работа {#上下文涨得快}

**Симптом** В каждом [задании](glossary.md#任务书) повторяется один и тот же кусок дисциплины («сначала прочитать файл, потом менять», «бизнес-код не трогать», «после правок прогнать тесты»), хотя [исполнитель](glossary.md#执行者) и так это делает.

**Причина** Каждая фраза координатора попадает в его собственный transcript, а transcript только растёт. Повторили дисциплину — заплатили за этот раунд, **и за неё же придётся платить в каждом следующем**. Повторять то, что собеседник уже знает, — нулевая польза при постоянных издержках.

**Что делать** Дисциплина уходит в механизмы, а не в реплики каждого раунда: то, что выражается через `allowed_tools`, раздел «границы» брифа или индекс верстака, не надо писать в задание; в задании — только то, что изменилось в этом раунде. Само разделение труда экономит больше всего (см. [../guide/context.md#第一层分工省得最多](../guide/context.md#第一层分工省得最多)). При resume старые большие результаты инструментов можно заменить указателями на файлы через `-T`.

## Прерывания и преемственность {#中断与接续}

### Процесс убили, машина перезагрузилась {#进程被杀}

**Симптом** Прогон оборвался на середине, открываете терминал заново и не понимаете, как всё подобрать.

**Причина** Подбирать нечего. [Родословная](glossary.md#血缘) (`runs/lineage.json`) хранит соответствие «имя шага → session_id» и сбрасывается на диск после каждого шага; запись идёт сначала в `.tmp`, затем атомарной заменой — убийство посередине не оставит половинчатого файла.

**Что делать** Вернитесь в **тот же каталог** и запустите `flower` снова: каждый шаг продолжится в прежней сессии — требования заново не выспрашивают, цель заново не ставят, и даже тупики, которые пробовал координатор, всё ещё помнятся. Если сказать нечего — просто Enter (см. [../guide/continuity.md#进程被杀和机器重启](../guide/continuity.md#进程被杀和机器重启)). Исключение — судья: он не `Step`, его выдают прямо из gate, он никогда не идёт по родословной, поэтому каждый раунд смотрит новая пара глаз.

### Каждый раз начинается с нуля, преемственности нет {#接不上}

**Симптом** Запускаете в том же каталоге, а оно снова выспрашивает требования.

**Причина** Три вида «не сошлось», и на всех flower **молча откатывается к старту с нуля, без ошибки** — [преемственность](glossary.md#接续) это бонус, её отказ не должен мешать человеку работать:

- `runs/lineage.json` отсутствует, либо `workspace` внутри не совпадает с вашим текущим путём (так бывает после копирования каталога)
- сессии уже нет в `runs/sessions.db` (базу удаляли)
- файл родословной повреждён

**Что делать** Сначала посмотрите, есть ли `runs/lineage.json` и верен ли `workspace` (обязанности трёх файлов — в [../guide/continuity.md#落在磁盘上的三个文件](../guide/continuity.md#落在磁盘上的三个文件)). Отсутствие преемственности после смены каталога — **намеренное**: `project_key` выводится из пути рабочей области, старую сессию по новому месту не найти.

### Хочется начать заново, но не потерять историю {#想重开}

**Симптом** Требования развернулись в другую сторону, и не хочется, чтобы оно продолжало прошлый разговор.

**Причина** Поведение по умолчанию — продолжать. В уже использованном каталоге `flower "заодно поддержи подсветку блоков кода"` — это не новая задача, а ещё одна реплика.

**Что делать** `--new`. Это **архивирование, а не удаление**, старое остаётся в `notes/archive/`. При [пробуждении](glossary.md#唤醒) сначала печатается строка с текущим размером контекста; если он кажется большим — тоже сюда.

### Пропала сеть — оно не падает и не двигается {#断网}

**Симптом** В интерфейсе нет новых событий, процесс жив, выглядит как зависание.

**Причина** Обрыв сети трактуется как «подождать», а не как провал. flower висит и ждёт: сначала проверяет DNS, потом TCP, и продолжает только когда прошло (см. [../guide/continuity.md#韧性断网时挂着等而且错误不进接续后的上下文](../guide/continuity.md#韧性断网时挂着等而且错误不进接续后的上下文)). В HT001 это было подтверждено реальным сбоем (см. [../cases/ht001.md#六断网续跑第一次被真实故障验证](../cases/ht001.md#六断网续跑第一次被真实故障验证)).

**Что делать** Ждите; с `-v` видно, что проверки идут. Ошибки, накопившиеся за время ожидания, **не попадают в контекст после продолжения** — они оседают только в `runs/manifest.json`, а принимающая сессия видит чистую площадку и не сбивается на череду таймаутов.

### Двойной Ctrl-C — завершение отработало не полностью {#双重-ctrl-c}

**Симптом** После `kill` (SIGTERM) и после двойного Ctrl-C остаётся разное состояние.

**Причина** Известный пробел. Двойной Ctrl-C бросает `KeyboardInterrupt`: в `cli.py` блок `finally` в `_drive` вызывает `rt.close()`, но **не** вызывает `rt.rescue()` — `rescue()` вызывают только обработчики SIGHUP/SIGTERM.

**Что делать** Родословная сохраняется на обоих путях (атомарный сброс на диск после каждого шага), поэтому следующий запуск всё равно подхватит работу — этот пробел не приводит к потере прогресса. Если нужно полное завершение, используйте `kill <pid>`, а не долбите Ctrl-C.

## Параллельность и изоляция {#并行与隔离}

### `not in a git repository` {#不是-git-仓库}

**Симптом** С включённой изоляцией ничего не поднимается, ошибка `not in a git repository`.

**Причина** `worker(..., isolate=True)` даёт каждому агенту приватную копию через git worktree; если workspace не git-репозиторий, создать её невозможно.

**Что делать** Здесь **нет молчаливой деградации** — либо действительно запускайтесь внутри репозитория, либо выключайте `isolate`. Изоляция гарантирует, что несколько агентов правят одновременно и не видят рабочих деревьев друг друга; она не гарантирует отсутствие конфликтов при слиянии.

### Изолированный агент не может писать в верстак {#隔离写不进工作台}

**Симптом** Subagent сообщает «отказано в праве на запись», скрипты и результаты не сохраняются на диск; либо результат оседает в одном worktree и другим агентам не виден.

**Причина** worktree — **приватная копия** каждого агента, верстак — **общий слой** между агентами. Если общее положить внутрь приватного забора, остальные его, естественно, не достанут.

**Что делать** При включённой изоляции направляйте верстак **за пределы репозитория**:

```python
wb = Workbench(Path.cwd(), home=Path.cwd().parent / ".flower-proj").ensure()
```

Когда верстак лежит вне рабочей области, `Runtime` автоматически выдаёт доступ через `add_dirs`; `Runtime(workbench=True)` это уже делает, а при самостоятельном создании `Workbench` доступ нужно выдавать самому.

!!! warning "У верстака два значения по умолчанию, и они разные"
    `Workbench(workspace)` — этим путём идут CLI и `starter_flow()` — кладёт верстак в `<workspace>/.flower`; а `Runtime(workbench=True)` (то есть `-W`) кладёт его в `<run_dir>/workbench`, то есть `runs/workbench`. Поэтому после запуска `flower` у вас появится `.flower/`, а вызов `Runtime(workbench=True)` из Python **этого не сделает**.

### После `flower` есть `.flower/`, а в своём скрипте его нет {#两个工作台默认值}

**Симптом** Бриф записан в `.flower/notes/需求.md`, а координатор ведёт себя так, будто его не читал; **ошибки нет**.

**Причина** У вас на руках два объекта верстака. Бриф записан в каталог A, а индекс, вставляемый в system prompt, сканирует каталог B, и обещание «с первого хода знает, где лежит файл требований» **молча перестаёт работать**. Оба варианта ошибки не дают ошибки: самостоятельно собранный `brief_path` относительно cwd процесса и `<run_dir>/workbench`, создаваемый `-W`, — это два разных каталога; вытащить путь обратно из `Runtime` тоже не выйдет — `cli.py` сначала вызывает `main()`, чтобы собрать `Workflow`, и только потом создаёт `Runtime`, а `brief_path` к тому моменту давно зафиксирован.

**Что делать** Создайте `Workbench` сами и подключите **один и тот же объект** и к `Workflow`, и к `Runtime` — тогда расположение зафиксировано:

```python
wb = Workbench(Path.cwd()).ensure()
wf = Workflow(channel=ch, workbench=wb, steps=[...])
rt = Runtime(workspace=".", workbench=wb)
```

`tests/trial_offline.py` фиксирует это: пятое утверждение проверяет, что бриф появляется в `prompt_block()`. Кроме того, индекс вставляется только в system prompt **координатора**, subagent его не наследует (замерено $0.2461, `tests/prelude_live.py`) — путь должен пересказать координатор, каждый subagent сам его не узнает (см. [../guide/workflow.md#工作台要挂在-workflow-上](../guide/workflow.md#工作台要挂在-workflow-上)).
