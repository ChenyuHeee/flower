# Конфигурация

У flower нет формата конфигурационного файла, и нет подкоманды конфигурации, которая реально работала бы, — вся конфигурация это **переменные окружения** плюс **файл `.env`**, плюс набор объектов-политик, которые можно задать только со стороны Python. Эта страница собирает в одно место то, что разбросано по пяти разным местам: каждая переменная, в каком порядке ищутся учётные данные, какой синтаксис понимает `.env`, что именно изолирует `setting_sources=[]`, что один запуск оставляет на диске, что теряет каждый из трёх слоёв хранилища сессий, как ведётся ожидание при обрыве сети. Термины — строго по [глоссарию](glossary.md).

## Полная таблица переменных окружения {#环境变量}

Четыре группы: учётные данные и endpoint, которые flower читает напрямую; выбор модели; поиск путей; и то, что flower **пишет** дочернему процессу агента. Последнюю группу задавать не надо — если зададите, она всё равно будет перезаписана.

### Учётные данные и endpoint {#凭证变量}

| Переменная | Назначение | По умолчанию | Обязательна | Источник |
|---|---|---|---|---|
| `ANTHROPIC_API_KEY` | Официальный key Anthropic. Если он есть, запрос идёт с заголовком `x-api-key` | нет | **одна из двух** вместе с `ANTHROPIC_AUTH_TOKEN` | `env.py:28`, `:146`, `:157-158` |
| `ANTHROPIC_AUTH_TOKEN` | Token, выданный шлюзом. Если `ANTHROPIC_API_KEY` нет, используется `authorization: Bearer` | нет | то же | `env.py:28`, `:147`, `:159-160` |
| `ANTHROPIC_BASE_URL` | Корневой адрес API endpoint. Сторонний шлюз ставит сюда свой адрес, **без `/v1`** — проба склеивает `<BASE_URL>/v1/messages` | `https://api.anthropic.com` | нет | `env.py:151`, `:162`, `:210`; `resilience.py:70` |

Если не задана ни одна (или обе — пустые строки), `check_credentials()` возвращает ту самую четырёхстрочную ошибку, а `Runtime.__init__` бросает `RuntimeError` (`env.py:184-194`; `runtime.py:156-158`).

### Выбор модели {#模型变量}

flower читает только три из них для собственных решений, остальные просто загружаются и прозрачно передаются в SDK.

| Переменная | Назначение | По умолчанию | Обязательна | Источник |
|---|---|---|---|---|
| `ANTHROPIC_MODEL` | Имя основной модели. Заодно определяет значение по умолчанию для окна [handoff](glossary.md#换代): в имени есть `1m` или нет `haiku` → 1 миллион, есть `haiku` → 200 тысяч | нет (решает сторона endpoint) | нет | `env.py:153`; `agent.py:77-81` |
| `ANTHROPIC_DEFAULT_OPUS_MODEL` | Отображение модели для уровня opus. Если `ANTHROPIC_MODEL` пуста, определение окна откатывается сюда | нет | нет | `agent.py:78`; `cli.py:1205` |
| `ANTHROPIC_DEFAULT_SONNET_MODEL` | Отображение модели для уровня sonnet. Сама flower её не читает, только загружает и одалживает | нет | нет | `env.py:34`; `cli.py:1206` |
| `ANTHROPIC_DEFAULT_HAIKU_MODEL` | Отображение модели для уровня haiku. **Проба учётных данных использует её в первую очередь** | проба откатывается на `ANTHROPIC_MODEL`, затем на `claude-3-5-haiku-20241022` | нет | `env.py:152-153` |
| `CLAUDE_CODE_SUBAGENT_MODEL` | Какую модель использует [subagent](glossary.md#subagent). flower её не интерпретирует, её потребляет SDK | нет | нет | `env.py:35`; `.env.example` |
| `CLAUDE_CODE_EFFORT_LEVEL` | Уровень размышления. То же самое: только загружается, не интерпретируется | нет | нет | `env.py:35` |

Если при `flower setup` задать имя модели, то `ANTHROPIC_MODEL`, `ANTHROPIC_DEFAULT_OPUS_MODEL` и `ANTHROPIC_DEFAULT_SONNET_MODEL` **пишутся все три сразу** (`cli.py:1204-1206`).

### Что flower пишет дочернему процессу агента {#写出的变量}

Эти три генерируются `CompactPolicy.env()` и подкладываются в `ClaudeAgentOptions.env` (`agent.py:48-58`, `:241-245`), они управляют встроенным в harness [compact](glossary.md#压缩). **Задавать их у себя в shell бессмысленно** — реально работает та копия, которую flower передаёт дочернему процессу.

| Переменная | Назначение | По умолчанию | Обязательна | Источник |
|---|---|---|---|---|
| `DISABLE_AUTO_COMPACT` | `=1` выключает автоматический compact. Пока включён [handoff](glossary.md#换代), **пишется принудительно** — если оба механизма работают одновременно, не разобрать, кто именно откатил контекст | handoff включён по умолчанию, так что фактически всегда `1` | нет (пишет flower) | `agent.py:51`; `runtime.py:444-447` |
| `DISABLE_COMPACT` | `=1` выключает заодно и `/compact`. Пишется только при `CompactPolicy(mode="off")` | не пишется | нет (пишет flower) | `agent.py:52-53` |
| `CLAUDE_CODE_AUTO_COMPACT_WINDOW` | Окно автоматического compact (в токенах). Пишется только при `CompactPolicy(window=N)` | не пишется | нет (пишет flower) | `agent.py:56-57` |

### Что читает контейнерная обёртка {#容器变量}

Эти две читает не сам flower, а shell-обёртка `docker/flowerbox`. Полное описание — в [развёртывании](deploy.md).

| Переменная | Назначение | По умолчанию | Обязательна | Источник |
|---|---|---|---|---|
| `FLOWER_HOME` | Где искать тот `.env`, который пойдёт в `--env-file` | каталог на уровень выше расположения самого скрипта | нет | `docker/flowerbox:12` |
| `FLOWER_IMAGE` | Какой образ использовать | `flower-box` | нет | `docker/flowerbox:13` |

**Ключи в `.env` не ограничены перечисленными выше.** Парсер загружает в `os.environ` **все** строки вида `k=v`, никакого белого списка нет (`env.py:30`, `:102-107`). Набор `KNOWN` из тех 9 ключей учётных данных работает ровно в двух местах: как белый список при одалживании конфигурации из `~/.claude` (`env.py:72`) и как набор полей, которые печатает `describe()` при запуске с `-v` (`env.py:205`).

## Приоритет поиска учётных данных {#凭证查找优先级}

Если `load_dotenv()` вызвана без пути, она по очереди читает **все существующие** файлы в следующем порядке (`env.py:45-53`, `:78-112`):

1. **Переменные окружения процесса** — всегда наивысший приоритет. Никакой `.env` не перебьёт уже экспортированное значение. (`env.py:91`)
2. **Файл, на который указывает `$FLOWER_ENV`** — только если она задана. (`env.py:48-49`)
3. **`$PWD/.env`** — текущий рабочий каталог. В каком проекте `cd`, тот и читается. (`env.py:50`)
4. **`${XDG_CONFIG_HOME:-~/.config}/flower/.env`** — глобальное расположение, один файл на пользователя; именно его пишет `flower setup`. (`env.py:51`, `:39-42`)
5. **`.env` в корне репозитория с исходниками** — три уровня вверх от `flower/core/env.py`. Существует только при запуске из исходников; установленный через pip / pipx / uv flower лежит в site-packages, там этого пункта нет. (`env.py:52`)
6. **Блок `env` в `~/.claude/settings.json`, затем в `~/.claude/settings.local.json`** — последний откат, **берутся только 9 ключей учётных данных**. (`env.py:56-75`, `:109-111`)

**Какой файл побеждает**: пункт 3 (проектный `.env`) бьёт пункт 4 (глобальный `.env`), пункт 4 бьёт пункт 5 (`.env` в корне репозитория), все трое бьют пункт 6 (конфигурацию Claude Code), и никто из них не бьёт пункт 1 (окружение процесса).

Реализовано это как «**ключ, у которого уже есть значение, не перезаписывается**» (`env.py:90-93`): кто идёт раньше, тот занимает ключ, а последующие лишь заполняют пропуски. То есть приоритет считается **по ключам, а не по файлам** — если в проектном `.env` написан только `ANTHROPIC_BASE_URL`, token спокойно придёт из глобального файла. Первое встреченное значение одноимённого ключа фиксируется навсегда.

Пункт 6 включается только при **автоматическом поиске**. Если путь задан явно (`load_dotenv("/path/to/.env")`), читается ровно этот один файл, без каких-либо откатов (`env.py:86-87`, `:109`).

### Пункт 6: одолжить token у Claude Code {#借用}

По очереди читаются `~/.claude/settings.json` и `~/.claude/settings.local.json`, берётся dict `data["env"]`, из него выбираются эти 9 ключей (`env.py:31-36`, `:65-74`):

```text
ANTHROPIC_API_KEY   ANTHROPIC_AUTH_TOKEN   ANTHROPIC_BASE_URL
ANTHROPIC_MODEL     ANTHROPIC_DEFAULT_OPUS_MODEL    ANTHROPIC_DEFAULT_SONNET_MODEL
ANTHROPIC_DEFAULT_HAIKU_MODEL    CLAUDE_CODE_SUBAGENT_MODEL    CLAUDE_CODE_EFFORT_LEVEL
```

Если файла нет, он не читается или это невалидный JSON (`OSError` / `ValueError`), возвращается пустой словарь и работа идёт дальше — **сбой отката не должен уносить с собой весь запуск** (`env.py:62-63`, `:66-69`).

Позиция в коде такая: одалживается только ответ на вопрос «где искать token»; всё остальное из settings.json (правила разрешений, hook, настройки модели) не перенимается, поэтому обещание переносимости из `setting_sources=[]` не нарушается (`env.py:17-19`, `:59-61`). `install.sh:77` прямо рекламирует это как фичу: у кого на машине настроен Claude Code, тот вообще не увидит экрана конфигурации.

!!! warning "Текст ошибки в продукте противоречит реальному поведению"
    Когда учётные данные не найдены вообще, последняя строка печатаемой flower ошибки такая:

    ```text
    flower 不读 ~/.claude/settings.json —— 那是可移植性的代价。
    ```

    (`env.py:184-194`, сама строка — на `:192`; то же самое утверждение встречается в `.env.example:2`, `env.py:3-4`, `agent.py:10-12`.) **Истина — в коде: он читает.** `env.py:56-75` плюс `:109-111` явно читают эти два файла, а `install.sh:77` вообще подаёт это как преимущество. Этот текст на сегодня вводит в заблуждение — на машине, где настроен Claude Code, ваш token с большой вероятностью пришёл именно оттуда.

## Правила разбора `.env` {#env-解析}

Правила разбора настолько коротки, что их можно выучить наизусть (`env.py:95-107`, 13 строк): по строкам `strip`, пропускаются пустые строки, строки, начинающиеся с `#`, и строки без `=`; остальные режутся по **первому** `=` на key и value, к обеим частям применяется `strip`, а к value ещё раз `.strip("'\"")` — одинарные и двойные кавычки по краям срезаются безусловно, **парность не требуется**.

**Понимаются такие записи**:

| Запись | Результат |
|---|---|
| `KEY=VALUE` | нормально |
| `KEY = VALUE` | нормально — пробелы вокруг знака равенства срезаются |
| `KEY="VALUE"` / `KEY='VALUE'` | нормально — кавычки по краям срезаются |
| `KEY=a=b` | value равно `a=b` — режется по первому `=`, последующие знаки равенства остаются в значении как есть |
| `# комментарий` | вся строка пропускается |
| пустая строка | пропускается |

**А такие — не понимаются**. Ошибки не будет, вы молча получите неожиданное значение:

| Запись | Что получится на самом деле |
|---|---|
| `export KEY=VALUE` | ключом становится `export KEY`, у самого `KEY` значения по-прежнему нет |
| `KEY=value # пояснение` | value равно `value # пояснение` — комментарий в конце строки не отрезается |
| `KEY=$OTHER` | литерал `$OTHER`, подстановки переменных нет |
| многострочное значение (кавычки через несколько строк) | обрабатывается построчно, вторая строка не содержит `=` и пропускается целиком |

**Пустое значение занимает ключ.** Если `ANTHROPIC_AUTH_TOKEN=` встретится в файле с высоким приоритетом, `take()` выполнит `os.environ["ANTHROPIC_AUTH_TOKEN"] = ""`, и последующие файлы уже ничего не подставят, потому что «ключ существует» (`env.py:90-93`); а `check_credentials()` проверяет истинность, и пустая строка считается «не настроено» (`env.py:186`). **В итоге нет ни учётных данных, ни отката.** Не нужен ключ — удаляйте строку целиком, не оставляйте пустую.

## Цена переносимости {#可移植性}

Весь механизм — одна строка в `build_options()` (`agent.py:207`):

```python
"setting_sources": [] if portable else ["project"],
```

`portable=True` — значение по умолчанию у `Runtime`, и **в командной строке нет переключателя, чтобы это отключить**: отключить можно только через Python API, написав `Runtime(portable=False)`, тогда будет `["project"]`, то есть чтение проектного `.claude/`.

### Что изолировано

| Что изолировано | Последствие |
|---|---|
| Настройки в `~/.claude/` на хосте | Тамошние правила разрешений, hook, настройки модели не действуют. **Единственное исключение — учётные данные**, см. [одалживание](#借用) |
| Проектный `.claude/` | То же самое, читается только при `portable=False` |

Доменные возможности этим путём не идут — они распространяются вместе с репозиторием и загружаются через `plugins=[{"type": "local", "path": PLUGIN_DIR}]` (`agent.py:26`, `:210-212`), см. [развёртывание](deploy.md). Доменные инструкции же **добавляются поверх** родного системного промпта Claude Code, а не заменяют его (`agent.py:198-202`), поэтому специализация не покупается ценой потери общих способностей.

### Что брать с собой при переезде на другую машину

- **Учётные данные: один файл**. Достаточно скопировать `~/.config/flower/.env` или заново настроить его на новой машине. Без него не заработает ничего — ничто не наследуется автоматически.
- **Состояние преемственности: целиком каталоги**. `runs/` (база сессий, манифест, родословная) и `.flower/` (верстак).
- **Но пути должны совпадать**. В `lineage.json` хранится абсолютный путь рабочей области; если он не совпадает, файл считается отсутствующим, происходит молчаливый откат к новой сессии, **без ошибки** (`lineage.py:65-66`). Причина в том, что `project_key` в SDK выводится из пути рабочей области (`/`, `_`, `.` заменяются на `-`, `runtime.py:40-41`), и после переноса каталога старый `session_id` уже не находится.

## Раскладка на диске {#磁盘布局}

Один запуск flower пишет два дерева: `<run_dir>/` — учёт и сессии, `<workspace>/.flower/` — [верстак](glossary.md#工作台). По умолчанию оба оказываются в текущем каталоге, но **их база отсчёта разная**.

!!! warning "`runs/` следует за текущим каталогом, а не за `-w`"
    `-r/--run-dir` по умолчанию равен `"runs"`, и `Runtime` делает с ним `Path(run_dir).resolve()` (`runtime.py:93-94`) — относительно **текущего рабочего каталога**, а не относительно рабочей области, заданной через `-w`. Если запустить `flower -w /path/to/proj` из `~`, база сессий ляжет в `~/runs/`, а не внутрь проекта.

### `<run_dir>/` — по умолчанию `./runs/` {#run-dir}

```text
runs/
  sessions.db        SQLite, полный transcript (включая по одному на каждый subagent)
  manifest.json      манифест запуска: session_id / стоимость / повторы / причины отказов по каждому шагу, накапливается между процессами
  lineage.json       родословная: имя шага → session_id, по ней подхватывается повторный запуск в том же каталоге
  aside/             отдельный Runtime для вопросов оракулу, со своими sessions.db + manifest.json
  workbench/         только на пути run / once и только если задан -W
```

| Путь | Содержимое | Источник |
|---|---|---|
| `runs/sessions.db` | Полный transcript. Пишет его `PruningSessionStore`, три слоя политик — [ниже](#会话存储) | `runtime.py:109-112` |
| `runs/manifest.json` | JSON-массив, [манифест запуска](glossary.md#运行清单), **накапливающийся между процессами**. Поля — в таблице ниже | `runtime.py:532-533`, `:564-586` |
| `runs/lineage.json` | `{"workspace": "…", "woke": N, "steps": {"步骤名": "session_id"}}`. Сначала пишется `.tmp`, потом `replace` — атомарная замена | `lineage.py:31`, `:87-97` |
| `runs/aside/` | Отдельный Runtime для [оракула](glossary.md#旁路顾问). **Стоимость и родословная не смешиваются с основным манифестом** | `cli.py:632-634` |
| `runs/workbench/` | Расположение верстака по умолчанию при `Runtime(workbench=True)` — вне рабочей области. Путь `go` его не использует | `runtime.py:148-151` |

Каждая строка `manifest.json` — это `asdict(StepResult)` плюс две правки (`runtime.py:44-71`, `:579-582`):

| Поле | Тип | Значение |
|---|---|---|
| `step` | `str` | Имя шага. Четыре формы: `<名>`, `<名>#round<N>` (отправлен на переделку), `<名>#retry<N>` (обычный повтор), `<名>·判定#<N>` ([судья](glossary.md#判定者)) |
| `session_id` | `str \| None` | Последняя живая [сессия](glossary.md#会话) этого шага |
| `ok` | `bool` | Получилось или нет |
| `cost_usd` | `float` | Сколько стоил этот шаг |
| `num_turns` | `int` | Сколько было раундов |
| `text` | `str` | Итоговый ответ этого шага |
| `error` | `str \| None` | Причина отказа. При убийстве по SIGHUP / SIGTERM — `killed-by-signal` (`runtime.py:556-558`) |
| `started_at` / `ended_at` | `float` | Секунды epoch |
| `attempts` | `int` | Фактическое число попыток. `>1` означает, что были повторы |
| `errors` | `list[str]` | Причины всех предыдущих отказов. **Только здесь, модель их не видит** |
| `resumed` | `bool` | Подхвачено ли с точки обрыва через resume, а не начато заново |
| `retired` | `list[str]` | session_id, сожжённые при [handoff](glossary.md#换代) на этом шаге, по порядку |
| `context` | `int` | Реальный размер контекста, который видел [главный поток](glossary.md#主线程) в последнем раунде |
| `duration_s` | `float` | Дописывается вручную — это `@property`, и `asdict()` его не забирает |
| `run` | `str` | Метка текущего процесса `YYYYmmdd-HHMMSS-<6 位 hex>`. **Обязана быть уникальной для каждого экземпляра** |

Стратегия записи — **добавление, а не перезапись**: перед каждым сбросом на диск файл перечитывается заново, строки со своим `run` заменяются на актуальные, чужие строки остаются как есть (`runtime.py:564-586`). Поэтому при параллельном запуске нескольких flower в одном каталоге учёт не затирается.

Всё в `runs/` — чистые данные, их в любой момент можно разобрать офлайн через sqlite3 или [`tools/analyze_run.py`](https://github.com/ChenyuHeee/flower/blob/main/tools/analyze_run.py).

### `<workspace>/.flower/` — верстак {#工作台目录}

```text
.flower/
  INDEX.md      автоматически генерируемый индекс, вставляется в system prompt главного агента
  scripts/      скрипты, которые придётся запускать второй раз. Первая строка `# desc: одна фраза` попадает в индекс
  artifacts/    длинные результаты свыше 2000 символов: отчёты, данные, логи
  notes/        решения, фиксируемые между шагами
  spill/        крупные результаты инструментов, сброшенные на диск; имя файла = первые 16 знаков sha256 содержимого + `.txt`
```

Три подкаталога плюс индекс создаёт `Workbench` (`workbench.py:73-92`). `INDEX.md` идёт через `system_prompt.append` уровня сессии, и **subagent его не наследует** — поэтому правило «длинные результаты писать в `artifacts/`» обязан пересказать [координатор](glossary.md#协调者) в [задании](glossary.md#任务书), это единственный канал.

Путь `go` всегда создаёт в `notes/` следующее:

| Файл | Содержимое | Источник |
|---|---|---|
| `notes/需求.md` | Замороженный [бриф](glossary.md#需求确认书), четыре раздела: цель / критерии приёмки / границы / неизвестное и допущения | `brief.py:44-45`; `clarify.py:105` |
| `notes/目标.md` | Замороженные два раздела: цель / список проверок для вердикта | `workflow/goal.py:124` |
| `notes/问答记录.md` | Дописываемая запись всех вопросов и ответов, включая записи входящих «человек сказал сам». **В контекст не идёт, только архив** | `human.py:421-433` |
| `notes/交接-<步骤名>.md` | [Handoff-документ](glossary.md#交接书). Предыдущее поколение убирается в `notes/archive/交接/<步骤名>-<时间戳>.md` | `runtime.py:388-403` |
| `notes/archive/<YYYYmmdd-HHMMSS>/` | Архивируемые при `--new` / `/new` `lineage.json` + `需求.md` + `目标.md` (**перемещаются, не удаляются**) | `lineage.py:100-117` |

**При `--isolate` верстак переезжает за пределы репозитория**: `<родительский каталог workspace>/.flower-<имя workspace>/` (`starter.py:47-55`). worktree — приватная копия каждого агента, а верстак — общий слой между агентами, и общее нельзя класть внутрь приватной изгороди. В этом случае модели даются абсолютные пути (`workbench.py:69-71`, `:142-145`).

**У `spill/` два писателя с разными алгоритмами выбора места**:

| Кто пишет | Когда | Куда | Порог |
|---|---|---|---|
| `spill_guard` (hook `PostToolUse`) | **До** того, как результат инструмента попадёт в модель | `<корень верстака>/spill/` (`guard.py:130`) | `spill_threshold`, по умолчанию 4000 символов |
| `TrimPolicy` (при `load`) | При переигрывании истории перед resume | `<workspace>/.flower/spill/` — фиксированная строка относительно рабочей области (`trim.py:49`, `:303`) | `min_chars`, по умолчанию 2000 символов |

При раскладке по умолчанию это один и тот же каталог. Но когда верстак переезжает (`-W` кладёт его в `runs/workbench/`, `--isolate` — за пределы репозитория), пути расходятся: копия `TrimPolicy` всегда остаётся внутри рабочей области, потому что `Read` агента обязан до неё дотягиваться.

`spill_guard` подставляет не одну строку, а строку-указатель плюс **первые 400 символов** (`guard.py:132-140`). Вызовы, читающие сам сброшенный файл, пропускаются, иначе «нужен полный текст — прочитай его через Read» превращается в пустые слова: прочитанное снова превысит порог, снова уйдёт на диск, бесконечный цикл (`guard.py:155-170`).

### Структура таблиц в `sessions.db` {#sessions-db}

Три таблицы, DDL — в `stores/sqlite.py:27-51`:

```sql
CREATE TABLE entries (
    store_key TEXT NOT NULL,
    seq       INTEGER NOT NULL,
    uid       TEXT,
    payload   TEXT NOT NULL,
    PRIMARY KEY (store_key, seq)
);
CREATE UNIQUE INDEX entries_uid
    ON entries(store_key, uid) WHERE uid IS NOT NULL;
CREATE TABLE meta (
    store_key TEXT PRIMARY KEY,
    mtime     INTEGER NOT NULL,
    next_seq  INTEGER NOT NULL
);
CREATE TABLE summaries (
    project_key TEXT NOT NULL,
    session_id  TEXT NOT NULL,
    mtime       INTEGER NOT NULL,
    data        TEXT NOT NULL,
    PRIMARY KEY (project_key, session_id)
);
```

| Таблица | Что такое одна строка | Суть |
|---|---|---|
| `entries` | Одна запись transcript, `payload` — исходный JSON | `uid` — это `uuid` записи, он работает **ключом идемпотентности**: неудачный батч повторяется до 3 раз, и переигрывание не должно порождать дубликаты строк. Записи без `uuid` (заголовки, метки, признаки режима) не дедуплицируются, поэтому у уникального индекса есть `WHERE uid IS NOT NULL` |
| `meta` | Курсор одной сессии | `next_seq` — следующий номер, `mtime` — метка времени в миллисекундах и **строго монотонная** (`sqlite.py:72-79`): `list_sessions` и summary используют одни и те же часы, немонотонность заставит SDK ошибиться в определении свежести и уйти не по тому быстрому пути |
| `summaries` | Sidecar-сводка одного главного потока | **Участвует только основной transcript**, subagent-овые не считаются (`sqlite.py:122-123`) |

Устройство `store_key` (`sqlite.py:54-58`): `<project_key>/<session_id>`, у subagent дописывается ещё сегмент `subpath`. `project_key` SDK выводит из пути рабочей области — `/`, `_`, `.` заменяются на `-`.

Взглянем на реальный образец ([`human-test/HT002/runs/sessions.db`](https://github.com/ChenyuHeee/flower/blob/main/human-test/HT002/runs/sessions.db)):

```bash
sqlite3 runs/sessions.db "select store_key, next_seq from meta;"
```

```text
-Users-hechenyu-explore-test-ide/601c8c91-6c4b-4525-8a5f-295b99bf9515|37
-Users-hechenyu-explore-test-ide/47395075-bec7-466e-80cd-f4d60b360235|80
-Users-hechenyu-explore-test-ide/47395075-…/subagents/agent-a99a6ce30a5471f44|104
```

В этом файле 956 записей `entries`, 10 записей `meta` и 4 записи `summaries` — из 10 сессий 4 являются основными transcript, 6 принадлежат subagent, а число `summaries` в точности равно числу основных transcript.

## Три слоя хранилища сессий {#会话存储}

!!! note "Три слоя — это цепочка наследования, а не набор опций"
    `PruningSessionStore` наследует `TrimmingSessionStore`, который наследует `SqliteSessionStore`. `Runtime` **всегда** конструирует самый внешний класс (`runtime.py:109-112`), и в его параметрах нет точки входа для смены бэкенда. Способ «выключить какой-то слой» — выставить `enabled=False` у его объекта политики, а не подменять класс.

`append` (запись) всегда сбрасывает на диск всё целиком, не меняя ни символа. Три слоя влияют только на `load` (на ту копию, которая читается обратно и подаётся модели). Фактический порядок в `load` такой:

```text
SqliteSessionStore.load     читает всё из таблицы entries по seq
  → TrimmingSessionStore.expire()   результаты Bash с ограниченным сроком годности → заменяются на «устарело»
  → TrimmingSessionStore.trim()     старые крупные tool_result → сброс на диск + замена на указатель
    → PruningSessionStore.prune()   синтетические сообщения об ошибках / старые отклонённые вызовы → запись удаляется целиком, цепочка сшивается
```

| Слой | Класс | Что теряется | Критерий |
|---|---|---|---|
| 1 | `SqliteSessionStore` | Ничего не теряется | —— |
| 2 | `TrimmingSessionStore` | Тела крупных результатов инструментов, устаревшие результаты эфемерных команд | Объём + срок годности |
| 3 | `PruningSessionStore` | Мусор от обрывов связи, старые отклонённые вызовы | Ошибка это или нет |

Второй слой — это [обрезка](glossary.md#裁剪), третий — [отсечение](glossary.md#剪除): **обрезка выбрасывает по объёму и ценности, отсечение — по признаку «ошибка это или нет»**, не путайте. Полные сигнатуры — в [Python API](api.md).

### `SqliteSessionStore` — фундамент {#sqlite-store}

```python
SqliteSessionStore(path: str | Path)
```

Реализация на SQLite без внешних зависимостей. Чтобы перейти на Postgres / S3 / Redis, достаточно реализовать тот же протокол; в SDK есть готовый набор тестов на соответствие `claude_agent_sdk.testing.session_store_conformance`, которым это можно сразу проверить (`sqlite.py:1-8`).

Кроме методов протокола есть три **синхронных** запроса для собственных нужд flower:

| Метод | Возвращает | Для чего |
|---|---|---|
| `projects()` | `list[str]` | Реально существующие в базе `project_key`. SDK выводит его из cwd; перед запросом лучше уточнить через этот метод, а не гадать |
| `has_session(project_key, session_id)` | `bool` | Проверяет одну строку `meta`, payload не читает. Проверять до старта [преемственности](glossary.md#接续) — resume несуществующей сессии взорвётся уже после старта дочернего процесса, когда деньги и время уже потрачены |
| `last_context(project_key, session_id, scan=60)` | `int` | Насколько большой контекст видел последний раунд этой сессии. Сканирует с конца только последние 60 записей. Считаются `input_tokens` плюс оба `cache_*` — если смотреть только на первый, при попадании в кэш он близок к 0 и оценка будет сильно заниженной |

### `TrimmingSessionStore` + `TrimPolicy` / `EphemeralPolicy` {#trimming-store}

```python
TrimmingSessionStore(path, workspace, policy: TrimPolicy | None = None,
                     ephemeral: EphemeralPolicy | None = None)
```

Два ортогональных правила. `TrimPolicy` отвечает за **объём**:

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `keep_recent` | `int` | `20` | Последние N `tool_result` сохраняются в исходном виде — контекст, которым сейчас пользуются, обрезать нельзя |
| `min_chars` | `int` | `2000` | Короче этого не обрезается. Замена на указатель обошлась бы дороже по токенам |
| `spill_dirname` | `str` | `".flower/spill"` | Каталог архива, **относительно workspace**. Обязан быть внутри рабочей области, иначе `Read` агента до него не дотянется |
| `enabled` | `bool` | `True` | При `Runtime(trim=False)` (значение по умолчанию) равен `False` |

Обрезанное тело записывается как `<первые 16 знаков sha256>.txt`, а на его месте появляется `[工具结果已归档:N 字符。完整内容在 <路径>,需要时用 Read 读取]` (`trim.py:54-57`, `:308-317`).

`EphemeralPolicy` отвечает за **срок годности**: результаты вроде `git status`, `ls`, `ps` очень короткие и по объёму никогда под обрезку не попадут, но их корректность затухает со временем — `git status` двадцатираундовой давности не «бесполезен», он **вводит в заблуждение**.

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `enabled` | `bool` | `True` | Получается из `Runtime(ephemeral=…)`, **по умолчанию включено** |
| `keep_recent` | `int` | `6` | Последние N записей сохраняются в исходном виде. Намного меньше, чем 20 у `TrimPolicy`, — окно «свежести» у таких вещей изначально короткое |
| `max_chars` | `int` | `2000` | Что больше — уходит к `TrimPolicy` на архивирование, этим путём не идёт |
| `text` | `str` | `"[{cmd} 的结果已过期(第 {age} 轮前),当前状态可能已变。需要请重新执行]"` | Текст замены |

Действует только на результаты инструмента **Bash**, и команда должна попадать под `EPHEMERAL_CMD`. `Read` сюда не входит: содержимое файла от течения времени не искажается настолько, чтобы вводить в заблуждение, и оно вполне может быть основанием рассуждений модели (`trim.py:153-160`). Устаревшее содержимое **на диск не сбрасывается** — архивировать протухший `git status` бессмысленно, достаточно выполнить команду заново.

Решающая функция — `is_ephemeral(cmd)`, и она **одновременно является списком разрешений, возвращаемых координатору**: `delegate_guard(allow_glance=True)` использует ту же самую функцию (`trim.py:63-68`, `:128-150`). Эти два множества обязаны всегда совпадать: если команду пропустили, но не обрезаем — устаревший `git status` навсегда займёт место в контексте; если обрезаем, но не пропускаем — координатор ради одного `ls` отправит subagent, обменяв 4.3k стоимости запуска на несколько десятков символов. Добавить команду в белый список — значит сказать сразу обе эти фразы.

**Когда что использовать**:

- Хочется лишь, чтобы мусор от обрывов не попадал в контекст → делать ничего не нужно, `Runtime` по умолчанию уже использует `PruningSessionStore`. `trim=False` просто не обрезает крупные результаты, отсечение выполняется всё равно.
- Долгий запуск, вывод инструментов очень большой → `trim=True`. В CLI на пути `go` это уже включено по умолчанию, выключается через `--no-trim`.
- У [координатора](glossary.md#协调者) включён `glance=True` → `ephemeral` обязан оставаться включённым, обоснование — в предыдущем абзаце.

### `PruningSessionStore` + `PrunePolicy` {#pruning-store}

```python
PruningSessionStore(path, workspace, policy: TrimPolicy | None = None,
                    prune: PrunePolicy | None = None,
                    ephemeral: EphemeralPolicy | None = None)
```

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `drop_api_errors` | `bool` | `True` | Удаляет синтетические сообщения с `isApiErrorMessage=true` или `message.model == "<synthetic>"` |
| `neutralize_interrupts` | `bool` | `True` | У `tool_result` с `[Request interrupted …]` **заменяется тело, блок не удаляется** |
| `interrupt_text` | `str` | `"[上一轮在此处被中断,该工具结果未产生]"` | Текст замены для предыдущего пункта |
| `keep_denials` | `int` | `1` | Сохраняет последние N вызовов инструментов, отклонённых permission hook; более ранние удаляются **вместе с вызовом и результатом** |

`keep_denials` — единственный параметр конструктора `Runtime`, пробрасываемый на этот слой (`Runtime(keep_denials=N)`). Почему 1, а не 0: последний отказ — полезный сигнал, он не даёт модели в том же раунде многократно повторять одну и ту же заблокированную команду. **Больше не ставьте**: отклонённый вызов никогда не выполнялся, в его результате нет никакой информации, а на замерах он занимает 273 символа (93 знака текста отказа плюс 180 знаков исходной мёртвой команды), и он **вводит в заблуждение**: на замерах координатор, прочитав несколько «не использовать Bash напрямую», перестаёт пробовать даже разрешённый `git status` и просто говорит «Bash ограничен, отправлю агента посмотреть» (`prune.py:135-148`).

Три структурных красных линии, нарушение которых сразу даёт ошибку API:

1. **Сам блок `tool_result` обязан остаться**, менять можно только `content`. Пропажа одного — это «Missing Tool Result Block» (`trim.py:20-22`; `prune.py:79-92`).
2. **Записи `isCompactSummary` / `isMeta` трогать нельзя** — это единственная форма существования той истории, которая была сжата (`trim.py:179-181`).
3. **Удалив запись, обязательно подцепить её детей к её родителю.** transcript — односвязный список по `parentUuid`, harness идёт от листа назад, и где цепочка порвётся, там вся предшествующая история потеряется (`prune.py:95-122`). Поэтому `relink()` должна получить полный список, **включающий** удаляемые записи, а фильтрацию делает сама.

**В SQLite оригинал не меняется ни на символ** — три слоя влияют только на «ту копию, которая подаётся обратно модели» (`trim.py:18`; `prune.py:8`).

## Устойчивость к обрыву сети {#韧性}

Долгосрочный workflow работает часами, и сеть обязательно оборвётся хотя бы раз. Поведение по умолчанию скверное: в момент обрыва harness вставляет в transcript синтетическое сообщение assistant (`model="<synthetic>"`, `isApiErrorMessage=true`) с текстом `API Error: Can't reach the API server …`; оно становится листом сессии, и при последующем resume подаётся обратно как «то, что модель сказала в прошлой реплике», после чего модель считает, что обсуждает сетевой сбой; кроме того, оно просачивается в `StepResult.text` и по workflow уходит в prompt следующего шага (`resilience.py:1-22`).

Слой [устойчивости](glossary.md#韧性) делает три вещи, и ни одну нельзя убрать: проба, продолжение вместо перезапуска с нуля, ошибки не попадают в контекст.

### Параметры `Resilience` {#resilience}

| Параметр | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `enabled` | `bool` | `True` | Получается из `Runtime(resilience=…)` |
| `max_attempts` | `int` | `6` | Максимум попыток на один [шаг](glossary.md#步骤), **включая первую** |
| `base_delay` | `float` | `4.0` | Начальная точка экспоненциального отката, секунды |
| `max_delay` | `float` | `120.0` | Верхняя граница отката, секунды |
| `probe_timeout` | `float` | `5.0` | Таймаут одной пробы, секунды |
| `probe_interval` | `float` | `15.0` | Как часто пробовать при обрыве сети, секунды |
| `max_offline_wait` | `float` | `3600.0` | Сколько максимум ждать при обрыве. По умолчанию 1 час — если дольше, это обычно не дребезг, а настоящая авария |
| `retry_unknown` | `bool` | `True` | Повторять и при ошибках, которые не удалось классифицировать. Большинство неизвестных ошибок временные, а фатальные уже отсеяны отдельно |
| `resume_prompt` | `str` | `"上一轮在中途被打断,没有跑完。检查一下工作台里已经落盘的东西,从中断处接着做,不要重头来过。"` | Что говорится модели при продолжении |

Формула отката (`resilience.py:119-121`):

```python
min(base_delay * 2 ** (attempt - 1), max_delay) * (0.75 + random() * 0.5)
```

То есть джиттер `±25%`, чтобы в момент восстановления сети куча процессов не ломанулась одновременно. При значениях по умолчанию: 1-й откат — 4 секунды (фактически 3~5), 2-й — 8 секунд (6~10), начиная с 5-го — потолок 120 секунд (90~150).

### Стратегия пробы {#探针}

- **Пробуется host:port из `ANTHROPIC_BASE_URL`**, а не `api.anthropic.com` (`resilience.py:67-72`). При собственном шлюзе доступность второго ничего не говорит о доступности первого.
- **Только DNS плюс TCP-рукопожатие**: `getaddrinfo`, затем `connect_tcp`, затем немедленное закрытие. HTTP не отправляется, учётные данные не передаются, денег не стоит (`resilience.py:75-85`). Проба обязана быть бесплатной, иначе «при обрыве сети пробуем каждые 15 секунд» само становится аварией.
- Любой сбой считается недоступностью — не различается, упал ли DNS или TCP отказал.
- `wait_online()` висит и ждёт: соединение восстановилось — возвращает `True`, истёк `max_offline_wait` — возвращает `False`. При первой недоступности уведомляет одной строкой `<host>:<port> 不可达,等待恢复(最多 60 分钟)`, при восстановлении — ещё одной строкой `<host>:<port> 恢复,继续`, **между ними экран не засоряется** (`resilience.py:126-140`).

Проба учётных данных перед стартом — это другое: она действительно отправляет один `POST <BASE_URL>/v1/messages` с `max_tokens=16` и таймаутом по умолчанию 20 секунд (`env.py:126-181`). `max_tokens` **не ставьте в 1** — на замерах модели с принудительной цепочкой рассуждений не помещают туда даже размышление, сервер мучается до 30 секунд и только потом отвечает; при 16 уходит всего 3.6 секунды (`env.py:120-123`).

### Классификация ошибок {#错误分类}

`classify(text)` возвращает один из трёх вариантов. **Сначала проверяется фатальность**: в тексте про 401 и подобное часто попадаются слова вроде «connection», и при обратном порядке можно ждать вечно (`resilience.py:53-64`).

| Класс | Что попадает (регулярные выражения — в `resilience.py:37-50`) | Поведение |
|---|---|---|
| `fatal` | `400` `401` `403` `404`, `invalid api key`, `authentication`, `unauthorized`, `permission denied`, `invalid_request`, `credit balance`, `quota exceeded`, `budget`, `max_turns`, `CLINotFound` | Немедленная остановка без повторов. Сколько ни повторяй — результат тот же, и каждый раз стоит денег |
| `transient` | `ENOTFOUND` `EAI_AGAIN` `ECONNRESET` `ECONNREFUSED` `ETIMEDOUT` `EPIPE` `EHOSTUNREACH` `ENETDOWN`, `socket hang up`, `fetch failed`, `Can't reach the API server`, `429` `500` `502` `503` `504` `529`, `overloaded`, `rate limit`, `timeout`, `service unavailable` | Ждать возвращения сети, затем продолжить через resume |
| `unknown` | Ничего не совпало | При `retry_unknown=True` (по умолчанию) тоже повторяется |

Разделение на повторяемое и неповторяемое — суть этого слоя: **сетевой дребезг надо переждать, ошибку учётных данных надо остановить немедленно**. Ждать при обрыве сети правильно; ждать при неверно записанном key — просто жечь время.

### Что не пускается в контекст {#错误不进上下文}

1. **Синтетические сообщения об ошибках.** `PruningSessionStore` при `load` удаляет их целиком и пересшивает `parentUuid` (`prune.py:27-32`, `:191-195`). **В SQLite они сохраняются как есть**, просто не подаются обратно.
2. **В потоке событий это `kind="error"`, а не `"text"`**, поэтому оно не попадает в `StepResult.text`, а значит и не уходит по workflow в prompt следующего шага (`resilience.py:17-18`).
3. **`resume_prompt` намеренно не содержит никаких деталей ошибки.** Модели нужно знать «тебя прервали, продолжай», а не то, был это `ENOTFOUND` или `503`. **Это относится к логам, а не к контексту** (`resilience.py:112-113`). Логи смотрите в поле `errors` файла `manifest.json`.

Продолжение вместо перезапуска: к моменту сбоя `session_id` уже получен, через resume работа подхватывается с точки обрыва, и предыдущие траты не пропадают зря.
