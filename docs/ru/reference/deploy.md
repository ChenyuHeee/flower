# Развёртывание и расширение

Чтобы перенести flower куда-то ещё, надо решить три вопроса: контейнер (огородить неограниченный Bash и заодно проверить утверждение «без CLI»),
[plugin](glossary.md#plugin) (предметные знания едут вместе с репозиторием и не смотрят на то, что установлено на хосте), сайт документации (push в `main` —
и он публикуется сам, `install.sh` висит на домене Pages). Три раздела независимы, читайте по необходимости.

## 1. Контейнер

### Зачем контейнер

**Во-первых, чтобы огородить.** У работающего [исполнителя](glossary.md#执行者) **неограниченный Bash** — белый список Bash во flower
(`delegate_guard`) действует только на [главный поток](glossary.md#主线程), а отправленный на задачу должен уметь запускать тесты, так что это сделано намеренно.
В контейнер монтируется только каталог вашего проекта, исходники фреймворка лежат внутри образа в `/opt/flower`, остальное на хосте не видно.

**Во-вторых, это сама по себе проверка ограничения [переносимости](glossary.md#可移植).** В образе нет Claude Code CLI,
нет Node, только Python и `claude-agent-sdk` — запросы уходят через нативный бинарник, поставляемый в wheel.
Если здесь всё запускается, то «без CLI» — не слова на бумаге.

Проверено на практике (2026-09-06, macOS 15 / arm64 / colima + docker 28.4.0):

| Что проверялось | Результат |
|---|---|
| Есть ли CLI в образе | `claude`, `node`, `npm`, `npx` — **ни одного нет** |
| Встроенный бинарник | `\177ELF` (207M) |
| Реальный запрос | отправлен через `cloud.infini-ai.com/maas` и получен ответ, `$0.1741 / 1 раунд` (это и есть нижняя планка одного раунда для Opus 5 + окно 1M) |
| Владелец файлов | файл, записанный в `/work` внутри контейнера, на хосте принадлежит `hechenyu:staff` — отображение верное |
| Видимость хоста | в контейнере `ls /Users` → `No such file or directory` |

### Что установлено в образе

Базовый образ `python:3.13-slim`, поверх apt ставит всего три пакета. У каждого есть причина:

| Что ставим | Зачем |
|---|---|
| `python:3.13-slim` | Нужен только Python ≥ 3.10. Ни Node, ни claude CLI не ставим |
| `git` | `--isolate` выдаёт каждому [subagent](glossary.md#subagent) отдельный worktree |
| `ca-certificates` | HTTPS до шлюза |
| `libstdc++6` | Бинарник из SDK — однофайловая сборка Bun, на Linux он нужен; в slim-образе его нет |

Исходники фреймворка попадают в образ через `COPY`, **не через bind mount** — поэтому агент внутри контейнера не может дотянуться до исходников фреймворка на хосте:

| Путь в образе | Содержимое | Откуда |
|---|---|---|
| `/opt/flower` | `pyproject.toml`, `flower/`, `examples/`, здесь же выполняется `pip install .` | `COPY` |
| `/work` | Рабочий каталог (`WORKDIR`), в рантайме сюда монтируется `$PWD` хоста | `docker run -v` |

Точка входа — `ENTRYPOINT ["flower"]`, `CMD` пустой: запуск контейнера без аргументов уходит в интерактивный ввод
(он спрашивает, что вы хотите сделать), а не печатает `--help`. Так не приходится брать фразу-запрос в кавычки в shell.

### Почему нельзя примонтировать `.venv` хоста

SDK выпускает wheel под платформу, и встроенный бинарник платформозависим:

```text
хост       claude_agent_sdk-0.2.152-py3-none-macosx_11_0_arm64.whl
           → _bundled/claude — это Mach-O 64-bit arm64, 191M
контейнер  claude_agent_sdk-0.2.152-py3-none-manylinux_2_17_aarch64.whl
```

Примонтированный не заработает, поэтому образ обязан делать `pip install` сам. С другой стороны, это и есть доказательство переносимости: один и тот же
`pyproject.toml`, при смене платформы меняется нативный бинарник, а код фреймворка не меняется ни на строку.

### Два скрипта

| Скрипт | Что делает |
|---|---|
| [`docker/build`](https://github.com/ChenyuHeee/flower/blob/main/docker/build) | Собирает образ. `cd` в корень репозитория, `docker build -f docker/Dockerfile -t flower-box .`; при `FLOWER_MIRRORS=1` (по умолчанию) сначала тянет `python:3.13-slim` из зеркала registry и делает retag, а также передаёт `--build-arg` для pip / apt |
| [`docker/flowerbox`](https://github.com/ChenyuHeee/flower/blob/main/docker/flowerbox) | Один запуск. Проверяет файл с учётными данными → проверяет, монтируется ли `$PWD` → определяет наличие TTY → `docker run` |

Переключатели `docker/build` — все через переменные окружения:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `FLOWER_IMAGE` | `flower-box` | Тег образа |
| `FLOWER_MIRRORS` | `1` | `0` = не подменять ни одного зеркала, всё тянуть с апстрима |
| `FLOWER_REGISTRY` | `dockerproxy.net` | Отсюда тянется базовый образ и переименовывается в `python:3.13-slim`, чтобы `FROM` попал в локальный |
| `FLOWER_PIP_INDEX` | `https://mirrors.aliyun.com/pypi/simple/` | Передаётся в `--build-arg PIP_INDEX_URL` |
| `FLOWER_APT_MIRROR` | `mirrors.ustc.edu.cn` | Передаётся в `--build-arg APT_MIRROR` |

Последние три работают только при `FLOWER_MIRRORS=1` — ветка `FLOWER_MIRRORS=0` вообще не задаёт build-arg.

`docker/flowerbox` знает две:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `FLOWER_HOME` | На уровень выше самого скрипта (то есть корень репозитория) | Где искать `.env`. Если `$FLOWER_HOME/.env` не найден — выход с кодом 1 |
| `FLOWER_IMAGE` | `flower-box` | Какой образ запускать |

`FLOWER_HOME` выводится из положения самого скрипта, путь не зашит — поэтому репозиторий можно клонировать куда угодно.

### Запуск

```bash
docker/build                       # достаточно один раз
cd ~/любой-каталог-проекта          # обязательно внутри $HOME, см. границы монтирования ниже
/path/to/flower/docker/flowerbox   # без аргументов → он спросит, что делать, кавычки не нужны
```

Если сеть до pypi.org / Docker Hub в порядке, сборка запускается так:

```bash
FLOWER_MIRRORS=0 docker/build
```

Аргументы `flowerbox` полностью совпадают с `flower` — он подставляет `"$@"` как есть после `ENTRYPOINT`.
`--clarify-only`, `--asks N`, `--timeout секунды`, `--isolate`, `-v` — всё передаётся, полная таблица в [командной строке](cli.md):

```bash
cd ~/proj
/path/to/flower/docker/flowerbox --clarify-only -v
/path/to/flower/docker/flowerbox "сделай мне X"
```

Реально выполняется вот эта строка (`-t` добавляется только при наличии TTY, см. ниже):

```bash
docker run -i $TTY --rm \
    --env-file "$FLOWER_HOME/.env" \
    -v "$PWD:/work" \
    -w /work \
    "$IMAGE" "$@"
```

### Границы монтирования и персистентность

```text
хост $PWD  ──монтируется──>  /work       ← агент работает здесь, результаты остаются на хосте
в образе                     /opt/flower ← исходники фреймворка, **не смонтированы**, до хоста не достать
```

Поэтому запускать из подкаталога внутри репозитория вроде `flower/human-test/HT001` тоже безопасно: смонтирован только `HT001`,
исходники фреймворка в зону монтирования не попадают.

| Что | Останется после выхода? | Почему |
|---|---|---|
| Всё под `$PWD` хоста, включая `runs/` и [верстак](glossary.md#工作台) `.flower/` | Останется | Это и есть тот каталог, который смонтирован как `/work` |
| Записанное по другим путям внутри контейнера | Не останется | `--rm`, контейнер удаляется при выходе |
| Учётные данные | В слои образа не попадают | Идут через `--env-file`; `.env` исключён в `.dockerignore`, так что даже `COPY . .` его не затащит |

!!! danger "Каталог проекта должен быть внутри `$HOME`, иначе результаты молча пропадут"
    **colima по умолчанию монтирует в VM только `$HOME`** (`mount | grep virtiofs` → `mount0 on /Users/<вы>`).
    Если запускать где-нибудь в `/tmp`, `-v` создаст внутри VM **пустой каталог**, и записанное туда хост никогда не увидит,
    **причём без единой ошибки** — результаты, [бриф](glossary.md#需求确认书), `runs/` — всё потеряно. Наступали:
    один прогон `once` отработал, $0.17 потрачены, а `runs/` на хосте просто нет.

    Сейчас `flowerbox` такое перехватывает: если `$PWD` внутри `$HOME` — сразу пропускает; если нет — пишет в `$PWD`
    файл-пробу и поднимает контейнер с `test -f /work/<проба>` (при настроенных дополнительных монтированиях проверка тоже проходит). Не прошла — выход с кодом 1
    и подсказка `colima start --mount '<путь>:w'`. Проба поднимает контейнер, так что сначала нужен `docker/build`.

### Учётные данные

Идут через `docker run --env-file`, **в слои образа не попадают**. `flowerbox` читает `$FLOWER_HOME/.env`,
по умолчанию это `.env` в корне репозитория:

```bash
cp .env.example .env       # впишите token; .env уже в gitignore
```

Учтите: `flower setup` пишет в `~/.config/flower/.env`, и **этот путь `flowerbox` не смотрит**.
Если уже настроено через `setup` и копировать второй раз не хочется — укажите туда `FLOWER_HOME`:

```bash
FLOWER_HOME=~/.config/flower /path/to/flower/docker/flowerbox
```

Имена ключей, приоритеты и как заполнять шлюз — см. [конфигурацию](config.md).

!!! warning "Без TTY вопросы висят до `--timeout`"
    `flowerbox` добавляет `-t` только при `[ -t 0 ]` — `docker run -t` в pipe / CI сразу ругается
    «the input device is not a TTY»; `-i` нужен всегда, иначе stdin вообще не пройдёт.

    Ответы на вопросы идут со стандартного ввода. Без TTY `input()` на первом же вызове бросает `EOFError` → текущий вопрос считается
    «ввод закрыт» и пропускается, а **поток ответов при этом просто завершается**, так что второй вопрос уже никто не примет, и остаётся только
    ждать до конца `--timeout` (по умолчанию 1800 секунд). Для работы без присмотра нужно явно `--timeout 0`. Обнаружив отсутствие TTY, скрипт
    сначала печатает предупреждающую строку.

### git submodule

В `.gitmodules` всего одна запись:

| path | url | Что это |
|---|---|---|
| `human-test/HT001` | `https://github.com/ChenyuHeee/cppide.git` | Репозиторий кода, **произведённый** тем самым запуском [HT001](../cases/ht001.md), хранится для архива |

Обычный `git clone` его не тянет, `human-test/HT001` остаётся пустым каталогом (в `git submodule status` такое состояние обозначено
ведущим `-`). Нужно ли с ним что-то делать:

| Что вы хотите | Нужна ли инициализация |
|---|---|
| Запускать flower, собирать образ | **Нет.** `.dockerignore` исключает `human-test/`, да и `Dockerfile` изначально `COPY`-ит только `pyproject.toml` / `flower` / `examples` |
| Локально полистать код, произведённый HT001 | Да: `git submodule update --init human-test/HT001` или сразу `git clone --recurse-submodules` |

### Сеть в Китае: откуда вся эта куча подмен зеркал

Когда это всё ставится за файрволом, узкое место — не полоса пропускания, а международные каналы. `docker/build` по умолчанию уже подменяет всё, что нужно,
а `FLOWER_MIRRORS=0` отключает это одним движением. Ниже — измерения и обоснование четырёх подмен; если у вас с сетью нет такой проблемы, читать не нужно.

??? note "Таблица измеренных скоростей и четыре подмены (2026-09-06, macOS/arm64)"

    | Источник | Скорость |
    |---|---|
    | `pypi.org` (индекс) | 32 KB/s |
    | `files.pythonhosted.org` (файлы пакетов) | **284 B/s** |
    | `github.com` (release asset напрямую) | 22 KB/s |
    | `cloud-images.ubuntu.com` | 382 B/s |
    | `deb.debian.org` | 32 KB/s |
    | `ports.ubuntu.com` (внутри VM) | 26 KB/s |
    | `download.docker.com` | **не подключается** (HTTP 000); внутри VM 4 KB/s |
    | `mirrors.tuna.tsinghua.edu.cn` | **не подключается** |
    | `mirrors.aliyun.com/pypi` (**файлы пакетов**) | 1.4 MB/s (хост) / 152 KB/s (внутри VM) |
    | `mirrors.ustc.edu.cn/ubuntu-cloud-images` | **28 MB/s** |
    | `mirrors.ustc.edu.cn/ubuntu-ports` (внутри VM) | 1.95 MB/s |
    | `mirrors.ustc.edu.cn/debian` | 435 KB/s |
    | `ghfast.top` (прокси GitHub) | **2.5 MB/s** |
    | `gh-proxy.com` (прокси GitHub) | 1.5 MB/s |
    | `dockerproxy.net` (прокси Docker Hub) | Работает (сразу отдаёт manifest) |

    Измеряя, не принимайте **страницу индекса** за файл пакета: у страницы `mirrors.aliyun.com/pypi/simple/` — 7.4 MB/s,
    а у настоящего wheel на 95.9 MB — всего 1.4 MB/s (внутри VM 152 KB/s — пользовательская сеть colima съедает часть).
    Оценивайте время по цифрам для файлов пакетов.

    **Точка подмены 1 — образ VM для colima.** colima использует не обычный Ubuntu cloud image, а свой
    кастомный образ **с предустановленным docker** (release asset из `abiosoft/colima-core`), поэтому при поднятии VM
    не нужно ставить docker через apt — и недоступный `download.docker.com` обходится стороной. Скачайте образ сами и скормите через `--disk-image`:

    ```bash
    A=https://github.com/abiosoft/colima-core/releases/download/v0.9.0-2/ubuntu-24.04-minimal-cloudimg-arm64-docker.qcow2
    mkdir -p ~/.colima/images
    curl -sSL -C - -o ~/.colima/images/colima-arm64-docker.qcow2 "https://ghfast.top/$A"
    # Проверка: digest берём из GitHub API. Не пропускайте — это то, что будет крутиться как VM
    curl -sSL https://api.github.com/repos/abiosoft/colima-core/releases/tags/v0.9.0-2 \
      | python3 -c "import json,sys;[print(a['digest'],a['name']) for a in json.load(sys.stdin)['assets'] if a['name'].endswith('arm64-docker.qcow2')]"
    shasum -a 256 ~/.colima/images/colima-arm64-docker.qcow2

    colima start --disk-image ~/.colima/images/colima-arm64-docker.qcow2 \
                 --cpu 4 --memory 6 --disk 20
    ```

    Прокси иногда обрывает поток (на практике curl 56), достаточно несколько раз перезапустить с докачкой `-C -`.

    **Точка подмены 2 — apt внутри VM.** Даже с образом, где docker предустановлен, boot-скрипт lima
    `30-install-packages.sh` всё равно один раз запускает `apt-get update`, чтобы поставить `rsync` —
    он идёт в `ports.ubuntu.com` (26 KB/s) и `download.docker.com` (4 KB/s), и это виснет на десятки минут.

    Что делать (**сначала прочитайте `/mnt/lima-cidata/boot.sh`, потом действуйте**: на упавший boot-скрипт он выдаёт лишь `WARNING` +
    `CODE=1` и продолжает, а в конце **обязательно** пишет `/run/lima-boot-done`, так что уронить этот шаг безопасно):

    ```bash
    export LIMA_HOME=~/.colima/_lima
    limactl shell colima -- sudo sh -c '
      cat > /etc/apt/sources.list.d/ubuntu.sources <<EOF
    Types: deb
    URIs: https://mirrors.ustc.edu.cn/ubuntu-ports/
    Suites: noble noble-updates noble-backports noble-security
    Components: main restricted universe multiverse
    Signed-By: /usr/share/keyrings/ubuntu-archive-keyring.gpg
    EOF
      sed -i "s|https://download.docker.com|https://mirrors.ustc.edu.cn/docker-ce|g" \
          /etc/apt/sources.list.d/docker.list
      pkill -f "apt-get update"          # boot.sh дойдёт до конца и запишет метку завершения
    '
    # colima start после этого нормально завершится; затем доставляем rsync (теперь 1.95 MB/s)
    limactl shell colima -- sudo sh -c 'apt-get update -q && apt-get install -y -q rsync'
    ```

    Заодно добавьте `127.0.0.1 lima-colima` в `/etc/hosts` внутри VM, чтобы убрать поток предупреждений
    `sudo: unable to resolve host`.

    **Точка подмены 3 — базовый образ.** `docker/build` сначала тянет `python:3.13-slim` с `dockerproxy.net`
    и делает retag, чтобы `FROM` в Dockerfile попал в локальный образ. На практике `dockerproxy.net` сразу отдаёт manifest
    (HTTP 200); `docker.1ms.run` / `docker.m.daocloud.io` возвращают 401, `hub.rat.dev` — 302,
    `docker.xuanyuan.me` — 403.

    **Точка подмены 4 — apt и pip внутри контейнера.** `--build-arg APT_MIRROR=mirrors.ustc.edu.cn`
    (`deb.debian.org` 32 KB/s → USTC 435 KB/s),
    `--build-arg PIP_INDEX_URL=https://mirrors.aliyun.com/pypi/simple/`. Учтите: `PIP_INDEX_URL` — это одновременно
    и переменная окружения, которую понимает сам pip, так что достаточно объявить `ARG`, и pip в RUN её подхватит —
    без явного `--index-url` тоже работает.

    Разовая подготовка (при описанных выше условиях сети) занимает около 25 минут, основное время — образ VM на 364 MB и wheel SDK
    на 95.9 MB. После этого `flowerbox` стартует за секунды.

## 2. plugin {#plugin}

### Что это

**Пакет предметных возможностей**, который едет вместе с репозиторием. Код фреймворка не содержит никаких предметных знаний, все предметные знания лежат в каталоге
`plugin/` в корне репозитория и вместе с кодом клонируются, ревьюятся и тегируются.

Проводка на стороне SDK — две строки в `build_options()` в
[`flower/core/agent.py`](https://github.com/ChenyuHeee/flower/blob/main/flower/core/agent.py):

```python
PLUGIN_DIR = Path(__file__).resolve().parent.parent.parent / "plugin"
...
if use_plugin and PLUGIN_DIR.is_dir():
    opts["plugins"] = [{"type": "local", "path": str(PLUGIN_DIR)}]
```

Вместе с `setting_sources=[]` (о нём отдельно ниже) это и есть причина, по которой flower одновременно [переносим](glossary.md#可移植)
и «понимает вашу предметную область»: он не спрашивает, что установлено на хосте, а признаёт только этот один каталог, привезённый в репозитории.

### Раскладка каталогов

| Путь | Что лежит | Когда срабатывает | Кто решает |
|---|---|---|---|
| `plugin/.claude-plugin/plugin.json` | Идентичность пакета: `name`, `description`, `version`, `author` | Читается один раз при загрузке | — |
| `plugin/skills/<name>/SKILL.md` | Предметные знания, загружаются по необходимости | **Вероятностно** — используется, если модель сочла релевантным | Модель |
| `plugin/agents/<name>.md` | subagent, отдельное окно контекста | Модель делегирует, либо явно указано в [workflow](glossary.md#流程) | Модель / вы |
| `plugin/hooks/hooks.json` | Перехват вызовов инструментов | **Детерминированно** — совпало, значит выполнилось | Код |
| `plugin/.mcp.json` | Подключение внешних инструментов | Регистрируется как инструмент, наравне со встроенными | Модель |

**Разница между вероятностным и детерминированным — ключ к выбору, а не разница в формулировках:**

- skill — это **знание, лежащее рядом**. Модель видит его `description` и читает его, только если сочтёт релевантным текущей задаче.
  Оценку релевантности делает модель, поэтому одна и та же фраза, запущенная дважды, может один раз задействовать skill, а другой раз нет.
- hook — это **код**. Совпало событие — выполнился, независимо от того, хочет ли этого модель и знает ли она о нём. Собственные
  [сброс на диск](glossary.md#落盘) и [изоляция](glossary.md#隔离) во flower сделаны как hook именно потому, что они не могут работать «иногда».

Поэтому критерий один: **это обязано происходить каждый раз?** Обязано — пишите hook. Просто «полезно знать» —
пишите skill. Сделать обязательное skill'ом — значит поставить дисциплину в зависимость от одного решения модели.

Сейчас в репозитории в `plugin/` есть только две вещи: `.claude-plugin/plugin.json` и `skills/example/SKILL.md`.
`agents/`, `hooks/`, `.mcp.json` **пока не существуют** — нужны, создавайте сами, имена каталогов строго как в таблице выше.

### Как написать skill: полный пример

Возьмём «генерацию release notes» — с нуля до подтверждения, что оно работает.

**Шаг первый: создать каталог.** Имя каталога — это имя skill, оно должно совпадать с `name` во frontmatter.

```bash
mkdir -p plugin/skills/release-notes
```

**Шаг второй: написать `plugin/skills/release-notes/SKILL.md`.** Имя файла обязано быть `SKILL.md`, заглавными.
Формат — YAML frontmatter + Markdown-текст, во frontmatter два поля:

| Поле | Назначение |
|---|---|
| `name` | Идентификатор skill. Совпадает с именем каталога |
| `description` | **Выберет модель его или нет — зависит только от этой строки**. Пишите «когда это надо применять», а не «что это такое» |

Минимальный файл, который можно использовать как есть:

````markdown
---
name: release-notes
description: Использовать при подготовке release notes. Когда пользователь говорит «напиши release notes», «что изменилось в этой версии», «релиз».
---

# Release notes

## Откуда брать материал

```bash
git describe --tags --abbrev=0        # предыдущий tag
git log --oneline <предыдущий tag>..HEAD   # коммиты этой версии
```

## Формат вывода

Три раздела, каждый — маркированный список, по строке на пункт; писать изменения, заметные пользователю, без внутреннего рефакторинга:

- **Добавлено** — что теперь можно делать из того, что раньше было нельзя
- **Исправлено** — что починили, симптом одной фразой
- **Несовместимо** — что придётся править при обновлении. Если нечего — раздел не пишем вовсе

## Границы

- Номер версии не выдумывать, читать из поля `version` в `pyproject.toml`.
- Если непонятно, заметен ли конкретный коммит пользователю, — перечислить и спросить, не решать за пользователя.
````

Для текста нет обязательного формата — это просто кусок текста, который попадёт в контекст. Ориентируйтесь на
[`plugin/skills/example/SKILL.md`](https://github.com/ChenyuHeee/flower/blob/main/plugin/skills/example/SKILL.md):
внятно описать **когда применять**, **шаги**, **каким должен быть результат**, **где границы** — полезнее, чем сваливать фоновые знания.

**Шаг третий: убедиться, что он загружен.** Проверяем ровно одну достоверную вещь — есть ли вообще каталог:

```bash
cd /path/to/flower
python3 -c "from flower.core.agent import PLUGIN_DIR; print(PLUGIN_DIR, PLUGIN_DIR.is_dir())"
```

Только вывод `/path/to/flower/plugin True` означает, что в `build_options()` тот самый `if` сработает.
Вывод `False` означает, что не загружено, и **в рантайме ошибки не будет** — см. предупреждение ниже.

**Не считайте проверкой «запустить фразу и посмотреть, вызвался ли skill `example`».** skill вероятностен: если модель его не вызвала,
это может значить и что он не установлен, и что она просто не сочла его нужным для текущей задачи — этот сигнал не различает два случая. К тому же
`build_options()` никогда не задаёт сессионную опцию SDK `skills=`, и попадут ли skill'ы из plugin в список доступных
координатору — на практике не проверялось. `True`/`False` из команды с `PLUGIN_DIR` выше — достоверны, пользуйтесь ими.

Чтобы поимённо включить конкретному [исполнителю](glossary.md#执行者) нужные skill'ы, используйте `worker(..., skills=[...])`
([`flower/core/roles.py`](https://github.com/ChenyuHeee/flower/blob/main/flower/core/roles.py));
имена берутся из поля `name` в `SKILL.md`, SDK также принимает квалифицированную запись вида `имя-плагина:имя-skill`.

!!! warning "В установленном flower нет `plugin/` — ни при одном из трёх способов установки"
    `PLUGIN_DIR` — это три уровня вверх от `flower/core/agent.py` и затем `plugin/`. При запуске из checkout исходников это `plugin/` в корне
    репозитория; но в wheel пакуется только каталог `flower` (в `pyproject.toml`:
    `[tool.hatch.build.targets.wheel] packages = ["flower"]`), и после установки в site-packages
    `site-packages/plugin` не существует, `PLUGIN_DIR.is_dir()` ложно — **молча пропускается, без ошибки и без предупреждения**.

    **Это не проблема контейнера, охват гораздо шире.** Каждый путь в `install.sh` — `uv tool install`,
    `pipx install`, самонастройка uv с последующей установкой через uv и запасной `pip install --user` — ставит wheel.
    То есть **у flower, установленного одной командой, пакет предметных возможностей всегда молча не работает**. Контейнер — лишь частный случай той же проблемы:
    `docker/Dockerfile` копирует только `pyproject.toml`, `flower/`, `examples/`, а `plugin/` в образ не попадает.

    Зафиксировано в [issue #15](https://github.com/ChenyuHeee/flower/issues/15). После установки сначала прогоните ту самую команду с
    `PLUGIN_DIR`: вывод `False` значит, что в этой установке пакета предметных возможностей нет. Чтобы им пользоваться,
    сейчас остаётся только запуск из checkout исходников.

### Почему `setting_sources=[]` вынуждает предметные знания идти через plugin

В той же функции есть ещё строка:

```python
"setting_sources": [] if portable else ["project"],
```

По умолчанию в SDK стоит `None` = читать все три источника: `~/.claude/settings.json` (пользовательский),
`.claude/settings.json` (проектный), `.claude/settings.local.json` (локальный). flower по умолчанию передаёт `[]`,
то есть **выключает их все**.

| | Читается? | Последствие |
|---|---|---|
| `~/.claude/` (хост) | Нет | Поведение одинаково на любой машине, результат не меняется из-за «а у меня тут настроено» |
| Проектный `.claude/` | Нет | Всё, что лежит в `.claude/skills/`, `.claude/agents/`, под flower **не работает ни в одном пункте** |
| `plugin/` | Да | Путь зашит в коде, едет вместе с репозиторием |
| Учётные данные | Не по этому каналу | Нужен свой `.env`; блоки `env` в `~/.claude/settings.json` и `settings.local.json` служат лишь последним запасным вариантом и **берут только 9 ключей учётных данных**, см. [конфигурацию](config.md) |

То, что `.claude/` не работает, — **не забытая настройка, а определение этого ограничения**: пока читается хотя бы один байт с хоста,
«одинаковое поведение на любой машине» не выполняется. Поэтому у предметных знаний остаётся один канал — `plugin/`, едущий с репозиторием.

Два переключателя (оба в `build_options()`, значения по умолчанию — переносимый набор):

| Параметр | По умолчанию | Что будет, если изменить |
|---|---|---|
| `portable` | `True` | Передать `False` → `setting_sources` становится `["project"]`, начинает читаться проектный `.claude/` (со стороны SDK: чтобы читался `CLAUDE.md`, нужен `"project"`). Переносимость при этом теряется |
| `use_plugin` | `True` | Передать `False` → `plugin/` не подключается вовсе, предметные возможности целиком на `AgentSpec.instructions` |

Попутно: `instructions` идут через [append](glossary.md#叠加) (`append` у `system_prompt`),
и с plugin это два разных канала — первое присутствует в контексте каждый раунд, второе загружается по необходимости. Короткие обязательные правила — в `instructions`,
длинные и изредка нужные знания — в skill.

## 3. Сайт документации

Сайт, который вы читаете, собран на mkdocs-material, исходники лежат в `docs/` в репозитории, push в `main` — и он публикуется сам.

| Звено | Что это |
|---|---|
| Конфигурация | `mkdocs.yml`, `docs_dir: docs` |
| Многоязычность | `mkdocs-static-i18n`, `docs_structure: folder` — `docs/zh/`, `docs/en/`… язык по умолчанию `zh` |
| Зависимости | `docs-requirements.txt` (версии зафиксированы). **Не** тот extra `docs` из `pyproject.toml` — CI ставит первый |
| Сборка | `mkdocs build --strict`. Битые внутренние ссылки и nav, указывающий на несуществующие страницы, сразу валят сборку, а не публикуют молча 404 |
| Редиректы | `hooks/redirects.py`, **после** сборки пишет заглушки с meta-refresh по итоговым URL, направляя старые плоские адреса (`/start/`, `/workflow/`, `/case-ht001/`…) на новые места |
| Деплой | `.github/workflows/docs.yml` → `actions/upload-pages-artifact@v3` + `actions/deploy-pages@v4`, публикация на GitHub Pages |

Локальная правка документации:

```bash
pip install -r docs-requirements.txt
mkdocs serve                  # локальный предпросмотр
mkdocs build --strict         # прогнать перед коммитом, та же команда, что в CI
```

CI срабатывает на push в `main` **и** при попадании изменений в эти пути; кроме того, можно вручную запустить
`workflow_dispatch` на странице Actions:

```text
docs/**  mkdocs.yml  hooks/**  docs-requirements.txt  install.sh  .github/workflows/docs.yml
```

### Почему `install.sh` раздаётся с Pages

В конце шага сборки есть строка:

```yaml
- run: cp install.sh site/install.sh
```

Скрипт установки попадает в артефакт сайта и, значит, висит на домене сайта документации, а установка одной командой выглядит так:

```bash
curl -fsSL https://chenyuheee.github.io/flower/install.sh | sh
```

Причина сугубо практическая: **`raw.githubusercontent.com` в Китае недоступен, а `*.github.io` доступен** (проверено).
Сам скрипт лежит в корне репозитория, при публикации просто копируется ещё раз — не нужно поддерживать две копии содержимого и не нужен отдельный CDN.

Что делает сам `install.sh`: выбирает установщик Python-инструментов (`uv` > `pipx` > поставить `uv` > `pip --user`),
ставит flower с GitHub и подсказывает следующий шаг. Он **не трогает учётные данные** — первый запуск `flower` спросит их сам и сохранит в
`~/.config/flower/.env`.
