# HT001 · Терминальная IDE с нуля

2026-09-07 агент под flower с нуля написал однофайловую C/C++ IDE, работающую в терминале macOS.
Он проработал 10.4 часа подряд, потратил $171.62 и сдал 12,212 строк продуктового кода и 13,291 строку тестов;
посреди прогона один раз оборвалась сеть — он сам продолжил и дошёл до конца. Эта страница не витрина результата:
здесь каждое заявление фреймворка измерено на реальном масштабе,
**включая те два, которые измерения не выдержали**: «координатор часто игнорирует ограничения прав» оказалось неправдой, а в собственной приёмке агент один критерий оценил неверно.

Полная запись (включая 19MB transcript) — в [ChenyuHeee/cppide](https://github.com/ChenyuHeee/cppide).
Каждое число ниже посчитано `tools/analyze_run.py` из `sessions.db` и воспроизводимо:

```bash
python tools/analyze_run.py /path/to/cppide/runs
```

!!! note "Откуда взяты числа на этой странице"
    `runs/` от HT001 лежат в упомянутом выше репозитории cppide, **не в репозитории flower**. Поэтому числа на этой странице
    **перенесены как есть** из тогдашних записей прогона; при написании страницы они заново по `sessions.db` не пересчитывались —
    чтобы пересчитать, нужно сначала склонировать cppide, а потом выполнить команду выше.
    [HT002](ht002.md) — наоборот: исходные записи лежат в этом репозитории, числа на той странице пересчитаны построчно,
    а два расхождения прямо написаны на самой странице.

## I. Экономика контекста: 94.8 % черновой работы не попало в главный поток {#一上下文经济学948-的现场没进主线程}

Это ключевое заявление фреймворка — [координатор](../reference/glossary.md#协调者) держит только решения,
черновая работа оседает в subagent и на диск. Сам механизм описан в [Экономике контекста](../guide/context.md).

| | Главный поток | subagent | Доля subagent |
|---|---|---|---|
| Ходы модели | 70 | 3.0K | **97.7 %** |
| Символы текста | 200.1K | 3.6M | **94.8 %** |
| Вызовы инструментов | **32** | **1,893** | —— |

За прогон было запущено 23 subagent, максимум выходных token — 184,377, медиана 72,197, минимум 11,684.

**Из 1,893 вызовов инструментов, делающих реальную работу (1,034 Bash / 471 Read / 258 Edit / 126 Write), в поле зрения координатора попали только 32 — соотношение 59:1.** В среднем на каждый запуск subagent приходится 82 вызова инструментов, которых он не видит.

Ранние мелкие тесты давали 83 %, на реальном масштабе — **94.8 %**. Чем больше масштаб, тем выше выигрыш от разделения труда:
накладные расходы на [задание](../reference/glossary.md#任务书) и ответ **фиксированы на каждый запуск**,
а объём отсечённой черновой работы растёт со сложностью задачи.

## II. Кривая контекста: впервые известно, где предел «долгогоризонтности» {#二上下文曲线第一次知道长程的上限在哪}

`input + cache_read + cache_creation` каждого сообщения assistant — это и есть контекст, который модель видела на том ходу:

```text
Ход 1     28.7K   ← стартовый пол (раньше измеряли ~34k, сходится)
Ход 20    35.2K
Ход 35   108.6K
Ход 50   158.2K
Ход 70   185.9K   ← конец
```

- монотонный рост на протяжении 70 ходов, наклон около **2.2K/ход**
- **compact не срабатывал ни разу** (`DISABLE_AUTO_COMPACT=1`; единственный провал — пустая запись на ходу с обрывом сети)
- израсходовано **18.6 %** окна в 1M

**Экстраполируя этот наклон, в стену упрёмся примерно на 440-м ходу.** В этот раз 70 ходов дали 12K строк кода,
то есть реальный предел [долгогоризонтности](../reference/glossary.md#长程) в текущей форме примерно в **6 раз** больше этого прогона.
Это число, с которым уже можно принимать решения; раньше оставалось только гадать.

Чтобы его пробить, рост главного потока должен стать **сублинейным** — больше оседать на диск, меньше оставаться в диалоге.

## III. Попаданий в кэш 96.1 % — только на этом и держатся $171.62 {#三缓存命中-961--17162-能成立全靠它}

```text
Всего входных 299.4M token
  попало в кэш   287.5M  (96.1%)
  создано кэша    11.8M
  без кэша         6.2K
Выход 2.3M (из них thinking 653.9K)
```

299M входных token стоили всего $171, потому что 96 % прошли по цене кэша.

**Вывод: экономика долгогоризонтного прогона строится на доле попаданий в кэш, а она зависит от стабильности префикса контекста.**
Любая оптимизация «переупорядочить контекст» — вынести старое, вставить в начало новый системный prompt — пробивает кэш,
и сэкономленные token могут не покрыть потерянную кэш-скидку. Раньше это не измерялось, теперь есть цифра.

Это же — побочная причина, почему flower использует [смену поколения](../reference/glossary.md#换代), а не compact:
смена поколения — это **новая сессия, где кэш строится с нуля**, а внутри одного поколения префикс всегда стабилен.

## IV. Переиспользование верстака: 61 скрипт, ни один не выброшен после написания {#四工作台复用61-个脚本没有一个写完就扔}

Заявление [верстака](../reference/glossary.md#工作台) — «скрипт пишется один раз, дальше просто запускается и больше не переписывается».
Проверяется это не вопросом агенту, а подсчётом по transcript, сколько раз скрипты в `.flower/scripts/` были записаны через Write/Edit и сколько раз выполнены через Bash:

```text
61 скрипт: записаны 95 раз, выполнены 331 раз
Выполнены > 1 раза (реально переиспользованы): 56, то есть 92%
Записаны, но ни разу не выполнены: 0
Отношение выполнений к записям 3.48
```

`wave5-verify.sh` записан 5 раз, запущен 45 раз — доводка итерациями, а потом многократное использование, ровно нужная форма.
**Ни один скрипт не был выброшен сразу после написания.**

## V. Координатору отказали 1 раз — и виноват белый список {#五协调者动手被拒-1-次而且是白名单的错}

Гипотеза до измерения была такая: «координатор часто игнорирует ограничения прав и порождает массу отклонённых вызовов». Измерение эту посылку снесло.

**Из 32 вызовов инструментов отклонён 1 (3.1 %)**, и это был вот этот:

```bash
which g++ clang++ make pkg-config 2>&1; echo ---; ls /usr/include/ncurses.h 2>&1; echo ---; ls /work/runs
```

Посегментное решение: `echo` пропущен, `ls` пропущен, **`which` заблокирован — его нет в таблице
[эфемерных команд](../reference/glossary.md#一次性命令)**.

Вся команда целиком только читает — это стандартная разведка окружения. **Модель сделала всё абсолютно правильно, неполон был белый список**,
и он заставил её заплатить за одну строчку `which g++` стоимостью запуска subagent (около 4.3k token).

Исправлено: добавлены `which` / `command -v` / `type` / `whereis` / `uname` / `arch` / `locale` / `nproc` /
`getconf` / `sw_vers`. У `command` и `type` **пропускается только форма запроса** —
голая `command rm -rf /` это выполнение, забыть тот `-v` значит открыть чёрный ход,
в `tests/glance.py` это стерегут 7 состязательных примеров.

**Запомнить здесь стоит не патч, а метод.** Долгая архитектурная дискуссия, чья исходная посылка на реальных данных равна 1/32,
да ещё и с перевёрнутой атрибуцией — проблема была не в модели, а в белом списке. **Сначала измерь.**

## VI. Обрыв сети и продолжение: первая проверка настоящим сбоем {#六断网续跑第一次被真实故障验证}

```text
01:52:40  tool_result: "Agent terminated early due to an API error"   ← прерван один subagent
01:55:41  assistant:   "API Error: ENOTFOUND"                          ← дошло до главного потока
          ↓  зонд висит и ждёт восстановления сети
          resumed=True, продолжение той же сессии, ещё 8+ часов до завершения
```

В manifest записано `attempts=2 / resumed=True / ok=True`. **10 часов работы не пришлось начинать заново.**
До этого [устойчивость](../reference/glossary.md#韧性) висела в статусе «всё ещё не проверено» — чтобы оборвать сеть, нужен sudo и правка hosts, и никто не хочет делать это на настоящем прогоне.

Синтетическое сообщение "API Error" было снято `PruningSessionStore` при загрузке, **модель его не увидела** —
дизайн [отсечения](../reference/glossary.md#剪除) тоже оказался проверен реальным сбоем.

Выявились две проблемы (см. issue #2):

1. Восстановление происходит **на уровне фреймворка**, а не транспорта. Цена — переигрывание всего контекста, а он тогда был большим.
2. **У прерванного subagent наполовину сделанная работа пропала.** Resume спасает главный поток,
   восстановление после прерывания на уровне subagent — отдельная задача.

## VII. Настоящая ли у него самопроверка {#七它的自我验证是真的吗}

Вот место, которое подозревать нужно в первую очередь: агент сам пишет тесты, сам их гоняет, сам объявляет о прохождении — это очень легко превращается в формальность.

Постфактум был запущен независимый аудирующий subagent, статически прочитавший все 58 скриптов и 22 артефакта. Вывод — **настоящая, и строгость редкая**:

- **Тавтологических утверждений — 0.** Во всём репозитории нет паттернов вида `[ 1 = 1 ]`.
- `|| true` встречается 8 раз, **7 из них оправданы** (`grep -c` возвращает 1 при отсутствии совпадений, подстраховка `ulimit` и т. п.).
- **Проверяется поведение, а не наличие файла.** `audit-idle-cost.sh:53` гоняет IDE вхолостую в pty 60 секунд,
  считает число запросов, реально принятых локальным фейковым сервером, и PASS ставится только при `-le 2`. `fix-p1-idle-verify.sh:100-110` идёт дальше:
  утверждает и то, что холостых запросов ровно 1, **и** то, что ghost по-прежнему отображается — чтобы правка ради ограничения запросов не убила заодно саму функцию.
- **Реально порождаются дочерние процессы.** `wave5-pty-drive.cpp:316` запускает TUI по-настоящему через `forkpty`; `audit-fake-ai-server.py` —
  настоящий socket-сервер с пятью видами инъекции сбоев `/err500 /err401 /badjson /drop /slow`;
  на всех AI-путях принудительно очищается `CPPIDE_API_KEY`.

Две вещи превзошли ожидания.

**Оно сделало для своего верификатора положительный и отрицательный контроль.** `验收审计.md:29-34`: сначала подаётся `ZZZ_NEVER_APPEARS_ZZZ`, чтобы убедиться, что драйвер даст FAIL,
затем настоящая строка, чтобы убедиться в PASS — чтобы не «проводить аудит вечно-PASS-ящим фейковым прибором». **Это проверка самого верификатора.**

**Оно само раскрыло своё слабое утверждение.** `for m in $must` в `wave5-b4-ai-states.sh:114`
разбивает `"AI 错误 请求超时"` по пробелам на три подстроки и грепает каждую по отдельности, а `AI` и `错误` неизбежно есть на любом экране —
номинально «прошло 3 проверки», реально различающая сила есть только у одной. **Это оно само записало в `验收审计.md:576-582`**,
а не аудитор откопал.

Из того же ряда: `wave5-verify.sh:296-302` семью строками комментария объясняет, почему проверка B3b понижена до SKIP
(утверждение о тайминге последнего экрана, к продуктовому коду отношения не имеет), с пометкой «логика вердикта и границы допуска не изменены ни на символ»;
`:236-238` фиксирует, что оно **нашло и починило собственное фальшивое утверждение, написанное раньше** —
`if pgrep ...` в урезанном образе без `pgrep` молча уходил в else и превращался в вечный PASS.

Качественные свидетельства переиспользования сходятся с цифрами раздела IV: `audit-fake-ai-server.py` переиспользован **7** скриптами;
`wave5-pty-drive.cpp` переиспользован **5+** сборками, причём компиляция кэшируется через `[ -x "$DRIVE" ] ||`;
драйвер wave4 → wave5 — это **расширение, а не переписывание** (в diff изменена 1 строка, добавлено 343, все 281 строка wave4 сохранены как есть).

**Всё это поведение возникло в версии без стража цели.** Единственным ограничением были те
10 разрешимых критериев приёмки из [брифа](../reference/glossary.md#需求确认书). Отсюда вывод: **сама по себе запись «сделано» в разрешимой форме уже провоцирует самопроверку и самораскрытие.**
Предельную ценность стража цели надо мерить от этой базы, а не от нуля.

Но следующий раздел показывает: **самопроверка сильна в технике верификации и при этом ошиблась в финальном вердикте по самому важному критерию.**

!!! warning "«Аудитор» здесь — не судья"
    Независимый аудитор в разделах VII и VIII — это **subagent, которого координатор запустил по собственной инициативе**, а не
    [судья](../reference/glossary.md#目标看守) из [стража цели](../reference/glossary.md#判定者):
    в этом прогоне стража цели не было вообще. Читается похоже, но делают они разное: аудитор — это разбор постфактум,
    судья — это ворота [вердикта](../reference/glossary.md#判定) в конце каждого хода.

## VIII. Правильно ли оно себя оценило — критерий 1 оценён неверно {#八它给自己打的分对吗--验收-1-判错了}

Был запущен второй независимый аудитор, который построчно сверил те 10 критериев приёмки с кодом.

**Критерии 2–10 подтверждаются полностью**, доказательства в коде есть. То, что в режиме тренировки код не вставляется, — вообще **структурная** гарантия:
единственная точка решения sink `ai.h:117` + единственный итоговый switch `app.cpp:590-615` + четыре early-return
`editor.cpp:679-683`, а не разбросанные if. Найденные самопроверкой P1–P4 тоже **все подтверждаются, все исправления доведены до кода**
(P4 подтверждается наполовину: та строка с синей парой цветов — мёртвый код, `ghostAttr()` и так идёт через `A_DIM`).

**Но критерий 1 оценён неверно.**

```text
Текст критерия:        «собрать отдельный исполняемый файл, запускать прямо в терминале macOS»
Поставленный артефакт: ELF 64-bit LSB pie executable, ARM aarch64, GNU/Linux
Его вердикт:           пройдено
```

Это проверил человек, руками запустив `file`.

Оно ничего не скрывало — заголовок §4 в `交付说明.md` так и звучит: «главный непроверенный риск: на macOS не запускалось ни разу»,
в §6 аудита перечислены шесть непроверенных аспектов macOS. **Оно раскрыло риск, но так и не связало этот факт обратно с вердиктом по критерию 1**,
а буквальное требование критерия 1 — ровно об этом.

### Но это не доказательство того, что «нужен независимый судья» {#但这不是需要一个独立判定者的证据}

Очень легко прочитать это как «значит, нужен страж цели». Неверно, и такое чтение — **сначала выстрелить, потом нарисовать мишень**,
ровно тот вид мотивированного рассуждения, который раскритикован разделом выше.

**Тогдашняя версия стража цели в конфигурации по умолчанию с высокой вероятностью тоже пропустила бы этот критерий.** У `judge()` по умолчанию `can_run=False`,
инструменты только `Read` / `Glob` / `Grep` — **он не может запустить `file`**.
Он пошёл бы читать исходники, увидел бы в `Makefile:25-38` реальную ветку Darwin и вынес бы «достигнуто». Ровно та же ошибка, что и при самопроверке.

### Настоящий структурный факт {#真正的结构性事实}

**Критерий 1 в окружении этого прогона принципиально непроверяем.**

Он утверждает нечто о «поведении артефакта на macOS», а весь прогон шёл в Linux-контейнере.
**Никакой судья не может проверить macOS-бинарник изнутри контейнера**, будь он самопроверкой или независимым.
Проблема не в том, «кто выносит вердикт», а в том, что **этот критерий сочли обычным разрешимым критерием и вынесли по нему вердикт**.

### Ещё три находки аудитора (самопроверка о них не сказала) {#审计员另外挖到的三条自审都没提}

- **Семантика квоты в `doTab()`**: `app.cpp:909` после `acceptGhost()` безусловно вызывает `noteActivity()` → `gen_++`
  → квота открывается заново, то есть **каждое принятие по Tab через 500ms снова запускает автоматический запрос**. Анализ P1 (холостой ход жжёт деньги)
  проверил только три точки отмены — `setMode` / `cancelInFlight` / `askNow` — и упустил самый частый путь трат.
- «Серый» из критерия 6 буквально верен только в 256-цветном терминале; в 8-цветном режиме жёстко зашит `A_DIM` (затемнение, а не серый).
- Подзаголовок §7 в `验收审计.md` гласит «9 критериев приёмки», а в таблице 10 строк — опечатка, но в шапке итоговой таблицы.

## Оставшиеся риски {#遗留风险}

**Целевая платформа поставки — macOS, но вся верификация выполнена внутри контейнера Debian aarch64, на живой macOS — ноль проверок.**
Это настоящий побочный эффект схемы с контейнерной изоляцией: ради безопасности агента заперли в Linux, а поставлять он должен под macOS.
README §10.24 самого проекта честно фиксирует это и перечисляет 4 рисковых пункта, но контур не замкнут.

Этот пробел позже закрыл [HT002](ht002.md) — тот прогон как раз ставил этот бинарник на настоящую macOS.

Неожиданный бонус: в контейнере видно только `/work`, поэтому в 19MB transcript
**ноль утечек имени пользователя хоста `/Users/hechenyu`** (`/work` встречается 11,495 раз).
[Изоляция](../reference/glossary.md#隔离) заодно изолировала и пути.

## Что этот прогон проверить не смог {#这一跑没能验证的}

- **Страж цели**: прогон был до его добавления. Координатор **по собственной инициативе** организовал независимый аудит, техника верификации очень крепкая,
  но по самому важному критерию вердикт был неверным (раздел VIII). Обе части вывода надо помнить вместе:
  разрешимые критерии, записанные в брифе, сами по себе провоцируют самопроверку, поэтому база для стража цели не равна нулю;
  а страж цели в тогдашней конфигурации по умолчанию **тоже пропустил бы этот критерий**, так что и он не панацея.
- **Поведение окна на 1M**: использовано лишь 18.6 %, до границы не дошли.
- **Поведение микро-compact при `DISABLE_AUTO_COMPACT=1`**: compact не срабатывал ни разу, так что это по-прежнему домысел.

## Что этот прогон изменил во фреймворке {#这一跑改了框架什么}

| Находка | Реализованное изменение |
|---|---|
| `which` заблокирован (раздел V) | в `is_ephemeral()` добавлены `which` / `command -v` / `type` / `whereis` / `uname` / `arch` / `locale` / `nproc` / `getconf` / `sw_vers`; в `tests/glance.py` добавлено 7 состязательных примеров, стерегущих форму запроса у `command` / `type` |
| Критерий 1 оценён неверно (раздел VIII) | пункт 1 в `JUDGE_RULES` изменён: **судят артефакт, а не исходники** — если можно запустить, запусти; если нельзя, всё равно проверь сам артефакт (платформа, размер, загружается ли) |
| «Я же раскрыл риск» обменялось на «пройдено» | вердикт должен различать «не сделано» и «здесь невозможно проверить». `Verdict.parse` теперь распознаёт **无法验证 / 没法验证 / 无法判定** как третье состояние `unreachable` → **поднять наверх и спросить человека, вердикт «пройдено» запрещён** |

| Восстановление после обрыва сети живёт на уровне фреймворка, полуготовая работа subagent теряется (раздел VI) | записано как issue #2, не закрыто |

но то же самое правило породило новый сбой.
