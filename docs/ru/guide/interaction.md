# Замена слоя взаимодействия

Ядро flower не знает о существовании UI. Всё, что происходит внутри прогона — модель говорит, вызывает инструмент, контекст почти заполнен, нужно что-то спросить у человека — сплющивается в одну и ту же структуру данных [`Event`](../reference/glossary.md#事件).
**[Слой взаимодействия](../reference/glossary.md#交互层) знает только `Event` и не импортирует ни одного типа SDK.**
Это и есть та граница, благодаря которой смена UI не трогает ядро: терминал, Web, HTTP-сервис, полностью автономный режим без человека — меняется потребитель `Event`, и больше ни одной строки.

## Какую проблему это решает

Поток сообщений SDK — это **внутренние типы**: `AssistantMessage`, `ToolUseBlock`, `ToolResultBlock`, `ResultMessage`, `SystemMessage`… Если UI потребляет их напрямую, последствий два: стоит SDK обновиться — фронтенд надо править следом; и поскольку форма у каждого сообщения своя, каждый UI заново пишет разбор «это основной текст или вызов инструмента».

`normalize(message)` превращает одно сообщение SDK в от 0 до N `Event`
([`core/events.py`](https://github.com/ChenyuHeee/flower/blob/main/flower/core/events.py)).
Цена — одно преобразование, взамен между слоем взаимодействия и SDK нет типовой зависимости.

Заодно эта граница решает четыре не столь очевидные вещи, и все четыре — внутри `normalize()`:

1. **Реплики [subagent](../reference/glossary.md#subagent) помечаются** (`payload["subagent"]`).
   Иначе [задание](../reference/glossary.md#任务书), которым его отправили, и промежуточные реплики subagent смешаются с основным текстом [главного потока](../reference/glossary.md#主线程), а дальше по [workflow](../reference/glossary.md#流程) отравят prompt следующего шага.
2. **Синтетическое сообщение об ошибке при обрыве связи отводится в `kind="error"`**. При обрыве сторона SDK пишет `API Error: …` в transcript как assistant-сообщение, и выглядит оно как речь модели (`model` равен `"<synthetic>"`).
   Если не перехватить его здесь, оно попадёт в `StepResult.text` и уйдёт в следующий [шаг](../reference/glossary.md#步骤).
3. **Граница compact сообщается явно** (`kind="reset"`). После границы модель «помнит» только резюме, и кэш prompt тоже рвётся здесь — прогон с [длинным горизонтом](../reference/glossary.md#长程) обязан это видеть.
4. **Уровень заполнения контекста приходит с каждым сообщением** (`payload["context"]` = `input_tokens` + `cache_read_input_tokens` + `cache_creation_input_tokens`). Это единственный источник критерия для [handoff](../reference/glossary.md#换代).

## Как этим пользоваться (минимальный код)

Слой взаимодействия подключает три вещи: **выход для событий** (куда рендерить), **канал вопросов** (кто отвечает) и **прерывание** (как крикнуть «стоп»). Ниже подключено всё, код можно запускать как есть:

```python
import asyncio

from flower import Event, HumanChannel, Runtime, starter_flow


def sink(ev: Event) -> None:
    """Рендер Event в ваш собственный UI — единственное, что нужно менять."""
    if ev.kind == "step":
        print(f"\n=== {ev.text} ({ev.payload['index']}/{ev.payload['total']}) ===")
    elif ev.kind == "text" and not ev.payload.get("subagent"):
        print(ev.text)
    elif ev.kind == "tool_call":
        print(f"  [{ev.tool}] {ev.text}")
    elif ev.kind == "handoff":
        print(f"  ~ 换代/{ev.payload.get('phase')}: {ev.text}")
    elif ev.kind == "retry":
        print(f"  ~ 重试: {ev.text}")
    elif ev.kind == "ask" and ev.payload.get("kind") == "mail":
        print(f"  ~ 人主动说:{ev.text}")
    # kind == "ask", не являющиеся mail, обрабатывает answerer ниже (pull-режим)


async def answerer(ch: HumanChannel) -> None:
    """Забор вопросов в pull-режиме. При переходе на Web / HTTP это второе место, которое надо править."""
    while True:
        ask = await ch.next_ask()           # без timeout ждёт бесконечно
        if ask is None:
            continue
        print(f"\n?? {ask.question} 选项={ask.options}")
        ch.answer(ask.id, "按你的判断来")     # или ch.decline(ask.id, "先跳过")


async def main() -> None:
    wf = starter_flow("帮我做一个 X", workspace=".", run_dir="runs", timeout_s=60)
    # Runtime берёт верстак, который workflow уже создал сам — не собирайте второй
    rt = Runtime(workspace=".", run_dir="runs", workbench=wf.workbench)
    task = asyncio.create_task(answerer(wf.channel))
    try:
        ctx = await wf.run(rt, on_event=sink)
    finally:
        task.cancel()
        rt.close()                          # закрыть соединение SQLite
    print(rt.total_cost(), ctx.get("_failed_at"))


asyncio.run(main())
```

Два легко забываемых завершающих момента: `rt.close()` обязательно в `finally`; если у `ctx["_failed_at"]` есть значение — прогон остановился на полпути (`on_fail="stop"`), не считайте это успехом.

!!! note "Верстак только один, не собирайте второй"
    [Верстак](../reference/glossary.md#工作台), созданный через `Runtime(workbench=True)`, лежит в `<run_dir>/workbench`, а `Workbench(ws)` по умолчанию — в `<ws>/.flower`: это не один и тот же каталог. Если драйвер сам склеивает путь, чтобы найти `需求.md`, получится, что «бриф пишется в каталог A, а внедрённый индекс сканирует каталог B» — и при этом ошибки не будет.
    Либо отдайте `Runtime` тот верстак, который создал workflow (как в коде выше),
    либо спросите у read-only проверки `wake_state()`, где он.

### Три выхода для событий

```python
await rt.run(spec, "…", on_event=sink)                  # 1. отдельный агент
await wf.run(rt, on_event=sink, on_step=progress)       # 2. весь workflow, передаётся в каждый шаг
wf = Workflow(steps=[...], channel=ch)                  # 3. канал вопросов, подключён к тому же выходу
```

Как подключается третий — видно в `Workflow.run`: **автоподключение происходит, только если `on_event` не `None` и `channel.on_event` всё ещё `None`**. Если вы подключили выход сами, его не перезапишут:

```python
ch = HumanChannel(on_event=my_own_sink)     # подключили сами — Workflow это не трогает
```

`on_step(step, result)` — другой колбэк, он вызывается один раз после каждого шага (**включая провалившиеся**) и получает полный `StepResult`. Прогресс-бар, запись на диск, алерты вешайте сюда, а не собирайте их из потока `Event` — основной текст рвётся на несколько кусков handoff'ами и повторами.

### Терминал: тот, что по умолчанию

Один такой есть и без всякого кода. `flower "帮我做一个 X"` идёт через
[`flower/cli.py`](https://github.com/ChenyuHeee/flower/blob/main/flower/cli.py),
и это **эталонная реализация слоя взаимодействия, а не часть фреймворка** — её можно заменить целиком; переключатели см. в [Справочнике CLI](../reference/cli.md).

Скажем честно про масштаб. Весь `cli.py` — это 1264 строки, 57KB, но **менять нужно не весь файл**. Настоящая точка замены — класс `Render` внутри него (`cli.py:382-578`, 197 строк), в его docstring так и написано: «Event → терминал. Сменить UI — значит сменить этот один класс.» Остальная тысяча с лишним строк — это прерывание, оракул, квитанции входящих, спасение по сигналам, то есть **специфичная для терминала** обвязка, которую при переходе на Web или HTTP и не нужно тащить.

Так что утверждение «около 200 строк заменяются целиком» верно — при условии, что речь о `Render`, а не о `cli.py`.

Если пишете свой терминальный UI, ключевое — поток, читающий стандартный ввод:

```python
import select
import sys
import threading


def start_input(ch: HumanChannel) -> threading.Event:
    """Читаем stdin постоянно: есть висящий вопрос — это ответ, иначе — во входящие. Возвращаем флаг остановки."""
    stop = threading.Event()

    def loop() -> None:
        while not stop.is_set():
            if not select.select([sys.stdin], [], [], 0.2)[0]:
                continue                        # опрос — только так реагируем на флаг остановки
            line = sys.stdin.readline()
            if not line:                        # EOF
                return
            raw = line.strip()
            if not raw:
                continue
            pend = ch.pending()
            if pend:
                ch.answer(pend[0].id, raw)      # безопасно между потоками
            else:
                ch.send(raw)                    # во входящие, не прерывая текущую работу

    threading.Thread(target=loop, daemon=True, name="stdin").start()
    return stop
```

Все три пункта — набитые шишки:

- **Используйте daemon-поток, а не `asyncio.to_thread(input, ...)`.** Заблокированный `input()` нельзя отменить, а `asyncio.run` перед выходом join'ит потоки дефолтного executor'а — в итоге работа сделана, но чтобы выйти, надо ещё раз нажать Enter.
- **Опрашивайте через `select`, не вызывайте `input()` прямо в цикле.** Та же неотменяемость: поток, зависший на `input()`, уже не разбудить никаким `stop.set()`.
- **Читайте постоянно, а не только когда есть вопрос.** Если читать только при наличии вопроса, всё, что человек набрал за те несколько часов работы, останется в буфере терминала и будет съедено как ответ на следующий вопрос — человек ещё не увидел вопрос, а на него уже «ответили».

### Web: очередь + WebSocket

```python
events: asyncio.Queue[dict] = asyncio.Queue()


def sink(ev: Event) -> None:            # синхронно, в потоке цикла событий, блокировать нельзя
    try:
        events.put_nowait({"kind": ev.kind, "text": ev.text,
                           "tool": ev.tool, "payload": ev.payload})
    except Exception:                   # ошибка фронтенда не должна уносить трёхчасовую работу
        pass


async def pump(ws) -> None:
    while True:
        await ws.send_json(await events.get())


@app.post("/answer")                    # поток обработки запроса — другой поток, и это норма
def answer(ask_id: str, text: str) -> dict:
    return {"ok": ch.answer(ask_id, text)}
```

`ev.raw` — это исходный объект SDK (в событии `ask` — `Ask`), он **не сериализуется в JSON и на фронтенд его отдавать не надо**: как только вы взялись за `raw`, фронтенд снова привязан к типам SDK и весь этот слой сделан зря. Четырёх полей `kind` / `text` / `tool` / `payload` достаточно.

### HTTP: порядковый номер + опрос

Когда постоянного соединения нет, нумеруйте события и дайте клиенту их забирать:

```python
import itertools
from collections import deque

seq = itertools.count(1)
log: deque[dict] = deque(maxlen=2000)   # держим только последние, память не растёт вместе с длительностью прогона


def sink(ev: Event) -> None:
    log.append({"seq": next(seq), "kind": ev.kind, "text": ev.text,
                "tool": ev.tool, "payload": ev.payload})


@app.get("/events")                     # GET /events?after=128
def events(after: int = 0) -> list[dict]:
    return [e for e in log if e["seq"] > after]


@app.get("/asks")                       # что сейчас висит и ждёт ответа
def asks() -> list[dict]:
    return [{"id": a.id, "question": a.question, "options": a.options,
             "waited_s": a.waited_s} for a in ch.pending()]


@app.post("/answer")
def answer(ask_id: str, text: str) -> dict:
    return {"ok": ch.answer(ask_id, text)}      # False = этот вопрос уже никто не ждёт
```

Две границы, которые надо знать: при заполнении `maxlen` теряются самые старые записи, и клиент, вернувшийся со слишком старым `after`, получит неполную выборку — интервал опроса должен соответствовать этой длине. И **`timeout_s` обязан быть конечным**: если никто не опрашивает, вопрос сам по себе не завершится, а `timeout_s=None` подвесит весь прогон навсегда. Значение по умолчанию `1800.0` секунд подходит.

### Полностью автономный режим: человека нет

```python
wf = starter_flow("帮我做一个 X", workspace=".", run_dir="runs", timeout_s=0)
rt = Runtime(workspace=".", run_dir="runs", workbench=wf.workbench)
ctx = await wf.run(rt, on_event=None)       # события отбрасываются целиком
```

Эквивалент в командной строке — `flower "帮我做一个 X" --timeout 0`.

`timeout_s=0` (и любое отрицательное значение) — это полностью автономный режим: вопрос **не попадает в очередь ожидания и не порождает событие `asked`**, он сразу закрывается со `state="timeout"`, а инструмент возвращает вот этот фиксированный текст —

```text
无人应答。按你自己的判断继续,并把这个问题和你采用的假设写进「未知与假设」那一段。不要重复提问,也不要停在这里。
```

— и прогон продолжается как ни в чём не бывало. Вопросы и ответы всё равно дописываются в `HumanChannel(log_path=...)` (`starter_flow` по умолчанию подключает `<верстак>/notes/问答记录.md`), так что потом видно, о чём агент спрашивал и какие допущения принял сам.

Если не хотите, чтобы он вообще открывал рот, используйте `max_asks=0`: вопрос сразу отклоняется (`state="over_budget"`) и тоже ничего не блокирует.
Обратите внимание: это **не** «убрать инструмент» — `allowed_tools` не является исключающим списком, и как только к [координатору](../reference/glossary.md#协调者) подключён `channel`, ему выдаются оба инструмента, `mcp__human__ask` и `mcp__human__inbox`, независимо от того, перечислены они или нет. Остановить вопрос могут только квота и таймаут.

!!! warning "В автономном режиме не давайте вопросу ждать вечно"
    `timeout_s=None` означает «ждать вечно». Когда никто не смотрит, один вопрос способен намертво остановить десятичасовой прогон — без ошибки, без таймаута, и по логам это никак не отличить. Для автономного режима корректных значений всего два: `0` (моментальный провал) либо конечное число секунд.

## Что происходит на самом деле

### Форма `Event`

```python
@dataclass
class Event:
    kind: EventKind                     # 15 значений, см. таблицу ниже
    text: str = ""
    tool: str = ""                      # заполнено только у tool_call
    payload: dict[str, Any] = field(default_factory=dict)
    raw: Any = None                     # исходный объект SDK / Ask; тронул — снова привязался к SDK
```

`str(ev)`: для `tool_call` это `[имя инструмента] краткое описание`, для остального — `text`; если `text` пуст — `<kind>`.

### 15 значений `EventKind`

| `kind` | Кто отправляет | Когда появляется | `text` | `payload` |
|---|---|---|---|---|
| `text` | `normalize()` | Основной текст модели | Текст | `subagent`, `parent_tool_use_id?`, `context?` |
| `thinking` | `normalize()` | Блок размышления | Содержимое размышления | То же |
| `prompt` | `normalize()` | **Ввод**: ваш prompt, задание, отправленное subagent | Текст ввода | То же |
| `tool_call` | `normalize()` | Модель инициирует вызов инструмента | Краткое описание (`file_path` / `command` / `pattern`, обрезано до 200 символов) | `id`, `input` + то же; `tool` — имя инструмента |
| `tool_result` | `normalize()` | Инструмент вернул результат | Первые 500 символов (пусто, если содержимое не строка) | `tool_use_id`, `is_error` + то же |
| `result` | `normalize()` | Один запрос к SDK завершён | subtype | `session_id`, `cost_usd`, `num_turns`, `is_error` |
| `error` | `normalize()` | Синтетическое сообщение при обрыве связи | Текст ошибки | `synthetic: True` |
| `reset` | `normalize()` | Граница compact или сброс сессии | `压缩(trigger) 167000 → 42000 tokens`; при сбросе сессии — `conversation reset` | `trigger`, `pre_tokens`, `post_tokens`, `micro`, `subtype` (пусто при сбросе сессии) |
| `system` | `normalize()` | Прочие системные сообщения SDK | subtype | `data` пробрасывается как есть |
| `task` | `normalize()` | Сообщение о ходе задачи | Имя класса сообщения | — |
| `unknown` | `normalize()` | Нераспознанный тип сообщения | Имя класса | — |
| `ask` | `HumanChannel` | Нужен ответ человека, у какого-то вопроса появился исход, либо человек сам что-то сказал | Вопрос / реплика человека | Две роли, см. ниже |
| `retry` | `Runtime` | Идёт повтор / ждём восстановления сети | Одна поясняющая фраза | `step`, `attempt` |
| `step` | `Workflow.run` | Граница шага | Имя шага | `index`, `total`, `resumed`, `woke` |
| `handoff` | `Runtime` | Handoff: приближается / пишется / выполнен | Фраза с уровнем заполнения | `phase`, `step`, `context`, `window` + см. ниже |

**Четыре kind не порождаются `normalize()`**: `ask` приходит из `HumanChannel`, `retry` и `handoff` — из `Runtime`, `step` — из `Workflow.run`. Держать их в одном `EventKind` — сознательное решение: **UI знает единственный набор `Event` и не заводит отдельный путь ни под «нужен ответ человека», ни под «граница шага».**

Когда пишете UI, оставьте ветку `else`. В `EventKind` будут добавляться новые значения, и старый UI не должен из-за этого падать.

### Три phase у `handoff`

| `phase` | Когда отправляется | Что дополнительно в `payload` |
|---|---|---|
| `near` | Уровень перешёл `warn_at`. **Отправляется один раз за поколение**, без спама | `at` (порог handoff) |
| `writing` | Началась запись [документа handoff](../reference/glossary.md#交接书). Запись занимает десяток-другой секунд, без этого события интерфейс выглядит зависшим | — |
| `done` | Документ написан, переключились на новую сессию | `degraded` (деградированная ли версия), `path` (куда записано; при отсутствии верстака — пустая строка), `sections` |

Сам механизм описан в [handoff](handoff.md).

### Две роли `ask`

`Event("ask")` несёт одновременно «вопрос» и «реплику человека», поэтому **UI обязан сначала посмотреть на `payload["kind"]`**:

| Роль | Как отличить | `payload` |
|---|---|---|
| Вопрос | Ключа `kind` нет | `id`, `options`, `state`, `answer`, `remaining`, `asked_at`; `raw` — тот самый `Ask` |
| Реплика человека | `payload["kind"] == "mail"` | `kind`, `state` (`queued` — положено / `delivered` — забрано), `id`, `amended` (в какой файл дописано; если путь не настроен — пустая строка). **Нет `options` и `remaining`** |

Один вопрос порождает **как минимум два** события: одно в момент вопроса (`state="asked"`) и ещё одно при появлении исхода (`answered` / `timeout` / `declined` / `over_budget` / `invalid`). UI достаточно обновлять одну и ту же запись по `payload["id"]`.

### Спросить человека: `Ask` и `HumanChannel`

```python
@dataclass
class Ask:
    id: str                                             # "q1", "q2"…
    question: str
    options: list[str] = field(default_factory=list)
    asked_at: float = field(default_factory=time.time)
    state: str = "asked"                                # пять исходов, см. выше
    answer: str = ""

    @property
    def waited_s(self) -> float: ...                    # сколько секунд прождали, один знак после запятой
    def event(self, remaining: int = 0) -> Event: ...
```

`HumanChannel` — это внутрипроцессный MCP-сервер плюс набор методов для UI. Со стороны модели видны только два инструмента: `mcp__human__ask` (задать вопрос, вызов подвисает в ожидании) и `mcp__human__inbox` (проверить входящие, **не блокирует**: если пусто, сразу возвращает пояснение). Полный конструктор:

```python
HumanChannel(
    *,                                  # всё только keyword-only
    on_event=None,                      # push-выход. Workflow подключает его сам, только если здесь None
    max_asks=None,                      # None = без ограничения; 0 = спрашивать нельзя. Сверх квоты — отказ, без блокировки
    timeout_s=1800.0,                   # None = ждать вечно; <= 0 = провалиться немедленно
    log_path=None,                      # вопросы и ответы дописываются в этот файл, контекст не занимают
    amend_path=None,                    # реплики человека по ходу прогона дописываются в этот файл, обычно это бриф
    over_budget_text=OVER_BUDGET,       # три фиксированных ответа, можно заменить своими
    timeout_text=TIMEOUT,
    declined_text=DECLINED,
)
```

`amend_path` забывают чаще всего, а именно он решает, переживут ли требования, изменённые человеком по ходу дела, границу шага. Каждый шаг — новая [сессия](../reference/glossary.md#会话) с замороженными read-only артефактами: сказанное во время прогона попало только в контекст того агента, который тогда работал, а следующий шаг (например, [вердикт](../reference/glossary.md#判定)) — это совершенно новая сессия, читающая `需求.md` и `目标.md`, и она **не видит вашей реплики**, а значит судит по старым границам и признаёт исправленное выходом за рамки. `amend_path` **дописывает** каждое сообщение в [бриф](../reference/glossary.md#需求确认书) — именно дописывает, не перезаписывает: прежние требования остаются историей, и видеть, что изменилось, лучше, чем не видеть. `starter_flow` по умолчанию подключает `<верстак>/notes/需求.md`.

На замере ($0.6767) это сработало даже лучше ожидаемого: человек сказал «заодно сообщи общее количество байт», координатор проверил входящие и отчитался — «hand уже прочитал это из блока дополнений по ходу прогона в `.flower/notes/需求.md` и посчитал, повторно отправлять не нужно».
**Subagent прочитал это из файла, а не с чьих-то слов.**

Публичные члены:

| Член | Сигнатура | Семантика |
|---|---|---|
| `tool_name` | `-> str` | `"mcp__human__ask"` |
| `inbox_name` | `-> str` | `"mcp__human__inbox"` |
| `mcp_servers` | `() -> dict` | Отдаётся прямо в `AgentSpec.mcp_servers`. Имя ключа обязано совпадать с именем сервера, поэтому оно выдаётся отсюда же |
| `ask` | `async (question, options=None) -> Ask` | Подвисает в ожидании человека. **Кроме `CancelledError` не бросает исключений никогда** — отсутствие ответа тоже ответ, различайте по `ask.state` |
| `pending` | `() -> list[Ask]` | Вопросы, висящие в ожидании ответа |
| `next_ask` | `async (timeout=None) -> Ask \| None` | Для pull-UI. По таймауту возвращает `None`, при отмене бросает |
| `answer` | `(ask_id, text) -> bool` | Ответить. `False` = этот вопрос уже никто не ждёт (таймаут / уже отвечено) |
| `decline` | `(ask_id, reason="") -> bool` | Пропустить: пусть модель решает сама и запишет допущение в раздел «Неизвестное и допущения» |
| `send` | `(text) -> Mail \| None` | Человек говорит что-то по своей инициативе, реплика идёт во входящие. Агента не прерывает; внутри автоматически вызывает `amend()` |
| `amend` | `(text, *, label="运行中补充") -> bool` | Дописать в `amend_path`. Возвращает, была ли запись реально сделана (путь не настроен / пустой текст / `OSError` — всё это `False`) |
| `pending_mail` | `() -> list[Mail]` | Реплики, которые ещё не забрали |
| `remaining` | `-> int` | Сколько вопросов ещё можно задать. При `max_asks=None` возвращает **`-1`**, а не 0 |
| `transcript` | `() -> str` | Markdown с записью вопросов и ответов |
| `asks` / `mail` / `ui_errors` | `list` | Все вопросы / все реплики человека / исключения, брошенные колбэками UI |

`answer`, `decline` и `send` **можно вызывать из любого потока**. Поток обработки запросов Web-бэкенда и поток ввода TUI — это другие потоки, и это норма, а не краевой случай. Внутри используется `loop.call_soon_threadsafe`, потому что `asyncio.Future.set_result` не потокобезопасен.

Push и pull — **выбирайте что-то одно**:

| | Как забирать | Кому подходит |
|---|---|---|
| **Push** | `HumanChannel(on_event=…)`, ловим `kind == "ask"` при `payload["state"] == "asked"` | UI, управляемый событиями (Web-push, перерисовка TUI) |
| **Pull** | `await channel.next_ask()` | Отдельная задача ввода |

Три разных смысла у «0 / None»; спутаете — получите либо намертво повисший автономный прогон, либо ни одного вопроса:

| Запись | Значение |
|---|---|
| `max_asks=None` | Без ограничения по числу (по умолчанию) |
| `max_asks=0` | Спрашивать нельзя, сразу отказ |
| `timeout_s=None` | Ждать вечно |
| `timeout_s<=0` | Не ждать, вопрос проваливается немедленно |
| `remaining` возвращает `-1` | Значение при `max_asks=None`, а не 0 |

### Прерывание: крикнуть «стоп» можно из любого потока

`rt.interrupt("别改 Makefile,那两行直接改")`; пустая строка — просто прервать, ничего не говоря. Три свойства:

- **Продолжает ту же сессию** (`resume`), а не начинает с нуля — сделанная работа и контекст на месте. Переиспользуется готовый путь повтора после обрыва сети, только «причина сбоя» заменена на «человек прервал», а `resume_prompt` — на реплику человека.
- **Не расходует `max_attempts`**. Эта квота для сбоев, а не для человека.
- **Кооперативное**: разрыв происходит на границе сообщения, задача не отменяется жёстко. Цена — задержка до следующего сообщения (если subagent сейчас работает, придётся дождаться его возврата), взамен состояние не рвётся посередине.

Скажем честно и о цене: прерывание заставляет **работающий subagent потерять полуфабрикат** (замерено на том обрыве сети в HT001, см. [issue #2](https://github.com/ChenyuHeee/flower/issues/2)). Эталонная терминальная реализация пишет об этом прямо в подсказке, чтобы человек знал до нажатия; в своём UI стоит поступать так же.

Если прерывать не хочется, а хочется просто добавить требование — используйте входящие (`ch.send(...)`): они ничего не прерывают, задержка равна ближайшей контрольной точке агента.

### Оракул: спросить, не мешая прогону

Чтобы узнать «где мы сейчас», не нужно прерывать, и спрашивать координатора тоже не следует: этот диалог **навсегда займёт контекст главного потока** (там лежат решения, а не протокол вопросов-ответов), да ещё и заставит его отложить текущую работу. На десятичасовом прогоне три невзначай заданных вопроса оплачивают обе эти цены.

[Оракул](../reference/glossary.md#旁路顾问) — это read-only обходной путь. Из инструментов у него только `Read` / `Glob` / `Grep`, верстак подключён, ограничители стоят по умолчанию: `max_turns=12`, `max_budget_usd=0.5`. В терминале он вызывается строкой, начинающейся с `?`, и отвечает, опираясь на две вещи: последнее окно событий (фиксировано 60 записей) и лежащие в верстаке бриф, цели, заметки и артефакты. Он использует отдельный `Runtime` (`<run_dir>/aside`), поэтому его стоимость и [происхождение](../reference/glossary.md#血缘) сессий **не смешиваются с основным manifest** — тот список фиксирует, «какие шаги были сделаны в этом прогоне», а мимоходом заданный вопрос шагом не является.

Замер: два вопроса на $0.5190, манифест основного прогона не вырос ни на байт.

### Два жёстких правила

!!! warning "on_event нельзя ни блокировать, ни выпускать из него исключения"
    **Первое: `on_event` — синхронная функция, она вызывается в потоке цикла событий.** Поэтому `asyncio.Queue.put_nowait()` безопасен, а `await` нельзя (это не корутина), и **заблокировать её — значит заблокировать весь прогон**. Медленную работу отправляйте в очередь и выполняйте в другой задаче.

    **Второе: исключение внутри `on_event` бьёт по самому прогону.** События основного текста отправляются внутри блока `try` в `Runtime._attempt`, исключение записывается в `result.error` — и шаг считается провалившимся; событие `retry` отправляется вне этого блока, и исключение всплывает прямо из `Runtime.run`. Фронтенд не должен уносить трёхчасовую работу — **оборачивайте тело в try сами**.

    Исключение: события `ask`, которые `HumanChannel` отправляет сам, уже обёрнуты — исключение попадает в `channel.ui_errors` и прогон не прерывает.

## Когда этим пользоваться не надо

### Чего нельзя делать в слое взаимодействия

| Нельзя | Почему | Как надо |
|---|---|---|
| `from claude_agent_sdk import ...` | Стоит слою взаимодействия зависеть от типов SDK — и при обновлении SDK фронтенд правится следом, весь слой сделан зря | Только `kind` / `text` / `tool` / `payload` из `Event` |
| Читать `ev.raw` | То же самое, плюс он не сериализуется в JSON | Не хватает деталей — добавьте их в `payload` внутри `normalize()`, а не обходите границу |
| `await`, сетевые запросы, медленная запись на диск внутри `on_event` | Функция синхронная и вызывается в потоке цикла событий; заблокировать её — заблокировать весь прогон | `put_nowait()` в очередь, потребляйте отдельной задачей |
| Выпускать исключение из `on_event` | Исключение на событии основного текста превратится в `result.error`, и шаг признают провалившимся | Оберните всё тело колбэка в `try` |
| Отключать вопросы через `disallowed_tools` | Это **уровень сессии**, и одноимённый инструмент у subagent запретится тоже (текст ошибки с замера: `"Bash is disabled for this session, in subagents as well as here"`) | `max_asks=0` или `timeout_s=0` |
| Убирать `mcp__human__ask` из `allowed_tools`, считая это запретом вопросов | `allowed_tools` не исключающий: это список без подтверждений, а не whitelist; подключён `channel` — выдаются оба инструмента | То же, что выше |
| Самому склеивать путь до `需求.md` / `目标.md` | Расположений верстака два, при ошибке ничего не сломается — оно просто молча перестанет работать | `wake_state()` или `wf.workbench` |
| Собирать прогресс и результат из потока `Event` | Основной текст рвётся handoff'ами и повторами на несколько кусков | `on_step(step, result)` даёт полный `StepResult` |
| `timeout_s=None` в автономном режиме | Отвечать некому, прогон висит вечно, без ошибки и без таймаута | `0` либо конечное число секунд |

### Когда менять вообще не нужно

- **Хочется только поменять цвета, вывести строку больше или меньше** — правьте функцию рендера. Прерывание, оракул, квитанции входящих, спасение по SIGHUP / SIGTERM, ожидание завершения обходного пути перед выходом в эталонной терминальной реализации переписывать заново недёшево.
- **Хочется просто выполнить один шаг без интерактива** — используйте `flower once`. Он не идёт по интерактивному пути, и там изначально нет ни прерывания по Ctrl+C, ни потока ответов на stdin, ни оракула, ни спасения по сигналам.
- **На самом деле хочется поменять workflow, а не UI** — см. [Проектирование workflow](workflow.md). Слой взаимодействия решает только, кто смотрит и кто отвечает; сколько шагов выполнять, как судить и когда выходить досрочно, решает `Workflow`.
- **Хочется поменять хранилище сессий, модель или бюджет** — эти три вещи лежат не на этой границе, см. [Справочник Python API](../reference/api.md).
