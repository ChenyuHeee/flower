# Преемственность

Запустите `flower` в том же каталоге ещё раз — и он продолжит тот же разговор с места, где остановился: процесс убили, терминал упал, машину перезагрузили — результат одинаковый. Вам не нужно знать слово session и не нужно помнить никаких id. Эта страница про то, на чём преемственность держится, когда она молча отказывает и как её намеренно отключить.

!!! note "Преемственность — это не смена поколения"
    [Преемственность](../reference/glossary.md#接续) — это **между процессами**: следующий процесс подхватывает предыдущий [прогон](../reference/glossary.md#运行).
    [Смена поколения](../reference/glossary.md#换代) — это **внутри одного прогона**: контекст почти заполнен, текущая [сессия](../reference/glossary.md#会话)
    пишет [документ передачи](../reference/glossary.md#交接书), и работу подхватывает новая сессия — см. [Смена поколения](handoff.md).

    Одно сцепляется с другим автоматически, ничего доводить руками не надо: [родословная](../reference/glossary.md#血缘) всегда помнит ту сессию, которая заступила на этот шаг **последней**, поэтому следующее пробуждение подхватывает именно преемника.

## Какую проблему это решает {#解决什么问题}

На диске, вообще-то, есть всё. В `runs/sessions.db` лежит **полный** transcript каждой исторической сессии, `需求.md` / `目标.md` — замороженные артефакты, код — в рабочей области.

**Теряется ровно одна строчка отображения** — «какой шаг какую сессию использовал». Раньше она жила только в памяти, в `ctx["_sessions"]`, и исчезала с выходом процесса. Новый процесс поднимался, и [координатор](../reference/glossary.md#协调者) оказывался новичком с амнезией: кого он посылал, какие тупики уже прошёл, почему отверг тот или иной вариант — всё заново.

В [HT002](../cases/ht002.md) он потратил час на перебор флагов компиляции. Смени процесс — и этот час прожит впустую.

## Как этим пользоваться (минимальный код) {#怎么用最小代码}

В командной строке настраивать нечего, на этом пути преемственность включена по умолчанию:

```bash
cd ~/proj && flower "写个 md 转 html 的脚本"     # 第一次
# …跑完,或者你按 Ctrl-C 走人,或者机器重启了

cd ~/proj && flower "顺便支持代码块高亮"          # 接着上次那段对话
cd ~/proj && flower                              # 什么都不说 = 接着做
cd ~/proj && flower --new "另一件事"              # 这次别接上次
```

Когда вы пишете свой [workflow](../reference/glossary.md#流程), преемственность тоже включена по умолчанию — значение `Workflow.continuous` по умолчанию равно `True`:

```python
import asyncio

from flower import AgentSpec, Runtime, Step, Workflow

terse = AgentSpec(
    name="terse",
    instructions="回答极简,一行以内,不解释不寒暄。",
    allowed_tools=["Read", "Glob"],
    max_turns=4,
)


async def main() -> None:
    wf = Workflow([Step("取词", terse, "读 seed.txt,只回文件里那个词。")])   # continuous по умолчанию True
    rt = Runtime(workspace=".", run_dir="runs")
    try:
        ctx = await wf.run(rt)
    finally:
        rt.close()
    print(ctx["_woke"])                  # какое это пробуждение по счёту, при первом запуске 1
    print(ctx["_sessions"])              # {"取词": "<session_id>"}


asyncio.run(main())
```

Выполните этот же код в том же каталоге второй раз: `ctx["_woke"]` станет `2`, а `ctx["_sessions"]["取词"]` будет **тем же самым id**, что и в первый раз — шаг «取词» продолжил прошлую сессию, а не открыл новую.

!!! tip "Просто узнать, подхватится ли этот каталог"
    `wake_state()` — это read-only проба, она **не пишет ни байта**:

    ```python
    from flower import wake_state

    st = wake_state(".", run_dir="runs")
    print(st["waking"], st["checks"], st["woke"], st["steps"])
    ```

    Возвращает `{"waking", "brief", "goal", "checks", "woke", "steps"}`. `waking` = бриф существует и все четыре раздела на месте;
    `checks` = сколько пунктов в списке проверок; `woke` = сколько раз уже было пробуждение; `steps` = отображение имён шагов в session_id.
    Именно на этом командная строка решает, спросить ли «что делаем» или «продолжаем прошлое».

## Что происходит на самом деле {#它实际做了什么}

### Три файла, которые ложатся на диск {#落在磁盘上的三个文件}

`run_dir` по умолчанию — `./runs`, **относительно текущего рабочего каталога, а не относительно workspace**.

| Путь | Что лежит |
|---|---|
| `runs/lineage.json` | Родословная: `{"workspace": "…", "woke": N, "steps": {"步骤名": "session_id"}}`. Вся преемственность держится на нём |
| `runs/sessions.db` | SQLite, полные transcript'ы. Таблицы — `entries` / `meta` / `summaries`, ключ — `project_key/session_id[/subpath]`; transcript'ы subagent'ов хранятся отдельно через subpath |
| `runs/manifest.json` | JSON-массив, манифест прогона, **накапливаемый между процессами**. По строке на шаг; единственное место, где потом можно найти session_id |

Файл родословной выглядит так:

```json
{
  "workspace": "/Users/you/proj",
  "woke": 3,
  "steps": {"干活": "47395075-bec7-466e-80cd-f4d60b360235"}
}
```

Каждая строка `manifest.json` — это все поля `StepResult`: `step`, `session_id`, `ok`, `cost_usd`,
`num_turns`, `text`, `error`, `started_at`, `ended_at`, `attempts`, `errors[]`, `resumed`,
`retired[]`, `context` — плюс дописанные вручную `duration_s` (это `@property`, `asdict()` его не забирает) и
`run` (метка процесса, `YYYYmmdd-HHMMSS-<6 位 hex>`).

Имя шага встречается там в четырёх формах, по которым сразу видно, как шаг завершился: `<步骤名>` (первая попытка),
`<步骤名>#retry<N>` (обычный ретрай), `<步骤名>#round<N>` (вердикт не прошёл, шаг вернули на доработку),
`<步骤名>·判定#<N>` (раунд [судьи](../reference/glossary.md#判定者)).

Запись **добавляет, а не перезаписывает**: перед каждым сбросом на диск файл перечитывается, дубликаты отсеиваются по полю `run` — строки этого процесса заменяются на свежие, чужие остаются как были. Поэтому параллельно запускать несколько flower в одном каталоге безопасно.

### `continuous=True` меняет семантику `resume_from` {#continuoustrue-改变了-resume_from-的语义}

Это то, что пропускают чаще всего: `Workflow.continuous` по умолчанию `True`, а значит `resume_from=None`
**не равно «совершенно новая сессия»**.

| Как написано | Внутри одного прогона | Между процессами (`continuous=True`) |
|---|---|---|
| `resume_from=None` (по умолчанию) | Новая сессия, только с контекстом из prompt | **Берёт сессию одноимённого шага из родословной и продолжает её** |
| `resume_from="上一步名"` | Продолжает ту же сессию, полный контекст | Так же |
| `resume_from=…, fork=True` | Ветвление, исходная сессия не загрязняется | Так же |

Чтобы каждый процесс стартовал с чистой новой сессии, нужно явно написать `Workflow(..., continuous=False)`.

При загрузке родословной есть ещё одна проверка: для каждой прочитанной пары `(имя шага, session_id)` сначала вызывается `runtime.has_session(sid)`, чтобы убедиться, что сессия ещё есть в `sessions.db`; используется только живая. Причина в том, что файл родословной может пережить `sessions.db`, а resume несуществующей сессии падает только после запуска дочернего процесса.

!!! warning "Имя шага — это ключ, стабильный между процессами"
    Родословная индексируется по `Step.name`. **Переименовали шаг — оборвали родословную**: ошибки не будет, просто следующий запуск начнётся с новой сессии.
    Имена с суффиксами (`#retry`, `#round`, `·判定#`) в родословную не попадают, `Lineage.remember` всегда работает с исходным именем.

### Два инварианта {#两条不变式}

**Первый: как только получен session_id — сразу пишем на диск, не дожидаясь конца шага.**

Жёсткое убийство процесса — ровно тот сценарий, от которого мы защищаемся. Мы на этом уже погорели: 2026-09-07 Terminal.app падал дважды, ядро слало SIGHUP, а действие SIGHUP по умолчанию — немедленное завершение, `finally` не выполняется вообще. Тогда родословная писалась **на границах шагов**, поэтому у прогона, умершего внутри первого шага, `steps` оказался пустым, и человека заставили заново отвечать на уже отвеченные вопросы (см. issue #6).

Теперь `Runtime.on_session` пишет на диск в тот момент, когда id получен — фактически это первое assistant-сообщение, init-сообщение системы в Python SDK не несёт `session_id`. Запись идёт сначала в `.tmp`, затем атомарная замена, поэтому убийство на полпути не оставит половинчатый файл; ошибка записи (`OSError`) молча проглатывается и прогон с собой не уносит.

Этот хук **накрывает только вызов `runtime.run`**, до gate его снимают через `try/finally`. Судья использует тот же `Runtime`, и если хук останется висеть, его сессия попадёт в родословную рабочего шага.

**Второй: не сошлось — считаем, что ничего нет, и не ругаемся.**

Не сойтись может тремя способами: изменился путь рабочей области (каталог скопировали — [HT001](../cases/ht001.md) как раз вытаскивали из контейнера), сессии больше нет в базе (удалили `sessions.db`), файл родословной побит. Любой из случаев молча откатывает к «начинаем с нуля».

Поле `workspace` — это страж: `project_key` в SDK выводится из пути рабочей области (`/`, `_`, `.` заменяются на `-`), и после переноса каталога старый session_id на новом месте просто не находится, поэтому при несовпадении пути считаем, что ничего нет.

**Преемственность — это приятный бонус, её отказ не должен мешать человеку работать.**

### Убитый процесс и перезагрузка машины {#进程被杀和机器重启}

Результат у обоих одинаковый — подхватывается, — но происходит разное:

| Ситуация | Что произошло | Следующий запуск |
|---|---|---|
| `Ctrl-C` один раз | Кооперативное прерывание, чистый разрыв **на границе сообщения**. Можно заодно что-то сказать и внутри того же процесса продолжить ту же сессию через resume. Прерывание не считается неудачной попыткой и не съедает квоту ретраев | Преемственности не касается |
| `Ctrl-C` дважды | Сразу бросается `KeyboardInterrupt` и процесс выходит. Из завершающих действий выполняется только закрытие хранилища, **шаг «в полёте» в `manifest.json` не попадает** | Родословная давно на диске, подхватится |
| `SIGTERM` / `SIGHUP` | Обработчик сначала вызывает `rescue()` и дописывает шаг «в полёте» в `manifest.json` (с пометкой `error="killed-by-signal"`), затем восстанавливает действие по умолчанию и действительно уходит | То же самое, подхватится |
| `SIGKILL`, отключение питания, перезагрузка | Никаких завершающих действий | Подхватится точно так же — все три файла на диске, родословная пишется в момент получения id |

Условие ровно одно: **тот же `workspace` и тот же `run_dir`**. `run_dir` отсчитывается от текущего рабочего каталога, поэтому `flower`, набранный из другого каталога, пойдёт искать другой `runs/` и ничего не подхватит.

### Судья — всегда новая сессия {#判定者永远是新会话}

Это гарантировано **конструкцией**, а не тем, что кто-то не забыл.

Судья — не `Step`: его отправляет напрямую `rt.run()` внутри gate у `with_goal`
(см. [Страж цели](goal.md)), и через родословную он не проходит никогда. Поэтому в каждом раунде и на каждом пробуждении это свежая пара глаз.

В этом и вся его ценность: **он не знает, сколько раз исполнитель пробовал и как ему было тяжело, а значит не станет искать за него оправдания.**
Дай ему преемственность — и страж цели выродится в самоаудит.

Раздел 4 в `tests/lineage_offline.py` фиксирует это намертво.

### Фраза, сказанная при пробуждении, должна попасть в три места {#唤醒时说的那句话要落到三个地方}

`flower "顺便支持代码块高亮"` в уже использованном каталоге — это **не новая задача, а ещё одна реплика**.
Она делает три вещи одновременно, и без любой из них молча ломается:

| Куда попадает | Что будет, если не попадёт |
|---|---|
| Дописывается в `需求.md` (`## 唤醒时追加`) | Не переживёт границу шага. Следующий шаг — новая сессия, читает только замороженные артефакты |
| Становится prompt'ом рабочего шага | Координатор её просто не получит |
| **Запускает перевывод `目标.md`** | Судья читает старый список, и **сделано ли новое требование, в вердикт вообще не входит** |

Третье пропускают чаще всего. Судья читает только замороженный `目标.md`, ваше добавление по ходу он не видит — без перевывода он вынесет «достигнуто» по старому списку, а то, ради чего вы всё затевали, никто не проверял. Цена — один лишний прогон постановки цели на каждое добавление ([HT002](../cases/ht002.md), замер: $0.41 / 3 минуты).

**Пробуждение молча** (просто Enter) ничего не дописывает, ничего не перевыводит и не стоит ни цента.

### Падение внутри первого шага (уточнение требований) тоже подхватывается {#崩在第一步确认需求之内也能接上}

У `clarify_step` есть `resume_prompt` (константа `CLARIFY_RESUME`): если упало посреди уточнения, при следующем старте [уточнителю](../reference/glossary.md#确认者) говорят «продолжай то незаконченное уточнение требований — не начинай заново», а не отправляют исходный запрос как новую задачу. В связке с инвариантом «получил session_id — сразу пишем на диск» прогон, умерший на первом шаге, когда `需求.md` ещё не заморожен, теперь тоже подхватывается, и отвечать заново не надо.

Обратная ситуация: уже замороженные предшествующие шаги **пропускаются целиком**: если в `需求.md` есть все четыре раздела, шаг 确认需求 пропускается (но содержимое всё равно заливается в ctx), если в `目标.md` всё на месте — пропускается 设定目标.

### При продолжении отправляется не та же самая фраза {#接续时发的不是同一句话}

За это отвечает `Step.resume_prompt`. В контексте собеседника **уже есть** бриф, цели и то, до чего он дошёл в прошлый раз; отправить ему ещё раз «сделай по этому брифу: <весь бриф целиком>» — чистый шум, а хуже того, это читается как «требования изменились, перечитай заново».

Если `resume_prompt` не задан, используется `prompt` — некоторым шагам как раз положено переслать текст полностью (постановке целей при перевыводе списка нужен именно весь бриф).

### При пробуждении сначала печатается строка {#唤醒时先报一行}

```text
<- 在 ~/explore/test-ide 接上上次  需求已确认 · 目标 15 条 · 干活上下文 80.2K · 第 3 次唤醒

== 干活 ==============================  3/3  <- 接上次 · 第 3 次唤醒
```

Без неё «помнит ли оно вообще что-нибудь» никак не воспринимается, а это и есть вся ценность этого слоя. В баннере `需求已确认` есть всегда, `目标 N 条` — только если список проверок непуст, `干活上下文 X` — только если в `sessions.db` удалось найти размер контекста последнего раунда той сессии.

**Число контекста выставлено напоказ намеренно** — почему, см. ниже в разделе «Цена».

### Устойчивость: висим и ждём при обрыве сети, и ошибки не попадают в контекст после resume {#韧性断网时挂着等而且错误不进接续后的上下文}

[Устойчивость](../reference/glossary.md#韧性) идёт в комплекте с преемственностью: за несколько часов работы сеть обязательно оборвётся хотя бы раз, а поведение по умолчанию отвратительное — в момент обрыва harness вставляет в transcript **синтетическое assistant-сообщение** (`isApiErrorMessage=true`, `model="<synthetic>"`) с текстом «API Error: Can't reach the API server …». Это сообщение становится листом сессии, и при следующем resume его скармливают обратно как «то, что модель сказала в прошлой реплике» — модель решает, что обсуждает сетевой сбой.

`Resilience` делает три вещи:

**Первое: проба — только DNS + TCP.** `reachable(host, port, timeout=5.0)` выполняет `getaddrinfo` и одно TCP-рукопожатие,
**никакого HTTP, никаких учётных данных, никаких денег**; любое исключение считается недоступностью. Какой адрес проверять, решает `endpoint()`, он следует за `ANTHROPIC_BASE_URL`, по умолчанию `https://api.anthropic.com`, порт по умолчанию `443` (для http — `80`).
**Со своим шлюзом проверять надо именно шлюз** — доступность `api.anthropic.com` ничего не говорит о доступности шлюза.

**Второе: отличать то, чего стоит ждать, от того, на чём надо останавливаться.** `classify(text)` возвращает `"transient"` / `"fatal"` / `"unknown"`,
причём **сначала проверяется fatal, потом transient** — в текстах вроде 401 часто встречается слово «connection», и при обратном порядке можно ждать вечно.
Значения по умолчанию: `max_attempts=6` (включая первую), `base_delay=4.0`, `max_delay=120.0`, `probe_timeout=5.0`,
`probe_interval=15.0`, `max_offline_wait=3600.0` (1 час), `retry_unknown=True`.
Отступ — `min(base_delay * 2**(attempt-1), max_delay)`, умноженный на джиттер ±25%.

Если session_id уже был получен, происходит **resume, а не старт с нуля**, и потраченное раньше не пропадает. При продолжении отправляется
`Resilience.resume_prompt`: «прошлый раунд был прерван посередине и не доведён до конца. Посмотри, что уже записано на верстак, и продолжай с места обрыва, не начинай заново». В нём **намеренно нет никаких деталей ошибки** — модели нужно знать «тебя прервали, продолжай», а не то, был это ENOTFOUND или 503.

**Третье: ошибки, порождённые штормом ретраев, не попадают в контекст после resume.** Этим занимается [обрезка](../reference/glossary.md#剪除).
Хранилище сессий в `Runtime` жёстко задано как `PruningSessionStore`, и при `load()` оно делает три вещи:

- Выкусывает синтетические сообщения об ошибках API. **В SQLite они остаются как есть**, просто не скармливаются обратно
- Выкусывает старые отклонённые вызовы, оставляя только последние `keep_denials=1`
- Заменяет `tool_result`, оставшийся от прерывания, нейтральным пояснением «[прошлый раунд прерван в этом месте, результат инструмента не получен]» — меняется только текст, сама запись остаётся

Оставлять 1, а не 0 — обоснованно: отклонённый вызов никогда не выполнялся, информации в результате нет, а места он занимает немало
(замер: один такой — 273 символа = 93 символа отказа + 180 символов **текста самой запрещённой команды**), и **он вводит в заблуждение** — на замере координатор, прочитав несколько «не используй Bash напрямую», перестал пробовать даже разрешённый `git status`, то есть выучил беспомощность. Но самая свежая запись полезна: она мешает модели в том же раунде раз за разом повторять одну и ту же перехваченную команду.

У выкусывания есть структурная красная линия: transcript — односвязная цепочка по `parentUuid`, и, выкусив запись, надо перецепить её детей к ближайшему живому предку, иначе цепочка обрывается и вся предшествующая история теряется.

В [HT001](../cases/ht001.md) это сработало на практике: обрыв сети 01:52:40 → 01:55:41, в `manifest.json` этот шаг помечен
`attempts=2` / `resumed=True` / `ok=True`, а после продолжения он проработал ещё больше 8 часов до завершения.

Последнее легко понять неправильно: **`Runtime(trim=False)` не означает «ничего не чистим»**. `trim` и так по умолчанию `False`,
но он выключает только слой **[усечения](../reference/glossary.md#裁剪) больших результатов инструментов**. Выкусывание мусора от обрывов, выкусывание отклонённых вызовов,
нейтрализация остатков прерывания, пометка результатов [одноразовых команд](../reference/glossary.md#一次性命令) как устаревших — эти четыре вещи делаются всегда
(`ephemeral` по умолчанию `True`, `keep_denials` по умолчанию `1`).

### Цена: контекст растёт всё время, и конца этому нет {#代价上下文会一直涨而且没有尽头}

Это неотъемлемая цена преемственности, а не баг.

Шаг «干活» в [HT001](../cases/ht001.md) шёл подряд 10.44 часа, контекст [главного потока](../reference/glossary.md#主线程)
на 1-м раунде — **28.7K**, на 20-м — **35.2K**, на 35-м — **108.6K**, на 50-м — **158.2K**, на 70-м — **185.9K**,
монотонный рост, наклон около **2.2K на раунд**; за весь прогон ни одного compact, израсходовано **18.6%** окна в 1M. Экстраполируя этот наклон,
в стену упрёмся примерно на **440-м раунде** — предел «long-horizon» в нынешнем виде примерно в **6 раз** больше того прогона. Вечная преемственность означает, что однажды вы упрётесь в окно.

Этим управляют два механизма:

1. **Усечение** (`flower --no-trim` выключает, на пути `flower` включено по умолчанию) — при resume старые большие результаты инструментов заменяются указателями на файлы, содержимое не потеряно, просто не сидит в контексте постоянно
2. **[Смена поколения](handoff.md)** — по достижении порога пишется документ передачи и берётся новая сессия. **Это не [compact](../reference/glossary.md#压缩)**:
   документ читаем и правим, вы видите, что потеряли. Поэтому контекст периодически падает вниз, а не растёт до самой стены

**Поэтому строка при пробуждении обязана печатать размер контекста**: человек видит цифру — значит, у него есть шанс самому решить начать заново до того, как всё упрётся в стену.

Заодно: `--rounds` (общее число рабочих раундов) **сбрасывается на каждом пробуждении**. Это сделано намеренно — новое пробуждение есть новое намерение, и наследовать израсходованные в прошлый раз раунды оно не должно.

### Начать заново {#重开一件事}

```bash
flower --new "另一件事"
```

Или прямо в приглашении пробуждения набрать `/new`:

```text
接着上次? 直接回车 = 接着做;也可以说点新的;/new = 重开一件事(Ctrl-C 退出)
> /new
要做什么? 一句话就够,回车开始(Ctrl-C 退出)
> …
```

**Архивируем, не удаляем.** `lineage.json`, `需求.md`, `目标.md` вместе **перемещаются** в `notes/archive/<YYYYmmdd-HHMMSS>/`, а `steps` и `woke` в родословной одновременно обнуляются. Все три — три грани одной и той же истории, и убрать только часть значит оставить полусостояние вида «цели ещё есть, а разговора уже нет».

`sessions.db` не трогается — это архив, каждый transcript в нём по-прежнему доступен для просмотра.

В коде этому соответствует `Lineage.archive(into, extra=[...])`.

## Когда этим пользоваться не стоит {#什么时候不该用它}

- **Сценарии, где каждый раз нужна чистая точка старта.** Пакетный прогон одного и того же workflow, контрольные замеры, воспроизведение бага для другого человека — во всех этих случаях тащить прошлый контекст нельзя. Пишите `Workflow(..., continuous=False)` или каждый раз меняйте `run_dir`.
- **Каталог будут переносить, копировать, или `run_dir` непостоянен.** Запуск в контейнере, где `runs/` лежит на внутренней файловой системе контейнера, или rsync рабочей области на другую машину — преемственность **молча откажет** (страж пути отвергнет несовпавшую родословную), не считайте её гарантией.
- **Намерение новое, а контекст уже большой.** Преемственность потащит за собой всю нерелевантную историю, и вы будете платить за неё токенами в каждом раунде. Лучше не терпеть, а сделать `--new`: заархивировать и начать заново.
- **Одноразовый одиночный агент.** `flower once` не проходит через `Workflow`, родословной у него нет; чтобы продолжить, придётся самому передать `--resume <session_id>`.
- **Использовать преемственность как резервную копию.** Она помнит только «какой шаг какую сессию использовал». Код, артефакты и решения должны оседать в рабочей области и на [верстаке](../reference/glossary.md#工作台), выкапывать их из transcript'ов не следует.
