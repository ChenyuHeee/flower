# Проектирование workflow

Фреймворк отвечает только за механику: как выполняется шаг, как сцепляются сессии, что делать при сбое, как экономить контекст.
**[Workflow пишете вы](../reference/glossary.md#流程)** — фреймворк не знает, какой у вас проект и на каком языке,
и знать не должен. Эта страница о том, как спроектировать workflow; полные таблицы полей `Step` и `Workflow` —
в [Python API](../reference/api.md).

## Какую проблему решает {#解决什么问题}

Один [long-horizon](../reference/glossary.md#长程) прогон не умещается в одну фразу prompt: сначала выяснить требования,
потом исследовать, потом реализовать, потом проверить — у каждого отрезка своя роль, свой контекст, свои критерии приёмки.
Если запихнуть всё в один промпт, модель сама решит, какой отрезок пропустить; если оформить это как workflow, то
**порядок, условия выхода и передача состояния становятся кодом на Python** — читаемым, тестируемым, с возможностью
перезапустить только сломавшийся шаг.

`Workflow` делает ровно три вещи:

- выполняет цепочку [шагов](../reference/glossary.md#步骤) по порядку;
- решает, что каждый шаг видит из предыдущих (три способа сцепки сессий + один словарь `ctx`);
- решает, когда повторять и когда выходить досрочно.

В нём нет никаких предметных допущений. Где резать, что принимать на каждом шаге, что делать при непрохождении — вот эти четыре вопроса и есть «проектирование workflow».

## Как этим пользоваться (минимальный код) {#怎么用最小代码}

```python
# flows.py
from flower import AgentSpec, Step, Workflow

terse = AgentSpec(
    name="terse",
    instructions="回答极简,一行以内,不解释不寒暄。",
    allowed_tools=["Read", "Glob"],
    max_turns=4,
)


def main() -> Workflow:
    return Workflow([
        # Новая сессия: видит только то, что передано в prompt
        Step("取词", terse, "读 seed.txt,只回文件里那个词。"),
        # Тоже новая сессия, результат предыдущего шага инъектируется в prompt (дёшево, защищает от загрязнения)
        Step("造句", terse, lambda ctx: f"用「{ctx['取词']}」造一个五字短句,只回短句。"),
    ])
```

```bash
flower run flows.py:main -w /path/to/repo
```

Аргумент `flower run` — это `модуль:атрибут` или `путь_к_файлу:атрибут`. Если полученный объект вызываемый, он сначала вызывается один раз;
затем полученный `Workflow` запускается. По окончании в терминал печатаются суммарные расходы и путь к манифесту прогона.

Можно написать и собственный драйвер — первый аргумент `Workflow.run` это `Runtime`:

```python
ctx = await wf.run(rt, on_step=lambda step, r: print(f"{step.name} ok={r.ok} ${r.cost_usd:.4f}"))
```

## Что он делает на самом деле {#它实际做了什么}

### Что получает Step и что обязан вернуть {#一个-step-收到什么必须返回什么}

`Step` — это не функция, а **декларация**. Реально выполняется `Runtime.run(step.spec, отрендеренный prompt, ...)` —
**один шаг = один вызов `Runtime.run` = одна [сессия](../reference/glossary.md#会话)**.

Первые три поля — позиционные аргументы, `Step(name, spec, prompt)`:

- `name` — имя шага. Оно же ключ в `ctx`, оно же имя строки в `runs/manifest.json`, оно же ключ
  межпроцессной [родословной](../reference/glossary.md#血缘).
- `spec` — каким `AgentSpec` выполнять. Задаёт белый список инструментов, модель и бюджет этого шага.
- `prompt` — `str` либо `(ctx) -> str`. Вызываемый вариант получает текущий `ctx`;
  **это самый дешёвый способ подать результат предыдущего шага** (второй — сцепить сессии, см. ниже).

«Возвращает» шаг объект `StepResult`, но в workflow вы получаете две вещи:

- `ctx[step.name]` — по умолчанию `result.text`; если задан `reduce` — то, что вернул `reduce`;
- `ctx["_results"][step.name]` — полный `StepResult` (расходы, число ходов, число попыток, `session_id`).

`result.text` **собирает только основной текст главного потока**: реплики subagent лежат в его собственном transcript,
выданное ему [задание](../reference/glossary.md#任务书) имеет `kind="prompt"`, синтетическая ошибка обрыва — `kind="error"`,
ни то, ни другое, ни третье внутрь не попадает.

### reduce: это не сахар {#reduce不是糖}

По умолчанию дальше передаётся дословный ответ модели. У некоторых шагов дословный ответ **не должен** идти дальше как есть:

```python
Step("确认需求", spec=确认者, prompt="帮我做一个 X",
     reduce=lambda r, ctx: ctx["_brief"].prompt_block())
```

На практике шаг уточнения требований, помимо четырёх разделов, **вклеивает в ответ весь код целиком**. Дальше по цепочке
должны идти именно разобранные четыре раздела, иначе вся эта груда кода попадёт в prompt следующего шага. `clarify_step`
подстрахован как раз этим полем.

`reduce` **обязан быть синхронной функцией**; `gate` / `when` / `on_reject` могут быть async.

### Как состояние течёт через ctx {#状态怎么在-ctx-里流动}

`ctx` — это `dict[str, Any]`, то есть сам `Workflow.context`. После каждого шага запись идёт по такой таблице:

| Ситуация | `ctx[имя шага]` | Остальное |
|---|---|---|
| `when(ctx)` вернул False | **не пишется**, шаг пропускается целиком | result не создаётся, в `_results` тоже не попадает |
| Пройден | `reduce(result, ctx)`, если не задан — `result.text` | |
| Сбой + `on_fail="stop"` (по умолчанию) | **не пишется** | пишется `ctx["_failed_at"]`, весь workflow останавливается на этом шаге |
| Сбой + `on_fail="skip"` | **не пишется** | выполнение продолжается дальше |
| Сбой + `on_fail="continue"` | `result.text` (неполный, **без `reduce`**) | выполнение продолжается дальше |

Независимо от прохождения, `ctx["_results"][имя шага]` пишется всегда; если `result.session_id` не пуст, он также
пишется в `ctx["_sessions"]` и попадает в родословную.

**Успешность прогона определяется по `ctx.get("_failed_at")`**, а не по наличию вывода у последнего шага.

Все ключи, начинающиеся с подчёркивания, кладёт сам `Workflow.run`: `_runtime`, `_on_event`, `_sessions`, `_results`,
`_lineage`, `_woke`, `_aborted`, `_failed_at` — не используйте их как имена своих шагов. Отдельные механизмы кладут ещё
свои (`_brief` / `_goal` / `_verdict` и т. д.), полный список — в [Python API](../reference/api.md).

Из них `_runtime` и `_on_event` предназначены для `gate`: gate может сам отправить агента вынести вердикт,
и процесс вынесения вердикта при этом всё равно виден в UI — иначе эти десять-двадцать секунд экран пустой
и выглядит как зависание. [Страж цели](goal.md) реализован именно так.

`ctx` — это один и тот же dict: **если запустить один и тот же объект `Workflow` второй раз, ключи с прошлого раза останутся**.
Нужен чистый старт — создайте новый объект или явно передайте `context={}`.

!!! warning "При on_fail=skip `ctx[имя шага]` не пишется"
    Нижестоящий `lambda ctx: ctx["некий шаг"]` тогда сразу упадёт с `KeyError`. Чтобы идти дальше с неполным результатом,
    используйте `on_fail="continue"`; если шаг действительно надо пропустить, нижестоящий код должен сам подстраховаться через `ctx.get(...)`.

### Вердикт и возврат на доработку: gate, on_reject, StepAbort {#判定与打回gateon_rejectstepabort}

`gate(result, ctx) -> bool` отвечает на вопрос «отработало, но годится ли». Две обязательные к пониманию детали:

- **Если `result.ok` ложен, `gate` вообще не вызывается** (короткое замыкание).
- **За попытку он вызывается ровно один раз**, вывод сохраняется для дальнейшего использования — у него могут быть побочные эффекты.
  Gate в `clarify_step` сбрасывает [бриф](../reference/glossary.md#需求确认书) на диск, повторный вызов означает повторную запись.

Как всё повторяется после непрохождения gate, зависит от того, задан ли `on_reject`:

| | Как выполняется следующий раунд | Имя в manifest |
|---|---|---|
| Только `retries` | С самого начала: исходный prompt, исходный `resume_from` | `X#retry1` |
| Плюс `on_reject` | **Продолжает ту самую отвергнутую сессию**, prompt заменяется на возвращённое из `on_reject`, `fork` принудительно False | `X#round2` |

Второй вариант — это «вернуть на доработку, указать, чего не хватает, и дать дописать»: уже сделанная работа и контекст остаются на месте.
Если `on_reject` вернул пустую строку или та попытка вообще не получила `session_id`, всё вырождается в запуск с начала.

`gate` может также бросить `StepAbort`, что означает **пробовать дальше бесполезно, не тратьте оставшиеся попытки**:

```python
from flower import StepAbort

def gate(result, ctx):
    if "这个环境装不了依赖" in result.text:
        raise StepAbort("环境缺依赖,再跑几轮也一样")
    return "验收通过" in result.text
```

После броска: причина пишется в `ctx["_aborted"]`, шаг считается сбойным и обрабатывается по `on_fail` (по умолчанию `"stop"`),
**цикл ретраев тут же прерывается**, ни одна из оставшихся `retries` не тратится.

Запомните разницу: **вернуть False — это «в этот раз не вышло, ещё раунд»; `StepAbort` — «ещё раз не поможет».**
Типичный случай: цель признана невыполнимой в этом окружении и спросить некого — продолжать вхолостую тут самый дорогой вариант.

### Не путайте два слоя ретраев {#两层重试别混}

| | `Step.retries` | `Runtime(resilience=...)` |
|---|---|---|
| За что отвечает | Прикладные сбои: gate не пройден, `result.ok` ложен | Инфраструктура: дрожь сети, обрыв связи, 5xx |
| Как повторяет | **Шаг целиком заново**, тот же prompt и тот же `resume_from` | **Resume с места обрыва**, ранее потраченное не пропадает |
| Что делает до этого | Ничего | Держит DNS + TCP-пробы и ждёт возврата сети (без HTTP, без учётных данных — проба обязана быть бесплатной) |
| Что не повторяется | —— | Ошибка учётных данных или параметров останавливает сразу, без бесконечного ожидания |

Prompt, которым делается resume, **намеренно не содержит никаких деталей ошибки** — модели нужно знать «тебя прервали, продолжай»,
а не то, был ли это ENOTFOUND или 503.

### Как сцеплять шаги {#把步骤串起来}

Состояние между шагами передаётся тремя способами; выбор определяет, что увидит следующий шаг:

| Запись | Что видит следующий шаг | Где применять |
|---|---|---|
| `resume_from=None` (по умолчанию) + инъекция в prompt | Только те слова, которые вы инъектировали | Шаги независимы. Дёшево, защищает от загрязнения |
| `resume_from="имя предыдущего шага"` | Полную историю сессии | Нужна связная память |
| `resume_from="имя предыдущего шага"` + `fork=True` | Полную историю, но в отдельной ветке | Ревью / параллельные варианты / ретраи не пачкают исходную линию |

Шаг, на который указывает `resume_from`, **обязан действительно породить сессию**. Если он был пропущен через `when` или вовсе не выполнялся,
`Workflow.run` бросает `ValueError` — без молчаливой деградации до новой сессии, потому что это тихо ломало бы допущение о «связной памяти».

Несколько выводов, за которые уже не раз было плачено:

1. **Один шаг — одна принимаемая цель.** Граница шага и есть граница контекста: там, где `resume_from=None`,
   все предыдущие результаты инструментов перестают постоянно висеть в контексте. См. [Экономику контекста](context.md).
2. **Сомневаетесь — начните с `clarify_step`.** В long-horizon прогоне «неправильно понята цель» — самая дорогая ошибка,
   и именно она относится к тому классу, который несколько слоёв экономии контекста вычистить не могут. См. [Предварительное уточнение](clarify.md).
3. **Выдаваемое задание должно быть самодостаточным.** У subagent чистый контекст, он не знает того, что знает
   [координатор](../reference/glossary.md#协调者). Нужный фон пишите в задание или скажите, какой artifact прочитать.
4. **Длинные результаты — на диск, а не в ответ.** Это уже прописано в `WORKER_RULES`; не отменяйте это своими
   `instructions` («вставь полный лог обратно, чтобы я посмотрел»).
5. **`gate` в первую очередь проверяет жёсткие условия.** Есть ли файл, равен ли код возврата нулю — то, что решается одной строкой на Python, не поручают модели.
   Если решать должна модель — берите готовый `with_goal`: он подменяет gate реализацией, запускающей отдельного
   [судью](../reference/glossary.md#判定者); не городите то же самое руками внутри gate.
6. **Параллельные правки одного репозитория — только `worker(isolate=True)`.** Завершающие действия (merge, уборка worktree, открытие PR)
   пока остаются на вашем workflow, harness лишь гарантирует, что правки лягут каждая в свой worktree.

### Workbench должен висеть на Workflow {#工作台要挂在-workflow-上}

Везде, где workflow пишет файлы в [workbench](../reference/glossary.md#工作台) — типичный случай
`clarify_step(brief_path=...)` — нужно самому создать `Workbench` и **одновременно** повесить его на `Workflow.workbench`
и передать в `Runtime`:

```python
from pathlib import Path

from flower import (HumanChannel, Runtime, Step, Workbench, Workflow,
                    clarify_step, coordinator, worker)

wb = Workbench(Path.cwd()).ensure()
ch = HumanChannel(log_path=wb.notes / "问答记录.md", timeout_s=1800.0)

主控 = coordinator("协调者", "", {
    "coder": worker("写代码与测试。要动手实现的活派给它。",
                    "你负责实现。每改一处就跑一次验证,别攒到最后。"),
}, channel=ch)

wf = Workflow(
    [
        clarify_step(ch, brief_path=wb.notes / "需求.md", prompt="帮我做一个 X"),
        Step("干活", spec=主控, prompt=lambda ctx: f"照这份需求做:\n\n{ctx['确认需求']}"),
    ],
    channel=ch,
    workbench=wb,
)

rt = Runtime(workspace=Path.cwd(), run_dir="runs", workbench=wb)
```

Вешать `channel` на workflow нужно по двум причинам: `run()` подключит его `on_event` к тому же выходу событий
(только если `channel.on_event` всё ещё `None`), а драйвер по этому же полю узнаёт, кому отвечать.

!!! warning "Самостоятельная сборка пути workbench молча ломается"
    Место по умолчанию для `Runtime(workbench=True)` — `<run_dir>/workbench`, а для `Workbench(ws)` — `<ws>/.flower`;
    **это не один и тот же каталог**. Когда workflow вызывается из CLI, он не видит `run_dir`, так что собранный вручную путь
    ведёт куда-то не туда: бриф пишется в каталог A, а инъектируемый индекс сканирует каталог B — **и ошибки при этом нет**.
    Создайте один объект и используйте его с обеих сторон — проблемы не будет; при наличии `Workflow.workbench` ключ `-W`
    в командной строке игнорируется, приоритет у него.

### `continuous=True`: повторный прогон по тому же пути {#continuoustrue同一个路径再跑一次}

Три способа сцепки выше касаются шагов **внутри одного прогона**. Межпроцессная сцепка — другая ось:

```python
Workflow([...], continuous=True)     # значение по умолчанию
```

При повторном прогоне в том же рабочем каталоге каждый шаг продолжает свою прошлую сессию — за счёт связки
«имя шага → session_id» в `<run_dir>/lineage.json`. При загрузке каждая запись проверяется через `runtime.has_session()`,
что сессия ещё есть в хранилище, и используется только живая: файл родословной может пережить `sessions.db`,
а resume несуществующей сессии падает только после запуска дочернего процесса.

Три следствия:

- **`resume_from=None` не равно «совершенно новая сессия».** В первый прогон — да, во второй — нет. Если новая сессия нужна каждый раз,
  пишите явно `Workflow(..., continuous=False)`.
- **При [непрерывности](../reference/glossary.md#接续) контекст будет только расти.** Если при продолжении надо сказать что-то иное, задайте
  `Step.resume_prompt` — то, что уже есть в контексте собеседника, повторно отправлять не следует.
- Шаги с явно заданным `resume_from` это не затрагивает, у него приоритет.

!!! warning "Имя шага — это межпроцессный ключ"
    Изменить имя шага значит оборвать родословную этого шага: в следующий прогон продолжения не будет, **и ошибки не будет тоже**.
    Имена ретраев с суффиксами `#retry1` / `#round2` **в родословную не попадают** (записывается всегда исходное имя) — это в том числе
    один из способов реализации правила «судья всегда в новой сессии».

Полный дизайн и `--new` — в [Непрерывности](continuity.md).

## Когда его не надо использовать {#什么时候不该用它}

- **Запускается один агент и вердикт не нужен** — не надо оборачивать в `Workflow`. Просто `await rt.run(spec, "…")`
  или из командной строки `flower once "读一眼这个仓库"`.
- **Форма ровно такая: «уточнить требования → задать цель → работать»** — берите готовый
  [`starter_flow()`](https://github.com/ChenyuHeee/flower/blob/main/flower/workflow/starter.py),
  писать самому не нужно:

    ```python
    from flower import starter_flow

    wf = starter_flow("帮我做一个 X", workspace=".", run_dir="runs",
                      rounds=3, timeout_s=1800.0, isolate=False)
    ```

    Это **три шага**: `确认需求` → `设定目标` → `干活` (с циклом вердикта, шаг вердикта называется `干活·判定#N`).
    При `goal=False` нет второго шага и цикла вердикта, при `clarify_only=True` остаётся только первый шаг.
    Он сам создаёт `HumanChannel` и `Workbench` и вешает их на workflow, поэтому `Runtime(workbench=wf.workbench)`
    берётся напрямую — не собирайте второй.

    Можно и без кода: зайти в каталог проекта и выполнить `flower "帮我做一个 X"` — запустится именно он.
    **Это не «рекомендуемый дизайн workflow»**, а просто способ запуститься с нулевой конфигурацией.

- **Шаги нарезаны мельче, чем «одна принимаемая цель»** — чистый убыток. Каждый шаг поднимает новую сессию,
  а у новой сессии есть стартовый пол (у координатора замерено около 34k контекста), размазать его не выйдет.
- **Хочется задним числом откатиться к конкретному сообщению** — через `Workflow` это не сделать, он никогда не передаёт `resume_at`.
  Вызывайте напрямую `Runtime.run(spec, "从这里重来", resume=sid, resume_at=uuid)`.

Как выбирать роль (`coordinator` / `worker` / `clarify` / `judge` / `oracle`) и пословная семантика полей `Step` и `Workflow` —
в [Python API](../reference/api.md); термины — в [Глоссарии](../reference/glossary.md).
