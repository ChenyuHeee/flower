# Handoff

Когда контекст почти заполнен, **сама текущая сессия** пишет [документ handoff](../reference/glossary.md#交接书) — читаемый и правимый человеком, — а затем эстафету принимает новая сессия. Без compact. Весь процесс виден в терминале, документ лежит на диске, правьте когда угодно — принимающая сессия читает именно этот файл.

!!! note "Handoff — это не преемственность"
    [Handoff](../reference/glossary.md#换代) — это смена [сессии](../reference/glossary.md#会话) **внутри одного прогона**;
    [преемственность](../reference/glossary.md#接续) — это подхват предыдущего [прогона](../reference/glossary.md#运行) **между процессами**,
    см. [Преемственность](continuity.md).

    Обе механики сцепляются автоматически, дополнительной проводки не нужно: [родословная](../reference/glossary.md#血缘) записывает
    **последний** `session_id` этого шага, а это и есть преемник — поэтому следующее пробуждение цепляется к преемнику, а не к сожжённому поколению.

## Какую проблему это решает

Встроенный в SDK auto-compact срабатывает на отметке **окно −33k** (замерено: при окне `200000` порог равен `167000`;
сам алгоритм сжатия сидит в бинарнике harness, изменить его нельзя — можно повлиять только на то, сработает он или нет), и делает он вот что: **сворачивает историю в один абзац**.
Это идёт вразрез со всем остальным в фреймворке:

| | Когда принимается решение | Что остаётся |
|---|---|---|
| `spill_guard` | В момент возврата инструмента | Большой результат [сбрасывается на диск](../reference/glossary.md#落盘), в контексте остаётся одна строка с путём |
| Замороженные артефакты (требования / цель) | В конце того шага | Один документ, следующий шаг читает только его |
| **auto-compact** | **Только когда контекст уже заполнен** | **Резюме, написанное самой моделью** |

flower от начала до конца делает одно: **решает на месте, что стоит оставить**. [Compact](../reference/glossary.md#压缩) — единственное место с «починкой задним числом»,
и у его продукта четыре изъяна:

- **сгенерировано моделью** — что попадёт в резюме, решает модель в тот момент, вы в этом не участвуете
- **нечитаемо** — оно написано для модели следующего круга, не для человека
- **неизменяемо** — оно внутри harness, нет файла, который можно открыть
- **вы не знаете, что потеряли** — ни увидеть, что именно выпало, ни сказать заранее «вот это не выбрасывай»

Handoff возвращает всё это в общую колею: **ещё один замороженный артефакт**, той же формы, что бриф и цель —
структурированный, лежащий на диске, **его можно открыть, поправить строку и дать прогону идти дальше**. Именно так устроен и сам этот проект —
`HANDOFF.md` в корне репозитория — это та же самая вещь, написанная человеком.

## Как пользоваться (минимум кода)

В командной строке handoff включён по умолчанию:

```bash
flower                       # handoff включён по умолчанию
flower --window 200000       # нужно указывать, только если определилось неверно (по умолчанию 1 000 000)
flower --no-handoff          # выключить — откат на встроенный auto-compact
```

В собственном коде handoff управляется через `Runtime(handoff=…)`, по умолчанию `True`:

```python
from flower import HandoffPolicy, Runtime

# по умолчанию: HandoffPolicy(enabled=True, window=default_window(), headroom=50_000, max_generations=8)
rt = Runtime(workspace=".", run_dir="runs", workbench=True)

# явно заданное окно (при смене шлюза или модели крутить надо именно это)
rt = Runtime(
    workspace=".",
    run_dir="runs",
    workbench=True,
    handoff=HandoffPolicy(window=200_000, headroom=50_000, max_generations=8),
)

rt = Runtime(workspace=".", run_dir="runs", handoff=False)   # выключить, откат на auto-compact
```

Все параметры `Runtime.__init__` — keyword-only, `workspace` обязателен. `handoff` принимает экземпляр `HandoffPolicy` или
`bool`; `bool` эквивалентен `HandoffPolicy(enabled=…)`.

!!! warning "Включённый handoff = auto-compact принудительно выключен"
    `Runtime(handoff=True)` — это **значение по умолчанию**, и при сборке каждой попытки оно делает следующее: если
    `handoff.enabled` и `spec.compact is None`, spec подменяется на
    `CompactPolicy(mode="no_summary")` — то есть в дочерний процесс инжектируется **`DISABLE_AUTO_COMPACT=1`**.

    Причина: если обе механики работают одновременно, невозможно сказать, кто именно уронил контекст в очередной раз. Цена — **отсутствие страховочной сетки**:
    когда круг записи handoff падает, нельзя ни остановиться, ни сделать вид, что всё нормально, и дотянуть до жёсткого потолка, поэтому обязателен путь деградации (см. ниже).

    Чтобы оставить auto-compact как подстраховку, нужно **явно** задать `AgentSpec(compact=CompactPolicy(mode="auto"))` —
    если spec задан сам, он уважается и не перекрывается. Учтите: это **молча побеждает** предположения, на которых стоит половина логики handoff.

## Что он делает на самом деле

### Момент срабатывания: два пути в handoff

**Первый: уровень дошёл до порога.** Критерий — `_handoff_due`: `handoff.enabled`, **не круг записи handoff**,
`_ctx >= handoff.at`, и на этом шаге уже был получен `session_id`. `_ctx` — это размер контекста, который **главный поток**
реально видел на последнем круге — смотрим только на [главный поток](../reference/glossary.md#主线程), контекст [subagent](../reference/glossary.md#subagent)
— дело его собственного transcript, он рассеивается по завершении и не должен вынуждать главный поток менять поколение.

На отметке `warn_at` сначала выдаётся предупреждение о приближении — один раз на поколение, экран не засоряется.

**Второй: API прямо сообщает «не влезает».** См. раздел про `is_overflow` ниже.

Оба пути **не ограничены `max_attempts`** и **не расходуют лимит повторов** (внутри `attempt -= 1`) —
handoff не является отказом.

### Документ handoff: пять секций, обязательны только две

Каждая секция страхует от своего класса ошибок принимающего:

| Секция | Поле | От чего страхует |
|---|---|---|
| Чем занят сейчас | `doing` **обязательно** | не понимать, где ты стоишь |
| Что уже решено | `decided` | заново обсуждать уже решённое (нужно писать **почему**) |
| Тупики | `deadends` | **самая дорогая секция** — см. ниже |
| Следующий шаг | `next` **обязательно** | сначала полчаса решать, чем заняться |
| Обстановка | `scene` | **пути** к ключевым файлам и артефактам. Указатели, не содержимое |

`Handoff.missing()` проверяет только `REQUIRED = ("doing", "next")`, `complete()` — это его отрицание.
**Жёсткое требование непустых «тупиков» вынуждает выдумывать** — в начале задачи эта секция и должна быть пустой.
Кроме того, у вердикта `complete()` есть последствия: при нехватке обязательной секции этот handoff **целиком заменяется механически собранным деградированным артефактом**
(см. ниже), а это гораздо хуже, чем настоящий handoff с одной недописанной секцией. Поэтому остальные три секции опциональны — написали, значит польза; не написали, handoff всё равно состоится.

В `to_markdown()` пустые секции пишутся как `(空)`; шапка `prompt_block()` прямо сообщает принимающему «ты принимаешь эстафету»,
чтобы он не пошёл выпрашивать контекст у человека. Поле `step` используется только в шапке документа и в разборе не участвует.

#### Почему «тупики» — самая дорогая секция

Потому что это **то, что принимающему дороже всего открывать заново**, и то, что пишущий чаще всего упускает.

У исполнителя системный оптимистический сдвиг ([страж цели](goal.md) разбирает ровно то же самое): он напишет, что у него получилось,
и забудет написать, что пробовал и не сработало. А дорого стоит именно второе — в [HT002](../cases/ht002.md) на проблему компиляции ушёл час,
и если бы вывод этого часа не был записан, принимающий прошёл бы тот же круг ровно так же.

Поэтому в `HANDOFF_PROMPT` под это отведён отдельный абзац, вместе с измеренной ценой.

### Как это выглядит

```text
# Контекст 130.0K/200K · ещё около 20K до handoff

# Контекст 152.0K/200K —— пишу handoff, готовлюсь к смене поколения
  - Сейчас делаю   добавляю в Makefile shim-заголовок для macOS, чтобы макрос sigemptyset больше не разворачивался в синтаксическую ошибку.
  - Решено         бизнес-исходники не трогаем — пользователь явно обозначил границу, поэтому идём путём генерации shim через Makefile.
  - Тупики         -D_ANSI_SOURCE отключает заодно и другие макросы; менять порядок include бесполезно.
  - Следующий шаг  на чистом clone прогнать make и убедиться, что shim работает.
<- handoff записан в ~/proj/.flower/notes/交接-干活.md
<- новая сессия принимает эстафету, контекст стартует с нуля (было 152.0K)
```

**Полностью автоматически, без остановки в ожидании вас** — long-horizon прогон не должен вставать из-за того, что человек ушёл обедать.

Событие — `Event("handoff")`, у `payload["phase"]` **три** значения: `near` (приближение), `writing` (идёт запись;
на запись handoff уходит десяток с лишним секунд, без этого события интерфейс выглядит зависшим), `done` (смена завершена). Payload у `done` дополнительно несёт
`context`, `window`, `degraded`, `path`, `sections`.

### Как считается порог

```python
at      = max(10_000, window - headroom)   # линия handoff, нижняя граница 10k
warn_at = max(1_000, at - 20_000)          # линия предупреждения о приближении
```

Нижняя граница `at` в 10k обязательна — ниже уже не написать даже handoff.

Шкала ниже нарисована для примера с `--window 200000`, **окно по умолчанию — 1 000 000**:

```text
  0--------------------------------------|-----|--------------|
                                       130K  150K           200K
                                     предупр handoff       потолок
```

Если `window` не задан, его определяет `default_window()` по **строке имени модели**, глядя только на две переменные окружения — `ANTHROPIC_MODEL` или
`ANTHROPIC_DEFAULT_OPUS_MODEL`:

| Имя модели | Определяется как |
|---|---|
| в имени есть отдельное слово `1m` | `1_000_000` |
| в имени есть `haiku` | `200_000` |
| всё остальное, **а также если обе переменные не заданы** | `1_000_000` |

Порядок важен: `1m` матчится первым, поэтому `claude-haiku[1m]` будет определён как 1 000 000, а не 200 000.

Почему `headroom` равен `50_000`: auto-compact срабатывает на отметке окно −33k, handoff обязан успеть раньше;
и сама «запись handoff» требует ещё одного круга. 50k удовлетворяет обоим условиям сразу.

**`--window` — главный переключатель при смене модели или шлюза.** Со стороны SDK надёжный размер окна получить нельзя, остаётся угадывать по имени.
Реальное окно больше → handoff случается рано (расточительно, но без ошибок); меньше → не успеваем, обязательно надо подкрутить. Замер, о котором стоит упомянуть:
на машине разработки шлюз настроен на `claude-opus-5[1m]`. Если бы считать по 200 000, поколение менялось бы каждые 150 000,
а на деле можно дотянуть до 950 000 — **разница в 5 раз**, long-horizon работа была бы изрублена в лапшу.

Через `flower -v` перед стартом видно действующую конфигурацию учётных данных (эндпойнт, имя модели; токен маскируется, остаются первые 4 символа).

### `is_overflow`: превращает жёсткую ошибку в handoff на месте

Это то, что позволяет **не бояться взять 1 000 000 значением по умолчанию в `default_window()`**.

Если окно определено с завышением, порог никогда не будет достигнут, а auto-compact выключен — и тогда мы жёстко врежемся в API.
`is_overflow(*texts)` распознаёт этот сигнал: `prompt is too long`, `context length exceeded`,
`maximum context length`, `too many total text bytes`, `input length and max_tokens exceed` и т.д.

После распознавания идёт **тот же путь handoff**, только handoff этого поколения неизбежно будет деградированным — та сессия уже не потянет
«ещё один круг на запись handoff», поэтому берётся механически собранный деградированный артефакт, новая сессия как обычно продолжает работу, **и шаг не падает**.

Так цена завышенной оценки окна снижается с «шаг провалился» до «handoff этого поколения деградированный».

`is_overflow` — **функция уровня модуля**, а не метод `Handoff`, и принимает переменное число аргументов.

### Когда handoff не получается написать: деградация, а не остановка

Круг записи handoff тоже может упасть — оборвалась сеть, модель сбойнула, при разборе не хватило обязательной секции. Поскольку
auto-compact уже выключен, **страховки нет**, и остановка здесь равносильна удару в окно.

Что делается: из того, что известно, механически собирается **неполный handoff**, в `doing` ставится метка `[降级:交接没写成]`
(константа `DEGRADED`), в `scene` кладутся первые **1200** символов исходной задачи, и смена поколения происходит как обычно. Принимающему прямо сказано,
что полученное неполно и на обстановку надо посмотреть самому. Одновременно в `StepResult.errors` добавляется запись «交接降级(…)»,
а причину можно найти в `manifest.json`.

Этому соответствует функция уровня модуля `degraded(step, prompt, *, why="")`; `Handoff.degraded` — это read-only property,
которое проверяет наличие той самой метки в `doing`.

> **Неполный handoff несравнимо лучше, чем удар в окно.**

У круга записи handoff есть ещё две намеренные особенности: он выполняется с `max_budget_usd=None` — **handoff обязан быть написан,
он не должен упереться в бюджет**; и с `on_event=None` — этот круг не выводится в UI.

### Одна мина: круг записи handoff обязан быть освобождён от порога

Запись handoff идёт **уже после пересечения линии** — уровень к тому моменту, естественно, выше порога. Без освобождения
первое же сообщение круга записи снова оценивается как «пора менять поколение», его прерывают, не дав написать ни слова, **и каждое поколение выдаёт деградированный артефакт**,
причём внешне всё выглядит нормально (путь деградации работает отлично).

На этом уже прокололись на практике: первый настоящий прогон `tests/handoff_live.py` — **оба поколения handoff деградированные**. Офлайновые тесты этого не поймали —
там `_attempt` подменялся целиком, и подделка этот критерий не выполняла. Сейчас критерий вынесен в `Runtime._handoff_due()`,
и офлайн проверяет его напрямую.

### Предохранитель от разгона

`max_generations=8`.

!!! danger "`window` заданное слишком маленьким приведёт к бесконечным handoff и сожжёт деньги"
    Опасность в том, что **если порог ниже стартового пола этой роли** (у [координатора](../reference/glossary.md#协调者) замерено около 34k —
    один системный промпт плюс индекс [верстака](../reference/glossary.md#工作台) уже съедают столько), то каждая новая сессия пересекает линию с первого же слова
    → пишет handoff, меняет поколение, снова пересекает линию, **и так без конца**. А handoff не расходует лимит повторов — это сделано намеренно, поэтому единственный предохранитель — 
    `max_generations=8`.

    Нормальному длительному прогону 8 поколений не нужны; если предел всё же достигнут — почти наверняка `window` задан слишком маленьким, и сообщение об ошибке при достижении предела прямо так и говорит
    («порог, вероятно, ниже стартового пола этой роли, увеличьте window или используйте `--no-handoff`»).

### Полный ход одной смены поколения

```text
работа (session A)
  |  контекст главного потока пересёк порог  <- смотрим только на главный поток. Контекст subagent — дело
  |                                             его собственного transcript, он рассеивается по завершении
  |                                             и не должен вынуждать главную сессию менять поколение
  |- разрыв на границе сообщения  <- та же логика, что у прерывания по Ctrl-C: рвём чисто, не разрывая состояние
  |                                  (и цена та же: subagent'ы в полёте теряются. 50k запаса оставлены ровно на это)
  |- в той же сессии ещё один круг: пишем handoff
  |     почему пишет она сама — только у неё есть этот контекст. Любому другому пришлось бы сначала всё прочитать, а тогда смена бессмысленна
  |- заморозка в <верстак>/notes/交接-<имя шага>.md, предыдущее поколение переезжает в notes/archive/交接/
  |- новая сессия (resume=None, fork=False), prompt = prompt_block() документа handoff
работа (session B) продолжается
```

`HANDOFF_PROMPT` — это тот промпт, который заставляет текущую сессию написать handoff; в нём два плейсхолдера, `{used}` и `{window}`.
**Это не новая роль** — нужный контекст есть только у текущей сессии.

### Handoff не считается повтором; как ведётся учёт

| Поле | Что происходит при handoff |
|---|---|
| `attempts` | **не растёт** — оно считает неудачные попытки |
| `retired[]` | сожжённые на этом шаге session_id записываются сюда **по порядку** |
| `session_id` | всегда **последний преемник**, а не сожжённый |
| `context` | размер контекста, реально виденный главным потоком на последнем круге |
| `cost_usd` / `num_turns` | **накапливаются** через повторы и смены поколений |

Все эти поля попадают в `manifest.json`, и постфактум можно полностью восстановить «сколько поколений сожжено на этом шаге и сколько стоило каждое».

### Куда ложится handoff

`<верстак>/notes/交接-<имя шага без недопустимых символов>.md`; уже существующее предыдущее поколение переносится в
`notes/archive/交接/<имя шага>-<временная метка>.md`.

**Без верстака сброса на диск нет** — тогда `_handoff_path` возвращает `None`, документ всё равно передаётся принимающему через prompt,
смена поколения идёт как обычно, только **человек потом этот файл не найдёт**. Чтобы можно было посмотреть потом, включите верстак
(`Runtime(workbench=True)`, либо пусть его подцепит сам [workflow](../reference/glossary.md#流程)).

## Когда его не стоит использовать

- **Вы хотите именно compact.** `flower --no-handoff` или `Runtime(handoff=False)`.
  Handoff заодно выключает auto-compact; не нужен этот побочный эффект — не включайте.
- **Хотите, чтобы работали обе механики.** Явный `AgentSpec(compact=CompactPolicy(mode="auto"))` сохранит auto-compact,
  но после этого «кто именно уронил контекст в очередной раз» станет невыясняемым, и разбор усложнится. Верьте либо handoff, либо compact, но не обоим сразу.
- **Короткая задача, работа в один круг.** Handoff никогда не сработает, настраивать его бессмысленно — но помните, что `Runtime` по умолчанию
  с `handoff=True` всё равно выключает auto-compact.
- **Нет верстака, но вы рассчитываете прочитать handoff потом.** Сначала включите верстак, иначе документ существовал только в контексте того прогона.
- **Начинать длительный прогон, не подобрав `window`.** Если реальное окно меньше значения по умолчанию, первые поколения будут выдавать сплошь деградированные handoff,
  а деградированный handoff — как раз самый бесполезный вид handoff. Сначала подберите `--window` или прогоните что-нибудь короткое и посмотрите имя модели в `-v`.
- **Считать handoff всей политикой управления контекстом.** Это последний рубеж. Слои, которые режут на месте
  (сброс на диск, [подрезка](../reference/glossary.md#裁剪), [вырезание](../reference/glossary.md#剪除)), дешевле,
  см. [Экономику контекста](context.md).

## Ручки

| Симптом | Что крутить |
|---|---|
| Handoff слишком частый, работу постоянно прерывают | Выставьте `--window` в реальное окно модели (`-v` покажет действующее имя модели) |
| Handoff с самого старта, плюс сообщение про «стартовый пол» | То же самое, `window` задан слишком маленьким |
| Handoff всегда деградированный | Смотрите `errors` в `runs/manifest.json`, там записана причина деградации |
| Принимающий всё время повторяет работу прошлого поколения | Секция «тупики» в handoff написана слишком скудно. Можно прямо поправить этот файл |
| Хотите прочитать handoff потом, но файла нет | Верстак не включён. Handoff не сбрасывался на диск, прошёл только через prompt |
| Хотите именно compact | `--no-handoff` |
