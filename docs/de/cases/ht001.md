# HT001 · Ein Terminal-IDE von Grund auf schreiben

Am 2026-09-07 hat ein Agent unter flower von Grund auf eine C/C++-Einzeldatei-IDE geschrieben, die im macOS-Terminal läuft.
Er lief 10.4 Stunden am Stück, verbrauchte $171.62 und lieferte 12,212 Zeilen Produktcode und 13,291 Zeilen Tests ab;
unterwegs riss einmal das Netz ab, er lief von selbst weiter bis zum Ende. Diese Seite ist keine Erfolgsschau —
sie misst jede Behauptung des Frameworks einmal in realem Maßstab nach,
**einschließlich der zwei, die der Messung nicht standhalten**: Dass der Koordinator „Berechtigungsgrenzen häufig ignoriert", ist falsch — und in seiner eigenen Abnahme ist ein Kriterium falsch beurteilt.

Die vollständigen Aufzeichnungen (inkl. 19MB Transcript) liegen in [ChenyuHeee/cppide](https://github.com/ChenyuHeee/cppide).
Jede Zahl unten wird von `tools/analyze_run.py` aus `sessions.db` berechnet und ist reproduzierbar:

```bash
python tools/analyze_run.py /path/to/cppide/runs
```

!!! note "Woher die Zahlen auf dieser Seite stammen"
    Das `runs/` von HT001 liegt im oben genannten cppide-Repo, **nicht im flower-Repo**. Die Zahlen dieser Seite
    sind also **unverändert** aus den damaligen Run-Aufzeichnungen übernommen; beim Schreiben dieser Seite wurde
    nicht noch einmal gegen `sessions.db` nachgerechnet — wer nachrechnen will, muss zuerst cppide clonen

## 1. Kontext-Ökonomie: 94.8 % des Geschehens erreichen den Main Thread nie

Das ist die Kernbehauptung des Frameworks — der [Koordinator](../reference/glossary.md#协调者) hält nur Entscheidungen,
das Geschehen sinkt in Subagents und auf die Platte. Der Mechanismus selbst steht in [Kontext-Ökonomie](../guide/context.md).

| | Main Thread | Subagent | Subagent-Anteil |
|---|---|---|---|
| Modellrunden | 70 | 3.0K | **97.7 %** |
| Textzeichen | 200.1K | 3.6M | **94.8 %** |
| Tool-Aufrufe | **32** | **1,893** | —— |

Dieser Run hat 23 Subagents losgeschickt; deren Output-Token: max. 184,377, Median 72,197, min. 11,684.

**Von 1,893 tatsächlich ausgeführten Tool-Aufrufen (1,034 Bash / 471 Read / 258 Edit / 126 Write) erreichten nur 32 das Sichtfeld des Koordinators
— 59:1.** Pro losgeschicktem Subagent bleiben im Schnitt 82 Tool-Aufrufe für ihn unsichtbar.

Frühere Tests in kleinem Maßstab maßen 83 %, in realem Maßstab sind es **94.8 %**. Je größer der Maßstab, desto größer der Gewinn der Arbeitsteilung —
denn der Overhead aus [Task Brief](../reference/glossary.md#任务书) und Rückmeldung ist **pro Entsendung konstant**,
während das draußen gehaltene Geschehen mit der Komplexität der Aufgabe wächst.

## 2. Die Kontextkurve: zum ersten Mal wissen wir, wo die Obergrenze von „long-horizon" liegt

`input + cache_read + cache_creation` jeder Assistant-Nachricht ist genau der Kontext, den das Modell in dieser Runde gesehen hat:

```text
Runde  1   28.7K   ← Startboden (früher rund 34k gemessen, passt)
Runde 20   35.2K
Runde 35  108.6K
Runde 50  158.2K
Runde 70  185.9K   ← Ende
```

- 70 Runden monoton steigend, Steigung etwa **2.2K/Runde**
- **kein einziges Compact** über den ganzen Run (`DISABLE_AUTO_COMPACT=1`; der einzige Rückgang ist der leere Eintrag der Runde mit dem Netzausfall)
- **18.6 %** des 1M-Fensters verbraucht

**Extrapoliert man diese Steigung, trifft die Wand bei etwa 440 Runden.** Diese 70 Runden haben 12K Zeilen Code produziert,
die reale Obergrenze für [long-horizon](../reference/glossary.md#长程) in der aktuellen Form liegt also etwa beim **6-Fachen** dieses Runs.
Das ist eine Zahl, mit der man Entscheidungen treffen kann; vorher blieb nur Raten.

Um sie zu durchbrechen, muss das Wachstum des Main Thread **sublinear** werden — mehr auf die Platte, weniger im Dialog.

## 3. Cache-Trefferquote 96.1 % — nur dadurch halten die $171.62

```text
Gesamt-Input 299.4M Token
  Cache-Treffer     287.5M  (96.1%)
  Cache neu erzeugt  11.8M
  ungecacht           6.2K
Output 2.3M (davon thinking 653.9K)
```

299M Input-Token haben nur $171 gekostet, weil 96 % zum Cache-Preis liefen.

**Folgerung: Die Wirtschaftlichkeit eines long-horizon Runs steht und fällt mit der Cache-Trefferquote, und die hängt an der Stabilität des Kontext-Präfixes.**
Jede Optimierung, die „den Kontext umsortiert" — Altes wegräumen, vorne einen neuen System-Prompt einschieben — zerschießt den Cache;
die gesparten Token wiegen den verlorenen Cache-Rabatt womöglich bei Weitem nicht auf. Das war vorher nie gemessen, jetzt gibt es Zahlen.

Das ist auch ein Nebenargument dafür, dass flower [Handoff](../reference/glossary.md#换代) statt Compact benutzt:
Ein Handoff **öffnet eine neue Session und baut den Cache von vorn auf**, das Präfix bleibt innerhalb einer Generation durchgehend stabil.

## 5. Der Koordinator wurde 1-mal abgelehnt — und schuld war die Whitelist

Vor der Messung stand der Verdacht: „Der Koordinator ignoriert Berechtigungsgrenzen häufig und löst massenhaft abgelehnte Aufrufe aus." Die Messung hat diese Prämisse zerlegt.

**Von 32 Tool-Aufrufen wurde 1 abgelehnt (3.1 %)**, und zwar dieser:

```bash
which g++ clang++ make pkg-config 2>&1; echo ---; ls /usr/include/ncurses.h 2>&1; echo ---; ls /work/runs
```

Segmentweise beurteilt: `echo` durchgelassen, `ls` durchgelassen, **`which` blockiert — es stand nicht in der Liste der
[Ephemeral Commands](../reference/glossary.md#一次性命令)**.

Der ganze Befehl ist rein lesend, eine ganz normale Umgebungssondierung. **Das Modell hat es vollkommen richtig gemacht, die Whitelist war unvollständig** —
und zwang es, für ein einziges `which g++` die Startkosten eines Subagents zu bezahlen (rund 4.3k Token).

Behoben: `which` / `command -v` / `type` / `whereis` / `uname` / `arch` / `locale` / `nproc` /
`getconf` / `sw_vers` nachgetragen. Bei `command` und `type` wird **nur die Abfrageform durchgelassen** —
ein nacktes `command rm -rf /` ist Ausführung, das fehlende `-v` wäre eine offene Hintertür;
in `tests/glance.py` bewachen 7 Angriffsbeispiele diese Stelle.

**Das Merkenswerteste daran ist nicht der Patch, sondern die Methode.** Eine lange laufende Architekturdiskussion, deren Ausgangsprämisse in echten Daten bei 1/32 liegt —
und deren Ursachenzuschreibung obendrein verkehrt herum war: Das Problem lag nicht am Modell, sondern an der Whitelist. **Erst messen, dann reden.**

## 6. Netzausfall und Weiterlauf: zum ersten Mal durch einen echten Fehler validiert

```text
01:52:40  tool_result: "Agent terminated early due to an API error"   ← ein Subagent wurde unterbrochen
01:55:41  assistant:   "API Error: ENOTFOUND"                          ← Main Thread bekommt es mit
          ↓  Probe hängt und wartet auf die Rückkehr des Netzes
          resumed=True, dieselbe Session lief weiter, noch über 8 Stunden bis zum Abschluss
```

Das Manifest hält `attempts=2 / resumed=True / ok=True` fest. **10 Stunden Arbeit mussten nicht von vorn beginnen.**
Bis dahin stand [Resilienz](../reference/glossary.md#韧性) unter „noch nicht validiert" — das Netz zu kappen verlangt sudo und ein Editieren von hosts, das will niemand mitten in einem echten Run tun.

Diese synthetische „API Error"-Nachricht hat der `PruningSessionStore` beim Laden entfernt, **das Modell hat sie nie gesehen** —
damit ist auch das Design des [Prune](../reference/glossary.md#剪除) an einem echten Fehler validiert.

Zwei Probleme, die dabei sichtbar wurden (siehe Issue #2):

1. Die Wiederherstellung passiert auf der **Framework-Ebene**, nicht auf der Transportebene. Der Preis ist ein kompletter Replay des Kontexts — und der war damals groß.
2. **Der unterbrochene Subagent hat seine halbfertige Arbeit verloren.** Resume rettet den Main Thread;
   Unterbrechungswiederherstellung auf Subagent-Ebene ist ein anderes Problem.

## 7. Ist seine Selbstvalidierung echt?

Das ist die Stelle, der man am meisten misstrauen sollte: Ein Agent schreibt selbst Tests, führt sie selbst aus und erklärt sich selbst für bestanden — das wird leicht zur Formsache.

Im Nachhinein wurde ein unabhängiger Audit-Subagent losgeschickt, der statisch alle 58 Skripte und 22 Artefakte durchgelesen hat. Das Ergebnis: **echt, und von seltener Strenge**:

- **Null tautologische Assertions.** Im ganzen Repo kein Muster der Art `[ 1 = 1 ]`.
- `|| true` insgesamt 8-mal, **7 davon berechtigt** (`grep -c` liefert ohne Treffer 1, `ulimit`-Fallback und Ähnliches).
- **Beurteilt wird Verhalten, nicht Dateiexistenz.** `audit-idle-cost.sh:53` lässt die IDE 60 Sekunden im pty leerlaufen,
  zählt die beim lokalen Fake-Server tatsächlich eingegangenen Requests, PASS nur bei `-le 2`. `fix-p1-idle-verify.sh:100-110` geht weiter:
  Es prüft, dass im Leerlauf genau 1-mal angefragt wird, **und zusätzlich**, dass der Ghost weiterhin angezeigt wird — verhindert, dass „die Drosselung das Feature gleich mit erschlägt".
- **Echte Kindprozesse.** `wave5-pty-drive.cpp:316` fährt die TUI per `forkpty` wirklich hoch; `audit-fake-ai-server.py`
  ist ein echter Socket-Server mit fünf Fehlerinjektionen `/err500 /err401 /badjson /drop /slow`;
  auf allen AI-Pfaden wird `CPPIDE_API_KEY` zwangsweise geleert.

Zwei Dinge gingen über die Erwartung hinaus.

**Es hat für seinen eigenen Verifier eine Positiv-/Negativkontrolle gebaut.** `验收审计.md:29-34`: erst `ZZZ_NEVER_APPEARS_ZZZ` einspeisen, um sicherzugehen, dass der Treiber FAIL meldet,
dann den echten String, um PASS zu bestätigen — damit nicht „mit einer Maschine auditiert wird, die immer PASS sagt". **Das validiert den Validator selbst.**

**Es hat seine eigene schwache Assertion von sich aus offengelegt.** Das `for m in $must` in `wave5-b4-ai-states.sh:114`
zerlegt `"AI 错误 请求超时"` an Leerzeichen in drei Teilstrings und grept sie einzeln, wobei `AI` und `错误` auf praktisch jedem Bildschirm vorkommen —
nominell „3 bestanden", tatsächlich hat nur eine davon Trennschärfe. **Diesen Punkt hat es selbst in `验收审计.md:576-582` geschrieben**,
nicht der Auditor ausgegraben.

Ähnliches: `wave5-verify.sh:296-302` erklärt in 7 Kommentarzeilen, warum B3b auf SKIP heruntergestuft wurde
(Timing-Assertion auf dem letzten Bildschirm, ohne Bezug zum Produktcode), mit dem Vermerk „Beurteilungslogik und Toleranzbereich unverändert";
`:236-238` hält fest, dass es **eine eigene, früher geschriebene Fake-Assertion gefunden und behoben** hat —
`if pgrep ...` fällt in einem schlanken Image ohne `pgrep` stillschweigend in den else-Zweig und wird damit zum permanenten PASS.

Die qualitative Evidenz für Wiederverwendung deckt sich mit den Zahlen aus Abschnitt 4: `audit-fake-ai-server.py` wird von **7** Skripten wiederverwendet;
`wave5-pty-drive.cpp` von **5+** Kompilaten, mit `[ -x "$DRIVE" ] ||` als Compile-Cache;
der Treiber von wave4 → wave5 ist eine **Erweiterung, kein Rewrite** (der Diff ändert 1 Zeile und fügt 343 hinzu, die 281 Zeilen aus wave4 bleiben unverändert).

**All dieses Verhalten trat in einer Version ohne Goal Guard auf.** Die einzige Bindung waren die
10 entscheidbaren Abnahmekriterien im [Brief](../reference/glossary.md#需求确认书). Das zeigt: **„Fertig" in entscheidbarer Form zu formulieren, löst für sich genommen schon Selbstprüfung und Selbstoffenlegung aus.**
Der Grenznutzen des Goal Guard muss gegen diese Baseline gemessen werden, nicht gegen null.

Der nächste Abschnitt zeigt allerdings: **Die Selbstprüfung ist technisch sehr stark, trifft aber beim wichtigsten Punkt das falsche Endurteil.**

!!! warning "Der „Auditor" hier ist nicht der Judge"
    Der unabhängige Auditor aus Abschnitt 7 und 8 ist ein **vom Koordinator aus eigenem Antrieb losgeschickter Subagent**, nicht der
    [Judge](../reference/glossary.md#目标看守) des [Goal Guard](../reference/glossary.md#判定者) —
    dieser Run hatte überhaupt keinen Goal Guard. Beides liest sich ähnlich, tut aber Verschiedenes: Der Auditor ist eine nachträgliche Aufarbeitung,
    der Judge ist das [Verdict](../reference/glossary.md#判定)-Gate am Ende jeder Runde.

## 8. Ist seine Selbstbewertung korrekt? — Abnahmekriterium 1 ist falsch beurteilt

Ein zweiter unabhängiger Auditor wurde losgeschickt, um die 10 Abnahmekriterien Punkt für Punkt gegen den Code zu prüfen.

**Die Abnahmekriterien 2–10 treffen alle zu**, die Code-Belege liegen vor. Dass der Übungsmodus keinen Code einfügt, ist sogar **strukturell** garantiert:
ein einziger Sink-Entscheidungspunkt `ai.h:117` + ein einziges landendes switch `app.cpp:590-615` + vier Early-Returns
`editor.cpp:679-683`, keine verstreuten ifs. Die in der Selbstprüfung gefundenen P1–P4 treffen **alle zu, alle Fixes sind eingespielt**
(P4 zur Hälfte: die blaue Pair-Zeile ist toter Code, `ghostAttr()` geht ohnehin über `A_DIM`).

**Aber Abnahmekriterium 1 ist falsch beurteilt.**

```text
Wortlaut des Kriteriums:  "Kompiliert zu einer eigenständigen ausführbaren Datei, direkt lauffähig im macOS-Terminal"
Geliefertes Artefakt:     ELF 64-bit LSB pie executable, ARM aarch64, GNU/Linux
Sein Urteil:              bestanden
```

Diese Zeile wurde von Hand mit `file` nachgeprüft.

Verheimlicht hat es nichts — die Überschrift von §4 in `交付说明.md` lautet wörtlich „Größtes unverifiziertes Risiko: nie auch nur einmal auf macOS gelaufen",
und §6 des Audits listet sechs unverifizierte macOS-Flächen. **Es hat das Risiko offengelegt, diese Tatsache aber nie auf das Urteil zu Abnahmekriterium 1 zurückgeführt** —
obwohl genau das der wörtliche Inhalt von Kriterium 1 ist.

### Aber das ist kein Beleg dafür, dass „ein unabhängiger Judge nötig ist"

Man liest diesen Punkt leicht als „also braucht es den Goal Guard". Falsch — und so gelesen malt man **die Zielscheibe nachträglich um den Pfeil**,
genau die motivierte Argumentation, die der vorige Abschnitt gerade kritisiert hat.

**Der damalige Goal Guard hätte diesen Punkt in der Standardkonfiguration mit hoher Wahrscheinlichkeit ebenfalls übersehen.** `judge()` hat `can_run=False` als Default,
die Tools sind nur `Read` / `Glob` / `Grep` — **er kann `file` gar nicht ausführen**.
Er hätte den Quellcode gelesen, in `Makefile:25-38` tatsächlich einen Darwin-Zweig gefunden und „erreicht" geurteilt. Exakt dasselbe Versagen wie die Selbstprüfung.

### Die eigentliche strukturelle Tatsache

**Abnahmekriterium 1 ist in der Umgebung dieses Runs prinzipiell nicht verifizierbar.**

Es behauptet etwas über „das Verhalten des Artefakts auf macOS", während der gesamte Run in einem Linux-Container stattfand.
**Kein Judge kann ein macOS-Binary innerhalb des Containers verifizieren**, egal ob Selbstprüfung oder unabhängig.
Das Problem ist nicht „wer urteilt", sondern dass **dieser Punkt wie ein ganz normales entscheidbares Kriterium behandelt und dann beurteilt wurde**.

### Drei weitere Funde des Auditors (in der Selbstprüfung nicht erwähnt)

- **Kontingent-Semantik von `doTab()`**: `app.cpp:909` ruft nach `acceptGhost()` bedingungslos `noteActivity()` auf → `gen_++`
  → das Kontingent öffnet neu, sodass **jede Tab-Übernahme 500ms später erneut einen automatischen Request auslöst**. Die Analyse zu P1 (Leerlauf verbrennt Geld)
  hat nur die drei Abbruchpunkte `setMode` / `cancelInFlight` / `askNow` geprüft und diesen häufigsten Kostenpfad übersehen.
- Das „Grau" aus Abnahmekriterium 6 gilt wörtlich nur im 256-Farben-Terminal; in der 8-Farben-Stufe ist es fest auf `A_DIM` verdrahtet (gedimmt, nicht grau).
- Die Zwischenüberschrift von §7 in `验收审计.md` spricht von „9 Abnahmekriterien", die Tabelle hat aber 10 Zeilen — ein Tippfehler, allerdings in der Kopfzeile der Gesamtbewertung.

## Verbleibende Risiken

**Das Lieferziel ist macOS, aber die gesamte Verifikation lief in einem Debian-aarch64-Container; auf echter macOS-Hardware wurde nichts verifiziert.**
Das ist die reale Nebenwirkung der Container-Isolation: Aus Sicherheitsgründen wird er in Linux eingesperrt, ausliefern soll er für macOS.
Das README des Projekts hält das in §10.24 ehrlich fest und listet 4 Risikopunkte, schließt den Kreis aber nicht.

Diese Lücke wurde später von [HT002](ht002.md) geschlossen — jener Run hat genau dieses Binary tatsächlich auf macOS installiert.

Unerwarteter Nebeneffekt: Im Container ist nur `/work` sichtbar, deshalb enthält das 19MB-Transcript
**null Leaks des Host-Benutzernamens `/Users/hechenyu`** (`/work` kommt 11,495-mal vor).
Die [Isolation](../reference/glossary.md#隔离) hat nebenbei auch die Pfade isoliert.

## Was dieser Run nicht validieren konnte

- **Goal Guard**: Dieser Run liegt davor. Der Koordinator hat **aus eigenem Antrieb** ein unabhängiges Audit organisiert, die Verifikationstechnik ist hart,
  aber beim wichtigsten Punkt fiel das Urteil falsch aus (Abschnitt 8). Beide Schlüsse gehören zusammen notiert —
  ein Brief mit klar entscheidbaren Kriterien löst schon von sich aus Selbstprüfung aus, die Baseline des Goal Guard ist also nicht null;
  und der damals standardkonfigurierte Goal Guard **hätte genau diesen Punkt ebenfalls verfehlt**, er ist also auch kein Allheilmittel.
- **Verhalten im 1M-Fenster**: nur 18.6 % genutzt, die Grenze nie berührt.
- **Verhalten des Micro-Compact unter `DISABLE_AUTO_COMPACT=1`**: Über den ganzen Run wurde kein Compact ausgelöst, das bleibt Inferenz.
