# HT002 · Install it on macOS and get it running

2026-09-07. The task was one sentence: **clone [cppide](https://github.com/ChenyuHeee/cppide), install it on this macOS machine, get it running.** The result was **$38.24 / 4 steps / about 1 hour**. The program did run on macOS (PID 96040, arm64 Mach-O), and the [verdict](../reference/glossary.md#判定) was **unreachable**, surfaced to the human, who chose to accept it.

This was the **first run with a [goal guard](../reference/glossary.md#目标看守)** — everything built out of the [HT001](ht001.md) lessons, all of it hitting the real API for the first time that same day. It saved us from a hole HT001 fell into, and simultaneously produced a brand-new failure pointing the exact opposite direction: **it turned `git clone && make && ./cppide` into an hour.** The most valuable part of this page is the latter.

The raw records are in [`human-test/HT002/`](https://github.com/ChenyuHeee/flower/tree/main/human-test/HT002/); the accounting is computed from [`runs/manifest.json`](https://github.com/ChenyuHeee/flower/blob/main/human-test/HT002/runs/manifest.json) and `runs/sessions.db`:


## 1. The headline: it turned `git clone && make && ./cppide` into an hour

This is the most important finding of the run, more important than everything below about "the mechanism works."

In the set-goal step, the [judge](../reference/glossary.md#判定者) wrote itself a **15-item verdict checklist** (original in `目标.md` under [`.flower/notes/`](https://github.com/ChenyuHeee/flower/tree/main/human-test/HT002/.flower/notes)). By nature:

| Category | Count | Example |
|---|---|---|
| **Actually verifies "the thing works"** | **about 5** | build exits 0; process alive ≥30 seconds; restart command re-runnable in a fresh shell |
| **Verifies "the process followed the rules"** | **6** | mtimes of `~/.zshrc` / `.zprofile` / `.bash_profile` all earlier than this session; no `brew install` / `npm -g` / `sudo` was run; **`.flower/` mtime unchanged, nothing added to or removed from `runs/`** |
| **Unverifiable in principle** | **4** | take a screenshot and look at it; devtools console; manual clicking; personal confirmation by the user |

**Only a third of it verifies whether the thing actually works.** Six items verify whether the agent itself followed the rules — one of them checks the **mtime of the `.flower/` directory**, which is **the framework's own directory**.

### The item checking `.flower/` failed itself

This is not a theoretical problem. In the verdict round, the judge honestly wrote under "not passed":

> **All files under `.flower/` have mtimes earlier than session start** — literal failure: `INDEX.md` 16:14, `artifacts/01–05` (15:40–16:12), `notes/决策-项目形态与验收路径.md` 15:43 were all written during the session.

The reason: **the framework hard-requires long artifacts to be written into `.flower/artifacts/` and decisions into `.flower/notes/`.** That checklist item demands the directory not be touched. Two rules collide head-on, and the collision was manufactured by the checklist itself — if the worker had written no long artifacts at all, it would have been more compliant.

It did not paper over it: the work step proactively listed the conflict in its final report, and the decision record documents how it was handled — **not one existing file was touched** (`需求.md`, `目标.md`, `问答记录.md` all have identical mtime and MD5 before and after), only new files were added. The judge, after re-checking, agreed that "the tampering this item guards against did not happen," but still listed it as not passed per the rules and handed it to the human.

### Root cause 1: boundaries were treated as verdict items

The [boundaries](../guide/clarify.md) elicited in the clarify phase ("install only inside the project directory," "don't touch the business code") were meant to constrain **how the work is done**, but got written as checks verifying **the output**. Hence items like checking `.zshrc` mtime and `.flower/` mtime.

**A boundary is not a verdict item. Boundaries constrain the process; verdict items verify the result.** Once conflated, every additional boundary becomes an additional verdict item — and boundaries are exactly what the clarify phase encourages you to fill out. `CLARIFIER_RULES` says outright: "**state explicitly what will not be done**. This section governs everyone who does the work downstream."

You can trace every link of this amplification chain in the raw records: the boundary in the [brief](../reference/glossary.md#需求确认书) reads "do not touch the existing `.flower/` and `runs/` in the current directory," and by the time it reaches the verdict checklist it has been upgraded to "all files under `.flower/` have mtimes earlier than the start of this session" — from "don't touch what's there" to "no new files anywhere in the directory."

### Root cause 2: `JUDGE_RULES` only had pressure in one direction — and it was added that same day

Earlier that day, the following went into `JUDGE_RULES` from the [HT001](ht001.md) lessons:

- "every item must be verifiable on the spot," "anything missing or vague, you fill in"
- "you judge the artifact, not the source code" (with that macOS counterexample)
- "any item that cannot be verified in the current environment, flag it on the spot"
- "first figure out where you are (`uname -a` is fine)"

**Every one of these pushes toward more checks, stricter checks. Nowhere in the entire ruleset does it say "be proportional to the size of the task."**

In other words: optimizing against HT001's "over-claiming success" failure **produced the exact opposite failure — over-checking**. This one is self-inflicted, not a model problem.

### Root cause 3: it compounded with [issue #3](https://github.com/ChenyuHeee/flower/issues/3)

What actually blocked things were two portability defects on macOS:

- `src/proc.cpp` uses `::sigemptyset`, but the Apple SDK re-defines it as a function-like macro after the function prototype (guarded only by `#ifndef _ANSI_SOURCE`), so `::sigemptyset(&s)` expands to `::(*(&s)=0,0)`, a syntax error
- `src/ui.cpp` uses `::_exit` without including `<unistd.h>`

**Three lines would have fixed it.** But the user had answered "don't touch the business code" in the clarify phase, the agent enforced that strictly, and so it detoured into trying compiler flags, dispatching subagents, writing decision records. **If the user could have interjected "changing those two lines is fine," it would have been over in ten minutes.** A boundary written as a prohibition gets interpreted maximally strictly, and there is no channel mid-run to loosen it.

The raw records show how long the detour was: four blocking points in total, of which only the `::_exit` one could be solved by pure compiler flags; the `::sigemptyset` one had **6 combinations** of `-D`/`-U` tried, all failing (the `_POSIX_C_SOURCE` family also breaks `st_mtimespec` and `O_CLOEXEC` along the way). This dead end alone produced a 13.6K feasibility report.

### But fairness: the boundary forced out a better solution

The final approach was not to modify the source, but to **generate a shim header in the Makefile that does nothing but `#undef`**, then force it in front with `-include`:

```make
$(MACSHIM):
	@printf '#include <signal.h>\n#undef sigemptyset\n#undef sigfillset\n...' > $@
CPPFLAGS += -include $(MACSHIM) -include unistd.h
```

This is better than editing the source — the upstream repo needs no changes at all, and anyone who clones it can build. The shim is generated into `build/`, not committed; `clean` gained `rm -rf build` to reclaim it; `make -n UNAME_S=Linux` was actually run and the expansion contains no `-include`, so the Linux path is uncontaminated. The final `git diff` touches exactly one file, `Makefile`, **+14 / −2**.

So the boundary produced a **more expensive better solution**. The problem is not that it did the wrong thing; it is that **the human never got to make this trade-off** — and the reason they couldn't is exactly issue #3.

!!! note "Why `git status` shows 64 entries yet the source is unchanged"
    The cppide repo **committed** 30 `.o` files, 30 `.d` files and 2 binaries into version control, and they are Linux ELF aarch64 with mtimes later than the `.cpp` files — without a `make clean` first, `make` skips compilation and links the ELFs directly, which must fail. So of the 64 entries in `git status --porcelain`, 63 are git-tracked build products plus one `?? build/`. Filtered by extension, `git diff -- 'src/*.cpp' 'src/*.h' README.md config.sample.json | wc -c` is `0`. This precise phrasing was forced out by the compliance audit — the coordinator originally wanted to write the loose claim "zero changes in `src/`," and the audit pointed out that statement doesn't hold.

## 2. What the goal guard got right

The mechanism side all worked, and **the two changes made that day left direct fingerprints in the output**.

**The first item on the verdict checklist it wrote**:

> `uname -a` shows Darwin 25.2.0 (macOS)… every "runs / opens" item below must be a result actually obtained on this machine, **inferences like "the source has a macOS branch so it should run" are not accepted**

That is exactly the wording written into `JUDGE_RULES` that morning from the HT001 lessons.

**It used the `[cannot verify in this environment: …]` marker added that day three times**, each with a reason — devtools console (no drivable browser, and installing a headless one would cross the boundary), manual clicking (requires a human in front of the screen), personal confirmation (only the user can give it).

**The judge's first sentence was "I'm not drawing conclusions from that report. Go to the scene."** Then:

```text
file cppide        → Mach-O 64-bit executable arm64
lsof -p 96040      → txt points to /Users/hechenyu/explore/test-ide/cppide/cppide
                     started 16:10, still alive at 16:15
```

It wrote for itself: "**the 'delivered a Linux ELF' hole from the meta lessons — we didn't fall into it this time.** A Linux ELF cannot possibly run as a PID on Darwin. This was not inferred from the Makefile."

It also checked that the source really was untouched: every `.cpp` / `.h` under `src/` has mtime 15:32 (clone time); the only change is `Makefile` (16:06), and `.o` / `.d` (16:07) are tracked build products being rebuilt.

**It also stated honestly what it could not reach.** The judge's Bash was confined to the working directory, so it could not run the `git ls-remote` comparison or check `~/.zshrc` mtime, and had to take the independent audit's output on faith — it listed those two separately, noting "I could not re-run these myself."

## 3. Verdict "unreachable," then ask the human

Three-state verdicts plus human intervention: [the whole chain](../guide/goal.md) worked end to end for the first time.

The verdict was **unreachable**, stuck on the screenshot item: both `screencapture -x` and `-l <window-id>` returned `could not create image from display` — the TCC permission for screen recording was not granted, and granting it requires a human clicking through System Settings, which is itself a system change forbidden by the boundaries.

> "**Another round of subagents is not going to conjure this image. By the rules this cannot be passed, and it should not be judged 'not yet' either. It is simply unreachable, and the right move is to stop and hand it to the human.**"

So the "unverifiable in principle" category went from 3 items to 4 — **4 of 15 items cannot be verified at all in this environment** — and that fact was discovered **after** spending $35.8950 on work and $1.4037 on the verdict. The set-goal step cost only $0.4117; it should have been discovered right there.

The framework put this conclusion to the human (recorded as q7 in the Q&A record), three options, the human chose "accept this result," the gate opened, the workflow completed.

**It also refused a substitute.** The worker used AppleScript to read back the terminal window's text, a genuinely rendered TUI — line-number gutter, the body of `src/main.cpp`, the `─[编译]─[运行]─[AI*]─[输入]─` panel bar, the `练习模式 │ main.cpp │ 1:1 │ C++` status bar; not a blank screen, not an error screen. The judge said:

> "The worker did not pass this off as 'looking at the image.' That self-restraint is right. **But it does not substitute for the item the checklist requires, and I'm not going to count it for them either.**"

!!! warning ""Disclosed the risk" is not the same as passing"
    This is exactly what HT001 fell into: it wrote "never ran on macOS even once" into the delivery notes, and then still judged acceptance criterion 1 as passed. In HT002 the judge had *better* substitute evidence (real TUI text) and still refused to let it stand in for the checklist item. That distinction is the entire point of the three-state [verdict](../reference/glossary.md#判定) design — `UNREACHABLE` is not a polite way of saying `NOT_YET`, it means "stop and ask the human."

## 4. `allowed_tools` is not a hard whitelist

While analyzing this run I found a fact that contradicts the claim. Broken down by [session](../reference/glossary.md#会话), the tool calls were:

| Session | Actually used | What's in the whitelist |
|---|---|---|
| Clarify requirements | **WebFetch**, Glob, ask×6 | `clarify()` at the time gave only ask + `Read`/`Glob`/`Grep` |
| Set goal | **Bash ×11** | `judge()` defaults to `can_run=False`, **no Bash** |
| Work · verdict | **Bash ×31**, WebFetch | same as above |
| Work (coordinator) | Bash ×1, Agent ×6 | correct |

`goal_step` **has no code path that passes `can_run` at all**, so the "set goal" row cannot be a configuration issue.

**A $0.1 probe confirmed it**: give an agent `allowed_tools=["Read"]` and tell it to write a file —

```text
Write → permission layer: "requested permissions to write ... but you haven't granted it yet"
Bash  → path safety: "Output redirection was blocked. For security, Claude Code may
        only write to files in the allowed working directories"
```

**The model can call tools that are not in the whitelist**; they are merely stopped by the permission layer and path safety. So:

- `allowed_tools` is an **auto-approval list**, not an exclusive whitelist
- what actually protected `clarify()` / `judge()` at the time was the inherited `permission_mode="default"`
- and both had `delegate_only=False` → **no `delegate_guard` hook**. The coordinator was protected by a hook; **those two roles had no flower mechanism of their own at all**

The docstring of `clarify()` says "it gets no write tools — it cannot start working," and that entire $0.8908 negative-case experiment was run for that sentence. **The mechanistic basis of that sentence is wrong.**

!!! note "Both facts in this section have since changed"
    `whitelist_guard` is now wired in unconditionally: roles with `delegate_only=False` get the hook installed automatically by `Runtime`, so `clarify()` / `judge()` are no longer "without any mechanism." Also, `WebFetch` is now in `clarify()`'s whitelist, so the example in the first table row is void — **the conclusion still holds, but it now rests solely on the $0.1 probe evidence.** See the last section of this page.

## 5. The context curve: step boundaries reset it

```text
turn 1     36.8K
turn 25    80.2K   ← peak
turn 26    32.9K   ← cliff: new step = new session (resume_from=None)
turn 121   64.8K
```

Three of the four sample points (turns 1 / 25 / 121, 36.8K / 80.2K / 64.8K) match the raw records exactly; **the 32.9K at turn 26 does not check out on recomputation**: replaying main-thread assistant messages sorted by `store_key`, the 26th (the first of the new session) has `input + cache_read + cache_creation` = 31,972 tokens = **32.0K**, while 32.9K is the second value in that same session (31,970 + 948). This page keeps 32.9K — the difference is 0.9K, and the "cliff drop" conclusion holds either way.

HT001 climbed monotonically to 185.9K — one step running for 10 hours. HT002, split into four steps each opening a new session, has its **context structurally reset**. That is the direct effect of the design "the brief and the goal are frozen documents; downstream takes the documents, not the conversation" — visible in the curve.

Cache hit rate **90.8%** (HT001 was 96.1%). Hit rate rises with session length, so short sessions are actually slightly more expensive per unit — this is the same coin as the conclusion in HT001 section three, seen from the other side.

## What this run changed in the framework

| Finding | Change landed |
|---|---|
| Only about 5 of the 15 verdict items verify whether the thing works (section 1) | `JUDGE_RULES` gained counter-pressure: **checklist length is determined by the number of ways it can fail, not by how rigorous you want to look**, and this run was written into the rules as a counterexample ("an 'install and run it' task was written as 15 items, only 5 of which verify whether it works" — the rules round it to 5; this page's section-1 classification says about 5) |
| Boundaries were written as verdict items | `JUDGE_RULES` now states flatly: **"a boundary is not a verdict item"** |
| 4/15 items unverifiable in this environment, discovered only after spending $35.8950 + $1.4037 | The set-goal step now requires unverifiable items to be suffixed on the spot with `[cannot verify in this environment: reason]` — it got 3 right this time and missed the screenshot one |
| `clarify()` / `judge()` had no hook protection (section 4) | `whitelist_guard` is now wired in unconditionally: roles with `delegate_only=False` get it installed automatically by `Runtime`, no longer dependent on whether the workbench is enabled |
| Side effect: the set-goal judge now has no Bash | With `whitelist_guard` in place, unless `can_run=True` is passed explicitly, the `JUDGE_RULES` line "first run `uname -a` to see where you are" **cannot be executed** — a new trade-off created by the fix |
| The mechanistic basis of `clarify()`'s docstring was wrong | Fixed. `WebFetch` also entered `clarify()`'s whitelist, voiding that example, so the conclusion now rests on the $0.1 probe |
| No channel to interject mid-run (section 1, root cause 3) | Filed as [issue #3](https://github.com/ChenyuHeee/flower/issues/3), still open — here it compounded directly with over-complication; one sentence, "changing those two lines is fine," would have saved an hour |

One sentence for this run: **optimizing against the previous failure very easily produces a new failure pointing the opposite way.** HT001 taught the framework "don't pass things lightly"; HT002 immediately demonstrated what happens when that rule is not paired with "don't over-check." Both have to be in `JUDGE_RULES` — leave one out and it tilts.
