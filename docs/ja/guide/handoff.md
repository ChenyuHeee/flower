# ハンドオフ

コンテキストが埋まりかけたら、**いま走っているそのセッション自身**に、人が読めて書き換えられる[ハンドオフ文書](../reference/glossary.md#交接书)を書かせ、
新しいセッションを立てて引き継がせる。compact は使わない。過程はターミナルで見えるし、文書はディスクに残る。
直したければいつでも直せる —— 引き継ぐセッションが読むのは、まさにそのファイルだ。

!!! note "ハンドオフは継続ではない"
    [ハンドオフ](../reference/glossary.md#换代)は**同一のラン内部で**新しい[セッション](../reference/glossary.md#会话)に切り替えること。
    [継続](../reference/glossary.md#接续)は**プロセスをまたいで**前回の[ラン](../reference/glossary.md#运行)に接ぎ足すこと。
    [継続](continuity.md)を参照。

    両者は自動で噛み合い、追加の配線は要らない:[リネージ](../reference/glossary.md#血缘)が記録するのはそのステップの**最後の**
    `session_id` であり、それこそが後継者だ —— だから次回の起動は後継者に接がれ、燃やされた世代には接がれない。

## 何を解決するのか

SDK 内蔵の auto-compact は**ウィンドウ −33k** の地点で発火し(実測:ウィンドウ `200000` のときしきい値は `167000`。
圧縮アルゴリズム自体は harness のバイナリの中にあって変更できない。変えられるのは発火させるかどうかだけ)、
やることは**履歴を一段落に要約する**ことだ。これはこのフレームワークの他の部分とねじれている:

| | いつ決めるか | 何が残るか |
|---|---|---|
| `spill_guard` | ツールが返ったその瞬間 | 大きな結果を[スピル](../reference/glossary.md#落盘)し、コンテキストにはパス 1 行だけ残る |
| 凍結物(ブリーフ / ゴール) | そのステップが終わる時 | 1 通の文書。次のステップはそれだけを読む |
| **auto-compact** | **コンテキストが埋まってから振り返る** | **モデルが自分で書いた要約一段落** |

flower が最初から最後までやっているのは**その場で何を残すか決めること**だ。[compact](../reference/glossary.md#压缩)は唯一の「事後の穴埋め」であり、
しかもその産物には 4 つの欠点がある:

- **モデルが生成したもの** —— 要約に何を書くかはその時のモデルの判断次第で、あなたは関与していない
- **読めない** —— それは次のターンのモデルのために書かれていて、人のためではない
- **直せない** —— harness の中にあり、開けるファイルが 1 つもない
- **何が失われたか分からない** —— 何が落ちたかも見えないし、落ちる前に「それは落とすな」と言うこともできない

ハンドオフはこれを同じ流儀に引き戻す:**もう一つの凍結物**であり、ブリーフやゴールと同じ形をしている ——
構造化されていて、ディスクに落ちていて、**開いて 1 行直してから続きを走らせられる**。そしてこれはこのプロジェクト自身のやり方でもある ——
リポジトリのルートにある `HANDOFF.md` は、人が書いた同じ種類のものだ。

## 使い方(最小のコード)

コマンドラインはデフォルトでハンドオフ付きだ:

```bash
flower                       # デフォルトでハンドオフ付き
flower --window 200000       # 判定を間違えたときだけ指定する(デフォルトは 100 万)
flower --no-handoff          # 無効化 —— SDK 内蔵の auto-compact に戻る
```

自分でコードを書くときは、ハンドオフは `Runtime(handoff=…)` で制御する。デフォルトは `True`:

```python
from flower import HandoffPolicy, Runtime

# デフォルト:HandoffPolicy(enabled=True, window=default_window(), headroom=50_000, max_generations=8)
rt = Runtime(workspace=".", run_dir="runs", workbench=True)

# ウィンドウを明示指定(ゲートウェイやモデルを変えたとき、まず調整すべきはこれ)
rt = Runtime(
    workspace=".",
    run_dir="runs",
    workbench=True,
    handoff=HandoffPolicy(window=200_000, headroom=50_000, max_generations=8),
)

rt = Runtime(workspace=".", run_dir="runs", handoff=False)   # 無効化、auto-compact に戻る
```

`Runtime.__init__` はすべて keyword-only で、`workspace` は必須。`handoff` は `HandoffPolicy` インスタンスか
`bool` を受け取り、`bool` を渡した場合は `HandoffPolicy(enabled=…)` と等価だ。

!!! warning "ハンドオフを有効にする = auto-compact が強制的に切られる"
    `Runtime(handoff=True)` は**デフォルト値**であり、各試行を組み立てるたびに次のことをする:
    `handoff.enabled` かつ `spec.compact is None` なら、spec を
    `CompactPolicy(mode="no_summary")` に差し替える —— つまり子プロセスに **`DISABLE_AUTO_COMPACT=1`** を注入する。

    理由は、2 つの仕組みが同時に走ると、あるときコンテキストが落ちたのはどちらの仕業なのか説明できなくなるからだ。
    代償は**セーフティネットが無いこと**:ハンドオフ文書を書くターンが失敗しても止まれないし、
    何事もない顔でハード上限まで粘ることもできない。だから劣化パスが必須になる(後述)。

    auto-compact を保険として残したければ、**明示的に** `AgentSpec(compact=CompactPolicy(mode="auto"))` を渡すこと ——
    spec 側が自分で指定した場合はそれを尊重し、上書きしない。ただしこれはハンドオフ側の前提を**黙って上書きする**点に注意。

## 実際に何をしているか

### 発火のタイミング:ハンドオフに入る二つの経路

**一、水位がしきい値に達する。** 判定は `_handoff_due`:`handoff.enabled` かつ**ハンドオフ文書を書くターンではない**
かつ `_ctx >= handoff.at` かつそのステップが既に `session_id` を取得済み。`_ctx` は**メインスレッド**の最後のターンが実際に見た
コンテキスト規模だ —— 見るのは[メインスレッド](../reference/glossary.md#主线程)だけ。[subagent](../reference/glossary.md#subagent)
のコンテキストはそれ自身の transcript の話で、走り終われば消える。メインスレッドにハンドオフを強いる筋合いはない。

`warn_at` の地点でまず接近の通知を 1 回出す。世代ごとに 1 回だけで、画面を埋めない。

**二、API が直接「入りきらない」と言ってくる。** 下の `is_overflow` の節を参照。

どちらの経路も **`max_attempts` に縛られず**、しかも**再試行の枠を消費しない**(内部で `attempt -= 1`)——
ハンドオフは失敗ではない。

### ハンドオフ文書:5 つのセクション、必須は 2 つだけ

各セクションが「引き継いだ人がやらかすこと」を 1 種類ずつ防ぐ:

| セクション | フィールド | 何を防ぐか |
|---|---|---|
| いま何をしているか | `doing` **必須** | 自分がどこに立っているか分からない |
| 決まったこと | `decided` | 既に決着した話を蒸し返す(**なぜ**を添えること) |
| 行き止まり | `deadends` | **一番高くつくセクション** —— 下記 |
| 次の一手 | `next` **必須** | 何をやるか決めるだけで 30 分使う |
| 現場 | `scene` | 主要なファイルと成果物の**パス**。中身ではなくポインタ |

`Handoff.missing()` が検査するのは `REQUIRED = ("doing", "next")` の 2 つだけで、`complete()` はその否定だ。
**「行き止まり」を必須にすると捏造を誘発する** —— タスクの冒頭では、そこは本来空であるべきだ。
しかも `complete()` の判定には結果が伴う:必須セクションが欠けると、そのハンドオフ文書は**丸ごと機械的に組み立てた劣化版に差し替えられる**
(後述)。それは 1 セクション足りない本物のハンドオフ文書よりずっと悪い。だから残りの 3 つは任意だ —— 書けば効くが、書かなくてもハンドオフは止めない。

`to_markdown()` では空のセクションは `(空)` と書かれる。`prompt_block()` の冒頭は引き継ぐ側に「あなたは引き継ぎ手だ」と明示し、
背景を人に聞き返しに行くのを防ぐ。`step` フィールドは文書の見出しに使うだけで、パースには関与しない。

#### 「行き止まり」がなぜ一番高くつくのか

それが**引き継いだ人が再発見するのに最も金を払わされるもの**であり、書く側が最も落としやすいものだからだ。

ワーカーには系統的な楽観バイアスがある([ゴールガード](goal.md)が同じことを論証している):
自分が何を成し遂げたかは書くが、何を試してダメだったかは書き忘れる。そして本当に高いのは後者だ ——
[HT002](../cases/ht002.md) では 1 つのコンパイル問題で 1 時間回り道した。その 1 時間の結論を書き残さなければ、
引き継いだ人はそっくり同じ道をもう一度回る。

だから `HANDOFF_PROMPT` にはこの点を突く一段落があり、その実測コストも添えてある。

### 見た目

```text
# 上下文 130.0K/200K · 还有约 20K 到换代

# 上下文 152.0K/200K —— 写交接准备换代
  - 现在在做  在给 Makefile 加 macOS 垫片头,让 sigemptyset 宏不再展开成语法错误。
  - 已定的事  不改业务源码 —— 用户明确说过边界,所以走 Makefile 生成 shim 这条路。
  - 走不通的  -D_ANSI_SOURCE 会把别的宏一起关掉;改 include 顺序无效。
  - 下一步    在干净 clone 上跑一次 make 验证 shim 成立。
<- 交接写在 ~/proj/.flower/notes/交接-干活.md
<- 新会话接手,上下文从 152.0K 重新开始
```

**全自動で、あなたを待って止まりはしない** —— ロングホライズンな実行が、人が食事に行ったせいで詰まってはいけない。

イベントは `Event("handoff")` で、`payload["phase"]` には**三つ**の値がある:`near`(接近)、`writing`(執筆中。
ハンドオフ文書を書くには十数秒かかるので、これを出さないと画面が固まったように見える)、`done`(交代完了)。`done` の payload はさらに
`context`、`window`、`degraded`、`path`、`sections` を持つ。

### しきい値の計算

```python
at      = max(10_000, window - headroom)   # 换代线,有 10k 下限
warn_at = max(1_000, at - 20_000)          # 逼近提醒线
```

`at` の 10k 下限は必須だ —— これより低いとハンドオフ文書すら書けない。

下のスケール図は `--window 200000` を例にしている。**デフォルトのウィンドウは 100 万**だ:

```text
  0--------------------------------------|-----|--------------|
                                       130K  150K           200K
                                       提醒  换代          硬上限
```

`window` を指定しない場合は `default_window()` が**モデル名の文字列**で判定する。見るのは `ANTHROPIC_MODEL` と
`ANTHROPIC_DEFAULT_OPUS_MODEL` の 2 つの環境変数だけだ:

| モデル名 | 判定 |
|---|---|
| 名前に独立した `1m` という語が含まれる | `1_000_000` |
| 名前に `haiku` が含まれる | `200_000` |
| その他、**および 2 つの変数がどちらも未設定** | `1_000_000` |

順序に注意:`1m` が先にマッチするので、`claude-haiku[1m]` は 20 万ではなく 100 万と判定される。

`headroom` がなぜ `50_000` なのか:auto-compact はウィンドウ −33k で発火するので、ハンドオフはその前に間に合わなければならない。
さらに「ハンドオフ文書を書く」こと自体にもう 1 ターン必要だ。50k はこの両方を同時に満たす。

**`--window` は、モデルやゲートウェイを変えたときにまず調整すべきスイッチだ。** SDK 側から信頼できるウィンドウサイズは取れず、名前から推測するしかない。
実際のウィンドウがもっと大きい → ハンドオフが早すぎる(無駄だが誤りではない)。もっと小さい → 間に合わないので、必ず調整すること。実測の一例:
開発機のゲートウェイの設定は `claude-opus-5[1m]` だった。以前のように 20 万として計算すると 15 万ごとに世代交代してしまうが、
実際には 95 万まで走れる —— **5 倍の差**だ。ロングホライズンな作業がずたずたに切り刻まれる。

`flower -v` を使えば、走り出す前に現在有効な認証設定(エンドポイント、モデル名、token は先頭 4 桁だけ残してマスク)を確認できる。

### `is_overflow`:ハードエラーをその場のハンドオフに変える

これが、**`default_window()` のデフォルト値を 100 万に取れる**前提だ。

ウィンドウを大きく判定しすぎると、しきい値には永遠に届かず、しかも auto-compact は切られている —— そうなると API に正面から突き当たる。
`is_overflow(*texts)` はこのシグナルを認識する:`prompt is too long`、`context length exceeded`、
`maximum context length`、`too many total text bytes`、`input length and max_tokens exceed` など。

認識した後に通るのは**同じハンドオフ経路**だ。ただしこの世代のハンドオフ文書は必然的に劣化版になる —— そのセッションはもう
「もう 1 ターン使ってハンドオフ文書を書く」ことができないので、機械的に組み立てた劣化版をそのまま使い、通常どおり新しいセッションに引き継いで続行する。
**このステップは失敗しない。**

こうして、大きく判定しすぎた代償は「このステップが失敗する」から「この世代のハンドオフ文書が劣化版になる」まで下がる。

`is_overflow` は `Handoff` のメソッドではなく**モジュールレベルの関数**で、しかも可変長引数だ。

### ハンドオフ文書が書けなかったとき:劣化させる、止めない

ハンドオフ文書を書くターンも失敗しうる —— ネットワークが切れる、モデルが暴れる、パースしたら必須セクションが欠けている。
auto-compact は既に切られているので、**保険は無い**。ここで止まることはウィンドウに突き当たることと同義だ。

やり方:手元にある既知の情報から機械的に**不完全なハンドオフ文書**を組み立て、`doing` に `[降级:交接没写成]` の印を付け
(定数 `DEGRADED`)、`scene` に元のタスクの先頭 **1200** 文字を詰め込んで、そのままハンドオフする。引き継ぐ側は、
受け取ったものが不完全であり、自分で現場を見に行くべきだと明示的に伝えられる。同時に `StepResult.errors` に「交接降级(…)」が 1 件追加され、
`manifest.json` から理由を辿れる。

対応するのはモジュールレベルの関数 `degraded(step, prompt, *, why="")` だ。`Handoff.degraded` は読み取り専用のプロパティで、
`doing` にその印があるかどうかを判定する。

> **不完全なハンドオフ文書は、ウィンドウに突き当たるよりはるかにましだ。**

ハンドオフ文書を書くターンには、意図的な取り決めがもう 2 つある:`max_budget_usd=None` で走らせる ——
**ハンドオフ文書は必ず書けなければならず、予算で詰まってはいけない**。そして `on_event=None` —— このターンは UI に流さない。

### 落とし穴が一つ:ハンドオフ文書を書くターンはしきい値から除外しなければならない

ハンドオフ文書を書くのは**線を越えた後**だ —— その時点で水位はもともとしきい値の上に張り付いている。除外しないと、
ハンドオフ文書を書くターンの最初のメッセージがまた「交代すべきだ」と判定され、1 文字も書けないうちに中断され、
**毎世代が劣化版を産む**。しかも見た目には何も問題がない(劣化パスがよく働いてしまうので)。

実際にやらかした:`tests/handoff_live.py` を初めて本当に走らせたとき、**2 世代のハンドオフ文書がどちらも劣化版**だった。
オフラインテストは捕まえられなかった —— そちらは `_attempt` を丸ごと差し替えていて、偽物はこの判定を通っていなかった。
いまは判定を `Runtime._handoff_due()` に切り出し、オフラインで直接検証している。

### 暴走を止めるブレーキ

`max_generations=8`。

!!! danger "`window` を小さく設定すると無限にハンドオフして課金が燃える"
    危ないのはこれだ:**しきい値がそのロールの起動フロアを下回る**([コーディネーター](../reference/glossary.md#协调者)は実測で約 34k、
    システムプロンプトと[ワークベンチ](../reference/glossary.md#工作台)のインデックスだけでそれだけ食う)と、新しいセッションは口を開いた瞬間に線を越える
    → ハンドオフ文書を書く、交代する、また越える、**永遠に止まらない**。しかもハンドオフは再試行の枠を消費しない。これは意図的だ。したがって唯一のブレーキが
    `max_generations=8` になる。

    正常な長時間の実行で 8 世代に届くことはない。本当に届いたなら、ほぼ確実に `window` が小さすぎる ——
    上限に達したときのエラーメッセージはそう書いてある(「しきい値がこのロールの起動フロアを下回っている可能性が高い。window を大きくするか `--no-handoff`」)。

### ハンドオフ一回の全体像

```text
干活(session A)
  |  メインスレッドのコンテキストがしきい値を越える  <- 見るのはメインスレッドだけ。subagent のコンテキストは
  |                            それ自身の transcript の話で、走り終われば消える。メインに交代を強いる筋合いはない
  |- メッセージ境界で切る       <- Ctrl-C の中断と同じ理屈:状態を裂かずにきれいに切る
  |                            (代償も同じ:飛行中の subagent は失われる。50k の余裕はそのために取ってある)
  |- 同じ session でもう 1 ターン走らせる:ハンドオフ文書を書く
  |     なぜ自分で書くのか —— そのコンテキストを持つのはそれだけだ。誰に書かせるにも先に読ませる必要があり、それでは交代の意味がない
  |- <工作台>/notes/交接-<步骤名>.md に凍結し、前の世代は notes/archive/交接/ へ移す
  |- 新しいセッション(resume=None、fork=False)、prompt = ハンドオフ文書の prompt_block()
干活(session B)が続きをやる
```

`HANDOFF_PROMPT` は現在のセッションにハンドオフ文書を書かせるためのプロンプトで、`{used}` と `{window}` の 2 つのプレースホルダを含む。
**これは新しいロールではない** —— そのコンテキストを持つのは、いま走っているそのセッションだけだ。

### ハンドオフは再試行ではない:記録のつけ方

| フィールド | ハンドオフ時にどう変わるか |
|---|---|
| `attempts` | **増えない** —— これが数えるのは失敗した試行だ |
| `retired[]` | このステップで燃やした session_id が**順番に**ここに記録される |
| `session_id` | 常に**最後に引き継いだもの**であり、燃やされたものではない |
| `context` | 最後のターンでメインスレッドが実際に見たコンテキスト規模 |
| `cost_usd` / `num_turns` | 再試行とハンドオフをまたいで**加算される** |

これらのフィールドはすべて `manifest.json` に入り、事後に「このステップは何世代燃やし、各世代でいくら使ったか」を完全に復元できる。

### ハンドオフ文書はどこに置かれるか

`<工作台>/notes/交接-<步骤名去掉非法字符>.md`。既存の前世代は
`notes/archive/交接/<步骤名>-<时间戳>.md` に移される。

**ワークベンチが無ければディスクには落ちない** —— そのとき `_handoff_path` は `None` を返す。文書は変わらず prompt 経由で引き継ぎ手に渡され、
ハンドオフも通常どおり進むが、**人が事後にそのファイルを辿れない**。事後に辿れるようにしたければワークベンチを有効にすること
(`Runtime(workbench=True)`、あるいは[ワークフロー](../reference/glossary.md#流程)が自前で 1 つ用意する)。

## 使うべきでないとき

- **どうしても compact を使いたい。** `flower --no-handoff`、あるいは `Runtime(handoff=False)`。
  ハンドオフは auto-compact も一緒に切ってしまうので、その副作用が嫌なら有効にしないこと。
- **両方を同時に走らせたい。** `AgentSpec(compact=CompactPolicy(mode="auto"))` を明示すれば auto-compact は残せるが、
  その後は「あるときコンテキストが落ちたのは誰の仕業か」を説明できなくなり、調査が難しくなる。ハンドオフを信じるか compact を信じるか、どちらかにすること。
- **短いタスク、単発の作業。** ハンドオフは決して発火しないので、設定する意味がない —— ただし `Runtime` のデフォルトが
  `handoff=True` である以上、auto-compact は切られていることは覚えておくこと。
- **ワークベンチが無いのに、事後にハンドオフ文書を読みたい。** 先にワークベンチを有効にすること。さもないと文書はそのランのコンテキストにしか現れない。
- **`window` を合わせないまま長時間の実行を始める。** 実際のウィンドウがデフォルト値より小さいと、最初の数世代のハンドオフ文書はすべて劣化版になり、
  劣化版こそ最も役に立たない種類のハンドオフ文書だ。まず `--window` で合わせるか、短いランを 1 回走らせて `-v` のモデル名を見ること。
- **ハンドオフをコンテキスト管理のすべてだと思う。** これは最後の一枚だ。その場で刈り取る層
  (スピル、[トリム](../reference/glossary.md#裁剪)、[プルーン](../reference/glossary.md#剪除))のほうが安い。
  [コンテキストの経済学](context.md)を参照。

## つまみ

| 症状 | どれを回すか |
|---|---|
| ハンドオフが頻繁すぎて作業が常に中断される | `--window` をモデルの実際のウィンドウに合わせる(`-v` で有効なモデル名が見える) |
| 開始直後にハンドオフし、「起動フロア」と言われる | 同上。`window` が小さすぎる |
| ハンドオフ文書がいつも劣化版になる | `runs/manifest.json` の `errors` を見る。劣化の理由が書いてある |
| 引き継いだ側が前世代と同じ作業を繰り返す | ハンドオフ文書の「行き止まり」が薄すぎる。そのファイルを直接書き換えてよい |
| 事後にハンドオフ文書を読みたいがファイルが無い | ワークベンチが無効。文書はディスクに落ちず、prompt を通っただけ |
| とにかく compact を使いたい | `--no-handoff` |
