# 事前確認

着手する前に要件を問いただす。[確認者](../reference/glossary.md#确认者)は質問だけをして手は動かさない役割で、
はっきりするまで問い続け、最後にちょうど四段構成の[要件確認書](../reference/glossary.md#需求确认书)を出力し、
ディスクへ凍結する。以降のすべての[ステップ](../reference/glossary.md#步骤)はこの文書を読んで開始し、要件を推測し直すことはない ——
そしてその問答は下流のコンテキストに**一度も入らない**。

## 何を解決するか

flower がコンテキストを掃除する手段が消すのはすべて**現場**だ:期限切れ、拒否された呼び出しの除去、エラーメッセージの除去、
大きな結果の[spill](../reference/glossary.md#落盘)。現場は失っても構わない、走らせ直せば再び得られる。

そうではない種類の誤りがある:**目標の理解が間違っている**。これはコンテキストを掃除すると**悪化する**唯一の種類の誤りだ。現場が捨てられたあとに
残るのは、まさに誤った前提の上に建てられたその判断であり、しかもそれは正しい判断とまったく同じに見える ——
その前提が疑わしいと示す痕跡はどこにもない。

[long-horizon](../reference/glossary.md#长程)はこれを最悪まで拡大する:誤った前提のまま数時間走り、
十数個の [subagent](../reference/glossary.md#subagent) を派遣し、ディスクに成果物を積み上げ、そのあとで露見する。
そのとき高くつくのは token ではなく、**成果物のひとつひとつが誤った要件に照らして作られている**ことだ。
[HT001](../cases/ht001.md) の請求額がこの比率を示す:要件を確認するステップが **$0.3704 / 5 ターン / 0.06h**、
そのあと作業するステップが **$171.2476 / 31 ターン / 10.44h**。

だから「立ち止まって尋ねる」経路が必要で、しかもそれは着手の**前**になければならない。

## 使い方(最小のコード)

### コード不要:コマンドライン

プロジェクトディレクトリに入って、そのまま走らせる:

```bash
cd /path/to/your/project
flower
```

```text
要做什么? 一句话就够,回车开始(Ctrl-C 退出)
> 帮我做一个 X
```

ターミナルにはこんな質問が出る:

```text
  ? 这个工具是给命令行用,还是要有 Web 界面?
     1) 纯命令行
     2) Web 界面
     3) 两个都要
你的回答 (回车=跳过,让它自己判断) > 1
```

- **番号**を入れて選ぶか、そのまま文章で答える
- **Enter = この質問をスキップ**。自分で判断させ、その仮定を「未知と仮定」に記録させる
- 四段が揃って初めて通過し、確認書は `.flower/notes/需求.md` に凍結される
- **再実行しても問い直さない** —— 確認をやり直したければそのファイルを削除するか、`--new` を付ける

何を聞くかだけ見て先へは進めたくない場合:`flower --clarify-only`。質問に上限を課す:`--asks 12`
(指定したときだけ選択肢の下に `(还能问 N 次)` の行が増える;既定は無制限で、その行は出ない)。誰も見ていない場合:`--timeout 0`。
この経路の実装は
[`flower/workflow/starter.py`](https://github.com/ChenyuHeee/flower/blob/main/flower/workflow/starter.py)。

!!! warning "回答は標準入力を通る。本物の端末で走らせること"
    パイプ、`nohup`、CI には答える人がいない:stdin が EOF を読んだ時点で、そのとき出ていた質問は「入力が閉じられた」として飛ばされ、
    以降の質問はすべて `--timeout` を待ち切ることになる。この場合は素直に `--timeout 0` を渡す ——
    すべての質問が即座に空振りし、自分で判断して仮定を「未知と仮定」に書く。

### 自分で配線する

```python
from pathlib import Path
from flower import HumanChannel, Step, Workbench, Workflow, clarify_step

wb = Workbench(Path.cwd()).ensure()
ch = HumanChannel(log_path=wb.notes / "问答记录.md")   # 既定では質問回数は無制限、人を 30 分待つ
wf = Workflow(channel=ch, workbench=wb, steps=[
    clarify_step(ch, brief_path=wb.notes / "需求.md", prompt="帮我做一个 X"),
    Step("干活", spec=协调者, prompt=lambda ctx: f"照这份需求做:\n\n{ctx['确认需求']}"),
])
```

`prompt` には**あなたの**元の要望だけを書く、一言で足りる。何を聞くかは確認者自身が決める ——
あなたの領域でどんな質問をすべきかを、フレームワークは知らないし、知るべきでもない。上の `协调者` はあなたが `coordinator()` で
作った `AgentSpec` だ。[ワークフローの設計](workflow.md)を参照。

`clarify_step()` の引数:

| 引数 | 既定 | 説明 |
|---|---|---|
| `channel` | — | `HumanChannel`。**同じインスタンス**を `Workflow(channel=...)` にも渡すこと |
| `brief_path` | — | 確認書の置き場所。渡した[ワークベンチ](../reference/glossary.md#工作台)の中でなければならない。下記参照 |
| `prompt` | — | あなたの元の要望。`str` または `Callable[[Ctx], str]` |
| `name` | `"确认需求"` | ステップ名。`ctx` のキー名でもある |
| `spec` | `None` | 自前の `AgentSpec`。渡すと `clarify()` は使われない |
| `instructions` | `""` | `CLARIFIER_RULES` のあとに追加される領域固有の指示 |
| `always_ask` | `False` | `True` = 毎回確認し直す(要件を変更したとき用) |
| `on_fail` | `"stop"` | 四段が揃わないときの行き先。`Step.on_fail` と同じ |
| `retries` | `0` | 四段が揃わないときのリトライ回数 |
| `**spec_kw` | — | `clarify()` へ透過:`can_read` / `model` / `effort` / `max_turns` / `max_budget_usd` |

走り終わると `ctx` に三つ入っている:

```python
ctx["确认需求"]     # str,四段のコンパクト版(prompt_block)。そのまま下流の prompt に差し込む;キー名 = ステップ名
ctx[BRIEF_KEY]     # "_brief" —— Brief オブジェクト。段ごとに取りたいならこれ
ctx[MISSING_KEY]   # "_brief_missing" —— 四段が揃わないときだけ存在:欠けている段を UI 表示用に
```

うまく動かないときはまずこのつまみを回す:

| 症状 | どれを回すか |
|---|---|
| 質問が多すぎ、細かすぎ | `max_asks` に上限を与える;`instructions` にあなたの領域で自明なことを書く |
| ろくに聞かずに着手する | `instructions` で必ず明らかにすべき事項を名指しする(回数は既定で無制限なので、上限をいじっても無意味) |
| 四段の中身が雑 | `instructions` にあなたの領域の見本を一つ与える |
| 無人なのに止まる | `timeout_s=0` |
| 毎回確認し直したい | `always_ask=True`、または確認書ファイルを削除する |

## 実際に何をしているか

### 発動タイミング:三箇所の配線、新しいフィールドはゼロ

`clarify_step()` が作るのはただの `Step` で、三つのコールバックを埋めてあるだけだ:

| どこに繋ぐか | いつ走るか | 何をするか |
|---|---|---|
| `Step.when` | このステップに入る前 | 確認書が既にあり四段が揃っていれば**スキップ**し、`ctx` に流し込む |
| `Step.gate` | このステップが終わり、結果を下流へ渡す前 | 四段が揃っていなければ**先へ進ませない**;揃っていれば `write()` で**凍結** |
| `Step.reduce` | 通過後 | 下流へ**パース済みの四段**を渡す。モデルの原文ではない |

**スキップしても `ctx` には流し込む。** ここは見落としやすい:`when` が `False` を返すと `Workflow` はこのステップを実行せず、
当然 `ctx[step.name]` も書かれない —— だから `clarify_step` は `when` の中で既存の確認書を流し込んでいる。
そうしないと再実行時に下流が `KeyError` を食らう。

`reduce` が渡すのは `Brief.prompt_block()` であってモデルの原文ではない。原文には余計に書いたものが混ざりうるからだ
(実測で、コード全文を返答に貼り付けてくる)。

[継続](../reference/glossary.md#接续)時、このステップは切り出しの一言を変える —— `CLARIFY_RESUME`:
「さっき途中までだった要件確認の続き —— **やり直しではない**……」。この一言がないと、
継続時に元の要望を新しいタスクとして再送してしまい、確認者が既に聞いたことを聞き直しかねない。

### 境界:問答は下流のコンテキストに入らない

```text
确认需求        独立会话  ────→  磁盘上一份冻结的四段确认书
                                          │
干活(下一步)   新会话(resume_from=None)◄─┘   只拿到那四段
```

`clarify_step` の `resume_from` は既定の `None` のままなので、次のステップは**新しい session** になり、確認書しか受け取らない。
その問答は[coordinator](../reference/glossary.md#协调者)のコンテキストに**一度も入っていない** ——
「入ったあとで刈られる」ではない。この差は実質的だ:刈られたものは `sessions.db` にまだ残っていて、
resume で戻ってくる可能性がある;一度も入っていないものにその問題は存在しない。

問答そのものは **`log_path` へ追記される**。こちらはコンテキストを食わず、compact の影響も受けず、機械を変えても残る ——
ワークベンチと同じ発想だ。

### 四段はそれぞれ別種の失敗を止める

| 段 | 何を書くか | 書かないとどうなるか |
|---|---|---|
| **目標** | 一言で:何を作るのか、誰が使うのか | 別物ができあがる |
| **受け入れ基準** | 判定可能な条件を一行ずつ。「ちゃんと動く」は不可、「`x` を走らせて `y` が出る」なら可 | 誰も「完了した」と判定できない |
| **境界** | **何をやらないかを明示** | スコープが膨張する。この段は以降の**すべての** subagent を縛る |
| **未知と仮定** | 聞けなかったこと、タイムアウトで空振りしたこと、自分で推測したことを一行ずつ | **誤った前提が黙って埋められる** |

四段目は long-horizon 実行のヒューズだ。前の三段のどれを書き間違えても、仮定が四段目に明示されてさえいれば、後で読む者が止める機会がある;
埋められてしまえば、数時間後に成果物が全部無駄だったと分かるまで気づけない。誤った前提を完全に避けることはできないが、**明示的**にはできる。

四段が揃って初めて通過し、どの段が欠けているかは `Brief.missing()` が報告する —— 返ってくるのは中国語の段名なので、そのまま表示できる。

パースは書き方にかなり寛容だ:`## 目标` / `**目标**` / `目标:` / `3. 边界` いずれも認識し、見出しの直後に本文が続く形
(`目标: 做一个 X`)も認識し、よくある別名も認識する(`验收条件`→受け入れ基準、`不做什么`→境界、
`未知项与假设`→未知と仮定);同じ段が複数回現れたら、中身のある最初のものを取る。例外が二つある:

- `Brief.parse()` は**まずフェンス付きコードブロックを剥がす**ため、**閉じていない**フェンスに出会うとそこから後ろを丸ごと捨てる。
  モデルの出力が途中で切れたとき、後続の段は一つもパースできない → 四段が揃わない → `gate` が差し戻す。
- `Brief.load()` は `"(未填)"` を空とみなす。確認書を手で編集する際に `to_markdown()` のプレースホルダ文言をそのまま写すと、
  その段は依然として欠落扱いになる。

### 境界:確認者は何に触れられるか

**制約なし**の確認者を一度走らせたことがある(`/tmp/probe_ask.py`、**$0.8908 / 230 秒**):
二つ質問したあと**そのままコードを書き始めた**;権限に止められると、**コード全文を返答の本文に貼り付けた**。
プロンプトに「コードを書くな」と書いても止まらない —— そのときのシステムプロンプトには実際そう書いてあった。だから機構は二段ある:

**一、hook で書き込み系のツールを止める。** `clarify()` の無審査リストは
`mcp__human__ask` に加えて(`can_read=True` のとき)`Read` / `Glob` / `Grep` / `WebFetch` / `WebSearch` で、
`Write` / `Edit` / `Bash` / `Agent` は含まない。実際にこれを執行するのは `Runtime` が自動で装着する `whitelist_guard` だ:
無審査リストから逆算して `Bash` / `Write` / `Edit` / `NotebookEdit` のうち止めるべきものを決め、
該当すれば `deny` する。「着手しないよう求められている」のではなく、**着手できない**。

読み取りを許すのは割に合う:リポジトリを一目見れば質問がいくつか減るし、この session は使い捨てなので読んで汚れても構わない
(`can_read=False` にすれば読み取りすら与えない)。

**これは hook でなければならず、`allowed_tools` だけでは足りない。** 後者は**無審査リストであって排他的ホワイトリストではない** ——
モデルはリストにないツールも普通に呼べる。今も有効な実測の証拠が二つある:

- [HT002](../cases/ht002.md) の「目標設定」の[judge](../reference/glossary.md#判定者)は
  実際に **`Bash` を 11 回**走らせた。`judge()` の既定は `can_run=False` で、リストに `Bash` は入っていない
  (あの実行時にはまだこの hook がなかった —— 今日同じ呼び出しをすれば `whitelist_guard` がその場で `deny` する。
  これはまさに、止めているのがリストではなく hook であることを示している)。
- **$0.1 のプローブ**:`allowed_tools=["Read"]` の agent にファイルを書かせる ——
  `Write` は権限層に拒否され(`"requested permissions to write ... but you haven't granted it yet"`)、
  `Bash` はパス安全性に拒否された(`"Output redirection was blocked. For security, Claude Code may
  only write to files in the allowed working directories"`)。**呼び出し自体は発行されており**、
  別の層が止めている。

`clarify()` は `permission_mode` を明示設定せず、`AgentSpec` の既定 `"default"` を継承する。
`coordinator()` の既定は `"acceptEdits"` —— この値を確認者に透過させた者は、その保護を失う。

**二、フレームワークは四段しかパースせず、それ以外はすべて捨てる。** `Brief.parse()` はフェンス付きコードブロックを先に抜き取ってから見出しを探す ——
貼り付けても下流には入らない。これが「下流を汚染する」ことに対する最後の関門だ。

### 境界:質問チャネル

モデル側の質問ツールは `mcp__human__ask`(引数 `question`、任意で `options`)。
`HumanChannel` はプロセス内 MCP サーバーで、**登録するツールは二つ** ——
`mcp__human__ask` と `mcp__human__inbox`;確認者の無審査リストには前者しか入っていない
(受信箱は coordinator 用)。

```python
HumanChannel(
    on_event=None,        # プッシュ型 UI のコールバック。Workflow に渡せば Workflow.run が自動で接続する
    max_asks=None,        # 既定は回数無制限
    timeout_s=1800.0,     # 30 分。None = 永久に待つ;<= 0 = 全自動
    log_path=None,        # 問答をこのファイルに追記する。コンテキストは食わない
    amend_path=None,      # 実行途中で人が言ったことをこのファイルに追記する(通常は確認書そのもの)
    over_budget_text=..., timeout_text=..., declined_text=...,   # 三種類の空振りの文面
)
```

long-horizon agent の常態は**誰も見ていない**ことなので、「立ち止まって人を待つ」は優雅に失敗できなければならない:

| 設定 | 挙動 |
|---|---|
| `timeout_s=1800.0`(既定) | 30 分待つ;時間切れで説明文を一つ返す。**エラーではない** |
| `timeout_s=None` | 永久に待つ。人が張り付いていると確信できるときだけ使う(CLI からこの値は渡せない、`--timeout` は float) |
| `timeout_s=0`(負数も同じ) | **全自動**:すべての質問が即座に空振りし、待つふりをしない |
| `max_asks=None`(既定) | **回数無制限** —— 何回聞くかは確認者自身が判断する |
| `max_asks=N` | 硬い上限。超過分の質問ツールは**その場で断られる**。ブロックもエラーもしない |
| `max_asks=0` | 質問禁止(CI / 無人運用) |

`remaining` は `max_asks=None` のとき `-1` を返す(0 でも無限でもない)。端末はこれを見て「あと N 回聞ける」を表示しない。

タイムアウト時に返る原文はこうだ:

> 応答なし。自分の判断で続け、この質問と採用した仮定を「未知と仮定」の段に書くこと。
> 質問を繰り返さず、ここで止まらないこと。

三種類の空振り(タイムアウト / 上限到達 / 人が自ら飛ばす)の文面はどれも同じ動作を指す:**仮定を四段目に書く**。
これが無人運用でも四段目に中身がある理由であり、long-horizon 実行が走り続けられる理由でもある。
上限をプロンプトに書くのは助言にすぎず、**チャネル側で数えて初めて保証になる**。

実測済みの機構上の事実がひとつ:プロセス内 MCP ツールのハンドラで外部の future を `await` しても**デッドロックしない** ——
ハンドラが待っている間もイベントループは回り続け、別のタスクでも**別のスレッド**でも答えを埋められる。
だから `answer()` / `decline()` は Web バックエンドや TUI の入力スレッドから直接呼べる(内部で
`loop.call_soon_threadsafe` を経由)。これは常態であって例外ではない。UI コールバックが投げた例外は `ui_errors` に収められ、
**実行を中断しない** —— フロントエンドが落ちたからといって三時間分の作業を道連れにすべきではない。全メンバー一覧は [Python API](../reference/api.md) を参照。

!!! warning "`max_turns` を小さくすると、「はっきりするまで問い続ける」は空文句になる"
    `clarify()` の `max_turns` の既定は `None`(無制限)。**質問一つがそのまま一ターン**なので、
    16 に設定するのは「多くても十数個まで」と言うのに等しく、しかもそれは**黙って**効く:チャネル側の `max_asks=None` は
    「無制限」と表示し続けるので、誰が絞ったのか人からは見えない。質問を開放したいなら、`HumanChannel.max_asks`
    と `clarify(max_turns=...)` の**両方の既定値を `None` のままにしておく**こと。

### 確認書の置き場所:渡したワークベンチの中でなければならない

ワークベンチのインデックスは system prompt に注入されるので、coordinator は開始時点で要件ファイルの場所を知っている。作業を振るときはパスを渡せばよく、
中身を[タスク指示書](../reference/glossary.md#任务书)に書き写す必要はない。

!!! warning "インデックスが届くのは coordinator まで"
    subagent は自前の system prompt を持ち、session 単位のその部分を**継承しない**(実測 **$0.2461**、
    `tests/prelude_live.py`)。つまり「coordinator がパスを伝える」のであって、「各 subagent が自動的に知る」のではない。

肝心なのは**どの**ワークベンチか。正しい書き方は一つだけ:自分で作り、それを `Workflow` に渡し、
ドライバに同じオブジェクトを `Runtime` へ渡させる。

```python
wb = Workbench(Path.cwd()).ensure()
wf = Workflow(channel=ch, workbench=wb, steps=[            # ← 渡す
    clarify_step(ch, brief_path=wb.notes / "需求.md", prompt="…"),
    ...,
])
```

間違った書き方が二つあり、どちらも**エラーにならない**ので特に注意が要る:

```python
# ✗ 自分でパスを組み立てる:プロセスの cwd 相対になり、Runtime(workbench=True) が作る <run_dir>/workbench
```

`Workflow(workbench=wb)` と `Runtime(workbench=wb)` の両方に渡す。`tests/trial_offline.py`
の 5 番目は「確認書が `prompt_block()` に現れる」ことを直接アサートし、11 番目はそのアサートが回帰を捕まえられることを確認している。

### 検証状況

**オフラインは全部グリーン**(`tests/clarify.py`、**52 項目**、費用ゼロ):質問チャネルの五つの意味論(ブロックして答えを待つ /
上限到達 / タイムアウトで空振り / スキップ / スレッドをまたいだ回答)、四段のパース(「コードを貼ってきた」サンプルを含む)、
`clarify()` の役割に書き込み系ツールが**ない**こと、`clarify_step` の三箇所の配線。

**CLI 経路もオフラインで通しで動く**:完全な確認書を事前に置く → 最初のステップをスキップ → チャネルが標準入力スレッドに自動接続 →
確認書が `ctx` に流し込まれる → クリーンに終了。

**実 API では走らせていない。** $0.8908 のプローブは**実リクエスト**だが、測ったのは「制約なしの確認者が何をするか」であって、
今のこの経路ではない。

## 使うべきでないとき

**要件が既に凍結済みのとき。** 要件がファイルに書かれている、上流システムから与えられる、あるいは今回は同じことの再実行だ ——
なら聞くことはない。要件テキストを作業ステップに直接食わせるか、`clarify_step` を残して `when` でスキップさせる
(確認書があるなら、そもそも聞かない)。

**聞ける人がおらず、しかも自分で推測させたくないとき。** `timeout_s=0` ではすべての質問が即座に空振りし、
四段目はそれ自身の仮定で埋まる —— 設計どおりだが、その確認書の信頼度はそれらの仮定の信頼度と等しくなる。
CI ではより綺麗なやり方は `max_asks=0`(質問を明示的に禁止)で、要件は外部から完全な形で与える。

**使い捨ての小さな作業。** 確認というステップ自体に費用がかかる:[HT002](../cases/ht002.md) の
「リポジトリを clone して、macOS でインストールして動かす」程度のことでも、要件確認に **$0.5306 / 9 ターン / 0.10h** かかった。
作業が小さいほど、このステップの占める割合は見苦しくなる。`flower once` のような単一 agent 経路にはこのステップはない。

**要件を変更するときに対話をやり直すべきではない。** 確認書は凍結物であり、ディスクに落ちた瞬間から要件はファイルが正となる ——
正しいやり方は**そのファイルを直す**ことだ。`--clarify-only` は既に確認済みのディレクトリでは**何もしない**
(そのワークフローはこのステップだけで構成され、そのステップはスキップされる)。確認し直すには `--new` を併用するか、
自分で配線する場合は `always_ask=True` を渡す。

**これは「終わったかどうか」を判定しない。** それは別の層で、[ゴールガード](goal.md)を参照。事前確認が止めるのは
「作ったものが望んだものではない」であって、「終わったと言うが実は終わっていない」は止められない。
