# Goal guard

「終わったかどうか」は worker が決めることではない。[judge](../reference/glossary.md#判定者) は目標だけを立て、
判定だけを行い、自分では手を動かさない役割だ。走り出す前に[brief](../reference/glossary.md#需求确认书)を判定可能な
チェックリストへ変換し、以降は 1 ラウンドの作業が終わるたびに**独立して 1 回判定**し、[verdict](../reference/glossary.md#判定) を出す ——
達成なら先へ進み、未達成なら「どこが足りないか」を添えて差し戻して続行させ、
達成不能と判定したら止まって人に聞く。

## 何を解決するのか {#解决什么问题}

[clarify](clarify.md) が防ぐのは**「作ったものが欲しかったものと違う」**である。この層が防ぐのは別の種類だ:
**「実は終わっていないのに、本人は終わったと言っている」**。この 2 つは失敗の仕方が違うので、必ず分けなければならない:

| | 失敗はどう見えるか | いつ露見するか |
|---|---|---|
| 要求が誤り | すべての成果物が誤った要求の上に建てられている | 数時間後、成果物が全部無駄になる |
| 完了度の判断が誤り | 半分しか走っていないテスト、1 箇所直して 3 箇所漏れ、「たぶん問題ない」 | 自分で使ってみたとき |

2 つめを worker 自身に任せられない理由は、**体系的な楽観バイアスがあるから**だ。
不誠実だからではない —— 自分の盲点が見えないのだ。自分が何をやったかは知っているが、何を漏らしたかは知らない。

だから判定は、**作業に関与しておらず、自分の[session](../reference/glossary.md#会话)で動く**役割に任せる。
そこから見えるのは目標と現場だけで、worker が何回試したか、どれだけ苦労したかは知らない。だから言い訳を代わりに考えることもない。
clarifier を独立 session で走らせるのと同じ理屈だ。

## 使い方(最小コード) {#怎么用最小代码}

### コード不要:コマンドライン {#零代码命令行}

```bash
flower                      # 默认就带目标看守
flower --no-goal            # 关掉:干活跑完就算完
flower --rounds 5           # 最多五轮活(默认 3)
flower --judge-can-run      # 让判定者能跑命令(判定更硬)
```

### 自分で配線する {#自己接线}

2 つの関数がそれぞれ半分を受け持つ。混同しないこと:`goal_step()` は**目標を立てる**(独立した step)、
`with_goal()` こそが**判定ループ**(作業 step を包む)である。

```python
from pathlib import Path
from flower import HumanChannel, Step, Workbench, Workflow, clarify_step, goal_step, with_goal

wb = Workbench(Path.cwd()).ensure()
ch = HumanChannel(log_path=wb.notes / "问答记录.md")   # デフォルトは質問回数無制限
goal_path = wb.notes / "目标.md"

work = Step("干活", spec=协调者, prompt=lambda ctx: f"照这个做:\n{ctx['确认需求']}")

wf = Workflow(channel=ch, workbench=wb, steps=[
    clarify_step(ch, brief_path=wb.notes / "需求.md", prompt="帮我做一个 X"),
    goal_step(ch, goal_path=goal_path),
    with_goal(work, ch, goal_path=goal_path, rounds=3),
])
```

`goal_step(channel, *, goal_path, ...)`:

| 引数 | デフォルト | 説明 |
|---|---|---|
| `goal_path` | — | 目標の置き場所。[workbench](../reference/glossary.md#工作台) の `notes/` 配下に置く。理由は brief と同じ |
| `brief_key` | `"确认需求"` | `ctx` のどのキーから brief を読むか。**読めなければ `"(没有确认书)"` しか手に入らない** |
| `name` | `"设定目标"` | step 名。`ctx` のキー名でもある |
| `spec` / `instructions` | `None` / `""` | 独自の `AgentSpec` を渡す、または judge にドメイン指示を追記する |
| `always_set` | `False` | `True` = 毎回設定し直す |
| `on_fail` / `retries` | `"stop"` / `0` | `Step` と同じ |
| `**spec_kw` | — | `judge()` に素通しする:`can_run` / `model` / `effort` / `max_turns` / `max_budget_usd` |

`with_goal()` は作業 step を判定つきのループに包む:

```python
with_goal(step, channel, *, goal_path, spec=None, rounds=3,
          instructions="", can_run=False, name=None, **spec_kw)
```

**`rounds` は総ラウンド数であって追加ラウンド数ではない** —— 実装上は `retries = max(0, rounds - 1)` になる。
したがって `rounds=3` は最大 3 ラウンド、`rounds=1` は「1 ラウンド走らせ、1 回判定し、通らなければ失敗」だ。
完全なシグネチャとフィールドの意味は [Python API](../reference/api.md) を参照。

`ctx` には 3 つのキーが増える:

```python
ctx[GOAL_KEY]     # "_goal" —— Goal 对象;ctx["设定目标"] 是它的 markdown
ctx[VERDICT_KEY]  # "_verdict" —— 最近一次 Verdict,给 UI 用
ctx[ROUND_KEY]    # "_goal_rounds" —— 跑了几轮
```

judge は `ctx["_runtime"]` 経由で派遣される —— `Workflow.run` がランタイムと event の出口を両方 `ctx` に入れるので、
`gate` は自分で agent を起こせるし、判定の過程もそのまま UI に流れる
(そうしないと十数秒のあいだ画面が真っ暗になり、止まったように見える)。

うまく回らないときは、まずこのつまみを回す:

| 症状 | どれを回すか |
|---|---|
| 判定が甘く、達成と言うが実際は未達成 | `--judge-can-run` で実際に走らせる。または `instructions` にドメイン判定基準を足す |
| 判定が厳しすぎて差し戻しが続く | `目标.md` の判定チェックリストが要求より高く書かれていないか見る。**そのファイルを直す** |
| ラウンドが空回りする | judge が「達成不能」を出すべきところで「未達成」を出している。何を達成不能とみなすか指示を足す |
| 高すぎる | `--rounds 1`、または `--no-goal` で完全に切る |
| 中断されたくない | `--timeout 0`:達成不能でも人に聞かず、そのまま止まる(理由はディスクに残る) |

## 実際に何をしているのか {#它实际做了什么}

### 目標はどう書かれるか {#目标长什么样}

`goal_step` は brief を読み、2 つの節を出力して `.flower/notes/目标.md` に凍結する:

```markdown
# 目标
让 conv.py 能把 md 转成 html。

# 判定清单
- 跑 `python conv.py a.md` 产出 a.html
- 输出里含 `<h1>`
- 列表被转成 `<ul><li>`
```

**判定チェックリストがこの層の価値のすべてだ。**「実装が完全」は判定できないが、「何を走らせ、何が見えるか」なら判定できる。
チェックリストは brief の「受け入れ基準」から来るが、各項目をその場で検証できる形に書き換える必要がある —— 曖昧な項目は judge が補う。
2 つの節がどちらも空でない(`statement` に中身があり、`checks` が空でない)ときだけ揃ったとみなし、そうでなければこの step は通さない。

### チェックリストの長さは「失敗の仕方が何通りあるか」で決まる {#清单的长度由有多少种失败方式决定}

judge がどれだけ厳密かで決まるのではない。`git clone && make && ./app` のようなタスクなら、**3〜5 項目で十分**だ:
ビルドが通る、起動する、使える。

**実測で踏み抜いた**([HT002](../cases/ht002.md)):「リポジトリをインストールして動かす」というタスクのチェックリストが **15 項目**に膨れ、
そのうち**5 項目**だけが「ものが使えるか」の検証、**6 項目**は「手順を守ったか」の検証
(`~/.zshrc` の mtime の確認、`.flower/` ディレクトリが改変されていないかの確認まで含む —— それはフレームワーク自身のディレクトリだ)、
**4 項目**は原理的に検証不能だった。

#### 境界は判定項目ではない {#边界不是判定项}

これがあの回の主因だ:

| | 何を制約するか | どう守るか |
|---|---|---|
| **境界** | **どう作業するか**(「プロジェクトディレクトリ内にだけインストールする」「業務コードに触るな」) | **越えないこと**で守る。事後の自己証明ではない |
| **判定項目** | **提出したもの**(「動いたか」「結果は正しいか」) | その場で検証して守る |

「`brew install` を走らせていないこと」を判定項目にするのは、境界を 1 つ足すたびにチェックを 1 つ増やすのと同じだ ——
そして境界とは、まさに clarify 段階で書き尽くすよう促されるものである。どうしても説明が要るなら一言で済ませ、6 項目に分解しないこと。

### 検証不能な項目は、目標設定の時点で警告される {#验不了的条目设目标时就会喊}

チェックリスト中に `[此环境无法验证:原因]` と付いた項目があると、`goal_step` は**目標を凍結したその瞬間に**通知を出す:

```text
  # 目标里有 4/15 条在这个环境里验不了 —— 判定时它们必然过不去,会停下来问你。
    现在改 .flower/notes/目标.md 还来得及:
      · 界面截图并实际看图 [此环境无法验证:屏幕录制未授权]
      · ...
```

**なぜ前倒しするのか**:これらの項目の運命は目標設定の瞬間に決まっており、判定時には必ず通らない。
HT002 では先に**作業に $35.90 + 判定に $1.40** を使い、そのあとで気づいた ——
気づきを目標設定の step まで前倒しすれば、同じ情報のコストは **$37** から **$0** に下がる。

通知するだけで、止めはしない:人はそのまま走らせることを選べる(HT002 は最終的に「この結果を受け入れる」を選んだ)。
`Goal.unverifiable` がこのリストで、event payload には UI 用の構造化データが入っている。

### 結論は 2 つではなく 3 つ {#三个结论不是两个}

```text
干活 ──> 判定 ──达成────> 往下走
              ├─未达成──> 打回,带上“差在哪”,续跑同一个会话接着做
              └─无法达成─> 停下来问人:接受 / 改目标 / 你判断错了
```

3 つめの結論が肝だ。「達成/未達成」しかなければ、**そもそも達成不能な**目標のために coordinator が
1 ラウンドずつ空回りし、予算が尽きるまで走る —— それこそが本当に金を燃やす。だから judge には明確に要求している:
「もう 1 ラウンド回しても無駄」なものだけが達成不能である(必要な外部条件の欠如、要求の自己矛盾、判定項目がそもそも検証不能)。
単に「まだ終わっていない」だけなら未達成を使う。

達成不能のとき、フレームワークは止まって人に聞く:

```text
  ? 目标被判为**无法达成**:缺少 X 依赖,判定项 2 无法验证
    怎么办?
     1) 接受这个结果,就这样往下走
     2) 修改目标
     3) 你判断错了,继续做
```

- **受け入れる** → この step は通ったことにし、理由は記録に残る
- **目標を修正する** → 新しい目標を続けて聞き、元の目標のうしろに**追記**する(何を変えたか見える)。そしてもう 1 ラウンド
- **判断が誤り**(および自分で書いた任意の自由回答)→ あなたの言い分を添えて差し戻し、もう 1 ラウンド

**応答する人がいなければ止まる**。空回りは続けない —— これは意図的だ。達成不能と判定され、しかも聞ける相手もいないなら、
走り続けることは 1 ラウンドずつ金を燃やすことであり、それこそ最も避けるべきことだ。停止時に投げるのは `StepAbort` で、理由は
`ctx["_aborted"]` に書かれる。目標ファイルも `runs/manifest.json` も残っているので、人が戻ってから続きを決められる。

!!! warning "「できていない」と「ここでは検証できない」は別の結論だ"
    `Verdict` の 3 つの値は `ACHIEVED` / `NOT_YET` / `UNREACHABLE` である。
    **`UNREACHABLE` は絶対に通過にしてはならない** —— それは「止まって人に聞く」経路であって、「もう 1 ラウンド」ではない。
    judge が書いた「无法验证 / 没法验证 / 验证不了 / 无法判定 / unverifiable」は**すべて**
    `UNREACHABLE` に寄せる。「ここでは検証できない」を「達成」とみなすのは、「たぶん大丈夫そう」の一言で作業を締めるのと同じだ。
    「未達成」とみなせば、そもそも検証できないことを 1 ラウンドずつやり直させることになる。

### 判定が曖昧 = 未達成 {#判定含糊--未达成}

`Verdict.parse` の認識順序:まず見出し節から「結論 / 判定」の節を取る。見出し節がない場合は、
全体が `1` / `true` なら達成、`0` / `false` なら未達成(judge に「0/1 だけ返せ」と要求すると、
本当に数字 1 つしか返ってこないことがよくある)。それでも当たらなければ結論テキストからキーワードを探す(長い語を先に)。最後に孤立した `1` / `0` を探す。

**どれにも当たらないとき `state` は空、`ok` は `False` となり、フレームワークは未達成として扱う。** これは意図的だ:
「判定できない」と「終わった」は別物であり、曖昧なものは一律で未達成とし、デフォルトの理由を一言添える
(「judge が明確な結論を出さなかったため、未達成として扱う」)。

### 判定するのは成果物であって、ソースコードではない {#判的是产出物不是源码}

!!! warning "ソースコードしか読まない判定では成果物を判定できない"
    [HT001](../cases/ht001.md) では、受け入れ基準の原文は「単体で実行可能なファイルをコンパイルし、macOS の
    ターミナルで直接実行できること」だったが、判定は `Makefile:25-38` に Darwin 分岐が確かにあることだけを読んで**通過**と判定した ——
    納品された成果物は `ELF 64-bit LSB pie executable, ARM aarch64, GNU/Linux` だった。

    **誤判定したのは goal guard ではない**:あの run にはまだこの仕組みがなく、この項目を判定したのは coordinator が自分で
    その場で派遣した独立監査役だった。だが goal guard に替えても同じく見逃す —— judge はデフォルトで `can_run=False` であり、手にあるのは
    `Read` / `Glob` / `Grep` だけだ。**`file` を走らせられない**ので、同じく `Makefile` を読みに行き、同じく
    Darwin 分岐を見て達成と判定する。この失敗の核心は「誰が判定するか」ではなく「何を証拠に判定するか」にある。

    この教訓は `JUDGE_RULES` に書き込まれた:判定するのは**成果物**であり、「ソースに macOS 分岐があるから
    動くはずだ」といった推論は受け付けない。

[HT002](../cases/ht002.md) は `judge_can_run` を有効にし、judge が実際に `file` / `lsof` を走らせた回であり、
だからこの落とし穴を避けられた —— その第一声は「あの返答を読んで結論は出さない。現場へ行く。」だった。そして:

```text
file cppide        → Mach-O 64-bit executable arm64
lsof -p 96040      → 起于 16:10,16:15 仍活着
```

判定 prompt の中の一文も同じ意味だ:自分で現場を見ろ、判定チェックリストと 1 項目ずつ突き合わせろ、**証拠が見えない判定項目は
不通過だ**。

### 「差し戻し」は続きから、やり直しではない {#打回是接着做不是重头做}

差し戻しには `Step.on_reject` を使う:次のラウンドは**否決されたばかりのその session を `resume`** し、prompt を判定フィードバックに差し替える
(`Verdict.feedback()` は「どこが足りないか」だけを渡し、解決策は渡さない)。だから、すでに終えた作業、読んだファイル、通った回り道は
すべてコンテキストに残っており、差分を埋めるだけでよい。

その違いは step 名に書かれ、`runs/manifest.json` で一目で分かる:

```text
干活            第一轮
干活#round2     被打回后接着做      ← on_reject 生效,resume 上一轮
干活#retry1     普通重试(重头跑)    ← 没有 on_reject 时的老行为
```

judge 自身は**常に新しい session** だ:`with_goal` の gate は `Runtime.run` を直接呼び、`resume` は渡さない。
step 名にはラウンド番号が付き(`干活·判定#1`)、サフィックス付きの名前はプロセス間の[lineage](../reference/glossary.md#血缘)には入らない。
gate で `ctx["_runtime"]` が取れないときは `StepAbort` を投げ、**通過を装わない**。

### スキップと再設定 {#跳过与重设}

目標ファイルが既に存在して揃っているとき、この step は**スキップされる**(brief と同じ)—— [long-horizon](../reference/glossary.md#长程) の
run が落ちて再起動したとき、前の結論をもう一度計算し直すべきではない。再設定したければそのファイルを消すか、`always_set=True` にする。

**例外:wake のときにもう一言言った場合。** その一言は brief に追記されるので、この step は**再導出される**
(`always_set=True`)。再導出しないと judge が読むのは凍結された古いチェックリストのままで、あなたが新しく足した事項が終わったかどうかは
判定に入りもしない —— 古いチェックリストで「達成」と判定してしまう。再導出のコストは実測 **$0.41 / 3 分**。
[continuity](continuity.md) を参照。

### judge はコマンドを走らせられるか {#判定者能不能跑命令}

デフォルトでは**走らせられない**。`judge()` の承認不要リストは質問ツールに `Read` / `Glob` / `Grep` を加えたもので、
`can_run=True` のときだけ `Bash` が加わる。トレードオフ:

- `Bash` を与える(CLI の `--judge-can-run`)→ 受け入れコマンドを実際に走らせられ、判定が硬くなる
- しかしワークスペースを改変できるようになる → 「ついでに直して」から通過と判定しかねず、そうなるとその判定は無意味だ

clarifier と同じく、**`Write` / `Edit` / `Agent` は無い**。これを執行するのは `whitelist_guard` という hook であり、
**`allowed_tools` ではない** —— 後者は**承認不要リストであって排他的ホワイトリストではない**。モデルはリストに無いツールも普通に呼べる。
この 2 点がなお成り立つ実測証拠:HT002 では「设定目标」の judge が **11 回 `Bash`** を走らせたが、
そのときの承認不要リストには `Bash` が入っていなかった。**$0.1 のプローブ**では、
`allowed_tools=["Read"]` の agent が `Write` と `Bash` の呼び出しを普通に発行し、それを止めたのは権限層とパス安全機構だった
(`"requested permissions to write ... but you haven't granted it yet"` /
`"Output redirection was blocked..."`)。今日ではこの 2 種類の呼び出しは hook がその場で `deny` する ——
**止めているのは hook であって、リストではない**。

!!! warning "目標を設定する judge はデフォルトで `Bash` を持たない"
    `goal_step()` には **`can_run` の仮引数が無い**ので、`**spec_kw` 経由で渡すしかない:`goal_step(ch, goal_path=…, can_run=True)`。
    明示しなければ `Bash` は無く、`JUDGE_RULES` の「まず `uname -a` で自分がどこにいるか確かめろ」という項目が実行できない ——
    その結果、このマシンではそもそも検証できないチェックリストを書いてくることがある。`with_goal()` は別で、
    独立した `can_run` の仮引数を持つ(デフォルト `False`)。

### なぜラウンド数には上限があり、質問回数には無いのか {#为什么轮数有上限而提问次数没有}

質問はほとんど金がかからないが、1 ラウンドの作業は正真正銘の出費だ。だから:

- **質問は回数無制限**(`max_asks=None`)—— はっきりするまで聞く。判断は clarifier 自身に委ねる
- **ラウンド数には上限**(`rounds=3`)—— ただし本当の歯止めはこの数字ではなく、3 つめの結論「達成不能」だ:
  それが出た時点で止まって人に聞くので、ラウンドを使い切るのを待たない

## 使うべきでないとき {#什么时候不该用它}

**判定のほうが作業より冗長になるほどタスクが小さいとき。** この層は単純な問題を複雑にする。しかもそれは実測済みだ:
HT002 の「リポジトリを clone して macOS 上でインストールして動かす」という件では、判定チェックリストが 15 項目に膨れ、
うち 6 項目は手順遵守の検証、4 項目は原理的に検証不能だった。その判定自体に **$1.4037 / 37 ターン / 0.09h** かかり、
run 全体で **$38.2409 / 0.97h** だった。タスクの失敗の仕方がもともと 2〜3 通りしかないなら、`--no-goal` のほうが割に合う。

**目標を判定可能なチェックリストに書けないとき。** 探索的な作業(「このリポジトリがだいたい何なのか見てくれ」)には「終わった」の判定基準が無く、
無理に目標を立てても、きれいだが判定の効かないチェックリストが出てくるだけだ。この種の作業には `flower once` か `--no-goal` を使う。

**肝心の判定項目がこの環境では検証できないとき。** judge はデフォルトで `can_run=False` で、ツールは
`Read` / `Glob` / `Grep` だけ —— **`file` を走らせられず**、ソースを読むしかない。[HT001](../cases/ht001.md) の
「macOS のターミナルで直接実行できること」という受け入れ基準では、run 全体が Linux コンテナ内で動いていた:
**コンテナ内で macOS バイナリを検証できる judge は存在しない**。自己審査だろうと独立だろうと関係ない。
`--judge-can-run` は一部を救える(少なくとも `file` は走らせられる)が、救えない部分は目標設定時に
`[此环境无法验证:…]` と印を付け、「止まって人に聞く」経路に乗せるべきだ。judge が賢くなることに期待するのではなく。

**無人稼働で、中断が許されないとき。** 達成不能と判定され、しかも応答する人がいなければ、この step は**止まり**、[workflow](../reference/glossary.md#流程) 全体がそこで終わる。
「とにかく最後まで走らせろ」が欲しいなら `--no-goal`。「止まるが待たない」が欲しいなら `--timeout 0` ——
質問は即座に空振りし、理由はディスクに書かれる。

**要求が正しいかどうかは面倒を見ない。** 判定チェックリストは brief から導出されるので、brief が誤っていれば、判定は誤ったことを正確に検証するだけだ。
それは [clarify](clarify.md) の層の仕事である。
