# 継続

同じディレクトリでもう一度 `flower` を走らせると、前回の会話の続きから話し始める —— プロセスが kill されても、
ターミナルが落ちても、マシンを再起動しても同じだ。session という言葉を知る必要はないし、id を覚える必要もない。
このページでは、それが何によって成り立ち、いつ静かに失効し、どうすれば意図的に継続しないようにできるかを説明する。

!!! note "継続はハンドオフではない"
    [継続](../reference/glossary.md#接续)は**プロセスをまたぐ**もので、次のプロセスが前回の[実行](../reference/glossary.md#运行)を引き継ぐ。
    [ハンドオフ](../reference/glossary.md#换代)は**同一実行の内部**のもので、コンテキストが埋まりかけたときに現在の[セッション](../reference/glossary.md#会话)が
    [ハンドオフ文書](../reference/glossary.md#交接书)を書き、新しいセッションが引き継ぐ —— [ハンドオフ](handoff.md)を参照。

    両者は自動で噛み合い、追加の配線は要らない。[リネージ](../reference/glossary.md#血缘)が記録するのは常にそのステップを
    **最後に**引き継いだセッションなので、次のウェイクで繋がるのは引き継ぎ後のセッションになる。

## 何を解決するか {#解决什么问题}

ディスク上には実はすべて残っている。`runs/sessions.db` にはすべての過去セッションの**完全な** transcript があり、`需求.md` / `目标.md`
は凍結済みの成果物で、コードはワークスペースにある。

**失われるのは一行のマッピングだけ** —— 「どのステップがどの session を使ったか」。以前はメモリ上の `ctx["_sessions"]` にしか存在せず、
プロセスが終われば消えた。だから新しいプロセスが立ち上がると、[コーディネーター](../reference/glossary.md#协调者)は記憶を失った新人になる。誰を派遣したか、
どの行き止まりを試したか、なぜある案を却下したか、すべて最初からやり直しだ。

[HT002](../cases/ht002.md) では、コンパイルフラグを試すのに一時間回り道した。プロセスが変われば、その一時間は無駄になる。

## 使い方(最小コード) {#怎么用最小代码}

コマンドラインでは何も設定しなくていい。`flower` というパスでは継続がデフォルトで有効だ:

```bash
cd ~/proj && flower "写个 md 转 html 的脚本"     # 初回
# …完走するか、Ctrl-C で離席するか、マシンが再起動する

cd ~/proj && flower "顺便支持代码块高亮"          # 前回の会話の続き
cd ~/proj && flower                              # 何も言わない = 続きをやる
cd ~/proj && flower --new "另一件事"              # 今回は前回に繋げない
```

自分で[ワークフロー](../reference/glossary.md#流程)を書く場合も継続はデフォルトで有効だ —— `Workflow.continuous` のデフォルト値が
`True` になっている:

```python
import asyncio

from flower import AgentSpec, Runtime, Step, Workflow

terse = AgentSpec(
    name="terse",
    instructions="回答极简,一行以内,不解释不寒暄。",
    allowed_tools=["Read", "Glob"],
    max_turns=4,
)


async def main() -> None:
    wf = Workflow([Step("取词", terse, "读 seed.txt,只回文件里那个词。")])   # continuous はデフォルト True
    rt = Runtime(workspace=".", run_dir="runs")
    try:
        ctx = await wf.run(rt)
    finally:
        rt.close()
    print(ctx["_woke"])                  # 何回目のウェイクか、初回は 1
    print(ctx["_sessions"])              # {"取词": "<session_id>"}


asyncio.run(main())
```

同じディレクトリでこのコードを二度目に実行すると、`ctx["_woke"]` は `2` になり、`ctx["_sessions"]["取词"]` は初回と
**同じ id** になる —— 「取词」ステップは新しいセッションを開かず、前回のセッションを続けて走らせたということだ。

!!! tip "このディレクトリが繋がるかどうかだけ知りたい"
    `wake_state()` は読み取り専用の探査で、**1 バイトも書かない**:

    ```python
    from flower import wake_state

    st = wake_state(".", run_dir="runs")
    print(st["waking"], st["checks"], st["woke"], st["steps"])
    ```

    返るのは `{"waking", "brief", "goal", "checks", "woke", "steps"}`。`waking` = ブリーフが存在し四つの節が揃っていること、
    `checks` = 判定リストの項目数、`woke` = すでにウェイクした回数、`steps` = ステップ名から session_id へのマッピング。
    コマンドラインはこれを使って、プロンプトで「何をするか」と聞くか「前回の続き」と聞くかを決めている。

## 実際に何をしているか {#它实际做了什么}

### ディスクに落ちる三つのファイル {#落在磁盘上的三个文件}

`run_dir` のデフォルトは `./runs` で、**カレントディレクトリ相対であって workspace 相対ではない**。

| パス | 内容 |
|---|---|
| `runs/lineage.json` | リネージ:`{"workspace": "…", "woke": N, "steps": {"步骤名": "session_id"}}`。継続はこれに全面的に依存する |
| `runs/sessions.db` | SQLite、全量の transcript。テーブルは `entries` / `meta` / `summaries`、key は `project_key/session_id[/subpath]` —— subagent の transcript は subpath で分けて保存される |
| `runs/manifest.json` | JSON 配列、**プロセスをまたいで累積する**実行マニフェスト。1 ステップ 1 行で、後から session_id を調べる唯一の場所 |

リネージファイルはこうなる:

```json
{
  "workspace": "/Users/you/proj",
  "woke": 3,
  "steps": {"干活": "47395075-bec7-466e-80cd-f4d60b360235"}
}
```

`manifest.json` の各行は `StepResult` の全フィールド —— `step`、`session_id`、`ok`、`cost_usd`、
`num_turns`、`text`、`error`、`started_at`、`ended_at`、`attempts`、`errors[]`、`resumed`、
`retired[]`、`context` —— に加えて、手で補った `duration_s`(`@property` なので `asdict()` では拾えない)と
`run`(プロセス標識、`YYYYmmdd-HHMMSS-<6 桁 hex>`)が入る。

ステップ名はそこに四つの形で現れ、そのステップがどう終わったか一目でわかる:`<步骤名>`(初回の試行)、
`<步骤名>#retry<N>`(通常のリトライ)、`<步骤名>#round<N>`(判定に通らず差し戻されて続行)、
`<步骤名>·判定#<N>`([ジャッジ](../reference/glossary.md#判定者)のラウンド)。

書き込みは**追記であって上書きではない**。毎回ファイルを読み直し、`run` フィールドで重複を除く —— 自プロセスの行は最新に差し替え、
他プロセスの行はそのまま残す。だから同じディレクトリで複数の flower を並行実行しても安全だ。

### `continuous=True` は `resume_from` の意味を変える {#continuoustrue-改变了-resume_from-的语义}

これが一番見落とされやすい。`Workflow.continuous` はデフォルト `True` なので、`resume_from=None` は
**「まっさらな新セッション」を意味しない**。

| 書き方 | 同一実行内 | プロセスをまたぐ場合(`continuous=True`) |
|---|---|---|
| `resume_from=None`(デフォルト) | 新セッション、prompt で渡したコンテキストのみ | **リネージ内の同名ステップの session を続けて走らせる** |
| `resume_from="上一步名"` | 同じセッションを続行、完全なコンテキスト | 左に同じ |
| `resume_from=…, fork=True` | 分岐し、元のセッションを汚さない | 左に同じ |

プロセスごとに必ずクリーンな新セッションにしたければ、明示的に `Workflow(..., continuous=False)` と書く。

リネージをロードするときには検証が一段入る。読み戻した `(步骤名, session_id)` はまず `runtime.has_session(sid)` で
`sessions.db` にまだ存在するかを確認し、生きているものだけを使う。理由は、リネージファイルが `sessions.db` より長生きする
可能性があり、存在しない session を resume すると子プロセスが起動するまでエラーが出ないからだ。

!!! warning "ステップ名はプロセスをまたいで安定するキーである"
    リネージは `Step.name` で索引される。**ステップ名を変えることはリネージを切ることと同じ** —— エラーにはならず、
    次回の実行が単にまっさらな新セッションになるだけだ。サフィックス付きの名前(`#retry`、`#round`、`·判定#`)はリネージに入らず、
    `Lineage.remember` が使うのは常に元の名前だ。

### 二つの不変条件 {#两条不变式}

**一、session_id を得た瞬間にディスクへ書く。ステップの完了を待たない。**

プロセスが強制的に殺される状況こそが防ぎたい場面だ。実際に踏んだことがある:2026-09-07 に Terminal.app が二度クラッシュし、
カーネルが SIGHUP を送った。SIGHUP のデフォルト動作は即終了なので、`finally` は一行も走らない。当時リネージは**ステップ境界**で
書いていたため、最初のステップの途中で死んだその実行では `steps` が空になり、人間はすでに答えた質問にもう一度答えさせられた(issue #6 を参照)。

現在は `Runtime.on_session` が id を得たその瞬間にディスクへ書く —— 実際には最初の assistant メッセージが最速で、
init システムメッセージは Python SDK では `session_id` を持たない。書くときはまず `.tmp` に書いてからアトミックに置き換えるので、
途中で殺されても半端なファイルは残らない。書き込み失敗(`OSError`)は黙って握りつぶし、その実行を巻き添えにはしない。

このフックが**覆うのは `runtime.run` の一行だけ**で、gate の前に `try/finally` で外している。ジャッジは同じ
`Runtime` を使うので、フックが付いたままだとジャッジの session が作業ステップのリネージに書き込まれてしまう。

**二、合わなければ無かったことにする。エラーにはしない。**

合わないケースは三つ。ワークスペースのパスが変わった(ディレクトリごとコピーされた —— [HT001](../cases/ht001.md) はコンテナから
コピーし出したものだ)、session がすでに DB にない(`sessions.db` を消した)、リネージファイルが壊れている。どれでも黙って
「最初から」に戻る。

`workspace` フィールドはガードだ。SDK の `project_key` はワークスペースのパスから導出される(`/`、`_`、`.` はすべて `-` に置換)ので、
ディレクトリをコピーした後の新しい位置では古い session_id はそもそも引けない。だからパスが合わなければ無かったことにする。

**継続はあくまで上積みであって、それが失効したからといって人の作業を止めてはならない。**

### プロセスが殺された場合と、マシンが再起動した場合 {#进程被杀和机器重启}

結果は同じ —— どちらも繋がる —— が、過程は違う:

| 状況 | 何が起きるか | 次の実行 |
|---|---|---|
| `Ctrl-C` 一回 | 協調的な割り込みで、**メッセージ境界**できれいに切断する。ついでに一言添えることもでき、同一プロセス内で同じセッションを resume して続行できる。割り込みは失敗試行に数えず、リトライ枠を消費しない | 継続とは無関係 |
| `Ctrl-C` 二回 | そのまま `KeyboardInterrupt` を投げて終了する。後始末はストレージを閉じるところまでで、**実行中だったステップは `manifest.json` に入らない** | リネージはとっくに書かれているので繋がる |
| `SIGTERM` / `SIGHUP` | ハンドラがまず `rescue()` を呼び、実行中のステップも `manifest.json` に書き込み(`error="killed-by-signal"` を付ける)、その後デフォルト動作に戻して実際に終了する | 同上、繋がる |
| `SIGKILL`、電源断、マシン再起動 | 後始末は一切ない | 同じく繋がる —— 三つのファイルはディスク上にあり、リネージは id を得た瞬間に書かれている |

前提は一つだけ:**同じ `workspace` と同じ `run_dir`**。`run_dir` はカレントディレクトリ相対なので、
別のディレクトリから `flower` を叩くと別の `runs/` を見にいき、繋がらない。

### ジャッジは常に新しいセッション {#判定者永远是新会话}

これは**構造上の保証**であって、覚えておくことに依存していない。

ジャッジは `Step` ではない —— `with_goal` の gate の中から直接 `rt.run()` で派遣される
([ゴールガード](goal.md)を参照)ので、リネージの経路を一切通らない。だから毎ラウンド、毎ウェイクで、まっさらな第二の目になる。

それこそがジャッジの価値のすべてだ。**ワーカーが何回試したか、どれだけ苦労したかを知らないので、代わりに言い訳を作ることもない。**
ジャッジに継続を持たせれば、ゴールガードは自己監査に成り下がる。

`tests/lineage_offline.py` の第 4 節がこれを固定している。

### ウェイク時に言った一言は、三箇所に届かなければならない {#唤醒时说的那句话要落到三个地方}

すでに使ったディレクトリでの `flower "顺便支持代码块高亮"` は、**新しいタスクではなく、もう一言付け足しただけ**だ。
これは同時に三つのことをする —— 一つでも欠ければ静かに失効する:

| どこに届くか | 欠けるとどうなるか |
|---|---|
| `需求.md` への追記(`## 唤醒时追加`) | ステップ境界を越えられない。次のステップは新しい session で、凍結済みの成果物しか読まない |
| 作業ステップの prompt として | コーディネーターがそもそも受け取らない |
| **`目标.md` の再導出のトリガー** | ジャッジが読むのは古いリストのままで、**新しく足した件が終わったかどうかが判定に入らない** |

三つ目が最も見落とされやすい。ジャッジは凍結された `目标.md` しか読まないので、途中で足したものは見えない —— 再導出しなければ
古いリストに基づいて「達成」と判定し、あなたが求めたその一件はまったく検証されない。代償は、追記のたびに目標設定が一回余分に走ること
([HT002](../cases/ht002.md) の実測で $0.41 / 3 分)。

**何も言わずにウェイクする**(そのままリターン)場合は追記も再導出もせず、一銭も余計にかからない。

### 最初のステップ(确认需求)の途中で落ちても繋がる {#崩在第一步确认需求之内也能接上}

`clarify_step` は `resume_prompt`(定数 `CLARIFY_RESUME`)を持つ。確認の途中で落ちて再起動したとき、
[クラリファイア](../reference/glossary.md#确认者)に伝えるのは「さっき途中までだった要件確認の続きから —— 最初からやり直しではない」であって、
元の要望を新しいタスクとしてもう一度送り直すのではない。上の「session_id を得た瞬間にディスクへ書く」と合わせて、
最初のステップで死んで `需求.md` がまだ凍結されていない実行も、今は答え直さずに繋がる。

逆に、すでに凍結された前段のステップは**ステップごとスキップされる**。`需求.md` の四節が揃っていれば「确认需求」をスキップし
(内容は ctx には流し込まれる)、`目标.md` が揃っていれば「设定目标」をスキップする。

### 継続時に送るのは同じ一言ではない {#接续时发的不是同一句话}

これを担うのが `Step.resume_prompt` だ。相手のコンテキストには**すでに**ブリーフも目標も前回どこまでやったかも入っているので、
「このブリーフの通りにやれ:<ブリーフ全文>」をそのまま再送するのは純粋なノイズであり、さらに悪いことに「要件が変わった、読み直せ」と
解釈されうる。

`resume_prompt` を与えなければ `prompt` がそのまま使われる —— 全文を再送すべきステップもあるからだ(「设定目标」がリストを
再導出するときに必要なのは、まさにその完全なブリーフだ)。

### ウェイク時にまず一行報告する {#唤醒时先报一行}

```text
<- 在 ~/explore/test-ide 接上上次  需求已确认 · 目标 15 条 · 干活上下文 80.2K · 第 3 次唤醒

== 干活 ==============================  3/3  <- 接上次 · 第 3 次唤醒
```

報告しなければ「本当に覚えているのか」がまったく感じ取れない。そしてそれこそがこの層の価値のすべてだ。バナー内の
`需求已确认` は常に出る。`目标 N 条` は判定リストが空でないときのみ、`干活上下文 X` は `sessions.db` から
そのセッションの最終ラウンドのコンテキスト規模を引けたときのみ出る。

**コンテキストの数字は意図的に見せている** —— 理由は下の「代償」の節にある。

### レジリエンス:切断時はぶら下がって待ち、しかもエラーは継続後のコンテキストに入れない {#韧性断网时挂着等而且错误不进接续后的上下文}

[レジリエンス](../reference/glossary.md#韧性)と継続はセットだ。一回で数時間走らせれば必ず一度はネットワークが切れるし、デフォルトの挙動はひどい ——
切断した瞬間、harness は transcript に**合成 assistant メッセージ**(`isApiErrorMessage=true`、
`model="<synthetic>"`)を差し込み、本文は "API Error: Can't reach the API server …" になる。このメッセージがセッションの葉になり、
以降の resume では「モデルが直前に言ったこと」として食わされるので、モデルは自分がネットワーク障害の話をしていたと思い込む。

`Resilience` は三つのことをする:

**一、プローブは DNS + TCP だけ。** `reachable(host, port, timeout=5.0)` は `getaddrinfo` と TCP ハンドシェイクを一度やるだけで、
**HTTP は送らず、資格情報も持たず、課金もされない**。例外はすべて到達不可扱い。どのアドレスを探るかは `endpoint()` が決め、
`ANTHROPIC_BASE_URL` に追随する。デフォルトは `https://api.anthropic.com`、ポートのデフォルトは `443`(http なら `80`)。
**自前のゲートウェイを使うならゲートウェイを探らなければならない** —— `api.anthropic.com` が通ってもゲートウェイが通る証明にはならない。

**二、待つべきものと止めるべきものを区別する。** `classify(text)` は `"transient"` / `"fatal"` / `"unknown"` を返し、
**先に fatal、次に transient を判定する** —— 401 のようなテキストはしばしば "connection" という語を含むので、順序を逆にすると永遠に待つ。
デフォルト値:`max_attempts=6`(初回を含む)、`base_delay=4.0`、`max_delay=120.0`、`probe_timeout=5.0`、
`probe_interval=15.0`、`max_offline_wait=3600.0`(1 時間)、`retry_unknown=True`。
バックオフは `min(base_delay * 2**(attempt-1), max_delay)` に ±25% のジッタを掛ける。

一度でも session_id を得ていれば **resume して続行し、やり直さない**ので、それまでの支出は無駄にならない。続行時に送るのは
`Resilience.resume_prompt`:「上一轮在中途被打断,没有跑完。检查一下工作台里已经落盘的东西,
从中断处接着做,不要重头来过。」これは**意図的にエラーの詳細を一切含まない** —— モデルが知る必要があるのは「中断された、続きをやれ」であって、
ENOTFOUND だったのか 503 だったのかではない。

**三、リトライの嵐が生んだエラーは resume 後のコンテキストに入れない。** これは[プルーニング](../reference/glossary.md#剪除)の仕事だ。
`Runtime` のセッションストアは `PruningSessionStore` に固定されていて、`load()` 時に三つのことをする:

- 合成 API エラーメッセージを取り除く。**SQLite にはそのまま残す**、食わせ直さないだけだ
- 古すぎる拒否済み呼び出しを取り除き、直近 `keep_denials=1` 件だけ残す
- 中断で残った `tool_result` を中立的な説明「[上一轮在此处被中断,该工具结果未产生]」に差し替える。本文だけ替えてエントリは残す

0 件でなく 1 件残すのには理由がある。拒否された呼び出しは一度も実行されていないので結果に情報はないが、場所は相応に食う
(実測で一件 273 文字 = 拒否文 93 文字 + **拒否されたコマンド原文** 180 文字)、しかも**誤誘導する** ——
実測では、コーディネーターが「Bash を直接使うな」を数件読んだあと、許可されている `git status` すら試さなくなり、学習性無力感を身につけた。
だが最新の 1 件は残す価値がある。同じラウンド内で同じブロック済みコマンドを繰り返し試すのを防げる。

除去には構造上のレッドラインが一つある。transcript は `parentUuid` の単一リンクなので、1 件取り除いたらその子を最も近い生存する祖先に
繋ぎ直さなければならない。さもなければそこで鎖が切れ、それ以前の履歴が全部失われる。

[HT001](../cases/ht001.md) では実測で一度これに当たった。切断のタイムラインは 01:52:40 → 01:55:41 で、`manifest.json` のそのステップは
`attempts=2` / `resumed=True` / `ok=True`。続行後さらに 8 時間以上走って完了した。

最後に誤解されやすい点:**`Runtime(trim=False)` は「何も掃除しない」という意味ではない**。`trim` のデフォルトは `False` だが、
それが切るのは**大きなツール結果の[トリム](../reference/glossary.md#裁剪)**という一層だけだ。切断の残骸の除去、拒否済み呼び出しの除去、
中断残留の中立化、[エフェメラルコマンド](../reference/glossary.md#一次性命令)結果の期限切れマーキング —— この四つはそのまま行われる
(`ephemeral` のデフォルトは `True`、`keep_denials` のデフォルトは `1`)。

### 代償:コンテキストは伸び続け、終わりがない {#代价上下文会一直涨而且没有尽头}

これは継続に固有の代償であって、バグではない。

[HT001](../cases/ht001.md) の「干活」ステップは連続 10.44 時間走り、[メインスレッド](../reference/glossary.md#主线程)のコンテキストは
第 1 ラウンド **28.7K**、第 20 ラウンド **35.2K**、第 35 ラウンド **108.6K**、第 50 ラウンド **158.2K**、第 70 ラウンド **185.9K** と
単調に増え、傾きはおよそ **2.2K/ラウンド**。全行程で圧縮は起きず、1M ウィンドウの **18.6%** を使った。この傾きで外挿すると、
壁にぶつかるのはおよそ **440 ラウンド** —— 現状の形での「long-horizon」の上限は、あの実行の約 **6 倍**だ。永久に継続するということは、
いつか必ずウィンドウにぶつかるということでもある。

これを管理する仕組みが二層ある:

1. **トリム**(`flower --no-trim` で切れる、`flower` のパスではデフォルトで有効)—— resume 時に古い大きなツール結果を
   ファイルポインタに差し替える。内容は失われず、常駐しなくなるだけだ
2. **[ハンドオフ](handoff.md)** —— しきい値に達したらハンドオフ文書を書いて新しいセッションに替える。**[compact](../reference/glossary.md#压缩) ではない**:
   文書は読めるし直せるので、何が落ちたかが見える。だからコンテキストは周期的に下がり、壁まで一直線に伸びない

**だからウェイク時の一行はコンテキストの数字を必ず報告しなければならない**。人間に見えて初めて、壁にぶつかる前に自分でやり直すか決められる。

ついでに一点:`--rounds`(作業の総ラウンド数)は**ウェイクのたびにリセットされる**。これは意図的だ —— 新しいウェイクは新しい意図であり、
前回使ったラウンド数を引き継ぐべきではない。

### 別件をやり直す {#重开一件事}

```bash
flower --new "另一件事"
```

あるいはウェイクのプロンプトで直接 `/new` と打つ:

```text
接着上次? 直接回车 = 接着做;也可以说点新的;/new = 重开一件事(Ctrl-C 退出)
> /new
要做什么? 一句话就够,回车开始(Ctrl-C 退出)
> …
```

**アーカイブであって削除ではない。** `lineage.json`、`需求.md`、`目标.md` をまとめて `notes/archive/<YYYYmmdd-HHMMSS>/` へ**移動**し、
リネージの `steps` と `woke` を同時にゼロに戻す。三つは同じ一続きの歴史の三つの面であり、一部だけ片付けると「目標は残っているのに会話がない」
という中途半端な状態になる。

`sessions.db` は触らない —— それはアーカイブであり、中の transcript はすべて引ける。

コードで書くときは `Lineage.archive(into, extra=[...])` に対応する。

## 使うべきでないとき {#什么时候不该用它}

- **毎回クリーンな出発点であることが要求される場面。** 同じワークフローをバッチで回す、対照評価をする、他人にバグを再現してもらう ——
  どれも前回のコンテキストを持ち込むべきではない。`Workflow(..., continuous=False)` と書くか、毎回 `run_dir` を変える。
- **ディレクトリが移動・コピーされる、あるいは `run_dir` が永続的でない場合。** コンテナ内で走らせて `runs/` がコンテナ内層のファイルシステムに落ちる、
  あるいはワークスペースを別のマシンへ rsync する —— 継続は**静かに失効する**(パスガードが合わないリネージを弾く)。
  保証として当てにしないこと。
- **今回が新しい意図で、しかもコンテキストがすでに大きい場合。** 継続は無関係な履歴まで背負い込み、毎ラウンドそのぶんの token を払う。
  我慢するくらいなら `--new` でアーカイブしてやり直したほうがいい。
- **単発の単一エージェント。** `flower once` は `Workflow` を通らないのでリネージがない。続行したければ自分で `--resume <session_id>` を渡す。
- **継続をバックアップ代わりにすること。** 記録しているのは「どのステップがどの session を使ったか」だけだ。コード、成果物、決定はワークスペースと
  [ワークベンチ](../reference/glossary.md#工作台)に落とすべきで、transcript から掘り返すことを当てにしてはいけない。
