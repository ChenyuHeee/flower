# よくある質問とトラブルシューティング

問題が起きたとき、人はどのモジュールが壊れているのかを知らない —— 自分が何を見たかしか分からない。だからこのページは**観察された現象**でグループ分けしてあり、サブシステム別ではない。

各項目の構造は同じ:**症状**(実際に目にするもの)→ **原因** → **対処**。

うち 5 項目は**既知の欠陥**であって、設計上そうなっているわけではない。該当項目にはバグであることを明記し、issue リンクと回避策を示す —— 意図的な仕様であるかのようには書かない。

## インストールできない / 起動しない {#装不上}

インストールの全手順は [install.md](../getting-started/install.md#一句话安装) にある。この節が扱うのは「インストールは終わったのにコマンドが動かない」ケースだけ。

### Python のバージョンが 3.10 未満 {#python-版本}

**症状**:インストール中に構文エラーが出る、あるいは pip が条件を満たすバージョンは見つからないと言う。

**原因**:flower は Python ≥ 3.10 を要求する。実行時依存は `claude-agent-sdk` ひとつだけで、ネイティブバイナリはその wheel に入っている —— したがってインストールできないのはたいていインタプリタのバージョンの問題であって、ネットワークの問題ではない。

**対処**:まずどのインタプリタに入れるのかを確認する。

```bash
python3 --version
```

3.10 未満なら別のものに切り替えてから入れる。システム同梱の `python3` は、ターミナルで `python` が指しているものとは違うことが多い。インストール後に調べるより、事前にバージョンを突き合わせるほうが安い([install.md](../getting-started/install.md#装之前确认-python) を参照)。

### インストールしたのに `flower: command not found` {#command-not-found}

**症状**:

```text
zsh: command not found: flower
```

**原因**:パッケージは入っているが、生成された実行スクリプトのあるディレクトリが `PATH` に入っていない。これは「入っていない」とは別の話だ —— `python3 -c "import flower"` がエラーにならなければ、パッケージ自体は無事だ。

**対処**:`flower` スクリプトの shebang は絶対パスなので、すでに `PATH` にあるディレクトリへシンボリックリンクを 1 本張れば済む。何かを source する必要はない。

```bash
ln -sf "$PWD/.venv/bin/flower" ~/.local/bin/flower
```

### macOS:`install.sh` の指示どおり PATH を足したのに、まだ command not found {#macos-path}

!!! warning "既知の問題([issue #16](https://github.com/ChenyuHeee/flower/issues/16))"

    このアドバイスは、それを必要としているまさにそのマシンで役に立たない。

**症状**:macOS で `install.sh` を実行し、最後に表示された指示どおり `~/.local/bin` を `PATH` に追加し、ターミナルを開き直しても、`flower` は依然として command not found。

**原因**:pip フォールバックの経路を通った場合、macOS の pip は実行スクリプトを `~/Library/Python/3.X/bin` に置くが、`install.sh` が追加を促すのは `~/.local/bin` だ。ディレクトリが食い違っているので、指示どおりにしても無駄になる。

??? note "`install.sh` がどの順でインストール方法を選ぶか、そしてあの指示の原文"

    優先順位は 2 段ではなく 4 段ある(`install.sh:35-56`):

    ```text
    1. uv がある        → uv tool install --force
    2. なければ pipx    → pipx install --force
    3. どちらもなければ → curl astral.sh/uv/install.sh で uv をブートストラップし、成功すれば uv でインストール
    4. ブートストラップも失敗 → "$PY" -m pip install --user --upgrade    ← 問題が起きるのはこれ
    ```

    最後の PATH の指示の原文(`install.sh:62-68`。`command -v flower` が見つからないときだけ表示される):

    ```text
    ! 但 flower 不在 PATH 上。
      把这一行加进你的 ~/.zshrc 或 ~/.bashrc:
        export PATH="$HOME/.local/bin:$PATH"
    ```

    `BINDIR` は `$HOME/.local/bin` にハードコードされている(`install.sh:63`)。経路 1 と 3 についてはこれで正しい —— uv はそこに入れる。**macOS で食い違うのは経路 4 の pip フォールバックだけ**だ。つまりこの罠は、前の 3 つの経路がすべて成立しなかったマシンでしか起きない。

**対処**:ディレクトリを推測せず、インタプリタに訊く。

```bash
python3 -c "import sysconfig; print(sysconfig.get_path('scripts', scheme='posix_user'))"
```

表示されたディレクトリを `PATH` に追加するか、そこから `~/.local/bin` にシンボリックリンクを張る:

```bash
ln -sf "$(python3 -c "import sysconfig; print(sysconfig.get_path('scripts', scheme='posix_user'))")/flower" ~/.local/bin/flower
```

### uv / pipx / pip で入れたものが同じ flower ではない {#三种装法}

**症状**:`flower` は動くのにソースを直しても反映されない。あるいはアップグレードしても古いバージョンのまま。あるいは同じマシンの 2 つのターミナルで挙動が違う。

**原因**:3 つのインストール方法はパッケージと実行スクリプトを別々の場所に置く。`PATH` 上で先に当たったものが動く。

??? note "3 つのインストール方法がどこに置かれるか"

    | インストール方法 | 実行スクリプト | いつ使うか |
    |---|---|---|
    | `python3 -m venv .venv` + `pip install -e .` | `.venv/bin/flower` | ソースを直すとき。直せば即反映される |
    | `uv tool install` / `pipx install` | `~/.local/bin/flower` | 使うだけで直さない、隔離された環境がほしいとき |
    | `pip install --user` | Linux は `~/.local/bin`、macOS は `~/Library/Python/3.X/bin` | フォールバック。ディレクトリは前項参照 |

**対処**:まず今動いているのがどれかを確認してから、どれを直すか決める。

```bash
which -a flower                      # PATH 上の同名のものをすべて列挙
head -1 "$(which flower)"            # shebang が指すインタプリタの環境にパッケージがある
```

ソースを直すなら venv + `-e .` にして、`uv` / `pipx` で入れたものと共存させないこと —— 共存させると、調査コストは入れ直すコストよりはるかに高くつく([install.md](../getting-started/install.md#从源码装) を参照)。

## クレデンシャルとゲートウェイ {#凭证}

### `缺少凭证:需要 ANTHROPIC_API_KEY 或 ANTHROPIC_AUTH_TOKEN` {#缺少凭证}

**症状**:

```text
缺少凭证:需要 ANTHROPIC_API_KEY 或 ANTHROPIC_AUTH_TOKEN
```

**原因**:flower は `setting_sources=[]` でホストマシンの設定を遮断しているので、クレデンシャルは自分で持ち込む必要がある。探索順序の全体は [config.md](config.md#凭证查找优先级) にある。

**対処**:リポジトリルートの `.env` に書くか、プロセス環境に書く。

```bash
cp .env.example .env        # ANTHROPIC_AUTH_TOKEN または ANTHROPIC_API_KEY を記入
```

`.env` はすでに gitignore されている。コンテナでの書き方は [deploy.md](deploy.md#凭证) を参照。

### 「flower は `~/.claude/settings.json` を読まない」と表示される —— この文言は誤り {#settings-json}

**症状**:クレデンシャルが正しく設定されていないとき、`env.py:192` が次の 1 行を出す:

```text
flower 不读 ~/.claude/settings.json —— 那是可移植性的代价
```

**原因**:この文言はコードと一致していない。`env.py:56-75` は `~/.claude/settings.json` を**実際に読んでいる**。読むのはクレデンシャルのフィールドだけで、最後段のフォールバックとして使う —— `install.sh` が宣伝しているのもまさにこれだ。この行はフォールバックが空振りしたあとにしか表示されないので、何かを失敗させることはない。ただし「flower は Claude Code の token を使えない」という誤った結論を人に抱かせる。[issue #13](https://github.com/ChenyuHeee/flower/issues/13) に記録済み。

**対処**:ローカルに Claude Code を入れてあるなら、クレデンシャルを取り直す必要はない。フォールバックが自動で拾う([install.md](../getting-started/install.md#本机装过-claude-code-的话可能一个问题都不问) を参照)。本当にこの行が出たなら、そのファイルにも使えるクレデンシャルフィールドがないということだ —— 前項のとおり `.env` を書く。

### どのクレデンシャルとエンドポイントが有効なのか分からない {#生效值}

**症状**:`.env` を直したはずなのにリクエストが古いゲートウェイに飛ぶ。あるいは今どのモデルを使っているのか説明できない。

**原因**:クレデンシャルとエンドポイントには複数の供給元(プロセス環境、`.env`、フォールバック)がある。どれが勝つかは設定ファイルではなく実行時に決まる。

**対処**:`-v` を付けて 1 回起動する。起動時に `describe()` が表示される:有効な `BASE_URL` とモデルマッピング、token はマスクされる。

```bash
flower -v
```

スイッチの一覧は [cli.md](cli.md#全局开关)、変数の一覧は [config.md](config.md#环境变量) にある。

### `.env` に `KEY=` を残すと、下流はもう埋められない {#空值占位}

**症状**:プロセス環境で token を export し、`.env` にも `ANTHROPIC_AUTH_TOKEN=` の行がある状態で、なお「クレデンシャルがない」と言われる。

**原因**:空値も代入の一種だ。高優先の供給元にある `KEY=` がそのキーを**占有**してしまい、低優先の供給元はもう埋めに来ない。そして `check_credentials()`(`env.py:184` に定義)が見るのは「値が空でないこと」なので、結局欠落として報告される。「占有」と「欠落」は別物なのに、現象はまったく同じ —— この種の問題がいちばん自力で見つけにくい理由がここにある。

**対処**:行ごと削除する。空値を残さない。

```bash
grep -n '^[A-Za-z_][A-Za-z0-9_]*=$' .env     # 空値の行をすべて列挙
```

削除したら `-v` でもう一度、有効値を確認する。パース規則は [config.md](config.md#env-解析) を参照。

### サードパーティゲートウェイ:接続はできるが最初のラウンドで失敗する {#网关}

**症状**:401 / 403。あるいはモデル名が存在しないと言われる。あるいは開始直後に[ハンドオフ](glossary.md#换代)し、しかも「起動フロア」と言われる。

**原因**:3 種類の設定ミスがあり、それぞれ現象が違う。

??? note "3 種類のゲートウェイ設定ミスの見分け方"

    | 現象 | 大半はこれ | どこを直すか |
    |---|---|---|
    | 401 / 403 | クレデンシャル自体は正しいが、このゲートウェイが発行したものではない。あるいは `BASE_URL` にパスが足りない/末尾スラッシュが余分 | [config.md](config.md#凭证变量) |
    | モデル名が存在しない | ゲートウェイが自前のモデル名しか受け付けず、マッピング未設定 | [config.md](config.md#模型变量) |
    | 開始直後にハンドオフし「起動フロア」と出る | ウィンドウが小さすぎる:しきい値がそのロールの起動フロアを下回っている([コーディネーター](glossary.md#协调者)は実測で約 34k) | `--window`、[handoff.md](../guide/handoff.md#阈值怎么算) を参照 |

**対処**:設定をいじる前に、まず `-v` で有効値を 1 回出す。特にウィンドウは突き合わせる価値がある —— 開発機のゲートウェイは `claude-opus-5[1m]` を設定しており、以前 20 万で計算していたときは 15 万ごとにハンドオフしていた。実際には 95 万まで回せるので、**5 倍の差**があり、[long-horizon](glossary.md#长程) な仕事はズタズタに切り刻まれる。

## 起動はするが挙動がおかしい {#行为不对}

このグループの症状はどれもエラーではなく、**コマンドは完走し、終了コードは 0 なのに、やっていることが違う**というものだ。最初の 4 項目は確認済みのコード欠陥で、issue も提出済み。ここにあるのは回避策であって修正ではない。最後の 1 項目は設計どおりの挙動。

### `flower setup` が起動するのは agent {#setup-跑成了-agent}

**症状**:`flower setup` を実行し、エンドポイントと token を訊いてくると思ったら、「何をしますか」と訊き始め、そのまま go の全フローを走り、`setup` という語をタスク記述として扱う。走り終わってもクレデンシャルは一文字も書かれていない。

**原因**:`cli.py:758` の `_CMDS` に `"go"`、`"run"`、`"once"` しか並んでおらず、`"setup"` が漏れている。デフォルトサブコマンドを補う処理が argv `["setup"]` を `["go", "setup"]` に書き換えてしまい、`setup` はサブコマンドから `go` の第 1 位置引数、つまり要求そのものに降格する。**設定ウィザードに到達できる argv は存在しない。** [#11](https://github.com/ChenyuHeee/flower/issues/11) として報告済み。

**対処**:Ctrl-C で止めて、設定ファイルを直接書く。もともと `setup` がやっていたのも、このファイルに書き込むことだけだ:

```bash
mkdir -p ~/.config/flower
cat > ~/.config/flower/.env <<'EOF'
ANTHROPIC_AUTH_TOKEN=sk-...
EOF
```

変数名の一覧とクレデンシャルの探索順序は [config.md](config.md#凭证变量) を参照。書き終えたら任意のディレクトリで `flower -v` を 1 回走らせる。起動時に表示される有効エンドポイントが答え合わせになる。

### 全角 `？` ではオラクル問答が起動しない {#全角问号}

**症状**:[オラクル問答](cli.md#旁路问答) の書き方に従って入力プロンプトで `？这个目录能删吗` と打ったのに、[オラクル](glossary.md#旁路顾问) が起動せず、現在の質問への回答として扱われるか、そのまま受信箱に入る。

**原因**:`cli.py:733` が `startswith("?")` の判定を 2 回続けて行っているが、**2 回とも同じ ASCII 文字**を使っている。コードの意図では、2 回目は全角 `？` を判定するはずだった。中国語入力メソッドがデフォルトで出すのは全角 —— この機能の主要ユーザーが、ちょうど 1 人も使えないことになる。[#12](https://github.com/ChenyuHeee/flower/issues/12) として報告済み。

!!! warning "これは要求を汚染する"
    外れた `？` はエラーにならず、捨てられもしない。通常の入力として処理される:
    確認フェーズでは今の質問への回答として、それ以外のときは受信箱へ入る。
    **こっそり訊きたかっただけの一言が、確認書に書き込まれる。** 打ち間違いに気づいたら、
    その場で `.flower/notes/需求.md` を直すこと。下流の基準になるのはそのファイルだ。

**対処**:半角に切り替えて `?` を打つか、先に半角 `?` を打ってから中国語に戻して本文を書く。

### `once` の累計コストが常に `$0.00`、経過時間が常に `0:00` {#once-计数为零}

**症状**:`flower once` を最初から最後まで走らせても、下部のステータス行の累計コストがずっと `累计 $0.00` を表示し、タイマーもずっと `0:00`。同じモデル・同じ仕事を `go` で走らせると数字は出る。

**原因**:`once` の `render()` は**イベントを 1 つ受け取るたびに `Render` を新規生成する**。アキュムレータも一緒に作り直されるので、毎回ゼロから始まる。累計値は繰り返しゼロクリアされているのであって、集計されていないわけではない。[#14](https://github.com/ChenyuHeee/flower/issues/14) として報告済み。

**対処**:数字が正確に必要なら `go` を使う。そちらの経路は影響を受けない。`once` の単発形態のままコストも見たいなら、走り終えてから `runs/manifest.json` を見る —— 各ステップのコストがそこに記録されており、その記録は正しい。詳細は [config.md](config.md#run-dir)。

### `plugin/` に置いた skill がいつまでもロードされない {#plugin-不加载}

**症状**:[deploy.md](deploy.md#写一个-skill完整例子) のとおり skill を書き、ディレクトリ構造も正しいのに、agent はその存在をまったく知らないかのように振る舞う —— **エラーも出ず、ログも 1 行も出ない**。

**原因**:`plugin/` が wheel に含まれていない。インストールされたパッケージでは `PLUGIN_DIR` が `<site-packages>/plugin` を指すが、そのディレクトリは存在せず、ロード前の存在判定で黙ってスキップされる。**`install.sh` の 3 経路すべてが該当する**。ロードできるのはソースチェックアウトのリポジトリだけだ。[#15](https://github.com/ChenyuHeee/flower/issues/15) として報告済み。

**対処**:まずパスが実際にどこへ解決されているかを自己診断する。

```bash
python3 -c "from flower.core.agent import PLUGIN_DIR; print(PLUGIN_DIR, PLUGIN_DIR.is_dir())"
```

`False` が出たらこれに該当する。skill を使いたいなら、現状の手段はひとつだけ:**ソースチェックアウトから走らせる**。

```bash
git clone https://github.com/ChenyuHeee/flower
cd flower
python3 -m venv .venv && .venv/bin/pip install -e .
ln -sf "$PWD/.venv/bin/flower" ~/.local/bin/flower
```

`-e` で入れたパッケージはチェックアウトディレクトリを指すので、`PLUGIN_DIR` は実在する `plugin/` に落ち、先ほどの自己診断は `True` を出す。

### `go` では `-T` の効果が見えない {#trim-与-go}

**症状**:`flower go` に `-T` を付け、付けた場合と付けない場合を比べても挙動がまったく同じで、スイッチが壊れているように見える。

**原因**:**これは設計どおりであって欠陥ではない。** `go` 経路はもともとデフォルトで[トリム](glossary.md#裁剪)が有効なので、`-T` が表す意図はすでに満たされており、もう一度指定しても変化はない。この経路での実際のスイッチは逆向きの `--no-trim` だ —— トリムを切りたいときにだけ明示する。`-T` が意味を持つのは `run` と `once` だけ。

**対処**:`go` でトリムが本当に有効かを確認したいなら `-v` で起動時の表示を見る。`-T` の有無で判断しないこと。切りたいなら `--no-trim` を渡す。スイッチの完全な意味は [cli.md](cli.md#全局开关) を参照。

## 完了したと言うが完了していない {#没做完}

[ゴールガード](../guide/goal.md) はまさにこの種を止めるために存在する —— ワーカーには系統的な楽観バイアスがあり、自分が何をやったかは知っているが、何を漏らしたかは知らない。ただしガード自身も誤判定するし、誤判定の方向には規則性がある。以下の 5 項目は「通すべきでないものを通した」と「いつまでも通さない」に分けてある。

### 「ここは検証できない」と言って通過する {#无法达成不是未达成}

**症状**:判定結果に「現在の環境ではこの項目を検証できないため、達成とみなす」と書かれ、フローがそのまま先へ進む。

**原因**:[ジャッジ](glossary.md#判定者)が「達成不能」と「未達成」を 1 つの結論に混ぜている。この 2 つは**別の結論**であり、[結論は 2 つではなく 3 つ](../guide/goal.md#三个结论不是两个) が言っているのはまさにこのことだ:「未達成」は差し戻して続行、「達成不能」は**止まって人に訊く**。受け入れるのか、目標を変えるのか、それとも判定が間違っているのか。「達成/未達成」の 2 択しかない場合、実際には達成できない目標のせいでコーディネーターがラウンドを空回りし続け、予算が尽きる。

**対処**:**「ここは検証できない」を達成として扱ってはならない。** ジャッジへの `instructions` に、あなたの場面で何が達成不能に当たるのかを名指しで書き、「達成不能」を出すべきときに出させる。止まって訊かれるのが嫌なら `--timeout 0` を渡す:達成不能ならそのまま停止し、理由はディスクに残る。ごまかして通されるよりよい。

### ソースを読んだだけで完了と言う {#判产出物}

**症状**:判定理由に「コード上で X は実装されている」「関数シグネチャは要件を満たしている」と書かれているのに、ビルド成果物もコマンド出力も、起動したサービスも、ひとつも触られていない。

**原因**:ジャッジがソースコードに誘導されている。[判定するのは成果物であってソースではない](../guide/goal.md#判的是产出物不是源码) —— ソースが正しく見えるかどうかと、提出物が使えるかどうかは別の話だ。前者はワーカーがすでに確信していることであり、もう一度確信しても新しい情報は生まれない。

**対処**:判定項目は**成果物**に対する断言として書く。「エクスポート機能を実装した」では不十分で、「`./app export out.csv` を走らせると `out.csv` に 3 列のヘッダがある」なら十分だ。目標を書く段階でそう書くべきで、そうしないとジャッジは曖昧な項目を自分で補完するしかなくなる。

### ジャッジがコマンドを実行できず、Makefile を読んで通してしまう {#判定者不能跑命令}

**症状**:目標は「Linux で動くバイナリをビルドする」で、判定は通った。自分で `file` を掛けてみると成果物は Mach-O で、ELF ではまったくない。

**原因**:ジャッジはデフォルトで `judge(can_run=False)` であり、手元には **`Read` / `Glob` / `Grep` しかない**。この 3 つはファイルを読めるが、**`file` は実行できないし、`./app --version` も実行できない**。そこで次善策として Makefile を読み、Darwin 側の分岐にクロスコンパイルが書かれているのを見て、条件は満たされたと判断する。嘘をついたわけではない。**能力の範囲内でもっとも証拠らしいものを見つけた**だけだ。

??? note "`can_run` を必ず有効にすべきなのはどんなとき"
    判断基準は単純だ:**目標に「ビルドされたもの」の類の語が出てきたら有効にする。**

    - 成果物系:バイナリ、イメージ、パッケージ、生成データ —— 有効に
    - 挙動系:サービスが起動する、コマンドが 0 を返す、出力があるパターンに一致する —— 有効に
    - 純テキスト系:ドキュメントを書いたか、あるフィールドを schema に追加したか —— 不要

    コマンドラインでは `--judge-can-run`。自分で配線する場合、入口ごとに書き方は違うが、最終的にはすべて `judge()` のその仮引数に落ちる:

    | 入口 | 渡し方 | 出所 |
    |---|---|---|
    | `judge()` | `can_run=` は正式な仮引数 | `roles.py:361` |
    | `with_goal()` | `can_run=` は仮引数で、`judge()` に転送される | `goal.py:155` → `:170` |
    | `goal_step()` | **`can_run` 仮引数はない**が、`**spec_kw` に入り、その一行が `judge(..., **spec_kw)` なので届く | `goal.py:97` → `:105` |
    | `starter_flow()` | `judge_can_run=` が `with_goal(can_run=…)` に変換される。`--judge-can-run` が通るのもこの経路 | `starter.py:105` → `:196` |

    代償として、ジャッジは実際にコマンドを実行するので、1 ラウンドの判定は遅く、高くつく。引き換えに得られるのは、検証対象が**現場そのもの**であって、現場の説明書ではないということだ。[ジャッジがコマンドを実行できるかどうか](../guide/goal.md#判定者能不能跑命令) を参照。

**対処**:目標が成果物に関わるなら `--judge-can-run` を有効にする。有効にしない場合は、「読めば判定できる」を判定項目を書く際の強い制約とする —— そう書けない項目は、そもそもコマンド実行が必要な項目だということだ。

### 判定リストが十数項目あり、いつまでも通らない {#清单长度}

**症状**:毎ラウンド差し戻され、足りない点が長々と並び、直すほど増え、仕事が終わらない。

**原因**:リストが「どれだけ厳密にやりたいか」で書かれていて、「この仕事には何通りの失敗の仕方があるか」で書かれていない。[リストの長さは失敗の仕方の数で決まる](../guide/goal.md#清单的长度由有多少种失败方式决定):`git clone && make && ./app` のようなタスクなら **3〜5 項目で十分**だ —— ビルドが通る、起動する、使える。[HT002](../cases/ht002.md#那条查-flower-的清单自己把自己判失败了) の実際の失敗例では、「リポジトリをインストールして動かす」というタスクが **15 項目**に書かれていた:ものが使えるかを検証しているのは 5 項目だけで、6 項目は手順を守ったかの検証、残り 4 項目は**原理的に検証不能**だった。

**対処**:`.flower/notes/目标.md` を直す。判定の根拠になるのはそのファイルだ。1 項目ずつ「これはどの失敗に対応するのか」と問い、答えられないものは削る。目標設定の段階で検証不能な項目には警告が出るので、警告された項目を無理に残さないこと。

### 境界が判定項目として書かれている {#边界不是判定项}

**症状**:リストに「`brew install` を実行していない」「プロジェクトディレクトリ外のファイルを変更していない」といった項目が現れ、ジャッジが潔白を証明するために `~/.zshrc` の mtime を調べたり、`.flower/` ディレクトリが触られていないかを調べたりする。

**原因**:境界と判定項目は別のものを制約する。混ぜたことが HT002 の主因だった([根本原因 1](../cases/ht002.md#根因一边界被当成了判定项))。

| | 何を制約するか | どう守るか |
|---|---|---|
| **境界** | **どうやって仕事をするか**(「プロジェクトディレクトリ内だけにインストールする」「業務コードに触らない」) | **越えないこと**で守る。事後の自己証明ではない |
| **判定項目** | **提出したもの**(「起動したか」「結果は正しいか」) | その場での検証で守る |

境界は、確認フェーズでたっぷり書くよう促される部分そのものだ。それを 1 項目ずつリストに移すと、境界を 1 つ増やすたびにチェックが 1 つ増えることになる。そしてこの種のチェックはたいてい検証できない —— 検証できない項目は、判定ラウンド全体を道連れにして失敗させる。

**対処**:境界は確認書の「境界」の節に置き、越えないことで守る。判定リストには入れない。どうしても説明が必要なら一文で済ませ、**6 項目に分解しない**。

## コンテキストとコスト {#上下文与花费}

long-horizon な実行では、コンテキストとコストは同じ問題だ:コンテキストが上限に達すればハンドオフするかそのステップが落ちるかであり、毎ラウンド繰り返している言葉には、以降の全ラウンドで毎回また金を払うことになる。

### 途中で勝手に新しいセッションを開き、「ハンドオフ」と言う {#换代打断}

**症状** イベントストリームに `handoff` が現れ、`payload["phase"]` が先に `near`、次に `done` となり、その間に[引き継ぎ書](glossary.md#交接书)を書く 1 ラウンド分の時間が余計にかかる。その後は通常どおり仕事が続く。

**原因** コンテキストがしきい値に近づいた。flower は **compact しない** —— 現在のセッションの状態を 5 節構成の引き継ぎ書として書き出し、新しいセッションを起こしてそれを読ませ、続きをやらせる。[compact](glossary.md#压缩) は「通らなかった道」のようなもっとも高価な情報まで一緒に消してしまうが、引き継ぎ書は明示的で、ディスク上にあり、いつでも書き換えられる:引き継いだセッションが読むのはそのファイルだ。

**対処** これは正常な経路なので、放っておいてよい。ハンドオフはリトライには数えない —— `attempts` は増えない(それが数えるのは失敗だ)。使い終わった session_id は `StepResult.retired` に記録され、外向きの `session_id` は常に生きている後継のほうだ([../guide/handoff.md#换代不算重试账怎么记](../guide/handoff.md#换代不算重试账怎么记) を参照)。どうしても SDK の auto-compact に戻したいなら `--no-handoff` を使う。

??? note "しきい値の由来と、デフォルト値がこれほど積極的な理由"
    `at = window - headroom`。`window` は**デフォルト 100 万**で、モデル名から判定する:名前に `haiku` を含むものは 20 万、それ以外は 100 万。`headroom` はデフォルト 50k —— auto-compact は −33k で発火するので、ハンドオフはその手前で済ませる必要があり、しかも「引き継ぎを書く」こと自体にもう 1 ラウンドかかる。50k はこの 2 つを同時に満たす。

    大きめに見積もっても致命的ではない:実際のウィンドウがもっと小さければしきい値には永遠に届かず、リクエストは API に「prompt が長すぎる」と突き返される。flower はこのシグナルを認識し(`handoff.is_overflow()`)、その場で機械的に組んだ縮退版でハンドオフするので、このステップは失敗しない([../guide/handoff.md#is_overflow把硬错变成当场换代](../guide/handoff.md#is_overflow把硬错变成当场换代) を参照)。

    実測で触れておく価値があること:開発機のゲートウェイは `claude-opus-5[1m]` を設定している。以前 20 万で計算していたときは 15 万ごとにハンドオフしていたが、実際には 95 万まで回せる —— **5 倍の差**があり、long-horizon な仕事はズタズタに切り刻まれる。

### 開始直後にハンドオフし、しかも止まらない {#一开局就换代}

**症状** エラーに「起動フロア」と出る、あるいは同じステップで繰り返しハンドオフし、`max_generations=8` に当たるまで止まらない。

**原因** `window` が小さすぎて、しきい値がそのロールの起動フロアを下回っている —— コーディネーターは実測で約 34k で、システムプロンプトと[ワークベンチ](glossary.md#工作台)のインデックスだけで消費してしまう。新しいセッションは口を開いた時点で線を越えるので、引き継ぎを書き、ハンドオフし、また越え、永遠に終わらない(ハンドオフはリトライ回数を消費しない。それは意図的だ)。

**対処** `--window` をモデルの実際のウィンドウに合わせる。`-v` で有効なエンドポイントとモデルマッピングが表示される。正常な長時間実行で 8 世代に達することはない。本当に当たったならほぼ確実にこれが原因で、エラーメッセージにもそう書いてある([../guide/handoff.md#一道防跑飞的闸](../guide/handoff.md#一道防跑飞的闸) を参照)。関連する別の症状として「引き継ぎが常に縮退版になる」があり、原因は `runs/manifest.json` の `errors` に書かれている。

### 途中で止まり、予算上限だと言われる {#预算到顶}

**症状** [ステップ](glossary.md#步骤)が終わっていないのに停止し、理由はコスト超過。

**原因** `AgentSpec(max_budget_usd=...)` は**ハードリミット**であってソフトな注意喚起ではない。`Runtime.total_cost()` は今回の実行の合計だ。

**対処** 上限を上げる前に、空回りしていないかを確認する。ラウンドごとに差し戻され、しかも毎回進展がないなら、たいていはジャッジが「達成不能」を出すべきところで「未達成」を出している —— 実際には達成できない目標は、予算が尽きるまで燃やし続ける([../guide/goal.md#三个结论不是两个](../guide/goal.md#三个结论不是两个) を参照)。正常に仕事をしていることを確認してから上限を上げる。

### この実行はなぜこんなに高いのか {#为什么这么贵}

**症状** コストが想定を大きく超えているが、出力を見ても金がどこに消えたか分からない。

**原因** 会計はモデルのコンテキストの中にはない。各ステップの `session_id`、コスト、リトライ回数、失敗理由は `runs/manifest.json` にのみ記録され、**プロセスをまたいで追記される**。リトライ履歴とエラー原文もここにしかない —— モデルからは見えず、これは意図的だ:拒否された呼び出しがコンテキストに積み上がると、コーディネーターは「どうせ Bash はブロックされる」と学習し、`git status` すら試さなくなる(`Runtime(keep_denials=1)` がデフォルトで既に消しているので、大きくしないこと)。

**対処** `runs/manifest.json` を開いてステップごとにコストを突き合わせる(ディスク上のレイアウトは [config.md#磁盘布局](config.md#磁盘布局))。実測の参考値をいくつか挙げる:

| | コスト |
|---|---|
| subagent 1 つの起動フロア(償却不能) | ~4.3k tokens |
| コーディネーターの起動フロア | ~34k tokens |
| `tests/smoke.py` 単一 agent のフルチェーン | ~$0.21 |
| `tests/flow_demo.py` workflow の 3 通りの繋ぎ方 | ~$0.39 |
| `tests/delegation.py` 分業 + コンテキスト分布の計測 | ~$0.71 |
| `tests/isolation.py` 3 つの issue に 3 つの worktree | ~$0.9 |

### コンテキストが仕事の進みより速く膨らむ {#上下文涨得快}

**症状** 毎ラウンドの[タスク指示書](glossary.md#任务书)で同じ規律(「まずファイルを読んでから直す」「業務コードに触らない」「直したらテストを走らせる」)を繰り返しており、[ワーカー](glossary.md#执行者)はもとよりそのとおりにやっている。

**原因** コーディネーターが言うことはすべて自分の transcript に入り、transcript は増える一方だ。規律を復唱すれば、そのラウンドで金を払い、**以降の全ラウンドでもその分をもう一度払い続ける**。相手がすでに知っていることを復唱する利得はゼロで、コストは永続する。

**対処** 規律は仕組みに入れ、毎ラウンドの発話には入れない:`allowed_tools`、確認書の「境界」の節、ワークベンチのインデックスで表現できるものは、タスク指示書に書かない。タスク指示書にはそのラウンドで何が変わったかだけを書く。分業そのものが最も節約になる層だ([../guide/context.md#第一层分工省得最多](../guide/context.md#第一层分工省得最多) を参照)。resume 時には、古い大きなツール結果を `-T` でファイルポインタに置き換えられる。

## 中断と継続 {#中断与接续}

### プロセスが kill された、マシンが再起動した {#进程被杀}

**症状** 途中で消えてしまい、ターミナルを開き直しても、どう拾い直せばいいか分からない。

**原因** 拾い直すものは何もない。[リネージ](glossary.md#血缘)(`runs/lineage.json`)はステップ名 → session_id を記録し、各ステップの終了時にディスクへ書き出す。書くときはまず `.tmp` に書いてからアトミックに置換する —— 途中で kill されても半端なファイルは残らない。

**対処** **同じディレクトリ**に戻ってもう一度 `flower` を走らせれば、各ステップは前回のセッションから続く:要求をもう一度問い直されることもなく、目標を設定し直すこともなく、コーディネーターがどの行き止まりを試したかまで覚えている。何も言うことがなければそのまま Enter([../guide/continuity.md#进程被杀和机器重启](../guide/continuity.md#进程被杀和机器重启) を参照)。ジャッジは例外だ —— それは `Step` ではなく gate から直接送り出されるもので、リネージの経路をそもそも通らない。だから毎ラウンド、まったく新しい目になる。

### 毎回ゼロから始まり、まったく継続していない {#接不上}

**症状** 同じディレクトリでもう一度走らせると、要求をまた一から問い直される。

**原因** 3 種類の「食い違い」があり、flower は一律に**黙って最初からやり直し、エラーは出さない** —— [継続](glossary.md#接续)は上乗せの機能であって、それが効かないことで人の仕事を止めるべきではない:

- `runs/lineage.json` が存在しない、あるいはその中の `workspace` が現在のパスと一致しない(ディレクトリをコピーして移すとこうなる)
- session が `runs/sessions.db` にもう存在しない(DB を消した)
- リネージファイルが壊れている

**対処** まず `runs/lineage.json` があるか、`workspace` が正しいかを見る(3 つのファイルの役割は [../guide/continuity.md#落在磁盘上的三个文件](../guide/continuity.md#落在磁盘上的三个文件) を参照)。ディレクトリを変えたあとに継続しないのは**意図的**だ:`project_key` はワークスペースのパスから導出されるので、古い session は新しい場所では引けない。

### やり直したいが、履歴は捨てたくない {#想重开}

**症状** 要求の方向が変わったので、前回の話の続きをさせたくない。

**原因** デフォルトの挙動が「続きから話す」だ。使用済みのディレクトリで `flower "顺便支持代码块高亮"` と打つのは新しいタスクではなく、もう一言付け足しただけになる。

**対処** `--new` を使う。これは**アーカイブであって削除ではない**。古いものは `notes/archive/` に残る。[ウェイク](glossary.md#唤醒)時には現在のコンテキスト規模が 1 行で報告されるので、大きすぎると感じたときもこの経路を使う。

### ネットワークが切れ、エラーも出さず動きもしない {#断网}

**症状** 画面に新しいイベントが出ず、プロセスは生きていて、固まったように見える。

**原因** ネットワーク断は失敗ではなく「少し待つ」として扱われる。flower はぶら下がって待つ:まず DNS を探り、次に TCP を探り、通ってから続行する([../guide/continuity.md#韧性断网时挂着等而且错误不进接续后的上下文](../guide/continuity.md#韧性断网时挂着等而且错误不进接续后的上下文) を参照)。HT001 ではこの経路が実際の障害で検証された([../cases/ht001.md#六断网续跑第一次被真实故障验证](../cases/ht001.md#六断网续跑第一次被真实故障验证) を参照)。

**対処** 待つ。`-v` で探査が走っているのが見える。待機中に溜まったエラーは**継続後のコンテキストには入らない** —— それらは `runs/manifest.json` に落ちるだけで、引き継いだセッションが見るのはきれいな現場だ。タイムアウトの連なりに引きずられることはない。

### Ctrl-C を 2 回続けて押すと、終了処理が完了しない {#双重-ctrl-c}

**症状** `kill`(SIGTERM)で落とした場合と、Ctrl-C を 2 回続けて押した場合とで、残る現場が違う。

**原因** 既知の穴。ダブル Ctrl-C が投げるのは `KeyboardInterrupt` で、`cli.py` の `_drive` の `finally` は `rt.close()` は呼ぶが、**`rt.rescue()` は呼ばない** —— `rescue()` を呼ぶのは SIGHUP/SIGTERM のハンドラだけだ。

**対処** リネージはどちらの経路でも保たれる(各ステップ終了時にアトミックに書き出す)ので、もう一度走らせれば同様に継続でき、この穴で進捗を失うことはない。完全な終了処理を通したいなら、Ctrl-C を連打せず `kill <pid>` を使う。

## 並行と隔離 {#并行与隔离}

### `not in a git repository` {#不是-git-仓库}

**症状** 隔離を有効にすると起動できず、`not in a git repository` と出る。

**原因** `worker(..., isolate=True)` は git worktree を使って各 agent にプライベートなコピーを与えるので、workspace が git リポジトリでなければ作れない。

**対処** これは**黙って縮退しない** —— 本当にリポジトリの中で走らせるか、`isolate` を切るかのどちらかだ。隔離が保証するのは「複数の agent が同時に変更しても、互いの作業ツリーが見えない」ことであって、マージが衝突しないことは保証しない。

### 隔離された agent がワークベンチに書き込めない {#隔离写不进工作台}

**症状** subagent が「書き込み権限が拒否された」と報告し、スクリプトも成果物もディスクに落ちない。あるいは成果物がどれか 1 つの worktree に落ちて、他の agent から見えない。

**原因** worktree は各 agent の**プライベートなコピー**で、ワークベンチは agent をまたぐ**共有レイヤー**だ。共有すべきものをプライベートな囲いの中に置けば、他人が取れないのは当然だ。

**対処** 隔離を有効にするときは、ワークベンチを**リポジトリの外**に向ける:

```python
wb = Workbench(Path.cwd(), home=Path.cwd().parent / ".flower-proj").ensure()
```

ワークスペースの外に置く場合、`Runtime` は自動的に `add_dirs` で許可を与える。`Runtime(workbench=True)` はこれを処理済みだが、自前で `Workbench` を作る場合は許可を自分で与える必要がある。

!!! warning "ワークベンチのデフォルト位置は 2 つあり、しかも違う"
    `Workbench(workspace)` —— CLI と `starter_flow()` が通るのはこちら —— はワークベンチを `<workspace>/.flower` に置く。
    一方 `Runtime(workbench=True)`(つまり `-W`)が置くのは `<run_dir>/workbench`、すなわち `runs/workbench` だ。
    だから `flower` を 1 回走らせれば `.flower/` ができるが、Python で `Runtime(workbench=True)` を呼んでも**できない**。

### flower を走らせると `.flower/` ができるのに、自分でスクリプトを書くとできない {#两个工作台默认值}

**症状** 確認書は確かに `.flower/notes/需求.md` に書き込まれているのに、コーディネーターは読んでいないかのように振る舞う。**エラーは出ない**。

**原因** 手元にワークベンチのオブジェクトが 2 つある。確認書はディレクトリ A に書かれ、system prompt に注入されるインデックスがスキャンするのはディレクトリ B で、「開始時点で要求ファイルの場所を知っている」という約束が**黙って破れる**。誤り方は 2 通りあり、どちらもエラーにならない:自分で `brief_path` をプロセスの cwd 相対で組み立てると、`-W` が作る `<run_dir>/workbench` とは別ディレクトリになる。`Runtime` から逆に取ろうとしてもだめだ —— `cli.py` は先に `main()` を呼んで `Workflow` を作り、その後で `Runtime` を作るので、その時点で `brief_path` はとうに固定されている。

**対処** 自分で `Workbench` を 1 つ作り、**同じオブジェクト**を `Workflow` と `Runtime` の両方に渡す。そうすれば位置は固定される:

```python
wb = Workbench(Path.cwd()).ensure()
wf = Workflow(channel=ch, workbench=wb, steps=[...])
rt = Runtime(workspace=".", workbench=wb)
```

`tests/trial_offline.py` がこれを固定している:5 番目のアサーションが、確認書が `prompt_block()` に現れることを検証する。なおインデックスが注入されるのは**コーディネーター**の system prompt だけで、subagent は継承しない(実測 $0.2461、`tests/prelude_live.py`)—— パスはコーディネーターが下流に伝える必要があり、各 subagent が自動的に知るわけではない([../guide/workflow.md#工作台要挂在-workflow-上](../guide/workflow.md#工作台要挂在-workflow-上) を参照)。
