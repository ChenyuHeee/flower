この macOS 上にインストールし、動かす。** 結果は **$38.24 / 4 ステップ / 約 1 時間**、
プログラムは確かに macOS 上で動き(PID 96040、arm64 Mach-O)、
[判定](../reference/glossary.md#判定)の結論は**達成不能**、人に上げて、人が受け入れを選んだ。

## 一、ヘッドライン:`git clone && make && ./cppide` を1時間に変えた

これが今回いちばん重要な発見で、下に並ぶ「機構は通った」という話のどれよりも重要だ。

目標設定のステップで、[ジャッジ](../reference/glossary.md#判定者)は自分向けに **15 条の判定チェックリスト**を書いた
(原文は [`.flower/notes/`](https://github.com/ChenyuHeee/flower/tree/main/human-test/HT002/.flower/notes) 配下の `目标.md`)。
性質で分類すると:

| 分類 | 条数 | 例 |
|---|---|---|
| **本当に「動くか」を検証している** | **約 5** | ビルドが exit 0;プロセスが ≥30 秒生存;再起動コマンドが新しい shell で再実行できる |
| **「過程がルールを守ったか」の検証** | **6** | `~/.zshrc` / `.zprofile` / `.bash_profile` の mtime がすべて今回のセッションより古い;`brew install` / `npm -g` / `sudo` を実行していない;**`.flower/` の mtime が変わっていない、`runs/` に人為的な追加削除がない** |
| **原理的に検証不能** | **4** | スクリーンショットを撮って目で見る;devtools console;人が手でクリック;本人による確認 |

**「これが本当に使えるのか」を検証しているのは三分の一しかない。** 6 条は自分自身がルールを守ったかを検証していて ——
そのうち 1 条が見ているのは **`.flower/` ディレクトリの mtime**、つまり**フレームワーク自身のディレクトリ**だ。

### `.flower/` を見るあの1条が、自分自身を不合格にした

これは理論上の問題ではない。判定のターンで、ジャッジは「未通過」の欄に正直にこう書いた:

> **`.flower/` 配下のファイルの mtime がすべてセッション開始より古い** —— 文字どおり失敗:`INDEX.md` 16:14、
> `artifacts/01–05`(15:40–16:12)、`notes/决策-项目形态与验收路径.md` 15:43 はいずれもセッション中に書かれている。

原因は:**フレームワークが、長い成果物は `.flower/artifacts/` へ、決定は `.flower/notes/` へ書くことを強制的に要求している**こと。
判定チェックリストのあの1条は、そのディレクトリに触るなと要求している。2 つのルールが正面衝突していて、しかもそれを作ったのは判定チェックリスト自身だ ——
ワーカーが長い成果物を一つも書かなければ、むしろ準拠していたことになる。

ごまかしはしなかった:作業ステップは最終報告でこの衝突を自ら挙げ、
決定記録にも扱いを書いた —— **既存ファイルは一つも動かさない**
(`需求.md`、`目标.md`、`问答记录.md` の 3 件は前後で mtime と MD5 が一致)、新規追加のみ。
ジャッジは再確認して「この条が防ごうとしていた改竄は起きていない」と同意したが、それでもルールどおり未通過に挙げ、人に判断を委ねた。

### 根本原因その一:境界が判定項目にされた

事前確認の段階で聞き出した[境界](../guide/clarify.md)(「プロジェクトディレクトリ内にしかインストールできない」「業務コードには触るな」)は、
本来**どう作業するか**を縛るものだったのに、**成果物**を検証するチェック項目として書かれてしまった。
その結果、`.zshrc` の mtime を見る、`.flower/` の mtime を見るといった条目が生まれた。

**境界 ≠ 判定項目。境界は過程を縛り、判定項目は結果を検証する。** これを混同すると、境界を1つ足すごとに判定が1つ増える。
そして境界はまさに、確認段階で書き尽くすよう奨励されているものだ —— `CLARIFIER_RULES` にはこう明記されている:
「**やらないことを明確にする**。この節はこの先の作業をする全員を縛る」。

生の記録と突き合わせれば、この増幅の連鎖が一段ずつ見える:
[要件確認書](../reference/glossary.md#需求确认书)の境界は「カレントディレクトリにある既存の `.flower/` と `runs/` に触らない」と書かれていたのが、
判定チェックリストでは「`.flower/` 配下のファイルの mtime がすべて今回のセッション開始より古い」に格上げされた ——
「既存のものを動かすな」が「ディレクトリ全体に新規ファイルを作るな」に変わっている。

### 根本原因その二:`JUDGE_RULES` の圧力が一方向しかない —— しかもそれはその日に足したもの

同じ日の早い時間に、[HT001](ht001.md) の教訓から `JUDGE_RULES` へこれらを書き込んだ:

- 「各条はその場で検証できなければならない」「欠けているもの、曖昧なものは、お前が補え」
- 「判定するのは成果物であり、ソースコードではない」(macOS のあの反面例つき)
- 「今の環境で検証できない条目は、その場で明示せよ」
- 「まず自分がどこにいるかを確かめろ(`uname -a` してよい)」

**どれもが、より多くのチェック、より厳格な方向へ押している。ルール全文のどこにも「タスクの規模に見合わせろ」という一文がない。**

つまり:HT001 の「通過を過剰に宣言する」失敗に合わせて最適化したら、**まったく逆の失敗 —— 過剰検査**を作り出した。
これは自分で作った失敗で、モデルの問題ではない。

### 根本原因その三:[issue #3](https://github.com/ChenyuHeee/flower/issues/3) と重なった

実際に詰まったのは macOS 上の 2 箇所の移植性欠陥だ:

- `src/proc.cpp` が `::sigemptyset` を使っているが、Apple SDK は関数プロトタイプのあとでそれを関数形式マクロとしても定義している
  (守っているのは `#ifndef _ANSI_SOURCE` だけ)。そのため `::sigemptyset(&s)` が `::(*(&s)=0,0)` に展開され、構文エラーになる
- `src/ui.cpp` が `::_exit` を使っているのに `<unistd.h>` を include していない

**3 行で直せる。** だがユーザーは確認段階で「業務コードには触るな」と答えており、agent はそれを厳格に実行した。
その結果、コンパイル flag を試す、subagent を派遣する、決定記録を書く、という迂回に入った。
**そのとき「あの2行は直してもかまわない」と一言挟めていたら、10 分で終わっていた。**
境界を禁止として書くと最大限に厳格に解釈され、途中でそれを緩める通路はどこにもない。

生の記録を見ればこの迂回の長さがわかる:ブロック点は全部で4つあり、
そのうち純粋なコンパイル flag で解決できるのは `::_exit` のものだけ。`::sigemptyset` のほうは **6 組**の `-D`/`-U` の組み合わせを試して全部失敗した
(`_POSIX_C_SOURCE` 系は連鎖して `st_mtimespec` と `O_CLOEXEC` まで壊す)。
この行き止まり自体が 13.6K の実現可能性レポートを1本生んでいる。

### ただし公平に言えば:境界がより良い解を引き出した

最終的な解はソースコードの修正ではなく、Makefile 内で**`#undef` だけを行うシムヘッダを生成**し、`-include` で強制的に前置するものだった:

```make
$(MACSHIM):
	@printf '#include <signal.h>\n#undef sigemptyset\n#undef sigfillset\n...' > $@
CPPFLAGS += -include $(MACSHIM) -include unistd.h
```

これはソース修正より良い —— 上流リポジトリは1行も変える必要がなく、誰が clone してもビルドできる。シムは `build/` に生成してリポジトリには入れず、
`clean` に `rm -rf build` を足して回収を担わせ、`make -n UNAME_S=Linux` で実測したところ展開後に `-include` は出ず、Linux 経路は汚染されていない。
最終的な `git diff` は `Makefile` の1ファイルだけ、**+14 / −2**。

つまり境界が生んだのは**より高コストのより良い解**だ。問題は間違ったことをしたという点ではなく、
**このトレードオフを人に判断させられなかった**点にある —— そしてできなかった理由がまさに issue #3 だ。

!!! note "`git status` に 64 件あるのにソース改変ゼロと言える理由"
    cppide リポジトリは 30 個の `.o`、30 個の `.d`、2 個のバイナリを**バージョン管理にコミットしている**。しかも Linux ELF aarch64 で、
    mtime は `.cpp` より新しい —— 先に `make clean` しないと、`make` はコンパイルを飛ばして ELF をそのままリンクしに行き、必ず落ちる。
    だから `git status --porcelain` の 64 件のうち 63 件は git に追跡されているコンパイル生成物で、残り 1 件が `?? build/` だ。
    拡張子でフィルタすると `git diff -- 'src/*.cpp' 'src/*.h' README.md config.sample.json | wc -c` は `0`。
    この厳密な言い方はコンプライアンス監査に押し出されて出てきた —— コーディネーターは当初ざっくり「`src/` は改変ゼロ」と書こうとし、監査がその文は成立しないと指摘した。

## 二、ゴールガードが正しくやったこと

機構側はすべて通り、しかも**その日の2つの変更が成果物に直接の指紋を残した**。

**ジャッジが書いた判定チェックリストの第1条**:

> `uname -a` は Darwin 25.2.0(macOS)を示す……以下すべての「動く/開く」系の条目は、この機械上で
> 実際に走らせて得た結果でなければならない。**「ソースに macOS 分岐があるから動くはずだ」という類の推論は受け付けない**

これはまさに、その日の朝に HT001 の教訓から `JUDGE_RULES` に書き込んだ文だ。

**その日に足した `[此环境无法验证:…]` マーカーを3回使い**、それぞれ理由を付けた ——
devtools console(駆動できるブラウザがなく、そのためにヘッドレスブラウザを入れるのは境界を越える)、
人が手でクリック(人が画面の前にいる必要がある)、本人による確認(彼本人しか出せない)。

**ジャッジの最初の一文は「あの返答を読んで結論を出すことはしない。現場を見に行く。」だった。** そして:

```text
file cppide        → Mach-O 64-bit executable arm64
lsof -p 96040      → txt は /Users/hechenyu/explore/test-ide/cppide/cppide を指す
                     16:10 に開始、16:15 時点でも生存
```

自分でこう書いている:「**meta の教訓にあった『Linux ELF を納品する』穴は、今回は踏まなかった。**
Linux ELF が Darwin 上で PID になることはありえない。これは Makefile から推論したものではない。」

ソースが実際に触られていないことも確認した:`src/` 配下のすべての `.cpp` / `.h` の mtime は全部 15:32(clone した時刻)で、
変わったのは `Makefile`(16:06)だけ。`.o` / `.d`(16:07)は追跡されているコンパイル生成物の再構築だ。

**手が届かないところも正直に申告した。** ジャッジの Bash は作業ディレクトリ内に制限されており、
`git ls-remote` の比較と `~/.zshrc` の mtime は実行できず、独立監査の出力を採用するしかなかった ——
この2条については「自分の手で再実行できていない」と別立てで説明している。

## 三、「達成不能」と判定し、それから人に聞く

三値判定と人の介入、[この経路全体](../guide/goal.md)が初めて実際に通った。

判定の結論は**達成不能**で、詰まったのはスクリーンショットの条目だ:`screencapture -x` も `-l <window-id>` も
`could not create image from display` を返す —— 画面収録の TCC 権限が付与されておらず、
付与するには人がシステム設定で操作する必要があり、それ自体が境界で禁止されたシステム変更にあたる。

> 「**もう一巡 subagent を派遣してもこの画像は出てこない。ルール上これを通過にはできないし、『未達成』でもない。
> これは達成不能であり、止まって人に渡すべきものだ。**」

こうしてチェックリストの「原理的に検証不能」な条目は 3 条から 4 条になった —— **15 条のうち 4 条はこの環境では検証しようがない**。
そしてそれがわかったのは、$35.8950 の作業と $1.4037 の判定を**使い切ったあと**だ。
目標設定のステップは $0.4117 しか使っていない。そのときに気づくべきだった。

フレームワークはこの結論を人に問い(問答記録 q7 に記録)、3 択のうち人は「この結果を受け入れる」を選び、gate が通過を許可し、ワークフローは完了した。

**代替品も拒否した。** ワーカーは AppleScript でターミナルウィンドウのテキストを読み戻していて、
それは実際にレンダリングされた TUI だった —— 行番号欄、`src/main.cpp` の本文、`─[编译]─[运行]─[AI*]─[输入]─` のパネル欄、
`练习模式 │ main.cpp │ 1:1 │ C++` のステータス欄。白画面でもエラー画面でもない。ジャッジはこう言った:

> 「作業した側はこれを『画像を見た』と偽らなかった。この自制は正しい。
> **だがこれはチェックリストが要求している条目の代わりにはならないし、私が代わりに勘定してやることもしない。**」

!!! warning ""リスクを開示した"は通過ではない"
    HT001 が落ちたのがこれだ:「macOS で一度も動かしていない」を納品説明に書き、それでも受入項目 1 を通過と判定した。
    HT002 ではジャッジがより良い代替証拠(実際の TUI テキスト)を手にしながら、それでチェックリストの条目を差し替えることを拒んだ。
    この違いが[判定](../reference/glossary.md#判定)の三値設計の意味そのものだ ——
    `UNREACHABLE` は `NOT_YET` の婉曲表現ではなく、「ここで止まって人に聞くべき」という状態だ。

## 四、`allowed_tools` はハードなホワイトリストではない

このランを分析していて、主張と食い違う事実が1つ見つかった。[セッション](../reference/glossary.md#会话)ごとにツール呼び出しを分解すると:

| セッション | 実際に使ったもの | ホワイトリストにあるもの |
|---|---|---|
| 要件確認 | **WebFetch**、Glob、ask×6 | 当時 `clarify()` は ask + `Read`/`Glob`/`Grep` のみ |
| 目標設定 | **Bash ×11** | `judge()` はデフォルト `can_run=False`、**Bash はない** |
| 作業・判定 | **Bash ×31**、WebFetch | 同上 |
| 作業(コーディネーター) | Bash ×1、Agent ×6 | 正しい |

`goal_step` には **`can_run` を渡すコード経路が一つもない**ので、「目標設定」の行が設定の問題であることはありえない。

**$0.1 のプローブ検証**:`allowed_tools=["Read"]` の agent にファイルを書かせてみた ——

```text
Write → 権限層:"requested permissions to write ... but you haven't granted it yet"
Bash  → パス安全:"Output redirection was blocked. For security, Claude Code may
        only write to files in the allowed working directories"
```

**モデルはホワイトリストにないツールを呼び出せる**。ただ permission 層とパス安全に止められているだけだ。したがって:

- `allowed_tools` は**承認不要リスト**であり、排他的なホワイトリストではない
- 当時 `clarify()` / `judge()` を実際に守っていたのは、継承された `permission_mode="default"` だった
- そしてこの2つは `delegate_only=False` → **`delegate_guard` の hook がない**。
  コーディネーターには hook が付いているが、**この2つの役割には当時 flower 自身の機構が何もなかった**

`clarify()` の docstring には「書き込みツールを与えない —— 着手できない」と書かれており、
あの $0.8908 の反面実測は丸ごとこの一文のために行われた。**この一文の機構的な根拠は間違っている。**

!!! note "この節の2つの事実はその後どちらも変わった"
    `whitelist_guard` は無条件に接続された:`delegate_only=False` の役割には `Runtime` が自動でこの hook を付けるようになり、
    `clarify()` / `judge()` は「機構が何もない」状態ではなくなった。また `WebFetch` は現在 `clarify()` のホワイトリストに入っているので、
    表の1行目のあの例はもう無効だ —— **結論は依然として成立するが、支えているのは $0.1 プローブの証拠だけになった。**
    詳細は本ページ最後の節。

## 五、コンテキスト曲線:ステップ境界でリセットされる

```text
第 1ターン   36.8K
第25ターン   80.2K   ← ピーク
第26ターン   32.9K   ← 断崖:新しいステップ = 新しいセッション(resume_from=None)
第121ターン  64.8K
```

4 つのサンプル点のうち 3 つ(第 1 / 25 / 121 ターン、36.8K / 80.2K / 64.8K)は生の記録と一つずつ一致する。
**第 26 ターンの 32.9K は再計算すると合わない**:`store_key` 順にメインスレッドの assistant メッセージを再生すると、
26 番目(新しいセッションの1件目)の `input + cache_read + cache_creation` は 31,972 token = **32.0K** で、
32.9K は同じセッションの2つ目の値(31,970 + 948)だ。本ページは 32.9K を残す —— 差は 0.9K で、
「断崖のように落ちる」という結論はどちらの値でも成立する。

HT001 は単調に 185.9K まで上がった —— 1 ステップが 10 時間走った。
HT002 は 4 ステップに分かれ、ステップごとに新しいセッションを開くので、**コンテキストが構造的にリセットされる**。
これは「要件確認書と目標は凍結物であり、下流は文書だけを受け取り会話は受け取らない」という設計の直接的な効果だ —— 曲線に見えている。

キャッシュヒットは **90.8%**(HT001 は 96.1%)。ヒット率はセッションの長さとともに上がるので、短いセッションはむしろ単価が少し高くなる ——
これは HT001 第三節の結論と同じコインの裏表だ。
