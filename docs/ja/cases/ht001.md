# HT001 · ターミナル IDE をゼロから書く

2026-09-07、ある agent が flower 上でゼロから、macOS のターミナルで動く C/C++ 単一ファイル IDE を書き上げた。
連続で 10.4 時間走り、$171.62 を使い、12,212 行のプロダクトコードと 13,291 行のテストを提出した。
途中で一度ネットワークが切れたが、自力で続きを走り切った。このページは成果の展示ではない —— フレームワークの各主張を実スケールで一通り計測したものであり、
**そのうち成立しなかった 2 つも含む**:コーディネーターが「頻繁に権限制限を無視する」というのは偽だった。そして自分で自分に下した受け入れ判定のうち 1 条は誤判定だった。

完全な記録(19MB の transcript を含む)は [ChenyuHeee/cppide](https://github.com/ChenyuHeee/cppide) にある。
以下の数字はすべて `tools/analyze_run.py` が `sessions.db` から算出したもので、再現可能:

```bash
python tools/analyze_run.py /path/to/cppide/runs
```

!!! note "このページの数字の出どころ"
    HT001 の `runs/` は上記の cppide リポジトリにあり、**flower リポジトリにはない**。したがって本ページの数字は
    当時の実行記録から**そのまま転記**したもので、このページを書く時点で `sessions.db` に対して再計算はしていない ——

## 一、コンテキストの経済学:現場の 94.8% はメインスレッドに入らなかった {#一上下文经济学948-的现场没进主线程}

これはフレームワークの中心的な主張 —— [コーディネーター](../reference/glossary.md#协调者)には意思決定だけを載せ、
現場は subagent とディスクに沈める。仕組み自体は[コンテキストの経済学](../guide/context.md)を参照。

| | メインスレッド | subagent | subagent 比率 |
|---|---|---|---|
| モデルターン | 70 | 3.0K | **97.7%** |
| 本文字数 | 200.1K | 3.6M | **94.8%** |
| ツール呼び出し | **32** | **1,893** | —— |

この run では 23 個の subagent を派遣し、出力 token は最大 184,377、中央値 72,197、最小 11,684。

**実作業のツール呼び出し 1,893 回(Bash 1,034 / Read 471 / Edit 258 / Write 126)のうち、コーディネーターの視界に入ったのは 32 回だけ
—— 59:1。** 1 回派遣するごとに、平均 82 回のツール呼び出しがコーディネーターには見えていない。

初期の小規模テストでは 83% だったが、実スケールでは **94.8%**。規模が大きいほど分業の利得は大きい ——
[タスクブリーフ](../reference/glossary.md#任务书)と応答のオーバーヘッドは**派遣ごとに固定**である一方、
外に締め出される現場はタスクの複雑さとともに増えるからだ。

## 二、コンテキスト曲線:「long-horizon」の上限が初めて分かった {#二上下文曲线第一次知道长程的上限在哪}

各 assistant メッセージの `input + cache_read + cache_creation` が、そのターンでモデルが見たコンテキストである:

```text
第 1ターン   28.7K   ← 起動時の下限(それ以前の実測は約 34k、一致)
第20ターン   35.2K
第35ターン  108.6K
第50ターン  158.2K
第70ターン  185.9K   ← 終了
```

- 70 ターン単調増加、傾きは約 **2.2K/ターン**
- 全期間で**compact は一度も発生していない**(`DISABLE_AUTO_COMPACT=1`;唯一の落ち込みはネットワーク切断ターンの空レコード)
- 1M ウィンドウの **18.6%** を使用

**この傾きで外挿すると、壁にぶつかるのは約 440 ターン。** 今回の 70 ターンで 12K 行のコードを産出したので、
現在の形態における[long-horizon](../reference/glossary.md#长程)の実際の上限は今回の約 **6 倍**。
以前は推測するしかなかったが、これは意思決定に使える数字だ。

これを突破するには、メインスレッドの増加を**劣線形**にする必要がある —— より多くをディスクに沈め、対話に残す量を減らす。

## 三、キャッシュヒット率 96.1% —— $171.62 で済んだのは完全にこれのおかげ {#三缓存命中-961--17162-能成立全靠它}

```text
総入力 299.4M token
  キャッシュヒット  287.5M  (96.1%)
  キャッシュ新規作成 11.8M
  キャッシュなし      6.2K
出力 2.3M(うち thinking 653.9K)
```

299M の入力 token が $171 で済んだのは、96% がキャッシュ価格だったから。

**帰結:long-horizon な run の経済性はキャッシュヒット率の上に成り立ち、そのヒット率はコンテキストのプレフィックスの安定性に依存する。**
「コンテキストを並べ替える」たぐいの最適化 —— 古い内容を移動する、先頭に新しいシステムプロンプトを挿す —— はいずれもキャッシュを破壊し、
節約した token は失ったキャッシュ割引に到底見合わない可能性がある。これは以前は計測していなかったが、今は数字がある。

これは flower が compact ではなく[ハンドオフ](../reference/glossary.md#换代)を使う付随的な理由でもある:
ハンドオフは**新しいセッションを開いてキャッシュを一から作る**ので、1 世代の中ではプレフィックスが常に安定する。

## 四、ワークベンチの再利用:61 個のスクリプト、書き捨てはゼロ {#四工作台复用61-个脚本没有一个写完就扔}

[ワークベンチ](../reference/glossary.md#工作台)の主張は「スクリプトは一度書けば、以降はそのまま走らせる。書き直さない」。
検証方法は agent に尋ねることではなく、`.flower/scripts/` 内のスクリプトが transcript 中で Write/Edit された回数と Bash で実行された回数を数えること:

```text
61 個のスクリプト:書き込み 95 回、実行 331 回
実行回数 > 1(実際に再利用された):56 個、92%
書いたが一度も実行されなかった:0 個
実行/書き込み比 3.48
```

`wave5-verify.sh` は 5 回書かれ、45 回走った —— 反復して磨き上げ、繰り返し使う。まさに望んだ形だ。
**書き捨てられたスクリプトは一つもない。**

## 五、コーディネーターの実作業が拒否されたのは 1 回、しかもホワイトリスト側の誤り {#五协调者动手被拒-1-次而且是白名单的错}

着手前の疑いはこうだった:「コーディネーターは頻繁に権限制限を無視し、大量の拒否呼び出しを引き起こす」。実測はこの前提を潰した。

**32 回のツール呼び出しのうち拒否は 1 回(3.1%)**、しかもその 1 回はこれ:

```bash
which g++ clang++ make pkg-config 2>&1; echo ---; ls /usr/include/ncurses.h 2>&1; echo ---; ls /work/runs
```

区間ごとの判定:`echo` 許可、`ls` 許可、**`which` は遮断 —— [エフェメラルコマンド](../reference/glossary.md#一次性命令)の表に載っていなかった**。

このコマンド全体は純粋に読み取りのみで、標準的な環境探索だ。**モデルは完全に正しく振る舞っており、ホワイトリストが不完全だった**。
たった一行の `which g++` のために subagent の起動コスト(約 4.3k token)を払わされた。

修正済み:`which` / `command -v` / `type` / `whereis` / `uname` / `arch` / `locale` / `nproc` /
`getconf` / `sw_vers` を追加。`command` と `type` は**クエリ形式のみ許可** ——
裸の `command rm -rf /` は実行であり、`-v` を書き忘れることが裏口を開けることに等しい。
`tests/glance.py` に 7 件の敵対サンプルを置いて守っている。

**ここで最も記録すべきなのはパッチではなく、方法だ。** 長く続いた設計議論の出発点となる前提が、実データでは 1/32 であり、
しかも原因の帰属が逆だった —— 問題はモデルではなくホワイトリストにあった。**まず計測しろ。**

## 六、ネットワーク切断からの継続:実障害で初めて検証された {#六断网续跑第一次被真实故障验证}

```text
01:52:40  tool_result: "Agent terminated early due to an API error"   ← subagent が 1 つ中断された
01:55:41  assistant:   "API Error: ENOTFOUND"                          ← メインスレッドが受信
          ↓  プローブがぶら下がったままネットワーク復旧を待つ
          resumed=True、同一セッションを継続、さらに 8 時間以上走って完了
```

manifest には `attempts=2 / resumed=True / ok=True` と記録されている。**10 時間の作業をやり直さずに済んだ。**
これ以前、[レジリエンス](../reference/glossary.md#韧性)はずっと「未検証」のままだった —— ネットワークを切るには sudo で hosts をいじる必要があり、本番の run 中にそれをやりたい者はいなかった。

その合成された "API Error" メッセージは `PruningSessionStore` が load 時に取り除いており、**モデルはそれを見ていない** ——
[プルーニング](../reference/glossary.md#剪除)の設計も同時に実障害で検証された。

露呈した問題が 2 つ(issue #2 参照):

1. 復旧が**フレームワーク層**で起きており、トランスポート層ではない。代償はコンテキスト全体の再送で、あのときのコンテキストは巨大だった。
2. **中断された subagent の作りかけの作業は失われた。** resume が救うのはメインスレッドで、
   subagent レベルの中断復旧は別問題だ。

## 七、その自己検証は本物か {#七它的自我验证是真的吗}

ここが最も疑うべきところだ:agent が自分でテストを書き、自分で走らせ、自分で合格を宣言する。形骸化しやすい。

事後に独立した監査 subagent を派遣し、58 本のスクリプトと 22 件の成果物を静的に読ませた。結論は**本物であり、しかも珍しいほど厳格**:

- **恒真アサーションは 0 箇所。** リポジトリ全体に `[ 1 = 1 ]` 系のパターンはない。
- `|| true` は計 8 箇所、**7 箇所は正当**(`grep -c` が無マッチで 1 を返す、`ulimit` のフォールバックなど)。
- **判定しているのは挙動であり、ファイルの存在ではない。** `audit-idle-cost.sh:53` は IDE を pty 内で 60 秒アイドルさせ、
  ローカルの偽サーバーが実際に受けたリクエスト数を数え、`-le 2` で初めて PASS。`fix-p1-idle-verify.sh:100-110` はさらに踏み込み、
  アイドル時にちょうど 1 回であることをアサートし、**かつ** ghost が依然として表示されることもアサートする —— 「レート制限の修正が機能ごと殺す」のを防ぐためだ。
- **本当に子プロセスを起こす。** `wave5-pty-drive.cpp:316` は `forkpty` で実際に TUI を走らせる;`audit-fake-ai-server.py`
  は本物の socket サーバーで、`/err500 /err401 /badjson /drop /slow` の 5 種類の障害注入に対応;
  すべての AI 経路で `CPPIDE_API_KEY` を強制的に空にする。

予想を超えていたことが 2 つある。

**自分の検証器に対して陽性・陰性コントロールを置いた。** `验收审计.md:29-34`:まず `ZZZ_NEVER_APPEARS_ZZZ` を食わせてドライバーが FAIL することを確認し、
次に本物の文字列を食わせて PASS することを確認する —— 「常に PASS する偽の機械で監査する」のを避けるためだ。**これは検証器そのものを検証している。**

**自分の弱いアサーションを自ら開示した。** `wave5-b4-ai-states.sh:114` の `for m in $must`
は `"AI 错误 请求超时"` を空白で 3 つの部分文字列に分割してそれぞれ grep するが、`AI` と `错误` はどの画面にも必ず現れる ——
名目上「3 条通過」だが、実際に識別力があるのは 1 条だけ。**これは監査員が掘り出したのではなく、自分で `验收审计.md:576-582` に書いたものだ。**

同種のものとして:`wave5-verify.sh:296-302` は 7 行のコメントで B3b をなぜ SKIP に降格したかを説明し
(最終画面のタイミングアサーションであり、プロダクトコードとは無関係)、「判定ロジックと許容範囲は一字も変えていない」と明記している;
`:236-238` は**自分が以前書いた偽アサーションを発見して修正した**ことを記録している ——
`if pgrep ...` は `pgrep` のない最小イメージでは黙って else に行き、常に PASS になる。

再利用の定性的証拠は第四節の数字と一致する:`audit-fake-ai-server.py` は **7 本**のスクリプトで再利用;
`wave5-pty-drive.cpp` は **5 本以上**のコンパイルで再利用され、`[ -x "$DRIVE" ] ||` でコンパイルをキャッシュしている;
wave4 → wave5 のドライバーは**書き直しではなく拡張**(diff は 1 行変更、343 行追加、wave4 の 281 行はそのまま維持)。

**これらの挙動はすべてゴールガードのないバージョンで起きた。** 唯一の制約は[ブリーフ](../reference/glossary.md#需求确认书)にある
10 条の判定可能な受け入れ基準だった。これが示すのは:**「完了」を判定可能な形で書くこと自体が、自己監査と自己開示を誘発する**ということだ。
ゴールガードの限界価値はこれをベースラインとして測るべきであり、ゼロを基準にしてはいけない。

ただし次節が示すとおり:**自己監査は検証技術としては非常に強いが、最も重要な 1 条の最終判定を誤った。**

!!! warning "ここでいう「監査員」はジャッジではない"
    第七節・第八節でいう独立監査員は、**コーディネーターが自発的に派遣した subagent** であり、
    [ゴールガード](../reference/glossary.md#目标看守)の[ジャッジ](../reference/glossary.md#判定者)ではない ——
    この run にはそもそもゴールガードがない。読み味は似ているが、やっていることは違う:監査員は事後の振り返り、
    ジャッジは各ターン終了時の[判定](../reference/glossary.md#判定)ゲートだ。

## 八、自己採点は正しかったか —— 受け入れ 1 は誤判定 {#八它给自己打的分对吗--验收-1-判错了}

2 人目の独立監査員を派遣し、10 条の受け入れ基準をコードに対して一条ずつ判定させた。

**受け入れ 2–10 はすべて事実**で、コード上の証拠がある。練習モードでコードを挿入しない点は**構造的**な保証ですらある:
唯一の sink 決定点 `ai.h:117` + 唯一の着地 switch `app.cpp:590-615` + 4 つの early-return
`editor.cpp:679-683` であり、散らばった if ではない。自己監査で発見された P1–P4 も**すべて事実で、修正もすべて実装済み**
(P4 は半分事実:あの青の pair 行はデッドコードで、`ghostAttr()` はもともと `A_DIM` を通る)。

**しかし受け入れ 1 は誤判定だった。**

```text
基準の原文:  「単一の実行可能ファイルにコンパイルし、macOS ターミナルで直接実行できること」
納品された成果物: ELF 64-bit LSB pie executable, ARM aarch64, GNU/Linux
その判定:  通過
```

これは人間が自分の手で `file` を走らせて確認した。

隠していたわけではない —— `交付说明.md` §4 の見出しはまさに「最大の未検証リスク:macOS では一度も走らせていない」であり、
監査 §6 も macOS の未検証面を 6 つ列挙している。**リスクは開示したが、その事実を受け入れ 1 の判定に接続し直すことは一度もなかった**。
そして受け入れ 1 の文言が要求しているのは、まさにその事実だった。

### だがこれは「独立したジャッジが必要だ」という証拠ではない {#但这不是需要一个独立判定者的证据}

これを「だからゴールガードが要る」と読みたくなる。違うし、そう読むのは**先に矢を放って後から的を描く**行為だ ——
まさに前節で批判したばかりの動機づけられた推論そのものである。

**当時のバージョンのゴールガードは、デフォルト設定ではこの 1 条を高い確率で見逃した。** `judge()` はデフォルトで `can_run=False`、
ツールは `Read` / `Glob` / `Grep` のみ —— **`file` を走らせられない**。
ソースを読みに行き、`Makefile:25-38` に確かに Darwin 分岐があるのを見て「達成」と判定するだろう。自己監査とまったく同じ失敗だ。

### 本当の構造的事実 {#真正的结构性事实}

**受け入れ 1 は、この run の環境では原理的に検証不能だった。**

これが主張しているのは「成果物の macOS 上での挙動」であり、run 全体は Linux コンテナ内にある。
**コンテナ内で macOS バイナリを検証できるジャッジは存在しない**、自己監査だろうと独立だろうと。
問題は「誰が判定するか」ではなく、**この 1 条が普通の判定可能な基準として扱われ、そして判定されてしまったこと**にある。

### 監査員が追加で掘り出した 3 件(自己監査では未言及) {#审计员另外挖到的三条自审都没提}

- **`doTab()` のクォータ意味論**:`app.cpp:909` は `acceptGhost()` の後に無条件で `noteActivity()` → `gen_++`
  → クォータを再オープンする。したがって**Tab で受け入れるたびに 500ms 後に自動リクエストがもう一度発火する**。P1(アイドルで金を燃やす)の分析は
  `setMode` / `cancelInFlight` / `askNow` の 3 つのキャンセル点しか見ておらず、この最も高頻度な課金経路を見落としていた。
- 受け入れ 6 の「グレー」は 256 色ターミナルでのみ文字どおり成立する;8 色段は `A_DIM` に固定(暗くなるだけで、グレーではない)。
- `验收审计.md` §7 の小見出しは「9 条の受け入れ基準」と書いているが、表は 10 行ある —— 誤記だが、総評の表頭に出ている。

## この run で検証できなかったこと {#这一跑没能验证的}

- **ゴールガード**:この run はそれの導入前。コーディネーターは**自発的に**独立監査を組織し、検証技術は非常に堅かったが、
  最も重要な 1 条で誤判定した(第八節)。2 つの結論を一緒に記録すべきだ ——
  ブリーフに判定可能な基準を明記するだけで自己監査を誘発できるので、ゴールガードのベースラインはゼロではない;
  そして当時のデフォルト設定のゴールガードも**あの 1 条を見逃した**ので、それも万能薬ではない。
- **1M ウィンドウでの挙動**:18.6% しか使っておらず、境界に触れていない。
- **`DISABLE_AUTO_COMPACT=1` 下でのマイクロ compact の挙動**:全期間で compact が発火せず、依然として推測のまま。
