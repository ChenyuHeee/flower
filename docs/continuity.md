# 接续:同一个路径 = 同一段对话

> 在同一个目录再跑一次 `flower`,它接着上次说 —— **进程被 kill 也一样**。
> 你不需要知道 session 这个词,也不需要记住任何 id。

```bash
cd ~/proj && flower "写个 md 转 html 的脚本"     # 第一次
# …跑完,或者你按 Ctrl-C 走人,或者机器重启了

cd ~/proj && flower "顺便支持代码块高亮"          # 接着上次那段对话
cd ~/proj && flower                              # 什么都不说 = 接着做
cd ~/proj && flower --new "另一件事"              # 这次别接上次
```

---

## 在此之前丢的是什么

磁盘上其实什么都在:`runs/sessions.db` 有每个历史 session 的**完整** transcript,
`需求.md` / `目标.md` 是冻结件,代码就在工作区。

**丢的只有一行映射** —— "哪一步用了哪个 session"。它以前只活在内存的
`ctx["_sessions"]` 里,进程一退就没了。于是新进程起来,协调者是个失忆的新人:
它派过谁、试过哪些死路、为什么否掉某个方案,统统重来一遍。

[HT002](case-ht002.md) 里它绕了一小时去试编译 flag。换个进程,那一小时白走。

## 怎么做到的

`<run_dir>/lineage.json`,就这一个文件:

```json
{
  "workspace": "/Users/you/proj",
  "woke": 3,
  "steps": {"干活": "47395075-bec7-466e-80cd-f4d60b360235"}
}
```

`Workflow.run` 开跑前读它,某一步在里面有记录就 resume 那个 session。
**步骤名是跨进程稳定的键** —— 整件事成立就靠这个。

两条不变式:

* **每一步跑完立刻写盘**,不是退出时写。进程被 kill 正是要防的场景。
  写的时候先写 `.tmp` 再原子替换,半途被杀不会留下半份文件。
* **对不上就当没有,不报错。** 三种对不上:工作区路径变了(目录被拷走 ——
  HT001 就是从容器里拷出来的)、session 已经不在库里(删过 `sessions.db`)、
  血缘文件坏了。任何一种都静默退回"从头开始"。
  **接续是锦上添花,它失效不该拦住人干活。**

## 判定者永远是新会话

这一条是**构造上保证**的,不是靠记得。

判定者不是 `Step` —— 它是 `with_goal` 的 gate 里 `rt.run()` 直接派出去的
(见 [goal.md](goal.md)),从来不经过血缘那条路。所以它每一轮、每一次唤醒
都是全新的一双眼睛。

那正是它的全部价值:**它不知道干活的人试了多少次、有多辛苦,也就不会替它找理由。**
让它跟着接续,目标看守就退化成了自我审计。

`tests/lineage_offline.py` 第 4 节把这条钉死了。

## 唤醒时说的那句话,要落到三个地方

`flower "顺便支持代码块高亮"` 在用过的目录里,**不是新任务,是又说了一句话**。
它同时做三件事 —— 少一件都会静默失效:

| 落到哪 | 少了会怎样 |
|---|---|
| 追加进 `需求.md`(`## 唤醒时追加`) | 活不过步骤边界。下一步是新 session,只读冻结件 |
| 当作干活那步的 prompt | 协调者根本收不到 |
| **触发重新推导 `目标.md`** | 判定者读的还是老清单,**新加的事做没做完根本不进判定** |

第三条最容易漏。判定者只读冻结的 `目标.md`,你中途加的东西它看不见 ——
不重推的话它会按老清单判"达成",而你要的那件事压根没验。
代价是每次追加多跑一次设目标([HT002](case-ht002.md) 实测 $0.41 / 3 分钟)。

**什么都不说地唤醒**(直接回车)则不追加、不重推,一分钱不多花。

### 接续时发的不是同一句话

`Step.resume_prompt` 管这个。对方的上下文里**已经有**确认书、目标、上次干到哪了,
再把「照这份需求做:<整份确认书>」原样发一遍是纯噪音,更糟的是它会被读成
"需求变了,重新看一遍"。

不给 `resume_prompt` 就沿用 `prompt` —— 有些步骤本来就该重发全文
(设定目标重推清单时,它要的正是那份完整确认书)。

## 唤醒时先报一行

```
↩ 在 ~/explore/test-ide 接上上次  需求已确认 · 目标 15 条 · 干活上下文 80.2K · 第 3 次唤醒

━━ 干活 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━  3/3  ↩ 接上次 · 第 3 次唤醒
```

不报的话"它到底记不记得"完全不可感知,而那正是这一层的全部价值。

**上下文那个数字是刻意摆出来的** —— 理由见下一节。

## 代价:上下文会一直涨,而且没有尽头

这是接续的固有代价,不是 bug。

[HT001](case-ht001.md) 单步跑十小时,主线程上下文 28.7K → **185.9K** 单调涨,
斜率约 2.2K/轮。永久接续意味着某天会撞窗口。

flower 不为此新加压缩机制,现有两层够用:

1. **`trim`**(`flower --no-trim` 可关,`go` 路径默认开)—— resume 时把旧的大工具
   结果换成文件指针,内容没丢,只是不常驻
2. 再往上是 SDK 自己的 compact

**所以唤醒那行必须报上下文数字**:人看得见,才有机会在撞墙之前自己决定 `/new`。

顺带一条:`--rounds`(干活总轮数)**每次唤醒重置**。这是有意的 —— 新的一次唤醒
是新的意图,不该继承上次用掉的轮数。

## 重开一件事

```bash
flower --new "另一件事"
```

或者在唤醒提示符里直接打 `/new`:

```
接着上次? 直接回车 = 接着做;也可以说点新的;/new = 重开一件事(Ctrl-C 退出)
> /new
要做什么? 一句话就够,回车开始(Ctrl-C 退出)
> …
```

**归档,不删。** `需求.md`、`目标.md`、`lineage.json` 一起移进
`notes/archive/<时间戳>/`。三样是同一段历史的三个面,只收其中一部分会留下
"目标还在但对话没了"这种半截状态。

`sessions.db` 不动 —— 它是档案,里面每一段 transcript 都还能查。

## 关掉

```python
Workflow(..., continuous=False)     # 老行为:每个进程都是全新会话
```

自己写 workflow 时才需要碰它。`flower` 那条路径默认开。

## 顺带修掉的:`manifest.json` 以前会被覆盖

`_persist` 写的是本进程的 `self.results`,而它每次从空列表开始、**从来不读回来** ——
所以在同一个 `run_dir` 跑第二次,第一次的账被整个冲掉。

以前这只是"分析数据丢了";有了接续,这份清单变成事后查 session_id 的唯一去处,
不能再丢。现在是**追加**,每行带 `run` 字段(进程启动时刻)可以按运行分组。

## API

| 东西 | 说明 |
|---|---|
| `Lineage.open(run_dir, workspace)` | 读血缘。对不上返回空的,不抛 |
| `Lineage.remember(step, sid)` | 记一条并立刻落盘 |
| `Lineage.archive(into, extra=[...])` | `--new` 走的那条路 |
| `wake_state(workspace, run_dir=…)` | **只读**探测:这个目录用过没有、目标几条、唤醒过几次 |
| `Workflow.continuous` | 默认 `True` |
| `Step.resume_prompt` | 接续时说什么。不给就沿用 `prompt` |
| `Runtime.has_session(sid)` / `.context_of(sid)` | 还在不在 / 最后一轮多大上下文 |

## 排错

| 症状 | 看哪 |
|---|---|
| 每次都从头开始 | `runs/lineage.json` 在不在?里面的 `workspace` 和你现在的路径一致吗 |
| 换了目录之后不接续了 | 有意的。`project_key` 由工作区路径推导,旧 session 在新位置查不到 |
| 想重开但不想丢历史 | `--new` 是归档不是删除,东西在 `notes/archive/` |
| 上下文太大了 | 唤醒那行会报。`/new` 重开,或者 `-T` 确认 trim 开着 |
| 加了新需求但判定没管 | 看 `需求.md` 末尾有没有 `## 唤醒时追加`,以及那次跑有没有走「设定目标」 |
