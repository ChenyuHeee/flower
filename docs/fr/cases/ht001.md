# HT001 · Écrire un IDE terminal depuis zéro

Le 2026-09-07, un agent a écrit sous flower, à partir de rien, un IDE C/C++ mono-fichier tournant dans un terminal macOS.
Il a tourné 10.4 heures d'affilée, dépensé $171.62, et rendu 12,212 lignes de code produit et 13,291 lignes de tests ;
le réseau est tombé une fois en cours de route, il a repris tout seul jusqu'au bout. Cette page n'est pas une vitrine —
c'est la mise à l'échelle réelle de chacune des affirmations du framework,
**y compris les deux qui n'ont pas tenu** : « le coordinateur ignore souvent les restrictions de permissions » est faux, et dans sa propre recette il y a un critère qu'il a mal jugé.

L'enregistrement complet (avec 19MB de transcript) est sur [ChenyuHeee/cppide](https://github.com/ChenyuHeee/cppide).
Chaque chiffre ci-dessous est calculé par `tools/analyze_run.py` à partir de `sessions.db`, reproductible :

```bash
python tools/analyze_run.py /path/to/cppide/runs
```

!!! note "D'où viennent les chiffres de cette page"
    Le `runs/` de HT001 est dans le dépôt cppide ci-dessus, **pas dans le dépôt flower**. Les chiffres de cette page sont donc
    **reportés tels quels** depuis l'enregistrement de l'époque ; ils n'ont pas été recalculés sur `sessions.db` au moment d'écrire cette page —
    pour les recalculer, il faut d'abord cloner cppide, puis lancer la commande ci-dessus.
    [HT002](ht002.md) fait l'inverse : l'enregistrement brut est dans ce dépôt, les chiffres de cette page-là ont été recalculés un à un,
    et les deux écarts sont indiqués directement sur la page.

## I. Économie du contexte : 94.8 % du terrain n'entre jamais dans le thread principal {#一上下文经济学948-的现场没进主线程}

C'est l'affirmation centrale du framework — le [coordinateur](../reference/glossary.md#协调者) ne contient que les décisions,
le terrain descend dans les subagents et sur le disque. Le mécanisme est décrit dans [Économie du contexte](../guide/context.md).

| | Thread principal | subagent | part subagent |
|---|---|---|---|
| Tours de modèle | 70 | 3.0K | **97.7 %** |
| Caractères de contenu | 200.1K | 3.6M | **94.8 %** |
| Appels d'outils | **32** | **1,893** | —— |

Ce run a dépêché 23 subagents, avec un maximum de 184,377 tokens de sortie, une médiane de 72,197 et un minimum de 11,684.

**Sur 1,893 appels d'outils sur le terrain (1,034 Bash / 471 Read / 258 Edit / 126 Write), seuls 32 sont entrés dans le champ de vision du coordinateur
— 59:1.** En moyenne, chaque fois qu'un subagent est dépêché, 82 appels d'outils restent invisibles pour lui.

Les petits tests antérieurs mesuraient 83 % ; à l'échelle réelle, c'est **94.8 %**. Plus l'échelle grandit, plus la répartition rapporte —
parce que le coût du [brief de tâche](../reference/glossary.md#任务书) et du rapport de retour est **fixe par dépêche**,
tandis que le terrain tenu à l'écart croît avec la complexité de la tâche.

## II. Courbe de contexte : on sait enfin où est la limite du « long-horizon » {#二上下文曲线第一次知道长程的上限在哪}

Pour chaque message assistant, `input + cache_read + cache_creation` est exactement le contexte vu par le modèle à ce tour :

```text
第 1轮   28.7K   ← 启动地板(此前实测约 34k,对上了)
第20轮   35.2K
第35轮  108.6K
第50轮  158.2K
第70轮  185.9K   ← 结束
```

- Croissance monotone sur 70 tours, pente d'environ **2.2K/tour**
- **Aucune compaction sur tout le run** (`DISABLE_AUTO_COMPACT=1` ; le seul recul est l'enregistrement vide du tour de coupure réseau)
- **18.6 %** de la fenêtre de 1M consommés

**En extrapolant cette pente, le mur est atteint vers 440 tours.** Ces 70 tours ont produit 12K lignes de code,
donc la limite réelle du [long-horizon](../reference/glossary.md#长程) dans la forme actuelle est d'environ **6 fois** ce run.
C'est un chiffre sur lequel on peut décider ; avant, on ne pouvait que deviner.

Pour le dépasser, il faut rendre la croissance du thread principal **sous-linéaire** — davantage sur le disque, moins dans la conversation.

## III. 96.1 % de hits de cache — $171.62 ne tient que grâce à ça {#三缓存命中-961--17162-能成立全靠它}

```text
总输入 299.4M token
  命中缓存  287.5M  (96.1%)
  新建缓存   11.8M
  未缓存      6.2K
输出 2.3M(其中 thinking 653.9K)
```

299M tokens d'entrée n'ont coûté que $171 parce que 96 % passent au tarif cache.

**Corollaire : l'économie d'un run long-horizon repose sur le taux de hits de cache, et ce taux dépend de la stabilité du préfixe de contexte.**
Toute optimisation qui « réorganise le contexte » — déplacer l'ancien contenu, insérer un nouveau prompt système en tête — casse le cache,
et les tokens économisés ne compensent probablement pas la remise de cache perdue. Ça n'avait jamais été mesuré ; maintenant on a le chiffre.

C'est aussi une raison collatérale pour laquelle flower utilise le [handoff](../reference/glossary.md#换代) plutôt que la compaction :
le handoff **ouvre une nouvelle session et reconstruit le cache depuis zéro**, le préfixe reste stable à l'intérieur d'une génération.

## V. Le coordinateur s'est vu refuser 1 appel direct — et c'était la faute de la liste blanche {#五协调者动手被拒-1-次而且是白名单的错}

Le soupçon de départ était : « le coordinateur ignore souvent les restrictions de permissions et déclenche une masse d'appels refusés ». La mesure a détruit cette prémisse.

**Sur 32 appels d'outils, 1 refus (3.1 %)**, et ce refus était :

```bash
which g++ clang++ make pkg-config 2>&1; echo ---; ls /usr/include/ncurses.h 2>&1; echo ---; ls /work/runs
```

Décision segment par segment : `echo` autorisé, `ls` autorisé, **`which` bloqué — il n'est pas dans la table des
[commandes éphémères](../reference/glossary.md#一次性命令)**.

La commande entière est purement en lecture, c'est une sonde d'environnement standard. **Le modèle a fait exactement ce qu'il fallait, c'est la liste blanche qui était incomplète**,
ce qui l'a forcé à payer un démarrage de subagent (environ 4.3k tokens) pour un simple `which g++`.

Corrigé : ajout de `which` / `command -v` / `type` / `whereis` / `uname` / `arch` / `locale` / `nproc` /
`getconf` / `sw_vers`. `command` et `type` **ne sont autorisés que sous leur forme d'interrogation** —
un `command rm -rf /` nu est une exécution, oublier le `-v` revient à ouvrir une porte dérobée ;
7 cas adverses dans `tests/glance.py` montent la garde.

**Ce qu'il faut retenir ici n'est pas le patch, c'est la méthode.** Une discussion d'architecture qui a duré longtemps avait une prémisse de départ à 1/32 sur des données réelles,
avec en plus une attribution inversée — le problème n'était pas le modèle, mais la liste blanche. **Mesurer d'abord.**

Le manifeste enregistre `attempts=2 / resumed=True / ok=True`. **10 heures de travail n'ont pas été refaites depuis le début.**
Avant ça, la [résilience](../reference/glossary.md#韧性) restait classée « toujours non vérifiée » — couper le réseau demande un sudo sur `hosts`, personne n'a envie de faire ça pendant un vrai run.

Ce message « API Error » synthétique a été retiré au chargement par `PruningSessionStore`, **le modèle ne l'a pas vu** —

Deux problèmes exposés (voir issue #2) :

1. La reprise a lieu **au niveau du framework** et non du transport. Le prix est un rejeu de tout le contexte, et ce contexte était volumineux.
2. **Le subagent interrompu a perdu son travail à moitié fait.** Le resume sauve le thread principal ;
   la reprise après interruption au niveau subagent est un autre problème.

## VII. Son auto-vérification est-elle réelle ? {#七它的自我验证是真的吗}

C'est l'endroit le plus suspect : un agent qui écrit ses propres tests, les lance et déclare le succès, ça vire vite à la formalité.

Après coup, un subagent d'audit indépendant a été dépêché, qui a lu statiquement les 58 scripts et les 22 livrables. Conclusion : **c'est réel, et d'une rigueur rare** :

- **0 assertion toujours vraie.** Aucun motif du type `[ 1 = 1 ]` dans tout le dépôt.
- 8 occurrences de `|| true`, **7 légitimes** (`grep -c` renvoie 1 sans correspondance, filet de sécurité `ulimit`, etc.).
- **Ce qui est jugé, c'est le comportement, pas l'existence d'un fichier.** `audit-idle-cost.sh:53` laisse l'IDE tourner à vide 60 secondes dans un pty,
  compte les requêtes réellement reçues par un faux serveur local, et ne PASS qu'à `-le 2`. `fix-p1-idle-verify.sh:100-110` va plus loin :
  il assert à la fois exactement 1 requête au repos **et** que le ghost reste affiché — pour éviter qu'« un changement de limitation de débit tue la fonctionnalité au passage ».
- **De vrais processus fils.** `wave5-pty-drive.cpp:316` lance réellement la TUI avec `forkpty` ; `audit-fake-ai-server.py`
  est un vrai serveur socket, avec cinq injections de pannes `/err500 /err401 /badjson /drop /slow` ;
  tous les chemins IA forcent le vidage de `CPPIDE_API_KEY`.

Deux choses ont dépassé les attentes.

**Il a fait un contrôle positif et négatif de son propre vérificateur.** `验收审计.md:29-34` : d'abord injecter `ZZZ_NEVER_APPEARS_ZZZ` pour confirmer que le pilote FAIL,
puis la vraie chaîne pour confirmer qu'il PASS — pour éviter « d'auditer avec une machine truquée qui PASS toujours ». **C'est vérifier le vérificateur lui-même.**

**Il a divulgué spontanément ses propres assertions faibles.** Le `for m in $must` de `wave5-b4-ai-states.sh:114`
découpe `"AI 错误 请求超时"` sur les espaces en trois sous-chaînes greppées séparément, alors que `AI` et `错误` apparaissent forcément sur n'importe quel écran —
nominalement « 3 critères passés », en réalité un seul discriminant. **C'est lui-même qui l'a écrit dans `验收审计.md:576-582`**,
ce n'est pas l'auditeur qui l'a déterré.

Dans le même genre : `wave5-verify.sh:296-302` explique en 7 lignes de commentaire pourquoi B3b a été rétrogradé en SKIP
(assertion de timing sur le dernier écran, sans rapport avec le code produit), en précisant « la logique de verdict et les marges de tolérance n'ont pas bougé d'un caractère » ;
`:236-238` consigne qu'il **a découvert et corrigé une fausse assertion qu'il avait lui-même écrite plus tôt** —
`if pgrep ...` passait silencieusement au else dans une image minimale sans `pgrep`, ce qui donnait un PASS permanent.

Les preuves qualitatives de réutilisation collent aux chiffres de la section IV : `audit-fake-ai-server.py` est réutilisé par **7** scripts ;
`wave5-pty-drive.cpp` est réutilisé par **5+** compilations, avec mise en cache de la compilation via `[ -x "$DRIVE" ] ||` ;
le pilote wave4 → wave5 est une **extension et non une réécriture** (le diff ne change qu'1 ligne et en ajoute 343, les 281 lignes de wave4 restent intactes).

**Tous ces comportements sont apparus sur une version sans gardien d'objectif.** La seule contrainte était les 10 critères d'acceptation décidables du [brief](../reference/glossary.md#需求确认书).
Cela montre que **mettre le « terminé » sous forme décidable suffit à induire l'auto-audit et l'auto-divulgation.**
La valeur marginale du gardien d'objectif doit se mesurer contre cette base-là, pas contre zéro.

Mais la section suivante le précise : **l'auto-audit est très fort sur la vérification technique, et pourtant il s'est trompé sur le verdict final du critère le plus important.**

!!! warning "L'« auditeur » ici n'est pas le juge"
    L'auditeur indépendant des sections VII et VIII est un **subagent dépêché spontanément par le coordinateur**, pas le
    [juge](../reference/glossary.md#目标看守) du [gardien d'objectif](../reference/glossary.md#判定者) —
    ce run n'avait tout simplement pas de gardien d'objectif. Les deux se ressemblent à la lecture, mais font autre chose : l'auditeur est un post-mortem,
    le juge est la porte de [verdict](../reference/glossary.md#判定) en fin de chaque tour.

## VIII. Sa propre note est-elle juste ? — le critère d'acceptation 1 a été mal jugé {#八它给自己打的分对吗--验收-1-判错了}

Un deuxième auditeur indépendant a été dépêché, pour juger les 10 critères d'acceptation un à un face au code.

**Les critères 2–10 sont tous exacts**, les preuves dans le code y sont. Le fait que le mode entraînement n'insère pas de code est même une garantie **structurelle** :
un unique point de décision de sink `ai.h:117` + un unique switch d'application `app.cpp:590-615` + quatre early-return
`editor.cpp:679-683`, pas des `if` éparpillés. Les P1–P4 trouvés par son auto-audit sont **tous exacts et tous corrigés**
(P4 à moitié exact : cette ligne de pair bleue est du code mort, `ghostAttr()` passait déjà par `A_DIM`).

**Mais le critère 1 a été mal jugé.**

```text
标准原文:  "编译出一个独立可执行文件,在 macOS 终端直接运行"
交付的产物: ELF 64-bit LSB pie executable, ARM aarch64, GNU/Linux
它的判定:  通过
```

Ce point a été vérifié à la main avec `file`.

Il n'a rien caché — le titre du §4 de `交付说明.md` est littéralement « le plus gros risque non vérifié : macOS n'a jamais été essayé »,
et le §6 de l'audit liste six surfaces macOS non vérifiées. **Il a divulgué le risque, mais n'a jamais reconnecté ce fait au verdict du critère 1**,
alors que l'exigence littérale du critère 1 portait exactement là-dessus.

### Mais ce n'est pas une preuve qu'« il faut un juge indépendant » {#但这不是需要一个独立判定者的证据}

Il est facile de lire ce point comme « donc il faut un gardien d'objectif ». C'est faux, et le lire ainsi revient à **tirer la flèche puis dessiner la cible** —
exactement le raisonnement motivé critiqué à la section précédente.

**Le gardien d'objectif de l'époque, en configuration par défaut, aurait très probablement raté ce point lui aussi.** `judge()` a `can_run=False` par défaut,
et pour outils uniquement `Read` / `Glob` / `Grep` — **il ne peut pas lancer `file`**.
Il irait lire les sources, verrait que `Makefile:25-38` contient bien une branche Darwin, et jugerait « atteint ». Exactement le même échec que l'auto-audit.

### Le vrai fait structurel {#真正的结构性事实}

**Le critère 1 est tout simplement invérifiable dans l'environnement de ce run.**

Il porte sur « le comportement de l'artefact sur macOS », alors que tout le run se déroule dans un conteneur Linux.
**Aucun juge ne peut vérifier un binaire macOS depuis le conteneur**, qu'il soit auto-audit ou indépendant.
Le problème n'est pas « qui juge », c'est que **ce critère a été traité comme un critère décidable ordinaire, puis jugé**.

### Trois points supplémentaires trouvés par l'auditeur (que l'auto-audit n'avait pas mentionnés) {#审计员另外挖到的三条自审都没提}

- **Sémantique du quota dans `doTab()`** : `app.cpp:909` appelle inconditionnellement `noteActivity()` après `acceptGhost()` → `gen_++`
  → réouverture du quota, donc **chaque acceptation par Tab redéclenche une requête automatique 500ms plus tard**. L'analyse de P1 (consommation au repos)
  n'avait examiné que les trois points d'annulation `setMode` / `cancelInFlight` / `askNow`, et a raté ce chemin de dépense, le plus fréquent.
- Le « gris » du critère 6 n'est littéralement vrai que sur un terminal 256 couleurs ; le palier 8 couleurs est figé à `A_DIM` (assombri, pas gris).
- Le sous-titre du §7 de `验收审计.md` dit « 9 critères d'acceptation » alors que le tableau en contient 10 — coquille, mais dans l'en-tête du tableau de synthèse.

## Risques résiduels {#遗留风险}

**La cible de livraison est macOS, mais toute la vérification s'est faite dans un conteneur Debian aarch64, zéro vérification sur une vraie machine macOS.**
C'est l'effet secondaire réel de l'isolation par conteneur : pour la sécurité on l'enferme sous Linux, alors qu'il doit livrer pour macOS.
Le §10.24 du README du projet consigne honnêtement ce point et liste 4 risques, mais sans boucler la boucle.

Cette lacune a été comblée plus tard par [HT002](ht002.md) — ce run-là consiste précisément à installer ce binaire sur un vrai macOS.

Bénéfice inattendu : dans le conteneur, seul `/work` est visible, donc dans les 19MB de transcript
**le nom d'utilisateur hôte `/Users/hechenyu` ne fuite nulle part** (`/work` apparaît 11,495 fois).
L'[isolation](../reference/glossary.md#隔离) a isolé les chemins par la même occasion.

## Ce que ce run n'a pas pu vérifier {#这一跑没能验证的}

- **Le gardien d'objectif** : ce run est antérieur à son ajout. Le coordinateur a organisé **spontanément** un audit indépendant, techniquement très solide,
  mais il s'est trompé sur le critère le plus important (section VIII). Les deux conclusions vont ensemble —
  écrire des critères décidables dans le brief suffit à induire l'auto-audit, donc la base du gardien d'objectif n'est pas zéro ;
  et le gardien d'objectif en configuration par défaut de l'époque **aurait raté ce même critère**, donc ce n'est pas une panacée non plus.
- **Le comportement dans la fenêtre de 1M** : seulement 18.6 % utilisés, la limite n'a pas été touchée.
- **Le comportement de la micro-compaction sous `DISABLE_AUTO_COMPACT=1`** : aucune compaction déclenchée de tout le run, ça reste une inférence.

## Ce que ce run a changé dans le framework {#这一跑改了框架什么}

| Constat | Changement effectué |
|---|---|
| `which` bloqué (section V) | `is_ephemeral()` complété avec `which` / `command -v` / `type` / `whereis` / `uname` / `arch` / `locale` / `nproc` / `getconf` / `sw_vers` ; 7 cas adverses ajoutés à `tests/glance.py` pour verrouiller la forme d'interrogation de `command` / `type` |
| Critère 1 mal jugé (section VIII) | Le 1er point de `JUDGE_RULES` devient : **on juge l'artefact, pas les sources** — l'exécuter si c'est possible, et sinon inspecter l'artefact lui-même (plateforme, taille, chargement possible) |
| « J'ai divulgué le risque » a valu un verdict de réussite | Le verdict doit distinguer « pas fait » de « invérifiable ici ». `Verdict.parse` reconnaît désormais **无法验证 / 没法验证 / 无法判定** comme un troisième état `unreachable` → **remonter la question à l'humain, jamais de verdict de réussite** |
| Le critère 1 est invérifiable par principe dans cet environnement | L'étape de définition d'objectif exige désormais de **marquer sur le champ les points invérifiables dans cet environnement**, au lieu de le découvrir une fois le travail fini |
| Reprise réseau au niveau framework, travail subagent à moitié fait perdu (section VI) | Consigné comme issue #2, non bouclé |

Les trois premiers points ont été confrontés à une vraie API pour la première fois dans [HT002](ht002.md), où « juger l'artefact et non les sources » a sauvé la mise une fois —
mais cette même règle a produit un nouvel échec.
