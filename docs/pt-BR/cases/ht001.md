# HT001 · Escrever um IDE de terminal do zero

Em 2026-09-07, um agent rodando sob flower escreveu do zero um IDE de arquivo único para C/C++ que roda no terminal do macOS.
Ele rodou 10.4 horas seguidas, gastou $171.62 e entregou 12,212 linhas de código de produto e 13,291 linhas de teste;
perdeu a rede uma vez no meio e retomou sozinho até o fim. Esta página não é uma vitrine de resultados — é cada afirmação do framework medida em escala real,
**incluindo as duas que não se sustentaram na medição**: a de que o coordenador "ignora com frequência as restrições de permissão" é falsa, e um dos critérios de aceitação que ele julgou sobre si mesmo foi julgado errado.

O registro completo (incluindo 19MB de transcript) está em [ChenyuHeee/cppide](https://github.com/ChenyuHeee/cppide).
Cada número abaixo é calculado por `tools/analyze_run.py` a partir de `sessions.db` e é reproduzível:

```bash
python tools/analyze_run.py /path/to/cppide/runs
```

!!! note "De onde vêm os números desta página"
    O `runs/` do HT001 está naquele repositório cppide acima, **não no repositório do flower**. Então os números desta página foram
    **transportados literalmente** do registro de execução da época; ao escrever esta página ninguém recalculou nada contra o `sessions.db` —
    para recalcular, é preciso primeiro clonar o cppide e então rodar aquele comando acima.
    O [HT002](ht002.md) é o oposto: o registro bruto está neste repositório, os números daquela página foram recalculados item por item,
    e os dois pontos que não fecharam estão escritos direto na página.

## 1. Economia de contexto: 94.8% do trabalho de campo nunca entrou na thread principal

Esta é a afirmação central do framework — o [coordenador](../reference/glossary.md#协调者) carrega apenas decisões,
e o trabalho de campo afunda para os subagents e para o disco. O mecanismo em si está em [economia de contexto](../guide/context.md).

| | Thread principal | Subagent | Fração no subagent |
|---|---|---|---|
| Turnos de modelo | 70 | 3.0K | **97.7%** |
| Caracteres de texto | 200.1K | 3.6M | **94.8%** |
| Chamadas de ferramenta | **32** | **1,893** | —— |

Esta execução despachou 23 subagents; o maior produziu 184,377 tokens de saída, a mediana 72,197 e o menor 11,684.

**Das 1,893 chamadas de ferramenta que fizeram o trabalho (1,034 Bash / 471 Read / 258 Edit / 126 Write), só 32 entraram no campo de visão do coordenador
— 59:1.** Em média, a cada despacho, 82 chamadas de ferramenta ficam invisíveis para ele.

Um teste anterior em escala pequena mediu 83%; em escala real é **94.8%**. Quanto maior a escala, maior o retorno da divisão de trabalho —
porque o custo do [brief de tarefa](../reference/glossary.md#任务书) e da resposta de volta é **fixo por despacho**,
enquanto o trabalho de campo mantido do lado de fora cresce com a complexidade da tarefa.

## 2. A curva de contexto: a primeira vez que se soube onde está o teto do "longo horizonte"

O `input + cache_read + cache_creation` de cada mensagem de assistant é exatamente o contexto que o modelo viu naquele turno:

```text
turno  1   28.7K   ← piso de inicialização (medições anteriores davam ~34k, confere)
turno 20   35.2K
turno 35  108.6K
turno 50  158.2K
turno 70  185.9K   ← fim
```

- Crescimento monótono ao longo de 70 turnos, inclinação de cerca de **2.2K/turno**
- **Nenhum compact aconteceu** em todo o percurso (`DISABLE_AUTO_COMPACT=1`; a única queda é o registro vazio do turno em que a rede caiu)
- Consumiu **18.6%** da janela de 1M

**Extrapolando por essa inclinação, a parede está em cerca de 440 turnos.** Estes 70 turnos produziram 12K linhas de código,
então o teto real do [longo horizonte](../reference/glossary.md#长程) na forma atual é cerca de **6 vezes** esta execução.
É um número com que se pode decidir algo; antes só se podia adivinhar.

Para romper esse teto, o crescimento da thread principal precisa ser **sublinear** — mais coisa afundada no disco, menos coisa retida na conversa.

## 3. Cache hit de 96.1% — é só por causa dele que $171.62 se sustenta

```text
entrada total 299.4M tokens
  hit de cache   287.5M  (96.1%)
  cache criado    11.8M
  sem cache        6.2K
saída 2.3M (dos quais thinking 653.9K)
```

299M tokens de entrada custaram apenas $171, porque 96% foram pelo preço de cache.

**Corolário: a economia de uma execução de longo horizonte se apoia na taxa de hit de cache, e a taxa de hit depende da estabilidade do prefixo do contexto.**
Qualquer otimização que "reorganize o contexto" — mover conteúdo antigo para outro lugar, inserir um novo trecho de system prompt no começo — fura o cache,
e os tokens economizados podem ficar muito abaixo do desconto de cache perdido. Isso nunca havia sido medido; agora há número.

Esse é também um motivo colateral para o flower usar [handoff](../reference/glossary.md#换代) em vez de compact:
handoff **abre uma sessão nova e reconstrói o cache do zero**, e o prefixo fica estável dentro de uma geração.

## 4. Reuso da bancada: 61 scripts, nenhum escrito e jogado fora

A afirmação da [bancada](../reference/glossary.md#工作台) é "escreva o script uma vez, depois só rode, nunca reescreva".
A verificação não é perguntar ao agent, é contar quantas vezes os scripts em `.flower/scripts/` aparecem no transcript sendo escritos com Write/Edit e sendo executados com Bash:

```text
61 scripts: escritos 95 vezes, executados 331 vezes
com mais de 1 execução (realmente reusados): 56, ou seja 92%
escritos mas nunca executados: 0
razão execução/escrita 3.48
```

`wave5-verify.sh` foi escrito 5 vezes e rodado 45 vezes — polido iterativamente e depois usado repetidamente, exatamente a forma desejada.
**Nenhum script foi escrito e jogado fora.**

## 5. O coordenador teve 1 chamada negada — e o erro era da allowlist

A suspeita antes de medir era: "o coordenador ignora com frequência as restrições de permissão e dispara um monte de chamadas negadas". A medição derrubou essa premissa.

**Das 32 chamadas de ferramenta, 1 foi negada (3.1%)**, e essa uma foi:

```bash
which g++ clang++ make pkg-config 2>&1; echo ---; ls /usr/include/ncurses.h 2>&1; echo ---; ls /work/runs
```

Julgamento segmento por segmento: `echo` liberado, `ls` liberado, **`which` bloqueado — ele não está na tabela de
[comandos efêmeros](../reference/glossary.md#一次性命令)**.

O comando inteiro é puramente somente-leitura, uma sondagem de ambiente padrão. **O modelo agiu perfeitamente certo; a allowlist estava incompleta**,
e isso o obrigou a pagar o custo de inicialização de um subagent (cerca de 4.3k tokens) por um único `which g++`.

Já corrigido: foram adicionados `which` / `command -v` / `type` / `whereis` / `uname` / `arch` / `locale` / `nproc` /
`getconf` / `sw_vers`. `command` e `type` **só são liberados na forma de consulta** —
um `command rm -rf /` pelado é execução, e omitir aquele `-v` equivale a abrir uma porta dos fundos;
há 7 amostras adversariais em `tests/glance.py` guardando isso.

**O que mais vale registrar aqui não é o patch, é o método.** Uma discussão de arquitetura que se arrastou por muito tempo tinha como premissa inicial algo que nos dados reais é 1/32,
e com a atribuição invertida — o problema não estava no modelo, estava na allowlist. **Meça antes de falar.**

## 6. Retomada depois da queda de rede: validada por uma falha real pela primeira vez

```text
01:52:40  tool_result: "Agent terminated early due to an API error"   ← um subagent foi interrompido
01:55:41  assistant:   "API Error: ENOTFOUND"                          ← a thread principal recebeu
          ↓  a sonda ficou pendurada esperando a rede voltar
          resumed=True, retomou a mesma sessão e rodou mais de 8 horas até concluir
```

O manifest registra `attempts=2 / resumed=True / ok=True`. **10 horas de trabalho não foram refeitas do zero.**
Até então, a [resiliência](../reference/glossary.md#韧性) estava pendurada em "ainda não verificada" — cortar a rede exige sudo e editar hosts, e ninguém quer fazer isso durante uma execução real.

Aquela mensagem sintética "API Error" foi retirada pelo `PruningSessionStore` no load, **o modelo não a viu** —
o design do [prune](../reference/glossary.md#剪除) também foi validado pela falha real, de carona.

Dois problemas expostos (veja a issue #2):

1. A recuperação acontece na **camada do framework**, não na camada de transporte. O preço é reproduzir todo o contexto de novo, e naquele momento o contexto era grande.
2. **O subagent interrompido perdeu o trabalho pela metade.** O resume salva a thread principal;
   recuperação de interrupção no nível do subagent é outro problema.

## 7. A auto-verificação dele é real?

Este é o ponto que mais merece desconfiança: o agent escreve os próprios testes, roda os próprios testes e declara aprovação — é fácil virar teatro.

Depois do fato, um subagent de auditoria independente foi despachado e leu estaticamente os 58 scripts e as 22 entregas. A conclusão é que **é real, e com um rigor incomum**:

- **Zero asserções tautológicas.** Em todo o repositório não existe nenhum padrão do tipo `[ 1 = 1 ]`.
- `|| true` aparece 8 vezes, **7 delas legítimas** (`grep -c` retornando 1 sem match, fallback de `ulimit` e afins).
- **O que se julga é comportamento, não existência de arquivo.** `audit-idle-cost.sh:53` deixa o IDE ocioso dentro de um pty por 60 segundos,
  conta quantas requisições o servidor falso local realmente recebeu, e só dá PASS com `-le 2`. `fix-p1-idle-verify.sh:100-110` vai além:
  afirma que a ociosidade dispara exatamente 1 vez **e** afirma que o ghost continua sendo exibido — evitando que "a mudança de rate limit mate a funcionalidade junto".
- **Processos filhos de verdade.** `wave5-pty-drive.cpp:316` usa `forkpty` para rodar a TUI de fato; `audit-fake-ai-server.py`
  é um servidor de socket real, com cinco tipos de injeção de falha `/err500 /err401 /badjson /drop /slow`;
  todos os caminhos de AI forçam `CPPIDE_API_KEY` vazio.

Duas coisas passaram das expectativas.

**Ele fez controle positivo e negativo do próprio verificador.** `验收审计.md:29-34`: primeiro alimenta `ZZZ_NEVER_APPEARS_ZZZ` para confirmar que o driver dá FAIL,
depois alimenta a string real para confirmar que dá PASS — evitando "auditar com uma máquina falsa que sempre dá PASS". **Isso é verificar o verificador.**

**Ele mesmo revelou a própria asserção fraca.** O `for m in $must` em `wave5-b4-ai-states.sh:114`
quebra `"AI 错误 请求超时"` por espaços em três substrings e faz grep em cada uma, e `AI` e `错误` aparecem inevitavelmente em qualquer tela —
nominalmente "3 checagens passaram", na prática só 1 tem poder de discriminação. **Essa foi ele mesmo que escreveu em `验收审计.md:576-582`**,
não foi o auditor que descobriu.

Na mesma linha: `wave5-verify.sh:296-302` usa 7 linhas de comentário para explicar por que a checagem B3b foi rebaixada a SKIP
(asserção de temporização da última tela, sem relação com o código de produto), e anota que "a lógica de julgamento e a faixa de tolerância não tiveram uma palavra alterada";
`:236-238` registra que ele **encontrou e corrigiu uma asserção falsa que ele mesmo havia escrito antes** —
`if pgrep ...` cai silenciosamente no else em imagens enxutas sem `pgrep`, virando um PASS permanente.

A evidência qualitativa de reuso bate com os números da seção 4: `audit-fake-ai-server.py` é reusado por **7** scripts;
`wave5-pty-drive.cpp` é reusado por **5+** compilações, com cache de compilação via `[ -x "$DRIVE" ] ||`;
o driver da wave4 → wave5 foi **estendido, não reescrito** (o diff altera só 1 linha e adiciona 343, mantendo as 281 linhas da wave4 intactas).

**Todos esses comportamentos aconteceram numa versão sem guarda de objetivo.** A única restrição eram os
10 critérios de aceitação julgáveis escritos no [brief](../reference/glossary.md#需求确认书). Isso mostra que **escrever "pronto" em forma julgável já é suficiente para induzir auto-auditoria e auto-divulgação.**
O valor marginal da guarda de objetivo tem de ser medido contra essa linha de base, não contra zero.

Mas a próxima seção mostra: **a auto-auditoria é tecnicamente muito forte na verificação, e ainda assim errou o veredito final do item mais importante.**

!!! warning "O "auditor" aqui não é o juiz"
    O auditor independente das seções 7 e 8 é um **subagent que o coordenador despachou por conta própria**, não o
    [juiz](../reference/glossary.md#目标看守) da [guarda de objetivo](../reference/glossary.md#判定者) —
    esta execução não tinha guarda de objetivo nenhuma. Os dois se parecem na leitura, mas fazem coisas diferentes: o auditor é retrospectiva pós-fato,
    o juiz é o portão de [veredito](../reference/glossary.md#判定) no fim de cada turno.

## 8. A nota que ele deu a si mesmo está certa? — a aceitação 1 foi julgada errado

Um segundo auditor independente foi despachado para julgar aqueles 10 critérios de aceitação item por item contra o código.

**As aceitações 2–10 são todas verdadeiras**, com evidência no código. O modo de treino não injetar código é até uma garantia **estrutural**:
um único ponto de decisão de sink em `ai.h:117` + um único switch de aterrissagem em `app.cpp:590-615` + quatro early-returns em
`editor.cpp:679-683`, e não ifs espalhados. Os P1–P4 que ele mesmo encontrou na auto-auditoria também são **todos verdadeiros, com todas as correções aplicadas**
(P4 é meio-verdadeiro: aquela linha do pair azul é código morto, `ghostAttr()` já ia por `A_DIM` de qualquer forma).

**Mas a aceitação 1 foi julgada errado.**

```text
texto do critério: "compilar um executável independente, rodando direto no terminal do macOS"
artefato entregue: ELF 64-bit LSB pie executable, ARM aarch64, GNU/Linux
julgamento dele:   aprovado
```

Um humano rodou `file` à mão para confirmar isso.

Ele não escondeu nada — o título da §4 de `交付说明.md` é literalmente "o maior risco não verificado: nunca rodou no macOS nenhuma vez",
e a §6 da auditoria lista seis frentes não verificadas no macOS. **Ele divulgou o risco, mas nunca reconectou esse fato ao julgamento da aceitação 1**,
sendo que a exigência literal da aceitação 1 é exatamente aquilo.

### Mas isso não é evidência de que "faz falta um juiz independente"

É muito fácil ler isso como "logo, precisamos da guarda de objetivo". Errado, e ler assim é **atirar a flecha primeiro e desenhar o alvo depois** —
exatamente o raciocínio motivado que a seção anterior acabou de criticar.

**A guarda de objetivo daquela época, na configuração padrão, provavelmente também teria deixado esse item passar.** `judge()` usa `can_run=False` por padrão,
e as ferramentas são só `Read` / `Glob` / `Grep` — **ele não consegue rodar `file`**.
Ele iria ler o código-fonte, veria que `Makefile:25-38` realmente tem um branch para Darwin, e julgaria "atingido". Exatamente a mesma falha da auto-auditoria.

### O fato estrutural de verdade

**A aceitação 1 é simplesmente inverificável no ambiente desta execução.**

Ela afirma algo sobre "o comportamento do artefato no macOS", e a execução inteira aconteceu num contêiner Linux.
**Nenhum juiz consegue verificar um binário de macOS dentro do contêiner**, seja ele auto-auditor ou independente.
O problema não é "quem julga", é que **esse item foi tratado como um critério julgável comum e então julgado**.

### Três outros achados do auditor (nenhum mencionado na auto-auditoria)

- **A semântica de cota em `doTab()`**: `app.cpp:909` chama `noteActivity()` sem condição depois de `acceptGhost()` → `gen_++`
  → reabre a cota, então **cada Tab aceito dispara outra requisição automática 500ms depois**. A análise do P1 (ociosidade queimando dinheiro)
  só examinou os três pontos de cancelamento `setMode` / `cancelInFlight` / `askNow`, e deixou passar justamente este, o caminho de gasto mais frequente.
- O "cinza" da aceitação 6 só se sustenta literalmente em terminais de 256 cores; no nível de 8 cores está fixado em `A_DIM` (escurecido, não cinza).
- O subtítulo da §7 de `验收审计.md` diz "9 critérios de aceitação", mas a tabela tem 10 linhas — erro de digitação, mas aparece no cabeçalho da avaliação geral.

## 9. Escala final de spill e da bancada

103 [spills](../reference/glossary.md#落盘), 791.4K caracteres convertidos em ponteiros de caminho, sem residência no contexto.

`.flower/` no fim: 58 scripts (250K), 22 entregas (330K), 5 notas (43K).

## Riscos remanescentes

**O alvo de entrega é macOS, mas toda a verificação foi feita dentro de um contêiner Debian aarch64; zero verificação em máquina macOS real.**
Esse é um efeito colateral real da abordagem de isolamento por contêiner: para ter segurança ele foi trancado no Linux, mas o que ele tem de entregar é macOS.
O próprio README §10.24 do projeto registra isso honestamente e lista 4 pontos de risco, mas não fecha o ciclo.

Essa lacuna foi coberta depois pelo [HT002](ht002.md) — aquela execução foi justamente instalar esse binário num macOS de verdade.

Um benefício inesperado: dentro do contêiner só `/work` é visível, então nos 19MB de transcript
**houve zero vazamento do nome de usuário do host `/Users/hechenyu`** (`/work` aparece 11,495 vezes).
O [isolamento](../reference/glossary.md#隔离) isolou os caminhos de carona.

## O que esta execução não conseguiu validar

- **Guarda de objetivo**: esta execução é anterior à sua adição. O coordenador organizou uma auditoria independente **por conta própria**, com técnica de verificação bem sólida,
  mas julgou errado o item mais importante (seção 8). As duas conclusões precisam ser registradas juntas —
  escrever critérios julgáveis com clareza no brief já induz auto-auditoria, então a linha de base da guarda de objetivo não é zero;
  e a guarda de objetivo na configuração padrão da época **também teria deixado aquele item passar**, então ela também não é bala de prata.
- **Comportamento na janela de 1M**: só 18.6% foi usado, o limite nunca foi tocado.
- **Comportamento do microcompact com `DISABLE_AUTO_COMPACT=1`**: nenhum compact foi disparado em todo o percurso, então continua sendo inferência.

## O que esta execução mudou no framework

| Achado | Mudança implementada |
|---|---|
| `which` bloqueado (seção 5) | `is_ephemeral()` ganhou `which` / `command -v` / `type` / `whereis` / `uname` / `arch` / `locale` / `nproc` / `getconf` / `sw_vers`; `tests/glance.py` ganhou 7 amostras adversariais guardando a forma de consulta de `command` / `type` |
| Aceitação 1 julgada errado (seção 8) | O item 1 de `JUDGE_RULES` passou a **julgar o artefato, não o código-fonte** — se der para rodar, rode; se não der, inspecione o artefato em si (plataforma, tamanho, se carrega) |
| "Eu divulguei o risco" comprou um aprovado | O veredito precisa distinguir "não foi feito" de "não dá para verificar aqui". `Verdict.parse` agora reconhece **无法验证 / 没法验证 / 无法判定** como um terceiro estado `unreachable` → **sobe para perguntar a um humano, e jamais pode julgar aprovado** |
| Aceitação 1 é inverificável por princípio neste ambiente | O passo de definir o objetivo agora exige **marcar na hora os itens que este ambiente não consegue verificar**, em vez de descobrir isso depois do trabalho feito |
| Recuperação de rede na camada do framework, trabalho pela metade do subagent perdido (seção 6) | Registrado como issue #2, sem ciclo fechado |

Os três primeiros itens foram para uma API real pela primeira vez no [HT002](ht002.md), e ali "julgar o artefato, não o código-fonte" salvou o dia uma vez —
mas essa mesma regra também criou uma falha nova.
